# 대화 화면 통일 — 간단 명료 · 투명성

> 상태: **완료** — ①②③④⑥ 전부 반영(⑤는 §7.5 로 불필요 판정)
> (2026-09-18 사용자와 공동 설계)
> 시안: https://claude.ai/code/artifact/3baf98e1-7360-40e9-bfff-c3c395cb40b5
> 목표 키워드 둘 — **간단 명료**, **투명성**. 대화·셸 수행·reasoning 을 투명하게
> 보여주되 최대한 간단하게. Main/Agent 창을 같은 컨셉으로.

## 1. 지금 무엇이 문제인가

**같은 대화를 세 가지로 렌더한다.**

| 뷰 | 코드 | 보여주는 것 |
|---|---|---|
| 개요 | `ov*` 함수 38개 | 질문 + 응답 + reasoning(접힘) — **도구 호출 없음** |
| 전문 (드로어) | `render*` 카드 | thought · action · observation **전부** |
| 흐름 | `team_*.js` 1073줄 | 에이전트 스윔레인 |

**투명성이 드로어 안에만 있다.** 기본 화면인 개요엔 도구 호출이 안 나오고,
슬래시 명령만 화이트리스트(`OV_SLASH_TOOLS`)로 예외 처리돼 있다. 원하는 것과
정확히 반대다.

**Main 과 Agent 는 데이터 모델부터 다르다.**

```
main   : ovEntries      ← user_message + stream_chunk + assistant_turn
agent  : ovChannels[k]  ← agent_msg (내부 작업까지 텍스트로 뭉쳐 나감)
```

그래서 **에이전트 창엔 생각도 도구도 안 보이고 최종 답만** 보인다.

## 2. 설계 원칙

**모든 줄은 같은 리듬.** `아이콘 · 종류 · 한 줄 요약 · 펼침표시` 4칸 그리드.

```
💭 생각   테스트 러너를 먼저 확인한다
⚡ shell  pytest tests/ -q                      ▸
✓ 결과    3826 passed, 27 skipped in 41.23s     ▸
```

**기본은 요약, 누르면 전문.** 투명성과 간결함이 충돌하는 지점의 답 —
다 보여주되 **깊이로** 보여준다. 펼칠 게 있는 줄에만 hover 시 `▸`.

> **정정(구현 후, 사용자 지적)**: 요약을 *한 줄 고정(ellipsis)* 으로 잘랐던
> 최초 방침은 틀렸다. 잘린 줄은 브라우저를 넓혀도 다 안 보이고, **생각처럼
> 펼칠 본문이 없는 줄은 읽을 방법이 아예 없다**. 대화가 밀리는 것보다 못 읽는
> 게 나쁘다 → 요약은 **줄바꿈**한다(`overflow-wrap: anywhere` 로 공백 없는 긴
> 경로도 끊는다). 그리고 시각은 코너 배지(absolute)가 글자를 덮어 겹쳤으므로,
> **행이 있는 카드는 시각을 같은 그리드 안**(`.row-time`)으로 들인다 — 겹칠
> 자리를 없애는 쪽이 여백을 상수로 비워두는 것보다 튼튼하다.

**스트리밍 폐기, 생성 중 한 줄.** 사용자 결정(밀도 ②):

```
● 생성 중 · 1.2K tokens
● 생성 중 · 4.8K tokens · 💭 사고 2.1K
```

숫자가 오르면 살아 있다는 뜻이고, 사고 토큰이 따로 잡히면 러너웨이가 바로
보인다. 본문이 흐르지 않으므로 **카드가 자라며 화면이 튀지 않는다**.
v8.60.0 무진전 표시(`⏳ 응답 대기 중 2:30 / 10:00 · 시도 1/4`)와 같은 자리·
같은 문법으로 이어진다.

## 3. 세 층 — 무엇이 채널이고 무엇이 중첩인가

**갈림선은 "말을 걸 수 있는가"** 하나다.

| | skill | inline agent | 상주 agent |
|---|---|---|---|
| 호출 | `run_skill` | `agent` (1회성) | spawn → 채널 |
| 컨텍스트 | 같은 ctx | 새 ctx · 끝나면 버림 | 새 ctx · 유지 |
| 수명 | 턴 안 | 턴 안 | 세션 내내 |
| 말 걸 수 있나 | 아니오 | 아니오 | **예** |
| 표현 | **중첩 블록** | **중첩 블록** | **채널 칩** |

skill·inline agent 는 끝나면 사라지므로 칩을 줘도 누를 일이 없다. 들여쓰기 +
좌측 레일(보라=skill, amber=inline)로 그리고 머리줄로 접는다. 서버는 이미
`scope_start` 에 `kind`·`depth`·`agent` 를 실어 셋을 구분할 정보가 다 있다.

## 4. 내부 작업 vs 왕래 — 통일의 범위

**세로로 흐르는 것**(생각·도구·결과·답)은 main 이든 agent 든 구분할 이유가
없으니 **한 이벤트로 통일**한다. **가로로 건너는 것**(왕래)은 방향과 상대를
실을 자리가 필요하므로 **`agent_msg` 를 유지**한다.

| | 내부 작업 | 왕래 |
|---|---|---|
| 참여자 | 1 — 자기 자신 | 2 — 보내는 쪽 / 받는 쪽 |
| 나타나는 채널 | 1곳 | 2곳 (`→` 와 `←`) |
| 이벤트 | `assistant_turn` + `task_id` ← **통일** | `agent_msg` ← 유지 |

### 주의: 대칭인 것은 peer ↔ peer 뿐

조사로 확인한 사실(시안 초안이 이걸 대칭으로 잘못 그렸다):

```
main → agent : key=<agent> direction=in  author=main        → 에이전트 창에만
user → agent : key=<agent> direction=in  author=user:<닉>    → 에이전트 창에만
peer → peer  : key=<수신>  direction=in  + key=<발신> out    → 양쪽
agent → 회신  : key=<agent> direction=out to=<요청자>        → 에이전트 창에만
agent → 질문  : key=<agent> direction=question               → 에이전트 창에만
```

`agent_message(key=…)` 의 `key` 는 "어느 창에 넣을지"인데 **main 창이라는 게
없다**. main 쪽에서 위임은 `⚡ agent` **도구 호출**로 나타난다.

**통일의 이득**: 에이전트 내부 작업을 `assistant_turn` 으로 떼어내면 에이전트
창도 main 만큼 투명해지고, `agent_msg` 는 본래 역할(왕래)만 남아 단순해진다.
`_emit` 이 **이미 스코프 task_id 를 자동 부착**하므로 배관은 대부분 있다.

## 5. 왕래 표현과 점프

세로선 + 화살표 + 상대:

```
← 방금 커밋 리뷰해줘                    main
← README 갱신해줘                      두정 (사람)
← 전송 세대 설명도 넣어주세요            reviewer (peer)
→ 폴백에 테스트가 없습니다               main
? 제가 추가할까요, 지적만 할까요?         두정 (답변 대기)
```

`author` 네임스페이스가 이미 셋을 구분한다 — `main` / `user:<닉>` /
`agent:<key>`. `(사람)` `(peer)` 꼬리표로 종류를 밝힌다.

### 점프 — 한 방향만

| 경로 | 가능 | 키 |
|---|---|---|
| main → agent | ✅ | `⚡ agent` 도구 호출이 `task_id` 를 이미 가짐 |
| peer ↔ peer | ✅ | `(author, to, seq)` — TeamView 중복제거 키 |
| agent → main | ❌ | main 쪽 대응 줄이 도구 호출이라 매칭 키가 다름 |

억지로 양방향을 맞추려면 도구 호출에 짝 키를 심어야 하는데 **이번 범위 밖**.
돌아가기 버튼으로 충분하다.

**돌아가기는 한 단계만.** 점프는 네비게이션이 아니라 **엿보기**라 새 점프가
이전 것을 덮고 한 번 누르면 사라진다. 스택이면 누를 때마다 라벨이 바뀌어
어디로 갈지 예측이 안 되는데, 채널 칩이 항상 보이므로 그 복잡도를 살 이유가
없다(사용자 지적으로 스택→단일 변경). 상태는 값 하나: `back = {c, a} | null`.

## 6. 질문 트레이 — 살린다

에이전트 질문은 대화에도 남지만 **어느 채널을 보고 있든** 입력창 위 트레이에
뜬다. docs 를 보는 중 reviewer 가 물어도 놓치지 않는다. 이미 있는 동작
(`ovAskTray` / `waiting_ask`)이라 그대로 살린다. 답하면 그 채널 대화에
`← <닉>` 으로 남아 누가 답했는지가 기록된다. 선착순.

## 7.5. ①단계 후 발견 — ⑤는 서버 쪽에서 이미 되어 있다

②를 준비하며 확인한 사실. **계획을 줄인다.**

`begin_agent_work` 는 상주 에이전트 작업에 `task_id = "<key>#<seq>"` 를 붙여
**`scope_start`(kind="run")** 를 방출하고, 같은 스레드의 후속 이벤트는
`_emit` 이 그 `task_id` 를 자동 부착한다. 프론트는 `ensureTaskGroup` 으로
`#messages` 에 **중첩 카드**를 이미 만든다.

즉 **에이전트의 내부 작업(생각·도구·결과)은 이미 `assistant_turn` +
`task_id` 로 흐르고 전문 드로어에 그려지고 있다.** 안 보였던 이유는 그게
드로어 안에 있고 기본 화면인 개요가 안 그렸기 때문이다 — 데이터가 없어서가
아니었다.

따라서:

- **⑤(서버 이벤트 통일)는 사실상 불필요**하다. 남는 일은 프론트가 그 카드를
  "채널"로 묶어 보여주는 것뿐이고, 그건 ②와 ⑥에 흡수된다.
- `agent_msg` 가 중복으로 나르던 **최종 답 텍스트**만 정리 대상이다
  (왕래 in/out/question 은 §4 대로 유지).
- **②의 위험이 크게 준다**: 개요를 지워도 에이전트 작업이 사라지지 않는다.
  오히려 **드러난다** — `#messages` 에 이미 다 있기 때문이다.

이 발견으로 6단계가 **5단계**가 된다(⑤ 삭제, 잔여는 ⑥에 병합).

### ④-R 생성 중 줄의 채널 귀속 — **v9.9.0 정정**

④ 는 생성 중 줄을 `data-ch` 없이 두어 **모든 채널에 보이게** 했다. 근거는
*"에이전트 채널에서 생성 표시가 사라지면 멈춘 것처럼 보인다"* 였고, 그때는
맞았다 — 상주 에이전트가 사실상 하나였기 때문이다.

에이전트 4대를 띄운 실세션에서 정반대가 됐다(사용자 제보): **멈춰 있는 세
채널에 옆 에이전트의 사고량이 비쳤다.** 컨텍스트는 에이전트마다 분리돼 있는데
진행 표시만 하나였던 것이다. "멈춘 것처럼 보인다"를 피하려다 "돌고 있는 것처럼
보인다"를 만들었고, 후자가 더 나쁘다 — 없는 활동을 지어내기 때문이다.

정정은 **두 층 모두**에서 필요했다:

- **서버** — `_stream_chars`/`_thinking_chars` 가 인스턴스 속성이었다. 렌더러는
  싱글턴이고 워커는 각자 스레드라 (1) 동시 진행분이 **한 숫자에 더해지고**
  (2) 한 쪽의 `stream_end` 가 **전원의 카운터를 0으로** 만들었다. 누적을
  `task_id` 별 `_tick_state` 로 가른다. 키는 `_emit` 이 쓰는 그 값
  (`_current_task_id()`) — 귀속의 출처가 하나여야 필터와 어긋나지 않는다.
- **프런트** — `.gen` 을 채널당 하나로 만들고 `appendToTimeline` 으로 붙인다.
  `data-ch` 도장·필터 적용·맨 아래 이동이 그 한 곳에서 일어나므로 **새 분기가
  없다**. 접히는 스코프 카드 안으로 들어가지 않게 `taskId` 는 비우고 채널만
  직접 지정한다(접으면 사라져 다시 "멈춘 것처럼" 보인다).

화면만 고치면 숫자가 여전히 섞인 값이라 서버가 먼저다. TC 는 두 사보타주
(서버 키를 전역으로 되돌리기 / 프런트 `data-ch` 떼기)로 각각 실패를 확인했다.
### ⑥ 점프 + 중첩 블록 — **완료**

  **~~생성 중 한 줄이 그 예외였다~~ → v9.9.0 에서 철회**, 아래 참조.

**실장에서만 잡힌 3건** (유닛·브라우저 TC 가 전부 그린인 상태에서 발견):

| 증상 | 원인 | 수리 |
|---|---|---|
| 상대 칩이 안 눌림 | 시각 배지(absolute)가 덮음 | `pointer-events:none` |
| 시각과 상대가 겹쳐 보임 | 여백을 폭 상수로 비운 첫 수리가 취약 | 꼬리 칸이 있는 줄은 시각을 **같은 그리드 안**(`.row-time`)으로 |

그리고 그 누수를 고치자 드러난 것: `.card-user{display:flex}` 가 UA 의
`[hidden]{display:none}` 을 **이겨** 속성만 붙고 안 숨었다. 클래스마다 때우는
대신 `#messages > [hidden]{display:none!important}` 한 줄로 표면 전체에 못
박았다 — 앞으로 추가될 카드 클래스도 자동으로 안전하다.

## 8.5. 실사용 보고 — ⑥ 이후 (사용자)

실제로 써 보고 나온 3건. 전부 **TC 가 그린인 상태**에서 나왔다.

| 증상 | 원인 | 수리 |
|---|---|---|
| 에이전트에게 물은 답의 거부 표시가 main 에 빨간 박스로 | `failed_turn` 리스너가 `task_id` 를 흘림 | `renderFailedEmission(…, taskId)` — 루트 append 경로는 예외 없이 task_id 를 날라야 한다 |
| 채널 칩을 누를 때마다 알 수 없는 위치로 스크롤 | 필터가 높이를 바꾸는데 scrollTop 은 그대로 | `ovSetChannel` → 맨 아래 + 자동 따라가기 복구 |
| "최신 응답" 독이 마지막 카드와 중복 | 전문이 드로어 안이던 시절의 유물 | `#dock` 제거 (+ 유일 소비처였던 `data-nav-ts` 앵커 동반 사망) |

**교훈**: 루트에 카드를 붙이는 경로는 `renderUserMessage`·`renderFailedEmission`
둘 다 같은 방식으로 새어 나갔다. `appendToTimeline` 이 채널 도장의 단일 지점인
것은 맞지만, **호출부가 task_id 를 안 주면 소용이 없다**. 새 카드 경로를 만들 때
"이 카드는 누구 것인가"를 먼저 답해야 한다.

## 8.6. ⑥ 의 미완 항목 — 에이전트 채널의 겹침 (v9.7.0)

§7.5 에 "`agent_msg` 의 **중복 최종답 정리**만 ⑥에서 함께" 라고 적어놓고
⑥에서 점프·중첩만 하고 **하지 않았다**. 사용자가 실사용에서 잡았다.

에이전트 채널이 이렇게 보였다 — 요청도 답도 각각 두 번:

```
← 받음   마지막 단어가 '맛보기'였어…              main   ①
🦀 [2] 🐺 player1: 마지막 단어가 '맛보기'였어…            ① ← 요청 중복
   💭 생각 …
   기차. 어릴 때 기차 여행하던 기억이 나네요!            ②
→ 보냄   기차. 어릴 때 기차 여행하던 기억이 나네요!  main  ② ← 응답 중복
```

**🦀 래퍼는 ⑥ 이전의 유물이다.** 그때는 카드가 에이전트 작업을 묶는 유일한
수단이었는데, 채널이 필터가 된 뒤로는 채널이 그 일을 한다. 남겨두면 (a) 기본
접힘이라 투명성이 클릭 뒤로 숨고 — ⑥의 목적과 정반대 — (b) main 은 평평한데
agent 만 한 겹 들어가 "같은 컨셉으로 통일"이 깨진다. 요청 경계는 왕래 줄이
이미 긋고 있다.

**구조를 더럽히지 않고 지울 수 있었던 이유**: `appendToTimeline` 이 그룹이
없으면 `channelOf(taskId)` 로 루트에 붙이는데, 그게 정확히 원하는 동작이다.
"카드 없음"은 새 예외가 아니라 **이미 있는 기본 경로**였다. 채널 등록만
카드 생성에서 떼어내면(`noteScopeChannel`) 나머지는 손댈 게 없고,
`ensureTaskGroup` 은 오히려 작아진다(파라미터 8→7, 3분기→삼항 1개).

**응답 중복은 조건부로 지운다.** `→ 보냄` 이 바로 위 최종답을 그대로 반복하면
영수증 한 줄로만 그린다. 무조건 접지 않는 이유는 kill→resume 재생이
`_replay_conversation` 으로 **`agent_message` 만** 내보내기 때문이다 — 그때는
최종답이 없어 이 줄이 그 답의 **유일한 기록**이다. 라이브/재생을 구분하는
값은 채널당 한 칸(`lastFinalByChannel`)이면 충분하다.

덤으로 `[2]` 오프바이원도 고쳤다 — `begin_agent_work` 가 1-based `seq` 를
0-based `index`(위임과 공유하는 프론트 표시 규약)로 넘기고 있었다.

## 9. 스텝 카드 — 사고·행동·관찰을 한 장으로 (v9.13.0)

③에서 카드를 한 줄 리듬으로 바꿨지만, **한 스텝은 여전히 카드 둘**이었다:
`card-assistant`(💭 생각 + ⚡ 행동)와 `card-observation`. 타임라인이 길어지면
어느 관찰이 어느 행동의 것인지 눈으로 다시 묶어야 했다 — 한 줄 리듬을 만든
이유가 바로 그 부담을 없애는 것이었는데 카드 경계가 짝을 갈라 놓았다.

```
접힘:  머리 한 줄                              [⚡ 도구] [✓]  ▸
펼침:  └ 행동 상세
       └ ✓ 결과
```

### 머리 = 그 스텝이 가진 것 중 가장 요약적인 것

생각이 있으면 생각, **없으면 행동**. 살아 있는 두 wire format 이 모두
`thought_required = False` 라 생각 없는 턴이 실측 1/3이다(세 세션에서
35중 12, 37중 13, 18중 2). 빈 자리에 `(생각 없음)` 같은 자리표시를 그리는
대안은 버렸다 — 줄을 하나 쓰면서 아무것도 알려주지 않고, 세 턴에 한 번꼴이면
비용이 작지 않다. 행동이 머리로 올라오면 도구 이름이 이미 `k` 칸에 있으므로
**배지에서는 뺀다**(같은 사실을 한 줄 안에서 두 번 말하지 않는다).

### 접힘에 배지를 남기는 이유

접힘의 목적은 *"안 읽고 지나가기"* 가 아니라 **"읽을 곳을 고르기"** 다. 도구
이름과 성패는 그 선택에 쓰이는 정보라, 접어서 아끼는 값보다 남겨서 얻는 값이
크다. 배지는 요약과 **같은 줄** 오른쪽 끝(= `makeRow` 의 꼬리 칸, 왕래 줄이
상대 이름에 쓰는 그 슬롯)이라 줄 수가 늘지 않고, 실패한 스텝이 접힌 목록에서
붉게 튀어나온다.

### 경계

| 모양 | 처리 |
|---|---|
| **실패** | 펼친 채로 두고 카드에 `failed` — 접힌 한 줄로는 왜 실패했는지 알 수 없다(③의 규칙 유지) |
| **다중 op** | 관찰이 하나로 합쳐져 오므로(`shell+monitor`) 오히려 잘 맞는다 — 종전엔 행동 2줄과 관찰 1줄이 카드 경계로 갈렸다 |
| **최종답** | 묶지 않는다. 읽히려고 있는 것이고 뒤따를 관찰도 없다 |
| **관찰 없는 행동** | 블로킹 `ask` — 행동만 그리고 관찰은 `render=False` 다. 배지 칸이 성패 없이도 성립해야 한다 |
| **행동 없는 관찰** | **구조적으로 없다.** `render_step("observation")` 은 `_append_observation`(`dispatch.py`) 한 곳에서만 나오고 `render=True` 인 호출부 여섯이 전부 같은 턴에 action 을 먼저 낸다. 개입은 `render=False` 라 관찰을 안 만들고 `retry_tick` 만 남는다(v9.8.0) |

### 병합 단위는 **턴**이지 "직전 행동" 이 아니다

서버는 `action()` 을 **op 마다** 부르므로 다중 op 턴은 `assistant_turn` 을
**N개** 내고, 관찰은 합쳐서 **하나**만 낸다(`[1/2] shell — OK …`). 처음에
"직전 행동" 으로 붙였더니 마지막 op 만 관찰을 받고 **앞 카드들이 성패 배지
없이 영영 남았다**(사용자 제보). 한 세션의 네 에이전트에서 다중 op 턴이
30건이었다 — 드문 모양이 아니다.

같은 턴의 두 번째 행동은 새 카드가 아니라 **그 카드의 본문**으로 들어가고,
도구 배지는 `⚡ 첫도구 +N` 으로 접는다(이름을 전부 늘어놓으면 머리 한 줄이
배지로 밀린다). 턴이 다르면 붙이지 않는다 — 개입 턴이 `state.turn` 을
되돌려 번호가 재사용될 수 있고, 블로킹 `ask` 는 관찰 없이 카드를 열어 둔 채
남기 때문이다.

### 관찰이 자기 카드를 찾는 법

채널별로 **관찰을 기다리는 카드 한 장**(`pendingStep[channel]`)을 들고 있다가
붙인다. DOM 을 뒤지지 않는 이유는 카드가 루트가 아니라 task group 본문에
들어갈 수 있어서다(`appendToTimeline`). 관찰은 언제나 자기 행동 뒤에 오므로
채널당 한 장이면 충분하다.

**못 찾으면 단독 카드로 떨어뜨린다.** 도착 순서에 기대는 판정이라 —
이 프로젝트는 `ask` 의 답을 도착 순서로 판정하다 한 번 데었다(docs/agent-ask)
— 안전망을 둔다. 앞으로 새 경로가 생겨도 최악이 "안 묶임" 이지 **"유실"** 이
아니다.


## 12. 런 블록 — 왕래 줄을 걷어내고 런을 단위로 (v9.23.0)

> 시안: https://claude.ai/artifact/4MWQDqM7YQ7fbenguYGuAq (사용자 승인)

§5 의 왕래 줄(`← 받음 / → 보냄 / ❓ 질문`)과 §8.6 의 영수증 장치는 여기서
**사라진다**. 사용자 지적: 보냄은 결국 `message`/`reply`/`answer` 도구 호출의
배관 쪽 기록이라 같은 본문이 도구 줄과 두 번 보였고, 받음은 일감의 경계를
긋는 것 말고는 정보가 없었다.

### 앵커는 런이다 — 받은 메시지가 아니다

블록 = 런 하나. `scope_start`(`key#seq`, `begin_agent_work`)에서 열리고
`scope_end` 에서 닫힌다. 받은 메시지를 앵커로 잡으면 두 군데서 어긋난다:

1. **수신 줄은 큐에 넣을 때 나간다** (`request()` → `agent_message(in)`),
   런은 워커가 꺼낼 때 시작한다. 바쁠 때 3건이 쌓이면 수신 줄 3개가 먼저 온다.
2. **사람 창 배치**는 N건이 런 1개다 (`_handle_human_batch`).

그래서 `scope_start` 가 **`seqs`**(이 런이 처리하는 inbox 항목들, 배치는 N개)를
싣고, 프론트는 블록이 없는 수신 줄을 `⏳ 대기` 로 두었다가 그 seq 를 품은
런이 열리면 머리로 끌어온다. 반대 순서(블록이 먼저)면 곧장 머리로.

```
┃ ← 사과                                  agt-b
┃ 💭 생각   '과' 로 시작하는 단어 — 과일
┃ → message 과일                          agt-b  ✓
┃ ─────────────────────────────────────────
┃ ✓ (2.1s) 과일 (→ agt-b)
⏳ 대기     진행 상황 보고해 줘             main
```

| 사실 | 어디에 한 번 |
|---|---|
| 받은 본문 | 블록 머리 `run-item` (`←` 본문 · 누가). 배치면 N줄 |
| 보낸 본문 | 도구 줄 `→ message/reply/answer/ask` (`SEND_TOOLS`, 아이콘 →, 꼬리에 상대) |
| 배달 결과 | 스텝 배지 ✓/✗ — 거부만 펼쳐서 사유 |
| 런 결과 | 최종답 카드가 꼬리(`run-final` + `✓ (2.1s)`). 없으면 `run-foot` 상태 한 줄 |
| 하네스 폴백 | `agent_msg.fallback` 인 out 만 `⚠ 폴백` 줄 — 도구 호출 없는 유일한 발신 |
| 사람 창 입력 | 머리의 `(사람)` 꼬리표 |
| 채널 점프 | main 의 `⚡ agent` 도구 줄에서만. 에이전트 쪽 상대 이름은 글자 |

### resume 는 새 소스가 필요 없다

처음엔 `conversation.jsonl` 에 런 경계 레코드를 더하려 했는데, 조사해 보니
이미 있었다: `scopes.jsonl` 이 상주 런의 `scope_start/end` 를 재생하고
(`ctx_dir: agents/<key>`), `_replay_scope_inner` 가 에이전트 history 를 그
창으로 잘라 도구 줄까지 재생한다. `seqs` 는 `scope_start` payload 에 박혀
사이드카로 같이 남는다. 재생 순서(스코프 재생 vs 대화 재생)는 보장되지 않으므로
양쪽 순서를 다 받는다. 구 세션(`seqs` 없음)은 `[index+1]` 하나로 잡고, 그보다
앞 seq 의 미귀속 수신 줄은 직전 블록의 것으로 본다 — 배치만 살짝 어긋난다.

### 함정 — 수신 줄의 `task_id` 는 보낸 쪽의 것

`_emit` 은 현재 스레드의 런을 `task_id` 로 붙인다. peer 의 `request()` 는
peer 워커 스레드에서 돌므로 AGT 앞으로 온 수신 줄이 `PEER#3` 을 달고 온다.
그걸로 배치하면 남의 블록 몸통에 들어간다(패치 중 실제로 났다, 브라우저
테스트가 잡음). 수신 줄과 블록 자체는 **자기 채널의 루트**에 `key` 로 놓는다.

### v9.7.0 과의 관계

§8.6 은 🦀 스코프 카드(기본 접힘)를 걷어내 채널에 평평하게 흘렸다 — 접힘이
투명성을 숨겨서였다. 런 블록은 그 자리를 잇되 **접히지 않는다**. 접히는
중첩 카드(skill/inline)는 그대로 블록 몸통 안에 담긴다.
