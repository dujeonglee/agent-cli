## 초록

코딩 에이전트는 한 사람이 한 세션을 통제하는 방식으로 설계되어 있다. 팀은 메신저 연동을 통해 작업을 위임할 수 있지만, 이 연동은 대개 세션과 분리된 작업을 실행한다. 실시간 공유 작업공간을 제공하지 않으며, 여러 사람이 동시에 에이전트에게 지시할 때 어떤 일이 일어나는지도 명확히 정의하지 않는다. 하나의 세션을 공유하려면 요청을 직렬화하여 짧은 질문이 긴 작업 뒤에서 기다리게 하거나, 세션을 분기하여 컨텍스트를 나누고 병합 작업을 떠안아야 하는 것처럼 보인다.

본 논문은 여러 개발자가 하나의 대화와 작업공간을 공유하는 코딩 에이전트 Coagora를 제시한다. Coagora의 동시성 계약은 추론과 효과를 분리한다. 턴은 병렬로 추론하고 스트리밍하지만, 컨텍스트 커밋과 게이트에 참여하는 충돌 작업공간 효과는 순서대로 실행한다. 각 턴은 그 턴을 만든 메시지 및 참가자와 계속 연결된다. 이 배치는 기존 동시성 제어 기법을 사용하지만, 다른 참가자의 추론을 막지 않고 writer 임계영역을 순서화하도록 락을 추론 아래에 둔다.

동일한 구현 안에서 병렬, 직렬, 거절 후 재시도 계약을 비교했다. 결정론적 워크로드에서 두 번째 사용자의 첫 토큰 도착 시간은 첫 번째 사용자의 작업 길이와 무관했다. 기울기는 병렬에서 0.00, 두 대안에서 모두 1.03이었다. 실모델 반복에서는 두 번째 사용자의 중앙 대기시간이 38.2초에서 10.8초로 줄었다. 독립된 강제 중첩 실행 30회에서 게이트가 없으면 참여 writer가 30/30회 겹쳤고 두 락에서는 모두 0/30회였다. 2 ms 외부 sampler는 혼합 또는 파손 읽기를 27/30회 대 0/30회 관찰했다. 병렬 실행은 세 질문 워크로드에서 입력 토큰을 1.49배 사용했고, 배타적 효과가 턴의 큰 부분을 차지할 때에만 이득이 감소했다.

writer 순서화와 구조적 귀속은 의미적 정확성을 보장하지 않으므로 Coagora는 더 좁은 강제 경계도 지원한다. turn-local view는 다른 진행 중 턴을 제외하고, 요청자가 승인한 write capability는 파일 효과를 staging한 뒤 exact 과제 oracle을 통과한 경우에만 게시한다. 세 팔, 20-block 실모델 실험에서 모든 팔이 exact 과제·저장소 정답 20/20과 교차 과제 파일 행동 0/20을 보였다. Scoped 응답 하나가 상대 완료 태그를 언급했지만 filtered context와 강제 팔에는 없었다. 강제 팔은 40개 write set을 모두 검증·게시했다. 별도의 19개 적대 검증은 시험한 모든 우회를 차단하고 동일 경로 게시를 순서화했으며 validation 및 version 충돌을 게시 없이 거부했다. 따라서 협조적 도구와 안정적인 경로 가정 아래 시스템은 승인된 canonical write set 밖에 도구를 통한 과제 파일이 게시되는 것을 방지한다. 응답 의미, oracle 품질, 여러 파일의 crash atomicity까지 보장하는 것은 아니다.

## 1 서론

코딩 에이전트는 이제 저장소를 읽고, 파일을 수정하고, 명령과 테스트를 실행하며, 제한된 감독 아래 풀 리퀘스트를 연다 [1, 2]. 연구와 텔레메트리는 에이전트가 상당한 작업을 완수할 수 있고 사용자가 실행 중인 에이전트를 자주 수정하거나 방향 전환한다는 점을 보여준다 [2, 3]. 그러나 그 상호작용 모델은 거의 전적으로 싱글플레이어다. 한 사람이 프롬프트, 컨텍스트, 제어권을 소유한다.

소프트웨어 개발은 협업 활동이다. 여러 제품이 Slack이나 Teams에서 에이전트를 호출할 수 있게 했고 [6, 14–18], 사용자들은 하나의 코딩 에이전트 세션에 Google Docs처럼 함께 접근하는 기능을 요청했다 [5]. 현재 배포된 메신저 패턴은 유용하지만 공동 작업이라기보다 위임에 가깝다. 멘션이 캡처한 스레드로 클라우드 작업을 시작하고, 에이전트는 다른 곳에서 일한 뒤, 풀 리퀘스트를 반환한다. 참가자는 보통 실행 중에 개입할 수 없으며, 두 사람이 동시에 행동할 때 적용되는 일반 규칙도 공개 문서에서 찾기 어렵다.

실시간 공유 세션은 대화, 작업공간, 제어를 한곳에 둘 수 있다. 동시에 조정 문제를 만든다. 시스템이 요청을 하나씩 받으면 짧은 질문이 긴 빌드 뒤에서 기다릴 수 있다. 사람마다 세션을 만들면 동시에 작업할 수 있지만 컨텍스트가 갈라지고 팀은 코드와 의사결정을 모두 병합해야 한다.

Coagora는 세 번째 계약인 **병렬 추론과 순서화된 효과**를 탐구한다. 모든 메시지는 즉시 시작하여 모든 참가자에게 스트리밍되는 독립 턴을 만든다. 턴들은 하나의 대화와 작업 디렉터리를 공유한다. 느리고 읽기 전용인 추론은 병렬로 유지하고, 컨텍스트 커밋과 충돌하는 파일 또는 셸 효과는 순서 계층을 통과시킨다. 턴 id는 각 스트림, 도구 호출, 결과, 인터럽트를 그 턴을 시작한 참가자와 연결한다.

이는 락이나 스냅샷 격리가 새롭다는 주장이 아니다. 기여는 대화형 에이전트 안에서 이 기법들을 배치한 위치에 있다. 기존 에이전트 시스템은 전체 실행 주위에 조정을 두고, 비관적 제어가 추론을 막으므로 너무 비싸다고 결론내리곤 한다 [11]. Coagora는 상태를 바꾸는 부분만 순서화한다. 그 결과 더 분명한 경계가 드러난다. 세션은 유효한 트랜스크립트와 참여 효과의 순서를 보존하면서도 모델은 다른 사람의 요청을 따를 수 있다.

본 논문은 세 가지 기술 질문과 나중에 수행할 한 가지 인간 질문을 다룬다.

- **RQ1 — 응답성.** 다른 참가자가 이미 작업 중일 때 직렬, 거절 후 재시도, 병렬 계약은 한 참가자의 대기를 어떻게 바꾸는가?
- **RQ2 — 무결성과 비용.** 어떤 효과를 순서화해야 하며, 언제 그 순서화가 병렬 추론의 이득을 없애고, 어떤 토큰 및 실행시간 비용이 남는가?
- **RQ3 — 공유 세션 정확성.** 동시 실행 중에도 재생, 압축, 귀속, 공정성, 수명주기가 올바르게 유지되는가? 공유 컨텍스트는 언제 의미적 교차 간섭을 일으키는가?
- **RQ4 — 첫 사용.** 쌍을 이룬 참가자는 실시간 세션을 공유하면서 무엇을 알아차리고, 추론하고, 행동하는가? §6은 계획된 연구를 위해 이 질문을 예약한다.

증거는 실행 중인 한 시스템에서 런타임으로 선택 가능한 세 계약을 비교해 얻었다. Coagora의 직렬 경로는 이 연구보다 먼저 존재했으며 기준선이 된다. 병렬과 거절 모드는 동일한 전송 계층, 컨텍스트 관리자, 도구, 계측을 사용한다. 결정론적 실험은 메커니즘과 경계를 검증하고, 실모델 실험은 모델 또는 제공자 행동에 의존할 가능성이 큰 결과를 확인한다.

본 논문의 기여는 다음과 같다.

1. 상태 위치, 동시성 계약, 귀속 단위, 개입 시점으로 구성한 **다중 사용자 코딩 에이전트 상호작용의 범위가 명확한 설계 공간**.
2. 병렬 턴과 원자적 컨텍스트 커밋, 충돌 단위 효과, 사용자별 입장 제어, 구조적 귀속, 재생, 턴 소유 인터럽트를 결합한 **공유 세션 상호작용 아키텍처**.
3. **절충과 격리 경계에 대한 경험적 설명.** 병렬 턴은 추론 수준의 선행 차단을 없애지만 모델 호출을 추가로 사용하고 오래된 스냅샷을 읽는다. 세 팔 실모델 실험은 프롬프트 스코핑, turn-local context, 강제 validated publication을 분리하고, 적대 검증은 이를 일반 의미적 정확성으로 부르지 않으면서 더 좁은 파일 게시 invariant를 확인한다.

계획된 first-use study는 이후 사람들이 이 절충을 어떻게 이해하고 관리하는지에 대한 증거를 더할 것이다. 그 전까지 본 논문은 병렬 계약이 팀 성능이나 장기 협업을 개선한다고 주장하지 않는다.

## 2 관련 연구와 설계 공간

### 2.1 개인용 에이전트에서 팀 접근으로

AI 페어 프로그래밍 연구는 대개 한 개발자와 한 어시스턴트 또는 에이전트를 다룬다. Copilot은 인간 페어 프로그래밍보다 산출량을 늘리면서 품질을 낮출 수 있고 [12], 개발자는 AI 제안을 인간의 제안과 다르게 검토하며 [1], 에이전트 행동을 이해하기 어렵다는 점은 도입 장벽으로 남아 있다 [2]. 실제 에이전트 세션 6,000개에서 사용자는 가능한 기회의 39%에서 에이전트를 중단하거나 방향 전환했다 [3]. 이 결과는 조향이 중요함을 보여주지만 제어자는 한 사람이라고 가정한다.

팀 접근은 메신저 연동을 통해 나타나고 있다. Claude Tag, Codex, GitHub Copilot, Devin, Cursor의 공개 문서 [6, 13–18]와 OpenTag [9], 문서화된 worktree 병렬 실행 [10], Coagora의 두 모드를 검토했다. 세션 상태가 어디에 있고 두 번째 요청이 들어올 때 어떤 일이 생기는지 문서로 확인할 수 있는 시스템을 포함했다. 이는 전체 제품을 망라한 조사가 아니라 범위를 정한 제품 및 문헌 조사이며, 아래 주장은 조사한 시스템에 한정된다.

다섯 메신저 연동은 비슷한 경로를 따른다. 멘션, 스레드 캡처, 클라우드 작업, 풀 리퀘스트 링크다. 신원과 지속 방식은 다르지만 실시간 상호작용 경계는 비슷하다. GitHub는 전체 스레드가 결과 풀 리퀘스트에 저장될 수 있다고 경고하며 [7], Slack AI를 통한 간접 프롬프트 주입은 채널을 모델 컨텍스트로 취급할 때 보안 문제가 생김을 보여준다 [19]. Claude Tag는 공유 채널 인스턴스를 멀티플레이어라고 설명하지만 동시 지시에 대한 프로토콜은 공개하지 않는다 [6].

### 2.2 여러 사람과 하나의 AI

가장 가까운 인간 중심 연구는 공동 글쓰기, 그룹 대화, 교육에서 찾을 수 있다. 다중 사용자 글쓰기 환경에 배치된 에이전트는 개인 작업공간인 동시에 팀의 공유 자원이 되었다 [20]. 그룹 대화 연구는 AI 참가자가 언제, 어디서, 어떻게 응답해야 하는지 연구했고 [21], GroupMemBench는 다자 대화에서 메모리가 여전히 어렵다는 점을 보여준다 [22].

프로그래밍 교육에서 Daryanto 등은 한 인간/한 AI 구성과 두 인간/한 AI 구성을 비교했다 [23]. 동료에게 보인다는 사실은 참가자가 AI 제안을 더 주의 깊게 살피게 했다. 그러나 그 시스템은 제안형이었고, 작업은 파일 및 셸 접근이 있는 지속적 자율 에이전트가 아니라 일회성 학습 과제였다. 에이전트가 작성한 풀 리퀘스트 연구 역시 실행 후 에이전트의 산출물 주위에서 일어나는 협업을 다룬다 [24]. 여러 사람이 실시간 실행 자체를 공유하지는 않는다. 더 일반적으로도 인간-에이전트 상호작용 공개 데이터는 부족하다 [25].

이 연구들은 인식, 책임성, 제어에 관한 질문을 제기하지만 공유 코딩 작업공간을 위한 동시성 계약은 제공하지 않는다.

### 2.3 공유 에이전트 상태의 동시성

다중 에이전트 시스템은 보통 공유 상태를 낙관적으로 조정한다. CoAgent는 saga 방식의 되돌리기로 잘못된 순서를 복구하고 [11], STORM은 쓰기 시점에 충돌 편집을 감지하며 [26], worktree 기반 도구는 브랜치를 격리한 뒤 병합한다 [10]. DeLM은 여러 에이전트를 공유 컨텍스트 위에서 실행하지만 동시 작업의 순서를 정하기보다 내용의 근거 여부를 검증한다 [27]. 이 시스템들은 하나의 목표를 위해 여러 에이전트를 조정한다. Coagora는 하나의 세션을 통해 여러 사람을 조정한다.

바쁜 스레드를 다루는 프레임워크는 다른 길을 택한다. LangGraph는 거절, 대기열, 인터럽트, 롤백을 제공한다 [8]. OpenTag는 스레드당 하나의 활성 실행만 허용하고 다른 요청에 409를 반환한다 [9]. 본 논문의 거절 후 재시도 및 직렬 조건은 앞의 두 정책에 해당한다. Justitia 같은 공정 스케줄러는 에이전트 작업 사이에 서빙 용량을 배분하고 [28], 일반 게이트웨이는 클라이언트별 요청량을 제한한다. Coagora가 다루는 더 좁은 문제는 한 세션 안의 슬롯을 놓고 함께 있는 사람들이 제출한 턴 사이의 공정성이다.

구현은 확립된 데이터베이스 개념을 사용한다. 불변 스냅샷과 원자적 커밋은 스냅샷 격리와 유사하며 [32], 그에 따른 오래된 읽기와 write skew 위험도 남는다. 자원 분류와 호환성은 세분화 락을 따르고 [33], 마지막 쓰기 우선 결과는 동시성 제어에서 익숙한 결과다 [34, 35]. 연구 질문은 이 메커니즘의 새로움이 아니라, 추론 아래에 배치했을 때 유용한 상호작용 경계를 만드는지다.

### 2.4 네 가지 설계 질문

조사한 시스템을 네 질문으로 비교한다.

1. **상태 위치:** 인간의 대화는 분리된 작업을 시작하는 실행기인가, 실시간 세션을 보여주는 창인가?
2. **동시성 계약:** 두 번째 요청은 거절, 직렬화, 배치, 나중 병합을 위한 격리, 또는 순서화된 효과를 동반한 동시 실행 중 무엇으로 처리되는가?
3. **귀속 단위:** 산출물은 풀 리퀘스트, 작업, 메시지, 턴 중 어느 단위로 귀속되는가?
4. **개입 시점:** 참가자는 작업 전후에만 개입할 수 있는가, 세션 전체가 실행 중일 때 가능한가, 아니면 자신이 소유한 한 턴에 개입할 수 있는가?

| 시스템 | 상태 위치 | 동시성 계약 | 귀속 | 개입 |
|---|---|---|---|---|
| Claude Tag [6] | 분리 | 동시 입력에 대해 문서화되지 않음 | 작업 / 조직 | 전 또는 후 |
| Codex Slack [14] | 분리 | 멘션마다 작업 생성 | 작업 | 전 또는 후 |
| Copilot Slack [16] | 분리 | 기본적으로 채널별 직렬 | PR / 요청자 | 전 또는 후 |
| Devin Slack [17] | 분리, 동기화 | 재개 가능, 세션 안에서는 직렬 | 작업 / 연결된 사용자 | 거친 스레드 응답 |
| Cursor Slack [18] | 분리 | 호출마다 격리된 VM | 작업 | 전 또는 후 |
| OpenTag [9] | 실시간 스레드 | 409로 거절 | 메시지 | 바쁠 때 불가 |
| 병렬 worktree 도구 [10] | 브랜치별 | 격리 후 병합 | 브랜치 | 에이전트별 |
| Coagora 직렬 | 실시간 세션 | 직렬, 경계에서 주입 | 턴 | 세션 조향 |
| **Coagora 병렬** | **실시간 세션** | **병렬, 효과 순서화** | **턴 / 요청자** | **소유 턴 취소** |

조사한 시스템 안에서 메신저 연동은 분리된 상태, 작업 단위 귀속, 실행 전후 개입에 모인다. 조사한 대안 중 하나의 실시간 컨텍스트, 동시 턴, 턴별 귀속, 턴 단위 제어를 모두 결합한 시스템은 없었다. 이 표는 Coagora가 탐색하는 좌표를 식별할 뿐, 문서화되지 않았거나 미래에 나올 시스템이 이 좌표를 차지할 수 없다고 주장하지 않는다.

CSCW는 이 좌표에 인간적 의미를 부여한다. 그라운딩은 협업자가 공통 이해를 쌓는 과정을 설명한다 [36]. 작업공간 인식은 누가 무엇을 어디에서 하는지 아는 문제다 [37, 38]. 접합 작업은 협력 활동을 조정하는 데 필요한 노동이다 [39]. 혼합 주도권 원칙은 에이전트가 언제 행동하거나 질문해야 하는지 설명하지만 [40], 다중 사용자 환경에서는 누구에게 물어야 하고 누가 행동을 중단할 수 있는지도 결정해야 한다. 이 개념들은 논의와 계획된 연구를 이끌지만, 기술 평가는 이를 측정했다고 주장하지 않는다.

## 3 하나의 공유 세션을 위한 계약

### 3.1 세션, 턴, 소유권

세션은 S = (C, W, T)다. 하나의 대화 컨텍스트 C, 하나의 작업 디렉터리 W, 활성 턴 집합 T로 구성된다. 여러 클라이언트가 같은 프로세스에 접속할 수 있다. 참가자가 늘어도 새 작업공간이나 컨텍스트는 생기지 않는다.

받아들인 모든 메시지는 하나의 턴을 만든다. 동시 메시지를 하나의 프롬프트로 합치지 않는다. 각 턴은 디스패치 시 단조 증가 id를 받고, 스트리밍 텍스트, 도구 호출, 확인, 오류, 영속 레코드가 모두 그 id를 가진다. reply_to 링크는 턴의 레코드를 원래 메시지에 연결한다. 따라서 인터페이스는 동시 스트림을 서로 구분된 이름표 있는 카드로 렌더링할 수 있다.

제어는 소유권을 따른다. 참가자는 자신의 활성 턴을 취소할 수 있지만, 레지스트리는 다른 사람의 턴을 취소하려는 시도를 거절한다. 취소는 부분 출력을 보존하고 슬롯을 반환하며 다른 턴을 중지하지 않는다. 이는 완전한 그룹 거버넌스 모델이 아니라 최소 정책이다.

### 3.2 공유 컨텍스트

각 추론 단계는 C의 불변 스냅샷을 읽는다. 진행 중인 다른 턴의 부분 출력은 보이지 않는다. 한 단계가 끝나면 assistant 메시지와 대응하는 도구 결과를 하나의 원자적 블록으로 완료 순서에 따라 커밋한다. 이는 채팅 API의 메시지 짝 제약을 보존하고, 영속 트랜스크립트가 유효한 직렬 커밋 순서와 일치하도록 한다.

절충은 오래된 읽기다. 스냅샷을 가져간 뒤 다른 턴이 커밋할 수 있으므로 실행 중인 턴은 잘 구성되었지만 더 오래된 트랜스크립트를 토대로 추론할 수 있다. 스냅샷 격리는 의미적 write skew도 허용한다. 두 턴이 같은 유효 상태를 읽고 서로 다른 파일을 수정하면서 저장소 불변식을 함께 깨뜨릴 수 있다. 이 계약은 트랜스크립트 구조와 효과 순서를 보존하지만 모델 추론의 정답을 보장하지 않는다.

### 3.3 순서화된 효과

추론은 읽기 전용이며 느리다. 작업공간 효과는 더 짧고 상태를 바꾸며, 서로 끼어들면 안전하지 않다. 따라서 Coagora는 추론을 동시에 진행시키면서 효과를 작업공간별 호환성 게이트로 보낸다.

| 효과 쌍 | 정책 | 이유 |
|---|---|---|
| 서로 다른 알려진 경로의 읽기 또는 쓰기 | 동시 | 자원이 충돌하지 않음 |
| 같은 경로의 작업 | 순서화 | 참여 임계영역의 중첩 방지 |
| 셸, 패키지, 삭제 대 모든 작업공간 효과 | 배타적 | 영향 경로 집합을 모르거나 디렉터리를 바꿀 수 있음 |
| 복합·인간 대기·명시적 비작업공간 도구 | 부모 게이트 없음; 말단 효과에서 락 | 부모 락을 잡으면 데드락 또는 무한 차단 가능 |
| 분류되지 않은 작업공간 효과 | 작업공간 배타 | 새 도구/plugin 누락을 막는 fail-closed 기본값 |

경로 키는 상대 구성요소와 symbolic link를 해소한다. 하나의 inode에 여러 이름이 있는 기존 hard link 파일은 경로 정규화만으로 합칠 수 없으므로 작업공간 배타로 보수적으로 내린다. 대기 중인 효과는 추월 없는 엄격한 FIFO를 따른다. 이 규칙은 앞에 있는 배타적 대기자 뒤에서 호환 가능한 작업을 늦출 수 있지만, 작은 파일 작업의 연속이 셸 명령을 영원히 굶기지 못하게 한다. 런타임 스위치로 락 없음, 작업공간 전체 뮤텍스, 충돌 단위 락을 선택한다.

계약은 충돌 쓰기를 병합하거나 롤백하지 않는다. 아래 가정 안에서 게이트에 참여하는 같은 자원의 임계영역은 차례로 실행되고 나중 쓰기가 이긴다. 그러나 게이트는 파일시스템 트랜잭션이 아니다. 외부 reader는 직접 덮어쓰기 중 빈 파일, 부분 파일, 또는 읽는 도중 바뀐 혼합 상태를 볼 수 있으며, 경로 정규화와 실제 실행 사이 rename/link TOCTOU도 남는다. 따라서 writer 순서화는 reader에 대한 원자적 가시성이나 의미적 합의와 다르다.

### 3.4 입장, 재생, 수명주기

병렬 세션은 기본적으로 진행 중인 턴을 네 개로 제한한다. 추가 요청은 공정 대기열에서 기다린다. 이미 활성 턴이 없는 참가자만 입장할 수 있으므로 한 사람이 자신의 백로그로 모든 슬롯을 채울 수 없다. 이 게이트는 입장 공정성을 제어하지만 이미 작업공간 게이트를 잡은 배타적 효과를 우회하지는 못한다.

영속 이벤트는 재생 버퍼에 추가하는 락 안에서 단조 증가 시퀀스 번호를 받는다. Server-Sent Events는 이 번호를 Last-Event-ID로 사용하므로 재접속한 브라우저는 놓친 이벤트만 요청할 수 있다. 너무 오래되었거나 미래이거나 이전 프로세스에서 온 커서는 명시적 리셋과 스냅샷을 일으킨다. 프로세스 epoch는 suspend/resume 사이의 스트림을 구분한다.

세션 상태는 마지막에 끝난 한 턴이 아니라 활성 턴 수로 결정된다. 유휴 프로세스는 suspend할 수 있고, 이력과 작업공간은 resume을 위해 남는다. 동시성 계약은 프로세스 시작 시 고정하므로 직렬과 병렬 턴이 서로 다른 컨텍스트 규칙 아래 섞이지 않는다.

### 3.5 보장과 경계

효과 보장은 다음 가정에 한정된다.

| 가정 | 범위 |
|---|---|
| A1 | 효과가 하나의 프로세스 내부 게이트를 통과한다. 외부 IDE와 다른 OS 프로세스는 참여하지 않는다. |
| A2 | 모든 말단 작업공간 효과가 올바른 intent를 선언한다. 누락 시 작업공간 배타로 내린다. |
| A3 | 키 생성부터 실행까지 canonical 자원이 안정적이다. symlink는 해소하고 감지된 hard link는 배타화하지만 rename/link TOCTOU는 남는다. |
| A4 | 셸 효과가 전경 호출 안에서 끝난다. 분리된 백그라운드 작업은 게이트 뒤에도 살아남을 수 있다. |
| A5 | 강제 모드에서는 등록된 협조적 도구만 변경에 참여하고, 과제가 완전한 파일 manifest와 내용/test oracle을 제공한다. 실행 가능한 hook, shell, 중첩 agent, 미분류 작업공간 효과는 fail-closed한다. |

| 속성 | 상태 |
|---|---|
| 참여하는 충돌 임계영역의 비중첩 | A1–A5 아래에서 강제 |
| 검증된 파일별 원자적 게시 | A1–A5 아래 capability 모드에서 강제 |
| 여러 파일 write-set의 crash-atomic 게시 | 보장하지 않음 |
| 잘 구성된 원자적 컨텍스트 커밋 | 보장 |
| 요청자에 대한 구조적 귀속 | 보장 |
| 턴 소유 취소 | 보장 |
| 보존 창 안의 정확한 증분 재생 | 보장 |
| 모든 턴에 항상 최신 컨텍스트 제공 | 보장하지 않음 |
| 턴의 승인된 canonical write set 밖 도구 기반 과제 파일 게시 | A1–A5 아래 capability 모드에서 방지 |
| 일반적인 응답 수준 의미 격리 | 보장하지 않음 |
| 서로 다른 효과 전반의 저장소 수준 정확성 | 보장하지 않음 |
| 악의적 참가자로부터의 보호 | 범위 밖 |

이 구분이 논문의 핵심이다. 아래에서 “무결성”은 의미적 정확성을 따로 명시하지 않는 한 물리적 및 구조적 무결성을 뜻한다.

## 4 구현

Coagora는 터미널 인터페이스와 다중 사용자 LAN 웹 인터페이스를 제공하는 Python 코딩 에이전트다. 두 프런트엔드는 renderer 추상화를 통해 같은 에이전트 루프를 호출한다. 하나의 운영체제 프로세스가 세션을 소유하고, 동시 턴은 공유 힙 위의 스레드로 실행된다.

컨텍스트 관리자는 불변 스냅샷과 원자적 블록 커밋을 제공한다. 컨텍스트, renderer, 영속 append 락은 순환을 막기 위해 하나의 획득 순서를 따른다. 턴 소유권과 reply 귀속은 thread-local이므로 한 턴이 더 새 요청의 id를 물려받을 수 없다. 병렬 턴은 각자의 시스템 프롬프트를 다시 만든다. 턴 스코핑은 현재 처리할 요청을 지정한다. 선택적인 turn-local view는 다른 진행 중 턴이 만든 레코드를 각 LLM 호출에서 추가로 제거하고, 완료된 턴은 다음 추론 경계부터 다시 공유한다. 이 필터가 활성인 동안 출처를 분리할 수 없는 공유 압축 요약은 보수적으로 제외한다. 필터링한 프롬프트가 예산을 넘으면 loop는 일시적인 view만 FIFO로 줄이며, 부분 프롬프트를 근거로 출처가 섞인 공유 cache를 압축하거나 token count를 다시 맞추지 않는다.

파일 manifest와 oracle을 제공하는 과제에서는 실행 전에 canonical write capability를 turn id에 결합한다. Canonical path와 감지한 inode identity를 예약하므로 겹치는 write set은 함께 진입하지 않고 대기한다. `write_file`과 `edit_file`은 private 임시 복사본에서 동작하고 같은 경로의 `read_file`은 그 staged 복사본을 본다. 범위 밖 쓰기는 도구 경계에서 거부한다. Manifest를 우회할 수 있는 shell, 중첩 agent, 실행 가능한 hook, 미분류 작업공간 효과는 fail-closed한다. 모델 완료 뒤 과제 oracle과 dispatch 시점 파일 version을 검사하고 검증된 파일만 atomic replace로 게시한다. Oracle이나 version 검사가 실패하면 아무 파일도 게시하지 않는다. 여러 파일 전체의 전이는 crash-atomic하지 않다.

작업공간 효과는 실행 전에 intent를 알린다. 효과 게이트는 intent를 canonical 자원과 락 모드에 대응시키고 대기 및 점유 시간을 기록한 뒤 작업 종료 시 모드를 해제한다. 기존 symlink는 target으로 해소하고 여러 hard link가 감지된 파일은 작업공간 배타로 내린다. intent 어휘는 fail-closed 배타인 `UNKNOWN_WORKSPACE_EFFECT`와 자식 말단 효과가 따로 게이트를 잡는 `NON_WORKSPACE_OR_COMPOSITE`를 구분한다. 이로써 plugin 선언 누락과 의도적인 복합 도구 우회가 하나의 무잠금 값에 섞였던 모호성을 없앴다. 영속 append는 크기가 제한된 striped lock도 사용한다. 직접적인 동시 O_APPEND 쓰기는 ext4에서는 온전했지만 Windows 마운트 WSL 파일시스템에서는 레코드를 손상시켰으므로 파일시스템 append 동작을 이식 가능한 성질로 간주하지 않는다.

웹 클라이언트는 하나의 SSE 스트림을 받고 간헐적으로 POST 요청을 보낸다. SSE는 브라우저 기본 재접속과 Last-Event-ID를 제공한다. 공유 쓰기 토큰은 행동을 허용한다. 선택적 읽기 전용 토큰은 트랜스크립트 스트림만 허용하고, 모든 변경 엔드포인트와 프롬프트, 지시문, 작업공간 내용을 노출하는 읽기 요청에는 403을 반환한다. 이는 관찰과 행동의 분리이지 참가자 사이의 기밀성은 아니다.

턴 메트릭을 켜면 서버는 수명주기, 효과, 압축, 거절, 토큰, capability, validation, conflict, publication 이벤트를 하나의 단조 시계로 기록한다. 메트릭은 프롬프트나 응답 텍스트가 아니라 구조적 메타데이터를 담는다. 첫 토큰 도착 시간은 사용자의 첫 시도에 대한 가장 이른 서버 레코드부터 계산한다. 거절 조건에서는 첫 409부터 시작하므로 재시도 지연도 포함한다.

오프라인 하네스는 실제 서버를 HTTP로 구동하고 모델만 결정론적 OpenAI 호환 SSE 엔드포인트로 교체한다. 프롬프트 지시문으로 타이밍과 도구 단계를 스크립트화하며, 조건마다 새 작업공간과 격리된 HOME을 사용하고 원시 JSONL과 파생 요약을 모두 커밋한다. 모델 순응, 제공자 배칭, 실제 턴 길이에 의존하는 질문은 온프레미스 엔드포인트의 실모델 실험으로 다룬다.

동시성 스위트는 턴 입장, 컨텍스트 원자성, 효과 호환성, 귀속, 재생, 읽기 전용 권한, suspend/resume을 포함한 저장소 테스트로 검증한다. 별도의 브라우저 스위트가 클라이언트 행동을 다룬다. 부록 A는 보고한 모든 결과를 재현 스크립트와 연결한다.

## 5 기술 평가

계약을 팀이 더 잘 협업한다는 증거가 아니라 시스템 및 상호작용의 기반으로 평가한다. HCI 시스템과 툴킷 평가 지침 [41]에 따라 결정론적 실험으로 메커니즘과 경계를 검증하고, 실모델 조건으로 배치 환경에 민감한 결과를 시험한다.

모든 비교는 동일한 바이너리에서 런타임 스위치 하나만 바꾼다. 각 반복 실험은 실험 단위를 명시한다. 이진 run 결과에는 exact binomial 95% 신뢰구간을, 무작위 또는 교대 블록 대비에는 양측 exact McNemar 검정을 사용한다. 한 run 안의 턴과 고빈도 snapshot은 기술 관측으로만 남기고 독립 시행으로 취급하지 않는다. 중앙값 대비에는 원시 run 표본이 있을 때 고정 시드 백분위 bootstrap 95% 신뢰구간을 사용한다. 결정론적 메커니즘 검사는 모집단 추정이 아니라 검증으로 해석한다.

### 5.1 RQ1: 응답성과 그 대가

#### 선행 차단

사용자 A가 L ∈ {2, 6, 15, 30}초인 작업을 시작한다. 사용자 B는 0.5초 뒤 한 줄 질문을 한다. FIFO 직렬화, 250 ms 거절 후 재시도, 병렬 턴을 비교한다. 240회 중 236회에서 귀속 가능한 첫 토큰을 얻었다.

| 계약 | L = 2 s | L = 6 s | L = 15 s | L = 30 s | dTTFT/dL |
|---|---:|---:|---:|---:|---:|
| 직렬 | 2.08 s | 6.16 s | 15.34 s | 30.86 s | 1.028 |
| 거절 + 재시도 | 2.31 s | 6.34 s | 15.42 s | 31.05 s | 1.027 |
| **병렬** | **0.292 s** | **0.291 s** | **0.291 s** | **0.235 s** | **−0.002** |

30초 조건은 상수 설정 오버헤드가 56 ms 낮은 두 번째 세션에서 수집했으며 같은 세션의 대조 측정이 이 변화를 재현한다. 기울기와 같은 L 안의 비교는 영향받지 않는다. 귀속 가능한 첫 토큰이 없었던 네 실행은 제외하고 원자료에 보고했다.

직렬과 거절 계약에서는 A의 작업이 1초 늘 때마다 B의 대기가 약 1초 늘어난다. 거절은 대기를 개선하지 않으면서 재시도 위상 페널티를 더한다. L = 15초일 때 250 ms와 1,000 ms 재시도 간격은 직렬보다 각각 172 ms와 794 ms 늦었고 61회와 16회 시도했다. 병렬에서는 B의 첫 토큰이 A의 작업 길이가 아니라 B의 요청과 런타임 오버헤드에 따라 결정된다.

직렬 조건은 내부 도구 경계에서 대기 중인 질문을 주입할 수 있으므로 실제 차단 단위는 항상 전체 작업이 아니라 **경계 간격**이다. L을 15초로 고정하고 A의 작업을 k개 호출로 나누면 이를 확인할 수 있다.

| 호출 수 k | 경계 간격 | 주입 | B의 포함 시간 |
|---:|---:|---:|---:|
| 1 | 15.0 s | 0/10 | 15.10 s |
| 2 | 7.5 s | 10/10 | 7.30 s |
| 4 | 3.75 s | 10/10 | 3.39 s |
| 8 | 1.875 s | 10/10 | 1.44 s |

포함 시간은 B가 답을 받을 때가 아니라 프롬프트에 들어갈 때 멈추므로 직렬에 유리한 측정이다. 호출이 여덟 번이어도 같은 전체 작업 길이에서 병렬 TTFT의 4.9배다. 경계가 잦으면 직렬화는 잘 작동하지만, 생성, 빌드, 테스트가 중간 경계를 제공하지 않으면 전체 작업 차단에 가까워진다.

입장 대기를 없애기 위해 상한을 함께 올리면서 전체 사용자 수를 2명, 4명, 8명으로 늘리면 질문자의 TTFT는 236 ms, 265 ms, 328 ms가 되었다. 동시에 질문하는 일곱 명은 7배가 아니라 39%를 더 썼다. 이는 다른 사용자의 작업을 기다리는 시간이 아니라 런타임 경합이다.

#### 실모델과 토큰 비용

온프레미스 실모델에서 A가 긴 생성을 시작한 지 2초 뒤 B가 질문했다. 12회 반복에서 중앙 TTFT는 **직렬 38.2초, 병렬 10.8초**였고 범위와 bootstrap 구간이 겹치지 않았다. 엔드포인트 부하가 더 높은 상태에서 반복해도 43.6초 대 12.3초로 비율이 유지되었다.

절대 이득은 여전히 제공자의 한계를 받는다. Coagora를 거치지 않고 동시에 여덟 생성을 실행하면 한 생성보다 2.68배 오래 걸렸고 총 처리량은 세 배가 되었다. 계약은 B의 요청이 모델에 도달하게 보장하지만, 엔드포인트 내부의 배칭과 디코드 경합을 없앨 수는 없다.

병렬 턴은 호출도 더 많이 사용한다. 같은 세 질문 워크로드에서 직렬 주입은 2회 호출과 15.6K 입력 토큰으로 답했고, 병렬은 3회 호출과 23.2K 토큰을 사용했다. **1.49배 프리미엄**이다. 선행 턴이 다섯 개 있어도 비율은 1.47배였다. 이력은 두 계약의 비용을 비례해 늘리므로 프리미엄은 호출 수의 비율이다. 병렬성은 지연 독립성을 얻는 대신 직렬 배칭 효율을 포기한다.

### 5.2 RQ2: 무결성과 효과 경계

#### 순서화가 막는 것

강제 중첩 probe는 팔마다 독립 프로세스와 임시 작업공간 30개를 사용하고 각 반복 안의 세 팔 순서를 무작위화한다. 분석 단위는 서로 상관된 sampler 관측 하나하나가 아니라 run 하나다. 주 2 ms 조건은 참여 writer 임계영역의 중첩, 게이트에 참여하지 않는 reader가 본 혼합/파손 상태, 두 writer 종료 후 최종 파일을 분리한다.

| 2 ms 조건 | 게이트 없음 | 작업공간 락 | 충돌 단위 락 |
|---|---:|---:|---:|
| 참여 writer 중첩이 있었던 run | 30/30 | 0/30 | 0/30 |
| 외부에서 혼합/파손 읽기를 본 run | 27/30, 95% CI [73.5%, 97.9%] | 0/30, [0%, 11.6%] | 0/30, [0%, 11.6%] |
| 최종 파일이 혼합/파손인 run | 3/30 | 0/30 | 0/30 |
| 빈/부분 상태를 본 run | 29/30 | 30/30 | 29/30 |

외부 혼합/파손 가시성에 대한 paired run 대비는 게이트 없음 대 어느 락에서도 exact p = 1.49 × 10⁻⁸이었다. 1, 5, 10 ms 민감도 조건에서도 방향은 유지됐다. 게이트 없음은 각각 24/30, 24/30, 13/30회였고 두 락은 모든 간격에서 0/30회였다. snapshot 총수는 노출 trace를 설명하는 용도로만 보고한다. 마지막 행은 보장 경계도 보여준다. 게이트는 참여 writer를 순서화하지만 직접 덮어쓰기는 gate 밖 reader에게 빈/부분 상태를 노출한다. reader 원자성에는 임시 파일 후 atomic replace 같은 다른 쓰기 primitive가 필요하다.

#### 거친 락이 비싸지는 시점

두 턴에서 완전히 직렬인 효과도 배타 효과 비중 s가 0.5 이하이면 이론상 처리량 손실이 없다. 한 턴의 추론이 다른 턴의 효과 뒤에 숨을 수 있기 때문이다. 이 경계를 넘으면 작업공간 뮤텍스가 점점 지배한다.

| 효과 비중 | 경로 | 작업공간 뮤텍스 | 충돌 단위 | 회복 |
|---:|---|---:|---:|---:|
| 25% | 서로 다름 | 1.987 | 1.992 | 1.00× |
| 50% | 서로 다름 | 1.974 | 1.983 | 1.01× |
| 75% | 서로 다름 | 1.662 | 1.977 | 1.19× |
| 90% | 서로 다름 | 1.368 | 1.983 | 1.45× |
| 90% | 같은 경로 | 1.369 | 1.368 | 1.00× |

같은 경로 대조군에서는 범위 차이가 없고, 서로 다른 경로에서는 락이 없는 성능에 거의 도달한다. 따라서 더 세밀한 락의 가치는 조건부다. 서로 다른 작업이라도 배타 효과가 턴의 큰 부분을 차지한 뒤에야 중요해진다.

실제 파일 쓰기 턴은 이 경계에서 멀리 떨어져 있다. 약 4분에 걸친 여덟 번의 쓰기는 효과 비중 10⁻⁵와 중앙 락 대기 0.1 ms를 만들었다. 셸 중심 작업은 동작점을 옮겼다. 1초 명령 세 개는 비중 0.025와 측정 불가능한 대기를, 5초 명령 세 개는 비중 0.094와 약 4.1초 대기를 만들었다. 이 워크로드조차 50% 경계 아래다. 파일 락은 드문 충돌을 보호하고, 배타적 셸 점유가 실제적인 지연 비용이다.

### 5.3 RQ3a: 동시 실행에서의 구조적 정확성

다음 실험은 공유 세션을 받치는 구성요소가 불변식을 유지하는지 시험한다. 일곱 개의 독립 연구 기여라기보다 하나의 공유 세션 기반을 검증하므로 함께 묶었다.

| 속성 | 실험 | 결과 |
|---|---|---|
| 재생 | 90턴, 지속 연결 대 11회 연결 해제/재연결 | 180/180 이벤트가 순서, 이름, payload에서 동일; 누락, 중복, 역순 없음 |
| 컨텍스트 압축 | 사용자 3명 × 30라운드, 800 ms 요약기 | 90/90 질문 보존; 락 없는 요약 중 42개 턴 이벤트가 들어오는 동안 4/4 압축 커밋 |

압축은 낙관적 방식의 비용을 보여준다. 요약은 턴을 계속 받기 위해 컨텍스트 락 밖에서 실행하지만, 긴 실시간 요약은 커밋 전에 무효가 되기 쉽다. 오래된 결과는 잘못 커밋되지 않고 폐기된다. 재생도 경계가 명확하다. 보존 버퍼 안에서는 증분 복구가 정확하고, 더 오래되거나 다른 스트림의 커서는 명시적 리셋과 스냅샷을 받는다.

입장 공정성과 효과 공정성은 다르다. 사용자별 게이트는 한 사람의 백로그가 모든 턴 슬롯을 채우지 못하게 하지만, 실행 중인 배타적 셸을 우회할 수는 없다. 직접 락 실험에서 다른 사용자의 파일 쓰기 대기는 중앙값에서 기준선과 비슷했고 p95에서 셸 점유 하나와 거의 같았다. 1초 점유에서는 996 ms, 5초 점유에서는 4,992 ms였다. 엄격한 FIFO는 기아를 막는 대신 배타적 작업 비용을 드러낸다.

스냅샷 결과는 추론을 막지 않는 대가를 수치화한다. 동시 턴은 유효하지만 더 오래된 컨텍스트를 일상적으로 읽고, 긴 실모델 생성은 결정론적 하네스보다 더 깊은 꼬리를 만든다. 인터페이스는 아직 이 오래됨을 보여주지 않는다.

### 5.4 RQ3b: turn-local 파일 게시 격리

구조적 소유권은 어느 요청이 턴을 만들었는지를 기록하고, 의미적 초점은 모델이 실제로 어느 요청을 따랐는지를 묻는다. 어느 하나도 모델이 고른 도구가 다른 요청의 파일을 바꾸는 것을 막지는 않는다. 따라서 Coagora는 세 층을 분리한다. scoped prompt는 현재 요청을 지정하고, turn-local context view는 다른 진행 중 턴의 레코드를 제외하며, 강제 capability는 모델이 어떤 행동을 생성하든 게시 가능한 범위를 통제한다.

실모델 실험은 온프레미스 엔드포인트의 Qwen3.6-27B-MLX-8bit를 사용했다. 각 run은 서로 다른 두 과제를 동시에 묶었다. 한 턴은 parser token/rule 파일을, 다른 턴은 CLI 소개/사용법 파일을 만들었다. 각 과제는 승인 경로 두 개와 8줄 exact-content oracle을 제공했다. 20개 block마다 새 workspace에서 scoped prompt, scoped prompt + turn-local context, turn-local context + canonical write capability·staging·validated publication의 세 팔을 실행했다. 팔 순서는 여섯 순열을 순환했다. temperature, top-p, seed는 명시적으로 고정하지 않았으므로 추론 범위는 결정론적 model revision이 아니라 이 endpoint와 수집 날짜다.

동시 두 요청 run이 분석 단위다. 사전 정의한 scorer는 모델 행동이 범위 밖 경로를 시도했는지와 mutation이 공유 workspace에 실제 게시됐는지를 구분한다. 두 과제 oracle, 최종 저장소, 어느 응답이 상대 과제의 literal 완료 태그를 담는지, 두 턴 중 더 긴 span과 전체 입력 토큰도 판정한다. 강제 팔의 게시는 `write_set_published` 감사 이벤트를 턴의 승인 manifest와 조인해 계산하며, 설계상 0으로 대입하지 않는다.

| run 단위 결과 | Scoped prompt | Turn-local context | 강제 게시 |
|---|---:|---:|---:|
| 상대 과제 경로를 시도 | 0/20 (0–16.84%) | 0/20 (0–16.84%) | 0/20 (0–16.84%) |
| 상대 과제 파일을 게시 | 0/20 (0–16.84%) | 0/20 (0–16.84%) | 0/20 (0–16.84%) |
| 두 과제가 exact oracle 통과 | 20/20 (83.16–100%) | 20/20 (83.16–100%) | 20/20 (83.16–100%) |
| 최종 저장소가 모든 oracle 통과 | 20/20 (83.16–100%) | 20/20 (83.16–100%) | 20/20 (83.16–100%) |

| 더 긴 턴 span 중앙값 | 59.5초 | 52.1초 | 59.5초 |
| run당 입력 토큰 중앙값 | 33,508 | 32,687 | 33,177 |

모든 이진 파일·정확성 결과는 팔 사이에서 같았다(각 대비의 paired exact McNemar p = 1.0). 유일한 응답 태그 불일치도 p = 1.0으로, 모집단 차이의 증거가 아니라 보장 경계의 사례다. Filtered context는 scoped prompt보다 입력 토큰 중앙값이 2.5% 적고 더 긴 턴 span 중앙값이 12.4% 짧았다. 강제 팔은 scoped보다 입력 토큰 중앙값이 1.0% 적고 span은 사실상 같았다. 이는 한 endpoint의 기술적 동작점이며 지연 또는 비용 우월성 주장이 아니다. 강제 팔은 요청마다 하나씩 `write_set_published` 이벤트 40개를 남겼고 차단 효과와 validation 실패는 없었다. 60개 run은 모두 하나의 구현 digest에서 첫 시도에 완료됐다.

실모델 workload는 모델 행동의 표본이지만, 유한 개의 협조적인 출력만으로 접근 제어 invariant를 세울 수는 없다. 따라서 범위 밖 경로, parent traversal, shell과 직접 primitive dispatch, 복합 agent, 미분류 plugin, validation 실패 및 부재, 외부 version 변경, symlink canonicalization, hard-link reservation, 동일 경로 두 턴의 순차 validated publication을 별도의 결정론적 적대 검증 19개로 시험했다. 19개 모두 예상 결과와 일치했다. staged write는 검증 전까지 보이지 않았고, validation 실패와 version 충돌은 workspace를 바꾸지 않았으며, 같은 파일이나 hard-link alias는 reservation을 동시에 보유하지 않았다.

따라서 주장은 의미적 정확성보다 좁다. §3.5의 등록된 협조적 도구와 경로 안정성 가정 아래 턴은 승인된 canonical write set 밖에 도구 기반 과제 파일 mutation을 게시할 수 없고, staged 파일은 과제가 제공한 oracle을 통과한 뒤에만 게시된다. 시스템 소유 history·감사 파일은 이 범위가 아니며, oracle이 사용자 의도를 완전히 포착하는지, 응답 텍스트가 격리되는지, 여러 파일 교체가 하나의 crash-atomic 전이인지까지 보장하지는 않는다.

### 5.5 타당성과 주장 경계

결정론적 타이밍은 제공자 분산을 없애지만 모델 순응이나 실제 서빙 경합을 나타내지 못한다. 따라서 메커니즘 검증, 적대적 격리 검사, 통제된 sweep에 사용하고, 응답성, 컨텍스트 행동, 토큰 사용, 압축 시간, 공정성 크기, 오래됨, 수명주기에는 실모델을 사용한다. 실증거 역시 한 온프레미스 엔드포인트, 세 팔 격리 실험을 위한 한 모델, 한 호스트, 주로 2–3명 사용자에 한정된다.

워크로드는 중첩과 경계를 드러내도록 설계한 합성 작업이다. 기술 결과는 계약이 구현 가능하고 어떤 실패가 있는지 보여주지만 실제 팀의 작업 분포를 설명하지 않는다. 무결성 비율은 명시한 sampling 간격의 독립 강제 중첩 run에 속하고 의미적 오염 횟수는 시험한 모델/워크로드 쌍에 속한다. 어느 것도 보편적 발생률이 아니며, 서로 상관된 snapshot을 Bernoulli 시행으로 사용하지 않는다.

저장소는 테스트 3,652개 중 3,617개 통과, 환경 제한 skip 35개, 보고 실행 실패 0개를 기록한다. 명시적 ANSI 색상 테스트가 의도한 조건에서 실행되도록 `NO_COLOR`는 해제했다. 53개의 headless-browser 스위트가 소스 수준 테스트로 도달할 수 없는 행동을 다룬다. 이 스위트는 구현에 대한 신뢰를 높이지만 외부 반복을 대신하지 않는다.

무엇보다 기술 메트릭은 더 나은 협업을 증명하지 않는다. §6은 첫 인간 증거를 위해 남겨 두었다. 연구가 끝날 때까지 인식, 조정, 통제, 배치 적합성에 관한 주장은 연구 질문으로 남는다.

**절차와 측정.** 각 블록 시작에 두 참가자가 첫 요청을 동시에 제출한다. 각 주 조건의 8분과 16분에 진행자는 10초 freeze probe로 “지금 상대방은 무엇을 하고 있습니까?”라고 묻는다. Module C 중간에 다섯 번째 probe를 한다. 독립 코더 두 명이 각 답을 상대의 로그 활동과 비교해 2점(과제 영역과 현재 행동 모두 정확), 1점(영역은 맞지만 행동이 모호하거나 틀림), 0점(틀림 또는 “모르겠다”)으로 채점한다. 불일치는 합의로 해결한다.

각 주 조건 후 참가자는 응답 속도, 상대 인식, 잘못된 요청을 수행한다고 느낀 정도, 통제감, 해당 환경에서 협업 의향을 묻는 7점 문항 다섯 개와 개방형 문항 하나에 답한다. 마지막 사건 기반 인터뷰에서 진행자는 메트릭과 이력 로그를 사용해 교차 사용자 파일 효과, 긴 직렬 대기, 인터럽트 또는 재시도, 압축, 최대 중첩 구간을 우선하여 구체적 사건 3–5개를 선택한다. 각 사건에 대해 참가자는 먼저 기억 여부(M2: hit 또는 miss)를 보고하고, 무슨 일이 있었다고 생각했는지(M3: 에이전트, 시스템/도구, 상대, 자신, 기타)와 무엇을 했는지 설명한다. 로그에 없는 사건 보고는 false alarm으로 남긴다. 이어 상대 인식, 인터럽트 권한, 명시적 또는 암묵적 조정 규칙(M4), 계약별 대기 행동, 업무 사용 조건(M5)을 묻는다.

**분석.** 로그는 M1과 M2의 정답지이자 인터뷰 prompt 선택 수단으로만 사용한다. 이 연구의 결과변수가 아니다. 지연, 중첩, 오염률은 이미 §5에서 더 큰 규모로 측정했다. 표본이 작고 질적이므로 가설 검정을 하지 않는다. M1 점수 분포와 “모르겠다” 응답, 사건 유형별 M2 hit/miss/false alarm, 독립 코딩한 M3 귀인, 사례 중심 M4 규범, 사용 의향/조건부/비의향으로 요약한 M5를 보고한다. 조건 설문은 기술 통계만 사용한다. 하나의 합쳐진 이야기보다 부정 및 반증 사례를 우선한다.

## 7 논의

### 7.1 하나의 공유 세션이 조정 문제를 바꾼다

분리된 위임에서는 어느 작업을 어디에서 시작했는지 추적하고 나중에 산출물을 맞춰야 한다. 실시간 세션은 그 접합 작업의 일부를 메커니즘으로 옮긴다. 대기열은 턴을 받아들이고, 효과 게이트는 상태 변경을 순서화하며, reply_to는 소유권을 기록한다. 노동 자체가 사라지지는 않는다 [39]. 참가자는 여전히 과제를 나누고, 동시 스트림을 감시하고, 언제 중단할지 결정하고, 의미적 중첩을 수리해야 한다.

지속적 트랜스크립트는 비대칭 그라운딩도 만든다 [36]. 늦게 온 참가자는 같은 레코드를 재생할 수 있지만 이력에 접근하는 것과 결정 이유를 이해하는 것은 다르다. 시퀀스와 귀속은 결정 요약, 파일별 이력, 턴 필터 같은 따라잡기 인터페이스를 가능하게 하지만 본 논문은 이를 시험하지 않는다.

제어 역시 다자 문제가 된다. “사용자는 자신의 턴을 중단할 수 있다”는 규칙은 예측 가능하고 한 참가자가 다른 사람의 작업을 취소하지 못하게 하지만, 공유된 파괴적 효과에는 충분하지 않다. 팀은 역할 기반 override, 눈에 보이는 동의, 정족수 승인을 원할 수 있다. 턴 id는 이런 정책을 적용할 단위를 제공한다.

### 7.2 설계 시사점

평가는 공유 에이전트 인터페이스를 위한 네 원칙을 제안한다.

1. **요청 소유권과 모델의 초점을 따로 보여라.** 올바른 작성자 이름표는 모델이 그 사람의 요청을 따랐다는 증거가 아니다. 인터페이스는 요청 턴과 그 턴이 영향을 준 파일 또는 명령을 모두 보여줘야 한다.
2. **오래된 컨텍스트를 드러내라.** 턴은 구조적으로 유효하면서도 여러 커밋 뒤처질 수 있다. 보이는 스냅샷 나이 또는 “더 새로운 활동 있음” 표시는 사용자가 계속할지, 새로고침할지, 취소할지 결정하게 한다.
3. **보호장치를 프롬프트뿐 아니라 효과에도 배치하라.** 프롬프트와 컨텍스트 스코핑은 여전히 모델 의존적이다. 따라서 manifest-bound 과제에서는 각 턴에 exact write capability를 주고 변경을 staging한 뒤 게시 전에 검증한다. 더 넓은 대화형 과제에는 눈에 보이는 경로 제안·승인 흐름이 추가로 필요하다.
4. **대기의 이유를 보이게 하라.** 사용자는 추론 슬롯, 배타 효과, 제공자 때문에 기다릴 수 있다. 원인과 해결법이 다르므로 하나의 일반적 busy 표시로는 계약을 숨기게 된다.

이는 측정한 시스템 행동에서 도출한 시사점이다. 사용자가 이를 이해하거나 가치 있게 보는지는 first-use 및 이후 현장 연구가 답해야 한다.

### 7.3 신뢰와 배치 경계

Coagora는 이미 저장소를 공유하는, 서로 신뢰하는 협업자를 가정한다. 모든 참가자의 메시지가 공유 컨텍스트에 들어가므로 한 참가자의 텍스트가 다른 턴에 영향을 줄 수 있다. 참가자별 비공개 트랜스크립트도 없고 악의적 쓰기 참가자를 막지도 않는다. 읽기 전용 토큰은 관찰과 행동을 나누지만 참가자 사이의 정보를 나누지는 않는다.

파일 게시 격리와 프롬프트 격리도 다르다. 강제 모드는 협조적인 등록 도구를 제한할 뿐 임의의 외부 프로세스나 적대적 코드를 제한하지 않으며, 디렉터리 제한은 컨테이너가 아니다. 반대로 컨테이너도 다른 참가자의 요청이 허용 파일 안에서 턴을 조향하는 일을 막지 못한다. 신뢰할 수 없는 사용자를 받으려면 더 강한 실행 경계와 다중 주체 정책이 모두 필요하다 [30, 31].

### 7.4 한계

- **짧고 합성된 워크로드.** 실험은 실제 작업에서 사건이 얼마나 자주 일어나는지가 아니라 메커니즘과 경계를 드러낸다.
- **좁은 배치 환경.** 실모델 결과는 한 엔드포인트와 한 호스트에서 나왔고, 세 팔 파일 격리 결과는 한 모델을 사용했다. 제공자 행동은 절대 지연을 바꿀 수 있으며 관찰된 응답 행동이 다른 모델로 옮겨간다고 단정할 수 없다.
- **토큰 비용.** 측정한 워크로드에서 병렬은 직렬 주입의 두 호출 대신 세 호출을 사용하여 입력 토큰을 1.49배 썼다.
- **컨텍스트 증가와 stale 압축.** 공유 이력은 참가자 수와 함께 빠르게 자란다. 압축 중에도 턴을 받을 수 있지만 긴 실시간 요약 5개 중 3개는 커밋 전에 stale이 되었다.
- **의미적 정확성.** validated publication은 승인 파일에 대해 제공된 oracle만 증명한다. Oracle이 불완전할 수 있고 응답은 여전히 요청 경계를 넘을 수 있으며, 개별적으로 유효한 write set도 함께 양립 불가능한 결정을 구현할 수 있다.
- **Manifest와 승인 사용성.** 평가한 API는 요청과 함께 완전한 경로 manifest와 oracle을 받는다. 모델 제안·요청자 승인 대화 흐름은 아직 없으며, oracle이 없으면 자동 게시하지 않는다.
- **파생 index.** Capability 모드 게시에서는 승인된 과제 manifest 밖에 쓰는 일반 code-index post-hook을 의도적으로 실행하지 않는다. 별도로 승인한 시스템 작업으로 재구축하기 전까지 index가 stale일 수 있다.
- **락 범위.** 분리된 백그라운드 프로세스의 효과는 프로세스 내 게이트를 벗어난다. 셸 작업은 여전히 거칠고 배타적이다.
- **단일 프로세스와 디렉터리 수준 격리.** 세션은 여러 머신에 걸치지 않으며 컨테이너가 아니다.
- **유계 재생.** 증분 재생은 보존 이벤트 창 안에서만 정확하다. 더 오래된 클라이언트는 명시적 리셋을 받는다.
- **제어 정책.** 동시 턴은 취소만 지원하고 턴 중 조향, 공유 undo, 그룹 승인을 지원하지 않는다.
- **인간 결과 부재.** 계획된 연구는 첫 사용을 설명할 수 있지만 장기 채택이나 팀 생산성을 증명하지 않는다.

## 8 결론

코딩 에이전트를 공유한다는 것은 한 채팅에 클라이언트를 더 붙이는 일만이 아니다. 시스템은 요청을 언제 실행할지, 각 행동을 누가 소유하는지, 어떤 상태를 동시에 바꿀 수 있는지, 참가자가 공유 트랜스크립트에서 무엇을 안전하게 추론할 수 있는지 결정해야 한다.

Coagora는 추론을 병렬로 유지하면서 컨텍스트 커밋과 참여하는 충돌 효과를 순서화한다. 하나의 구현 안에서 이 계약은 추론 수준의 선행 차단을 없애고 동시 실행에서 트랜스크립트, 귀속, 재생, writer 순서 불변식을 보존했다. 직접 덮어쓰기를 외부 reader에게 원자적으로 보이게 하지는 않는다. 그 비용은 추가 모델 호출, 오래된 스냅샷, 효과가 지배할 때의 배타적 대기다.

더 어려운 경계는 의미적이다. 트랜스크립트가 구조적으로 유효하고 참여 효과가 순서대로 실행돼도 모델은 다른 참가자의 요청을 따를 수 있다. 따라서 Coagora는 프롬프트 순응을 보안 주장으로 바꾸지 않고 scoped prompt와 turn-local context에 요청자 승인 파일 capability 및 validated publication을 결합한다. 실모델 실험은 이 세 층의 모델 행동을 보고하고, 적대 검증은 더 좁은 파일 게시 invariant를 확인한다. 명시한 가정 아래 턴은 canonical write set 밖에 도구 기반 과제 파일 mutation을 게시할 수 없지만 응답 의미와 oracle 적절성은 모델과 과제에 의존한다. 실용적인 공유 에이전트 인터페이스는 사람들이 이 경계를 이해하고 제어할 수 있도록 소유권, 최신성, 승인, 효과를 명확히 보여줘야 한다. 계획된 first-use study는 이 경계가 실제로 얼마나 보이고 관리 가능한지 시험할 것이다.
