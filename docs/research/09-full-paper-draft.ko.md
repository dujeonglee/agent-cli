## 초록 (Abstract)

AI 코딩 에이전트는 여전히 한 번에 한 사람만 사용한다고 가정한다. 팀은 메신저 연동으로 일을 맡길 수 있지만, 이 방식은 분리된 작업을 실행할 뿐이다. 에이전트가 일하는 동안 사람이 개입할 수 없고, 여러 사람이 동시에 지시할 때 적용할 규칙도 없다. 하나의 라이브 세션을 공유하려면 두 선택지만 있는 것처럼 보인다. 추론을 직렬화해 짧은 질문을 긴 빌드 뒤에 세우거나, 세션을 포크해 하나의 공유 컨텍스트를 포기하는 것이다.

우리는 이 양자택일이 필요하지 않음을 보인다. **병렬 추론과 직렬 부수효과**라는 계약은 느린 읽기 전용 작업과 짧은 상태 변경 작업을 분리한다. 각 메시지는 공유 컨텍스트 위에서 즉시 독립된 턴을 시작한다. 파일 쓰기, 셸 명령, 컨텍스트 커밋은 충돌 단위 락을 통과한다. 따라서 사용자는 다른 사람의 추론을 기다리지 않으면서도, 충돌하는 효과는 동시에 실행되지 않는다.

우리는 이 계약을 아홉 시스템을 포괄하는 4축 설계 공간에 배치하고 Coagora에 구현했다. Coagora는 이미 직렬 모드를 제공하므로 실험 조건은 런타임 스위치 하나로만 달라진다. 결정적 하네스에서 두 번째 사용자의 첫 토큰까지 시간은 첫 번째 사용자의 작업 길이에 영향을 받지 않았다. 기울기는 병렬에서 0.00, 직렬과 배포 프레임워크의 거부 게이트에서 각각 1.03이었다. 겹침을 강제한 절제 실험에서는 락이 찢어진 쓰기를 8.2%에서 0%로 줄였고, 병합이나 롤백은 필요하지 않았다. 실모델에서도 병렬이 3.5배 빨랐으며 입력 토큰은 1.49배 사용했다. 이 비율은 이력 길이에 따라 커지지 않았다.

공유 트랜스크립트는 다른 문제를 만든다. 한 턴이 다른 참여자의 지시를 따를 수 있다. 우리는 요청들이 명확히 달랐던 경우를 포함해 실모델 80턴 중 56턴에서 이를 관찰했다. 각 턴의 프롬프트에 그 턴이 처리해야 할 요청을 명시하자 한 모델에서는 80턴 모두에서 문제가 사라졌지만, 두 번째 모델에서는 줄어드는 데 그쳤다. 따라서 턴 스코핑은 보장이 아니라 측정된 완화책이다. 마지막으로 라이브 공유가 만드는 더 큰 연구 문제인 비대칭 그라운딩과 다자 제어권 중재를 제시한다.

## 1 서론

코딩 에이전트는 이제 자동완성을 넘어선다. 저장소를 읽고, 파일을 편집하고, 셸 명령과 테스트를 실행하며, 제한된 감독만으로 풀 리퀘스트를 연다 [1, 2]. 통제 연구에서는 사용자가 혼자 끝내지 못한 작업을 에이전트가 완수했고 [2], 대규모 텔레메트리에서는 실제 세션의 41%에서 에이전트가 모든 코드를 작성했다 [3]. 그러나 이런 발전의 상호작용 모델은 거의 모두 싱글플레이어다. 즉 **한 인간, 한 에이전트**를 전제한다.

소프트웨어 개발은 대개 혼자 하는 일이 아니다. 업계도 이 불일치를 인식하기 시작했다. GitHub Next의 Ace는 싱글플레이어 에이전트가 중복 작업, 조정 부채, 어긋난 산출물을 만든다고 지적한다 [4]. Claude Code 사용자들도 구글 독스 방식의 공유 세션을 요청해 왔다 [5]. 실무의 요구가 연구를 앞선 셈이다. 여러 사람이 하나의 자율 코딩 에이전트 세션을 동기적으로 공유한 발표 연구를 우리는 찾지 못했고(§2.3), 그런 세션의 조정 방식을 설명한 시스템 논문도 없다.

**팀은 지금 에이전트를 어떻게 공유하는가.** 널리 배포된 방법은 메신저 연동이다. Claude Tag, OpenAI Codex, GitHub Copilot, Devin, Cursor는 모두 Slack과 연결되고 일부는 Teams도 지원한다. 서로 다른 벤더의 제품이지만 흐름은 비슷하다(§2.2). @멘션이 작업을 시작하고, 스레드가 컨텍스트가 되며, 에이전트는 복제된 저장소를 가진 분리된 클라우드 샌드박스에서 일한 뒤 풀 리퀘스트(PR) 링크를 스레드에 돌려준다. 팀이 이미 대화하는 곳에서 시작할 수 있고, 현대 에이전트가 테스트 실패 뒤에도 작업을 반복할 수 있다는 장점이 있다.

같은 구조는 세 가지 한계를 갖는다. 첫째, 작업 도중에는 사람이 개입할 수 없다. 스레드는 실행과 알림을 위한 표면이지 라이브 작업공간이 아니다. 둘째, 동시 지시를 조정하는 공개 규칙이 없다. 예를 들어 Anthropic은 누구나 공유 채널에서 조타할 수 있다고 설명하지만, 두 사람이 동시에 조타할 때의 동작은 밝히지 않는다 [6]. 셋째, 컨텍스트가 스레드 경계에서 끊긴다. 다른 채널의 결정, 저장소의 암묵적 상태, 에이전트의 이전 작업을 다시 텍스트로 구성해야 한다. GitHub는 스레드 전체가 결과 PR에 저장되므로 정보 노출 위험이 생길 수 있다고 명시한다 [7].

**왜 하나의 라이브 세션을 공유하지 않는가.** 팀 전체가 하나의 대화 컨텍스트와 작업 디렉토리에 접속할 수도 있다. 그러나 기존 설계는 두 가지 타협 중 하나가 필요하다고 본다.

첫째는 *추론 직렬화*다. 바쁨 게이트가 스레드마다 하나의 실행만 허용한다. LangGraph의 이중 전송 전략은 거부, 큐잉, 인터럽트, 롤백을 제공하지만 동시 실행은 제공하지 않는다 [8]. CopilotKit의 OpenTag도 스레드를 잠그고 동시 요청에 HTTP 409를 반환한다 [9]. 그러면 짧은 질문이 다른 사람의 긴 빌드 뒤에서 기다리는 선행 차단(HOL)이 생긴다.

둘째는 *세션 포크*다. 사용자나 작업마다 브랜치 또는 워크트리를 만들고, 나중에 충돌을 수리하거나 병합한다 [10, 11]. 동시성은 얻지만 하나의 공유 세션은 잃는다. 병합 작업이 생기고, 한 에이전트가 다른 에이전트의 방금 전 작업을 보지 못하도록 컨텍스트가 갈라진다. 선행 다중 에이전트 연구가 비관적 락에 반대하는 이유는 이 락이 추론도 막는다고 가정하기 때문이다 [11].

**우리의 접근.** 응답성과 무결성은 서로 다른 계층의 문제이므로 분리해 다룬다. **병렬 추론, 직렬 부수효과** 계약에서는 모든 사용자 메시지가 즉시 독립된 *턴*을 시작한다. 여러 응답은 동시에 스트리밍되고, 각 응답은 원인이 된 메시지와 1:1로 연결된다.

순서를 정하는 대상은 상태를 바꾸는 작업뿐이다. 파일 쓰기, 셸 명령, 패키지 설치, 공유 대화 컨텍스트 커밋은 직렬 실행기를 통과한다. 충돌 단위 계층 락은 서로 다른 파일의 작업은 함께 허용하고, 같은 파일의 작업과 셸 명령 및 삭제는 배타적으로 실행한다. 추론은 읽기 전용이고 오래 걸리므로 이 락을 기다리지 않는다. 효과는 짧지만 뒤섞이면 위험하므로 락을 통과한다.

선행 비관적 설계와의 핵심 차이는 락의 위치다. 우리는 추론 아래에서만 락을 사용하고 충돌이 일어나기 전에 막는다. 따라서 병합, 롤백, 보상 단계가 필요하지 않다.

**증거는 어디서 오는가.** 우리는 이 계약을 오픈소스 코딩 에이전트 **Coagora**에 구현했다. Coagora는 이 연구 전에도 하나의 프로세스, 대화 컨텍스트, 작업 디렉토리를 여러 LAN 브라우저에 공유했다. 여러 사용자가 입력할 수 있었지만 동시 실행은 없었다. 공유 큐가 한 번에 하나의 턴만 허용했고, 이 직렬 계약은 지금도 기본값이다.

따라서 강한 기준선을 사용할 수 있다. 직렬 조건은 다른 시스템을 단순화해 재구성한 것이 아니라 Coagora의 실제 프로덕션 경로다. 병렬 계약과 거부 계약은 같은 전송, 컨텍스트 관리자, 도구, 계측을 유지한 채 선택형 게이트로 추가됐다. §6의 비교에서 바뀌는 것은 주변 시스템이 아니라 계약이다.

**기여.**

1. **설계 공간**: 다중 사용자 코딩 에이전트 상호작용을 네 축(상태 소재, 동시성 계약, 귀속 단위, 개입 지점)으로 정리해 배포·프로토타입 시스템 아홉 개를 배치하고 빈 좌표를 드러낸다(§3).
2. **동시성 계약**: 병렬 추론과 직렬 부수효과를, 단일 공유 컨텍스트 위의 스냅샷 읽기/원자적 커밋, 턴 스코프 인터럽트를 동반한 턴 id 다중화, 충돌 단위 계층 부수효과 락, 사용자별 공정 입장으로 정식화한다(§4).
3. **작동하는 공유 세션 에이전트 내부의 구현**(§5): 락 스코프·동시성 계약·공정성 게이트·턴별 프롬프트 스코핑을 각각 스위치로 노출해, §6 의 모든 주장이 **같은 바이너리 위에서** 도는 절제 팔을 갖게 했다. 결정적·키 불필요 재현 하네스와 커밋된 원시 데이터를 함께 제공한다.
4. **배포된 세 계약의 시스템 내부 비교**(§6). TTFT 독립성(병렬 기울기 0.00, 직렬과 거부-재시도 1.03, 240회 중 236회 분석 ✔), 강제 겹침에서의 무결성(락 없이 찢어진 쓰기 8.2%, 락 적용 시 0% ✔), 효과 비중이 커질 때 병렬성이 줄어드는 지점을 측정한다. 별도 실험은 직렬 비용이 경계 밀도를 따르고, 거부 비용이 재시도 간격을 따르며, 병렬 결과가 사용자 수 4배에서도 유지됨을 보인다(✔). 재접속, 동시 컨텍스트 압축, 구조적 귀속, 사용자별 공정성, 중단·재개 내구성, 실모델 동작도 평가한다. 실모델의 토큰 프리미엄은 N배가 아니라 1.49배였다(§6.10).
5. **연구 의제**: 세션 공유는 위임의 문제를 없애지만 자신의 문제를 만든다. 참여자 간 비대칭 그라운딩과 다자 제어권 중재이며, 이를 컴퓨터 지원 협업(Computer-Supported Cooperative Work, CSCW) 이론에서 도출해 열린 문제로 제기한다(§7).

## 2 관련 연구

### 2.1 한 개발자, 한 에이전트

AI 페어 프로그래밍 연구는 거의 항상 한 개발자와 한 AI의 2인조를 다룬다. Imai는 Copilot이 코드 생산량을 늘렸지만 인간 페어에 비해 품질은 낮췄다고 보고했다 [12]. 이후 연구에서는 개발자가 인간 파트너의 제안보다 AI 제안을 덜 검증하는 것으로 나타났다 [1]. Chen 등은 어시스턴트와 자율 에이전트를 비교하고, 에이전트 행동을 이해하는 일이 채택의 가장 큰 장벽이라고 밝혔다 [2]. SWE-chat은 실제 에이전트 세션 6,000건을 분석해 사용자가 가능한 상황의 39%에서 에이전트를 중단하거나 방향을 바꾸지만, 에이전트는 거의 멈춰 질문하지 않는다고 보고했다 [3].

이 결과는 두 가지 점에서 우리 연구를 뒷받침한다. 조타는 예외가 아니라 일상적인 사용 방식이다. 동시에 모든 선행 연구는 한 사람이 브레이크를 통제한다고 가정한다. 공유 세션은 여러 사람이 브레이크를 사용할 때의 규칙을 정해야 한다(§7.2).

### 2.2 메신저를 통한 팀 접근

Claude Tag [13, 6], OpenAI Codex [14, 15], GitHub Copilot [16, 7], Devin [17], Cursor [18]의 Slack·Teams 연동을 조사했다. 다섯 제품은 모두 멘션 → 스레드 포착 → 클라우드 샌드박스 → PR 링크라는 큰 흐름을 따른다. 차이는 주로 작업의 정체성에 있다. Claude Tag는 에이전트 자체 계정으로 PR을 열고 작업을 조직에 귀속한다. Copilot은 요청자의 저장소 권한으로 행동한다. Devin은 Slack 사용자를 이메일로 개별 계정에 연결한다.

문서에 드러난 두 세부 사항이 이 방식의 한계를 보여준다. GitHub는 스레드 전체가 PR에 저장된다고 설명하며, 이런 노출이 허용되지 않을 때는 다이렉트 메시지를 권한다 [7]. Slack AI를 대상으로 한 간접 프롬프트 주입은 스레드를 컨텍스트로 삼을 때의 위험이 실제임을 보여줬다 [19]. Claude Tag는 채널마다 하나의 인스턴스를 공유하는 방식을 “멀티플레이어”라고 부르지만, 충돌하는 동시 지시를 처리하는 프로토콜은 공개하지 않는다 [6].

이 시스템들은 유능한 백그라운드 에이전트다. 테스트 실패 뒤에 다시 시도할 수 있고, Devin은 웹 앱과 Slack 사이에서 세션을 유지한다. 공통된 한계는 더 좁고 분명하다. 실행 도중 사람이 개입할 수 없고, 여러 사용자의 동시 행동을 조정하지 않는다.

### 2.3 여러 인간과 하나의 AI: 코딩 밖에서, 또는 세션 밖에서

가장 가까운 연구는 협업 글쓰기, 그룹 대화, 교육에서 찾을 수 있다. 협업 글쓰기에서 Lehmann 등은 일주일 동안 다중 사용자 편집기에 에이전트를 배치했다. 팀은 에이전트를 기존 협업 규범에 편입했고, 에이전트 프로필은 개인 작업공간으로, 산출물은 공유 자산으로 사용했다 [20]. 코딩은 상태가 실행 가능하고, 효과를 되돌리기 어려울 수 있으며, 테스트라는 객관적 피드백이 있다는 점에서 다르다.

그룹 대화에서 Houde 등은 집단 아이디어 발상에 참여하는 에이전트를 연구하고, 에이전트가 언제·무엇을·어디에 답할지 제어하는 장치를 제안했다 [21]. GroupMemBench도 에이전트가 다자 채널에 배치되는데 기억 시스템은 여전히 한 명의 사용자를 기준으로 설계된다고 지적한다 [22]. 이 연구들은 참여와 기억을 다루지만, 공유 코딩 작업공간의 동시 실행은 다루지 않는다.

교육 분야의 Daryanto 등은 가장 비슷한 구성을 연구했다. 참가자 20명을 대상으로 인간 1명과 AI 1명의 2인조, 인간 2명과 AI 1명의 3인조 프로그래밍을 비교했다 [23]. 3인조는 AI 코드에 덜 과의존했는데, 동료가 지켜본다는 사실이 제안을 적용하기 전에 이해하도록 만들었기 때문이다. 그러나 이 연구는 협업 학습을 다루고, 파일과 셸을 조작하는 자율 에이전트가 아니라 제안형 어시스턴트를 사용하며, 일회성 실험실 과제와 학습 성과를 평가하고, 지속되는 공유 세션이 없다는 점에서 다르다. 그 책임성 결과는 §7.3의 질문을 뒷받침한다.

다른 연구는 에이전트의 *산출물* 주변에서 여러 사람이 협업하는 경우를 다룬다. 예를 들어 리뷰어의 참여도는 에이전트가 작성한 PR의 통합 여부를 강하게 예측한다 [24]. 하지만 이는 에이전트가 작업한 뒤에 일어나는 비동기 협업이며, 라이브 세션은 여전히 싱글플레이어다. 인간-에이전트 상호작용 공개 데이터 자체가 부족하고 [25], 다중 인간 세션 데이터는 아직 없다.

### 2.4 공유 상태 위 에이전트를 위한 동시성 제어

여러 에이전트가 공유 가변 상태에서 동시에 일할 때는 주로 낙관적 조정을 사용한다. CoAgent는 쓰기를 먼저 반영하고 잘못된 순서를 사가 방식으로 되돌리며, 비관적 락은 추론을 막는다고 본다 [11]. STORM은 버전을 추적하고 여러 에이전트가 하나의 코드베이스에 쓸 때 충돌을 감지한다 [26]. 상용 도구는 에이전트마다 브랜치나 워크트리를 분리하고 나중에 병합하는 경우가 많으며, Claude Code도 이 방식을 직접 문서화한다 [10].

DeLM은 하나의 공유 컨텍스트에서 여러 에이전트를 병렬 실행한다는 점에서 가장 가깝다 [27]. 그러나 DeLM은 컨텍스트에 들어갈 내용이 근거를 갖췄는지 검증할 뿐 동시 작업의 순서를 정하지 않는다. 다중성의 방향도 다르다. 하나의 목표를 위해 여러 에이전트가 일하는 것이지, 여러 사람이 하나의 에이전트를 공유하는 것은 아니다.

LangGraph 의 이중 전송은 한 스레드의 동시 요청에 대해 거부·큐잉·인터럽트·롤백을 열거하지만 동시 실행은 없다 [8]. OpenTag 는 분산 락과 409 로 스레드당 활성 실행 하나를 강제한다 [9]. LangGraph 의 네 전략 중 둘은 우리가 측정하는 팔에 대응한다: *거부*는 §6.1 의 거부-후-재시도 팔이고, *큐잉*은 큐에 든 요청이 어느 쪽이든 활성 실행을 기다리므로 행동상 직렬 팔이다. 나머지 둘은 동시성 계약이라기보다 조타 정책이다(*인터럽트*는 도는 턴을 버리고, *롤백*은 그 턴과 효과를 함께 버린다). 즉 둘째 사용자가 언제 서비스되는가가 아니라 *첫째* 사용자의 작업이 어떻게 되는가를 바꾸므로 우리는 측정하지 않는다.

우리 계약은 비관적 순서를 효과 계층에만 둔다. 추론은 이 락을 사용하지 않으므로 병렬로 유지된다. 충돌하는 효과는 실행 전에 정렬되기 때문에 사후 충돌 감지, 롤백, 병합이 필요하지 않다. 다중성의 방향도 다르다. 격리-후-병합 도구는 한 사람을 위해 에이전트를 병렬화하지만, 우리는 하나의 에이전트 위에서 사람을 병렬화한다.

인접한 세 갈래가 이 좌표가 다른 방향에서도 비어 있음을 확인해 준다. *서빙* 측에서 Justitia 같은 공정성 스케줄러는 가상 시간 큐잉으로 작업 병렬 에이전트들에 GPU 시간을 배분한다 [28]: *작업이나 에이전트* 사이의 공정성이지 하나의 세션을 공유하는 인간들 사이의 공정성이 아니다. 사용자별 공정성 자체는 다중 테넌트 서빙에서 물론 일상적이다 — API 게이트웨이는 클라이언트별 요율 제한과 토큰 버킷을 건다. 우리가 입장 게이트(§4.5)에 대해 펴는 주장은 "첫 사용자 수준 공정성 메커니즘"보다 좁으며 다음과 같다: **하나의 공유 에이전트 세션 안에서** *턴* 입도로 동작하는 공정성 메커니즘의 선행 사례를 우리는 찾지 못했다. 여기서 경합 자원은 그 세션 자신의 동시성 슬롯이고, 경쟁하는 당사자는 격리된 테넌트가 아니라 한 대화에 함께 있는 인간들이다.

*컨텍스트* 측에서 병렬 압축 파이프라인은 블록을 동시에 펼쳐 긴 단일 에이전트 이력을 요약한다 [29]: 압축 자체가 병렬이지만, *동시 사용자 턴이 덧붙이는 도중에* 대화를 압축한 선행 연구는 없으며 그것이 §6.6 이 재는 문제다. *다중 사용자* 측에서 최근 연구는 주체 간 권한 계층과 프라이버시를 다루고 [30], ProACT 는 협업 사용자 간 조정 붕괴를 감지한다 [31]. 둘 다 다중 사용자 *정책*을 다루지 동시 실행을 다루지 않으며, 동시성 계약의 경쟁자가 아니라 보완재다.

**고전 동시성 제어와의 관계.** §4의 메커니즘 자체는 확립된 데이터베이스 기법이다. 불변 스냅샷을 읽고 완료 순서로 원자 커밋하는 방식은 스냅샷 격리다 [32]. 따라서 write skew 같은 이상 현상도 이어받으며, §4.3과 한계 3에서 그 의미론적 형태를 설명한다. 호환성 행렬로 분류된 자원을 잠그는 방식은 세분화 락과 의도 락을 따른다 [33]. 자원 범위를 미리 알 수 없는 셸 명령과 삭제를 워크스페이스 배타로 승격하는 것도 같은 원리다. 비관적·낙관적 제어의 절충과 마지막 쓰기 우선 결과 역시 알려진 개념이다 [34, 35].

우리의 기여는 이 기법을 배치한 위치다. 선행 에이전트 시스템은 모델이 실행되는 계층에 동시성 제어를 적용하고, 비관적 락이 추론을 멈추므로 너무 비싸다고 결론낸다 [11]. 우리는 추론 아래, 상태가 바뀌는 지점에만 적용한다. 기법은 고전적이지만, LLM 턴이 트랜잭션처럼 동작하고 사람이 실시간으로 지켜보는 상황에서 이 배치가 실제로 유효한지가 시스템 연구의 질문이다. §6이 그 답을 측정한다.

### 2.5 이론적 렌즈

네 개의 CSCW 전통이 세션 공유의 의미를 틀 짓는다. *그라운딩* [36]: 협업자는 매체가 정하는 비용으로 공통 기반을 점진적으로 축적한다. 에이전트가 끼면 그라운딩은 삼자 문제가 되고, 지속되는 세션은 축적된 인간-에이전트 기반을 늦은 합류자에게는 없는 일급 자산으로 만든다(§7.1). *작업공간 인식* [37, 38]: 누가 어디서 무엇을 하는지 아는 것. 공유 편집기의 텔레포인터와 구조적으로 동형이되, 에이전트는 어떤 인간보다 더 많은 상태를 더 빨리 바꾼다. *접합 작업(articulation work)* [39]: 협업을 가능하게 하는 조정 노동으로, 자동화는 이를 제거하기보다 이동시키는 경향이 있다(§7.4). *혼합 주도 상호작용* [40]: Horvitz 의 원칙은 에이전트가 언제 행동하고 언제 물어야 하는지를 다스리지만 한 명의 인간을 전제한다. 다자 설정은 *누구에게 물을 것인가*라는 차원을 더하는데, 원래 원칙은 이를 다루지 않는다.

## 3 다중 사용자 코딩 에이전트 상호작용의 설계 공간

§2의 시스템들은 서로 달라 보이지만 네 가지 질문으로 구분할 수 있다. 이 질문을 미리 정한 것이 아니라 문서에서 도출했다. 각 시스템에 대해 “에이전트가 일하는 동안 두 번째 사람이 말하면 무슨 일이 일어나는가”를 기록하고, 모든 시스템을 분명하게 배치할 수 있을 때까지 답을 묶었다.

표 1은 Coagora의 두 모드를 포함한 아홉 시스템을 배치한다. 문서로 확인할 수 있었던 시스템의 지도일 뿐 4축 공간이 충분히 채워졌다는 주장은 아니다. 축마다 근거의 질도 다르다. 벤더는 대체로 동시성 동작(D2)을 명시하지만, 개입 지점(D4)은 인터페이스에서 추론해야 하는 경우가 많다.

**D1. 상태 소재.** 에이전트의 세션 상태는 인간이 대화하는 공간에 대해 어디에 사는가? *바깥*(대화가 분리된 실행기를 트리거하고, 상태는 실행 시점에 뜬 사본)인가, *안*(대화 표면이 라이브 세션을 보는 창이고, 상태가 원본)인가.

**D2. 동시성 계약.** 에이전트가 바쁜 동안 두 번째 지시가 도착하면 어떻게 되는가? *거부*(바쁨 게이트, 409), *직렬화*(선입선출(FIFO) 단일 활성 턴), *배치*(입력들을 하나의 프롬프트로 묶어 융합된 답 하나), *격리-후-병합*(사용자/작업별 포크 후 나중에 조정), 또는 *병렬 + 직렬 부수효과*(본 논문).

**D3. 귀속 단위.** 산출물을 그것을 야기한 인간까지 어느 입도로 추적할 수 있는가? *풀 리퀘스트*, *작업*, 또는 *턴*(모든 에이전트 메시지가 하나의 사용자 메시지에 1:1 로 연결).

**D4. 개입 지점.** 인간은 언제 작업에 영향을 줄 수 있는가? *실행 전/완료 후*뿐인가, *실행 중*인가, 실행 중이라면 세션 전체 범위인가 개별 턴 범위인가?

두 Coagora 행은 개입 범위뿐 아니라 개입 *종류*도 다르다. 직렬 모드는 조타를 지원한다. 턴 경계에서 메시지를 주입하면 활성 턴에 합쳐져 방향을 바꾼다. 병렬 계약은 현재 사용자가 소유한 턴의 취소만 지원하고(§4.2), 특정 실행 중 턴의 조타는 지원하지 않는다(§7.6 항목 8). 병렬 모드는 정확히 자기 작업만 멈출 수 있다는 정밀성을 얻지만, 취소 외에는 할 수 없다는 표현력의 손실이 있다. 설계 공간은 이 절충을 함께 보여줘야 한다.

이 지도에서 세 가지 패턴이 보인다. 첫째, 메신저 연동은 상태가 대화 밖에 있고, 작업 단위로 귀속하며, 실행 전후에만 개입하는 군집을 이룬다. §1의 한계는 특정 벤더가 아니라 이 좌표에서 나온다. 둘째, 세션 안의 상태, 병렬 실행, 턴 단위 귀속, 턴 범위 개입을 결합한 시스템은 없었다. 셋째, 두 Coagora 모드는 같은 시스템을 사용하고 중심 축인 D2만 다르다.

이후 절은 이 이동을 설계하고 구현하고 측정한다. 직렬과 거부 조건은 가상의 약한 기준선이 아니다. 배포 시스템이 실제로 사용하며, 그중 직렬은 Coagora가 이미 제공하던 계약이다.

## 4 계약: 병렬 추론, 직렬 부수효과

### 4.1 모델

**세션**은 삼중항 *S = (C, W, T)* 다. 하나의 공유 대화 컨텍스트 *C*, 하나의 작업 디렉토리 *W*, 그리고 턴 집합 *T*로 이루어진다. 클라이언트 수에는 제한이 없다. 에이전트는 각 이벤트를 한 번 생성하고 모든 구독자에게 같은 순서로 전송한다. 세션에는 항상 에이전트 프로세스가 하나만 있으며, 사용자가 접속해도 별도 프로세스·가상 머신·컨텍스트 포크가 생기지 않는다.

계약은 두 개의 약속이다:

> **(P) 병렬 추론.** 모든 사용자 메시지는 독립적인 턴 *t_i* 가 된다. *t_i* 의 추론은 다른 비행 중 턴과 무관하게 즉시 시작하고, 응답은 모든 참여자에게 동시에 스트리밍된다.
>
> **(S) 직렬 부수효과.** 어떤 턴이 만드는 모든 효과(파일 쓰기, 도구 실행, *C* 에 대한 모든 커밋)는 워크스페이스별 직렬 입장 메커니즘을 통해, 완료 순서로, 충돌하는 효과와 결코 동시가 아니게 적용된다.

두 약속의 비대칭은 의도적이다. 추론은 읽기 전용이고 수초에서 수분이 걸리며 사용자가 기다리는 시간의 대부분을 차지한다. 추론을 막으면 한 사람의 작업 길이가 다른 사람의 지연이 된다. 효과는 더 짧고, 턴들이 공유 상태를 망가뜨릴 수 있는 유일한 통로다. 따라서 추론은 병렬로 유지하고 충돌하는 효과만 정렬한다.

### 4.2 턴: 독립성, 다중화, 1:1 귀속

동시 메시지를 하나의 프롬프트로 묶지 않는다. 배치는 소유자가 불분명한 답을 만들고, 메시지별 추론 설정을 없애며, 개별 턴을 중단할 기회도 제거한다. 우리는 귀속을 화면 표시가 아니라 정확성 속성으로 다룬다.

각 턴은 큐에 들어갈 때가 아니라 *디스패치*될 때 단조 증가하는 **턴 id**를 받는다. 따라서 모든 id는 실제로 모델에 전달된 작업을 뜻한다. 스트리밍 텍스트, 도구 호출, 확인, 오류는 모두 이 id를 가진다. 런타임은 id로 동시 출력을 분리하고, 영속 응답은 원래 사용자 메시지를 가리키는 `reply_to`를 저장한다. 인터페이스는 각 스트림을 별도의 라벨 카드로 보여준다.

**턴 범위 인터럽트.** 인터럽트는 하나의 턴 id만 취소한다. 시스템은 부분 출력을 보존하고 턴을 완료 상태로 만든 뒤 슬롯을 반환한다. 다른 턴의 추론, 스트리밍, 효과는 계속된다. 레지스트리는 호출자의 연결 id를 확인하고 다른 사용자가 소유한 턴의 취소를 거부한다. 인터페이스도 같은 소유권 규칙을 따른다. 사용자의 입력창은 그 사용자의 턴이 실행 중일 때만 비활성화된다. 이는 각 사람이 자기 작업을 통제한다는 최소 정책이며, §7.2는 더 풍부한 정책이 필요한 이유를 설명한다.

### 4.3 공유 컨텍스트: 스냅샷 읽기, 완료 순서 원자 커밋

모든 턴은 하나의 대화 컨텍스트 *C*를 공유한다. 사용자마다 컨텍스트를 나누면 결국 격리-후-병합으로 돌아간다. 두 규칙이 공유 컨텍스트를 일관되게 유지한다.

- **스냅샷 읽기.** 각 추론 스텝에서 턴은 *C* 의 불변 스냅샷을 프롬프트로 읽는다. 다른 턴의 비행 중 부분 출력은 결코 보이지 않는다.
- **완료 순서 원자 커밋.** 스텝이 끝나면 턴은 결과(어시스턴트 메시지와 *모든* 대응 도구 결과 메시지)를 하나의 원자 블록으로, 직렬 커밋 사슬을 통해, 완료 순서로 커밋한다. 블록 경계는 불변식이다: 어시스턴트/도구-결과 쌍을 쪼개면 그 사이로 다른 턴의 커밋이 끼어들 수 있고, 이는 LLM 채팅 API 가 강제하는 메시지 짝 제약을 위반해 요청 자체가 거절된다.

두 규칙은 대화에 스냅샷 격리를 적용한다(§2.4). 데이터베이스와 같은 장점과 같은 한계를 갖는다.

비용은 제한된 최신성 저하다. 한 턴의 스냅샷은 그 뒤에 다른 턴이 커밋한 내용을 보지 못할 수 있다. 우리는 이 문제를 제거했다고 주장하지 않고 측정한다(§6.7, 한계 5). 다만 이는 신선도의 한계이지 구조적 일관성 위반은 아니다. *C*는 항상 어떤 직렬 실행으로도 만들 수 있는 올바른 트랜스크립트로 남는다.

물려받는 경계는 write skew다 [32]. 두 턴이 같은 정상 스냅샷을 읽고 서로 다른 파일을 고친 뒤, 함께 불변식을 깨뜨릴 수 있다. 예를 들어 두 턴 모두 한 함수의 호출자가 하나뿐이라고 보고 시그니처 변경이 안전하다고 판단할 수 있다. 쓰기는 모두 온전하고 순서와 귀속도 정확하지만 저장소는 일관되지 않다. 충돌이 겹치는 쓰기가 아니라 턴의 판단에 있으므로 효과 직렬화로는 잡을 수 없다. 따라서 이 계약은 물리적 무결성을 보장하지만 의미론적 정확성까지 보장하지 않는다. 한계 3에서 다시 다룬다.

### 4.4 효과 계층: 전역 뮤텍스에서 충돌 단위 계층 락으로

첫 실행기는 워크스페이스 전체에 뮤텍스 하나를 사용했다. 정확성은 지켰지만 서로 다른 파일을 다루는 턴까지 줄 세웠다. §6.4는 이 비용이 언제 나타나는지 측정한다. 효과가 턴의 대부분을 차지할 때 서로 다른 파일에 쓰는 두 턴의 유효 병렬도는 워크스페이스 뮤텍스에서 1.37, 충돌 단위 락에서 1.98이었다. 1.45배를 회복한 셈이다. 효과 비중이 작을 때는 직렬화할 시간 자체가 짧아 두 방식이 거의 같다.

현재 실행기는 *충돌* 단위로 락을 건다. 각 효과 의도를 분류하고 호환성 행렬을 확인한다. 세분화 락 [33]과 마찬가지로 의도마다 락 모드가 있고, 호환되는 모드는 함께 실행되며, 자원 집합을 알 수 없는 연산은 더 거친 락으로 승격된다.

| 의도 쌍 | 결정 | 근거 |
|---|---|---|
| FILE_WRITE/READ(경로 *p*) 대 FILE_WRITE/READ(경로 *q*), *p* ≠ *q* | **병렬** | 서로소 자원 |
| FILE_WRITE/READ(*p*) 대 FILE_WRITE/READ(*p*) | 직렬 | 같은 자원 |
| 무엇이든 대 SHELL 또는 PACKAGE | 직렬 (배타) | 셸의 파일 발자국은 정적으로 알 수 없다(파이프, 전개, 서브셸). 건전한 경로 키가 없다 |
| 무엇이든 대 FILE_DELETE | 직렬 (배타) | 삭제는 디렉토리를 지울 수 있다. `rm -r src/` 를 `write src/x.py` 옆에서 돌리면 배타 하에서는 없던 ENOENT 경쟁 부류가 *생긴다*. 삭제는 드물어 배타성이 거의 공짜다 |
| 정렬 대상 아님 (복합 도구, 사람 대기 도구, 워크스페이스 밖 상태) | **락 없음** | 이들에게는 이 락이 정렬할 워크스페이스 효과가 없다. 아래 참조 |
| 알 수 없는 파일 효과 | 직렬 (배타) | 안전 우선 기본값 |

경로 키는 구분자를 통일하고, 대소문자를 구분하지 않는 파일시스템에서는 케이스도 통일한다. 따라서 `A.txt`와 `a.txt`는 충돌한다. 입장은 **워크스페이스별 엄격한 FIFO이며 추월을 허용하지 않는다.** 큐의 첫 효과가 실행 중인 효과와 충돌하면, 뒤의 호환 가능한 효과를 먼저 실행하지 않고 기다린다. 일부 동시성을 포기하는 대신 파일 작업이 대기 중인 셸 명령을 계속 굶기는 일을 막는다. 런타임 스위치 `--lock-scope off | workspace | conflict`는 롤백 경로이자 §6.2와 §6.4의 절제 조건이다.

*정렬 대상 아님* 범주는 스레드 모델이 만드는 교착을 피한다. 서브에이전트와 스킬 같은 복합 도구는 중첩 에이전트 루프를 시작하고, 잎 도구가 다른 스레드에서 효과 락을 얻는다. 부모가 배타 락을 든 채 자식을 기다리면 어느 쪽도 진행할 수 없다.

이 범주에는 세 종류가 있다. 복합 도구는 잎 호출에서 각각 락을 건다. 사람의 응답을 기다리는 도구는 무기한 멈출 수 있으므로 다른 효과를 막아서는 안 된다. 세션 메모리, 코드 인덱스, 네트워크 가져오기처럼 워크스페이스 밖의 상태를 바꾸는 도구는 자체 가드를 갖는다. 이들은 이 락이 정렬할 워크스페이스 효과가 없다. 반면 종류를 알 수 없는 *파일* 효과는 계속 배타로 처리한다.

이 위치가 낙관적 설계와의 차이를 만든다(§2.4). 추론 경로의 락은 추론을 막지만, 우리 락은 추론이 사용하지 않는다. 충돌하는 효과는 실행 전에 정렬되므로 사후 감지, 롤백, 보상, 병합이 필요하지 않다. 같은 자원에 대한 쓰기는 순서에 따라 마지막 쓰기가 남는다. 비관적 순서와 이 결과는 고전적이다 [34, 35]. 기여는 이를 추론 아래에 배치하고 그 절충을 측정한 데 있다(§6.4).

### 4.5 입장: 상한, 공정 큐, 사용자당 턴 하나

병렬성에는 한도가 필요하다. 턴이 늘 때마다 토큰을 더 쓰기 때문이다. 세션은 기본적으로 비행 중 턴을 4개까지 허용한다. 한도를 넘은 요청은 거부하거나 합치지 않고 공정 큐에 넣는다. 큐는 앞에서부터 적격 요청을 찾으며, 사용자가 이미 활성 턴을 갖고 있으면 적격하지 않다. 즉 병렬성은 사용자 사이에만 존재하고, 한 사람의 백로그 안에서는 생기지 않는다. 한 사용자가 요청을 많이 제출해 모든 슬롯을 차지할 수 없다. 시스템이 시작한 턴은 예외이며, 한 사용자의 대기 요청이 다른 사용자의 즉시 실행 가능한 요청을 막지 않는다. §6.1은 초과 요청을 거부하고 재시도시키는 방식이 더 느림을 보인다.

### 4.6 세션 상태와 수명주기

세션 상태는 활성 턴 수로 결정된다. 턴이 하나라도 실행 중이면 RUNNING이고, 수가 0이 될 때만 IDLE이다. 한 턴이 끝나도 다른 턴이 남아 있으면 상태가 잠시 IDLE로 바뀌지 않는다. 유휴 세션은 프로세스를 종료해 중단할 수 있으며, 디렉토리와 이력은 나중 재개를 위해 남긴다.

동시성 계약은 세션을 시작할 때 선택하고 그 프로세스가 끝날 때까지 바꾸지 않는다. 서로 다른 컨텍스트 규칙을 사용하는 직렬 턴과 병렬 턴이 한 세션에 섞이지 않는다. 알 수 없는 계약 이름은 직렬 모드로 조용히 대체하지 않고 시작 오류로 처리한다. 그렇지 않으면 오타 하나가 전체 측정을 무효로 만들 수 있다.

### 4.7 순서, 재생, 멱등성

공유 세션은 연결이 끊겨도 이벤트 순서를 보존해야 한다. 모든 영속 이벤트는 재생 버퍼에 들어갈 때 단조 증가하는 `seq` 번호를 받는다. 번호 발급과 버퍼 추가는 같은 락 안에서 일어난다. 팬아웃 시점에 번호를 주면 두 턴이 번호를 받은 순서와 버퍼에 들어간 순서가 달라질 수 있고, 재접속한 사용자가 라이브 사용자와 다른 순서를 보게 된다.

서버는 `seq`를 서버 전송 이벤트(SSE)의 `id`로 보낸다. 브라우저는 자동 재접속 때 이를 `Last-Event-ID`로 돌려주므로 서버는 놓친 이벤트만 다시 보낼 수 있다. 세 경우에는 리셋과 전체 스냅샷이 필요하다. 커서가 보존 버퍼보다 오래됐거나, 아직 발급되지 않은 미래를 가리키거나, 이전 프로세스에서 만들어진 경우다. 마지막 경우는 프로세스별 스트림 epoch로 구분해 새 스트림을 옛 트랜스크립트에 잘못 이어 붙이지 않는다. 재생 가능한 영속 이벤트만 `seq`를 가지며 토큰 델타와 스피너 같은 일시 이벤트는 갖지 않는다. §6.5는 반복해서 연결이 끊긴 클라이언트가 계속 연결된 클라이언트와 정확히 같은 트랜스크립트에 도달하는지 확인한다.

## 5 구현

Coagora는 약 38,400줄의 Python과 6,300줄의 의존성 없는 브라우저 자산으로 이루어져 있다. 단일 사용자 터미널과 다중 사용자 LAN 웹 인터페이스를 모두 지원한다. 두 프런트엔드는 렌더러 인터페이스를 통해 같은 에이전트 루프를 호출하므로, 멀티플레이어 기능을 위해 별도 실행 경로를 만들지 않았다. 공개 저장소에는 구현과 원시 데이터가 함께 들어 있다. 이 절은 동시 세션을 재현하는 데 필요한 설계 결정을 설명한다.

**한 프로세스, 여러 스레드.** 각 세션은 하나의 운영체제 프로세스이고, 턴은 공유 힙 위의 스레드로 실행된다. 모든 효과를 대신 중개하는 부모 프로세스가 없으므로 §4의 보장은 하나의 주소 공간 안에서 강제해야 한다.

**컨텍스트 관리자의 락 규율.** 모든 턴이 공유 컨텍스트에서 스냅샷을 읽고 결과를 커밋하며, 압축도 같은 객체를 바꾼다(§6.6). 세션 전체의 교착을 막기 위해 락은 항상 컨텍스트 → 렌더러 → 파일 추가 순서로 얻는다. 각 획득 지점에 이 순서를 문서화했고, 역순 획득은 허용하지 않는다.

**턴 스코핑은 각 프롬프트에 속한다.** 병렬 턴은 각자 에이전트 루프와 시스템 프롬프트를 만든다. `--turn-scoping`을 켜면 그 프롬프트에 해당 턴이 처리할 요청을 명시한다(§6.7). 웹 인스펙터에서 프로젝트 지시를 바꾸면 프롬프트를 처음부터 다시 만들기 때문에, 스코핑 섹션도 재구성할 때마다 붙인다. 이 기능은 플래그와 병렬 계약이 모두 켜져 있을 때만 활성화된다. 직렬 모드에서는 주입된 질문이 실행 중인 턴의 방향을 바꿔야 하므로 같은 지시가 맞지 않는다. §6.7의 결과에 따라 병렬 세션의 기본값이 됐으며, 절제 실험을 위해 `--no-turn-scoping`을 남겼다.

**귀속은 스레드 로컬이어야 한다.** 각 스레드는 자신이 처리하는 질문 id를 저장하고, 그 스레드가 쓰는 모든 레코드는 모델 출력과 무관하게 같은 `reply_to`를 가진다. 첫 구현은 세션 전역 필드 하나를 사용했다. 직렬 모드에서는 문제가 드러나지 않았지만 동시 실행에서는 세 답변이 모두 마지막 질문에 귀속됐다. 라이브 실행에서 버그를 발견한 뒤 스레드 로컬 저장소로 옮기고 회귀 테스트를 추가했다. §6.7이 수정된 귀속의 정확성을 검증한다.

**프로덕션 경로가 원자 커밋을 사용해야 한다.** 컨텍스트 관리자에는 §4.3의 완료순 원자 커밋과 동시성 테스트가 이미 있었다. 그러나 §6.7의 최신성 지연을 계측하는 과정에서 실제 스텝 경로가 이 기능을 호출하지 않는다는 사실을 발견했다. 그 경로는 어시스턴트 레코드와 도구 관찰을 따로 추가했다. 직렬 실행에서는 올바르게 보이지만, 병렬 실행에서는 다른 턴이 두 레코드 사이에 끼어들 수 있다. 이제 실제 스텝 경로가 두 레코드를 하나의 원자 커밋으로 저장하며, 회귀 테스트가 동시 추가 중에도 쌍이 갈라지지 않음을 확인한다.

수정 뒤에는 이력 순서의 영향을 받을 수 있는 모든 목 실험을 다시 실행했다. 대상은 압축(§6.6), 귀속과 스코핑(§6.7), 공정성(§6.8), 수명주기(§6.9)다. 모든 구조적 결과가 재현됐다. 발급 사슬과 `reply_to` 대응은 완전했고, 관련 실험의 질의 90개와 204개가 모두 보존됐으며, 압축 4회가 모두 커밋됐고, 입장 게이트 위반은 없었다. 스케줄링에 민감한 내용 비율은 반복마다 달라졌고, 스코핑을 끈 한 실행은 38%를 기록했다. 이는 §6.7이 설명하는 변동성과 일치한다. 헤드라인 수치는 바뀌지 않았으며 새 원시 데이터는 `out/postfix/`에 있다.

실모델 실험도 원래 크기로 반복했다. 결론은 유지됐다. 턴 스코핑은 다시 오염을 40개 중 25개에서 0개로 줄였다(이전 실행은 26개 대 0개). §6.4의 작동점은 효과 비중 10⁻⁵와 락 대기 0.1 ms로 같았다. §6.10의 지연과 토큰 비율도 3.55배와 1.486배로 재현됐고, 절대 시간만 엔드포인트 부하에 따라 달라졌다.

달라진 결과는 하나였다. §6.4의 서로소 조건에서 오염이 6회 중 1회에서 6회 모두로 늘었다. 반면 같은 코드의 §6.7 전용 실험은 40개 중 25개와 26개로 거의 같았다. 따라서 레코드 순서가 아니라 엔드포인트 부하와 겹침 정도가 변화의 원인이다. 두 버그는 동시 시스템이 개별 프리미티브뿐 아니라 실제 프로덕션 경로까지 시험해야 함을 보여준다.

**Append 원자성은 파일시스템에 달렸다.** 쓰기를 직렬화할 부모 프로세스가 없으므로 durable 이력에는 모든 턴이 직접 덧붙인다. 탐침 결과 로컬 ext4 에서는 안전했지만(append 한 번이 `write(2)` 한 번이라 `O_APPEND` 원자성이 성립하고, 16 스레드가 8회씩 덧붙여도 무손상), WSL(Windows Subsystem for Linux)의 Windows 드라이브 마운트에서는 같은 탐침이 데이터 대부분을 잃었다: 4 KiB 페이로드에서 128줄 중 45줄만 남고 그중 15줄이 깨진 JSON 이었으며, 1 MiB 에서는 128줄 중 28줄이었다. 실패 양상이 위험한 종류인데, 레코드 로더가 파싱 불가한 줄을 조용히 건너뛰기 때문이다. 재개된 세션은 오류 없이 그냥 이력이 비어 있게 된다.

수리는 스트라이프된 프로세스 내 append 락이다(경로당 락 하나가 아니라 고정 개수의 스트라이프이므로 긴 세션이 락을 무한히 쌓지 않는다). 락을 걸면 같은 탐침이 128/128, 손상 0 으로 돌아온다. 하나의 공유 이력 파일에 대한 동시 append 는 다중 사용자 병렬 턴이 만들고 그 외에는 아무것도 만들지 않는데, 이것이 이 위험이 계약과 정확히 같은 시점에 나타난 이유다.

**도구 호출은 스트리밍된 content 에서 파싱한다.** 에이전트는 제공자 네이티브 함수 호출에 의존하지 않고 모델의 content 스트림에서 JSON 연산 배열을 파싱한다. 이는 함수 호출 지원이 제각각인 온프레미스 서버들을 가로질러 이식성을 유지한다. 파서는 증분식이라, 응답 스트리밍이 끝나기 전에 그 턴의 첫 도구 호출을 디스패치할 수 있다.

**웹 표면.** 다중 사용자 표면은 HTTP 다: 클라이언트당 하나의 SSE 스트림이 하향, 평범한 POST 가 상향. 여기서 SSE 는 WebSocket 대신 의도적으로 고른 것이다. 브라우저 네이티브 자동 재접속과 `Last-Event-ID` 가 §4.7 의 재생을 애플리케이션 기계가 아니라 전송의 속성으로 만들어 주고, 상향 방향은 가끔 오는 작은 메시지만 나르기 때문이다. 인증은 상수 시간으로 비교되는 공유 세션 토큰이다. 두 번째 읽기 전용 토큰을 켤 수 있으며(기본 off), 그것을 제시한 클라이언트는 스트림 구독만 할 수 있다: 모든 변이 엔드포인트가 403 으로 답하고, 트랜스크립트 이상을 노출하는 읽기 엔드포인트(프롬프트 검사, 프로젝트 지시사항, 워크스페이스 내용)도 마찬가지다. 이 분리가 존재하는 이유는 "보게 하기"와 "행동하게 하기"가 서로 다른 부여이고, 시연이나 리뷰는 전자이기 때문이다.

**중단과 재개.** 세션의 durable 상태는 append 전용 이력 파일이다. 재개 시 렌더러는 클라이언트가 붙기 전에 그 이력을 이벤트 버퍼로 재생하므로, 재접속하는 브라우저는 이전 대화를 특수 경로가 아니라 평범한 스냅샷 경로로 본다. 식별자 카운터는 압축된 캐시가 아니라 *전체* 이력에서 재도출되므로, 재개된 세션이 압축은 작업 창에서 떨어뜨렸으나 기록에는 귀속이 남아 있는 id 를 다시 발급하는 일이 없다(§6.9).

**계측 평면, opt-in.** `--turn-metrics` 를 주면 세션은 구조화된 이벤트를 `turns.jsonl` 에 덧붙인다: 턴 수명주기(큐 진입 → 디스패치 → 첫 토큰 → 완료), 효과 락의 큐 진입/획득/해제와 대기·보유 시간, 압축 세대, 거부, 콜별 토큰 사용량이 전부 하나의 단조 시계 위에 놓인다. §6 의 모든 수치는 이 파일이나 durable 이력에서 계산되고 클라이언트 측 타이밍은 결코 쓰지 않으므로 시계 차 보정이 없다. 첫 토큰까지의 시간은 세 계약 모두에 대해 한 번만 정의된다: 어떤 사용자의 첫 제출 시도를 기록한 **가장 이른 서버 측 레코드**부터 그 사용자의 첫 토큰까지의 구간이다. 규칙은 균일하고, 어느 레코드가 가장 이른지는 계약이 정한다 — 수용된 시도는 큐 진입으로, 거부된 시도는 거부로 기록되므로, 거부 계약에서는 기준점이 첫 409 가 되고 클라이언트의 재시도 대기 전체가 측정 구간 안에 들어온다. 이 평면은 구조적 메타데이터만 기록하고 프롬프트나 응답 텍스트는 결코 기록하지 않는다.

**과학을 위한 결정성.** 벤치마크 하네스(§6, `bench/multiuser/`)는 실제 서버를 HTTP 로 구동해 로컬 목 LLM 을 향하게 한다: OpenAI 호환 SSE 서버로, 지연·토큰 수·도구 스텝이 프롬프트에 박힌 지시자(`[[bench ttft= tok= n= work= fwrite= …]]`; 어느 스크립트가 어느 실험을 구동하는지는 부록 A 에 있다)로 스크립트되며 난수나 시계 의존 분기가 없다. 같은 입력이 같은 타임라인을 만들고, 스위트는 네트워크나 자격증명 없이 돌며, 각 조건은 격리된 `HOME` 을 가진 새 임시 워크스페이스를 받으므로 벤치마크가 운영자의 설정을 읽지도 쓰지도 못한다. 두 실험은 모델 계층을 의도적으로 우회해 도구와 락을 직접 구동한다(§6.2, §6.4). 그 이유는 가정이 아니라 하네스의 **실측된 속성**이다.

목은 대화에서 진행도를 읽는데(가장 최근 지시자 이후의 관찰), *공유* 세션에서는 동시 턴들의 관찰이 하나의 계수기에 들어온다. 각 호출이 어느 지시자를 해소했는지 로깅하면 결과가 정확히 보인다: 각 턴의 첫 호출은 자기 지시자를 고르지만 연속 호출부터 가장 최신 것으로 붕괴하고, 그 뒤 한 턴이 다른 턴의 경로에 쓰다가 에이전트 자신의 반복 감지에 걸린다. 공유 프롬프트 안에 목이 키로 삼을 턴별 신호가 없으므로 이것은 고칠 버그가 아니라 하나의 공유 컨텍스트로 **서로 다른** 동시 워크로드를 스크립트하는 것의 한계다.

동시 턴이 **같은** 워크로드를 돌아도 되는 실험(§6.1, §6.6~§6.9)은 영향받지 않으며 목을 쓴다. 통제 스윕이 아니라 실제 작동점이 질문인 곳(§6.4)에서는 자기 턴의 요청을 읽어 이 한계가 없는 실모델을 쓴다.

## 6 평가

평가의 질문은 세 가지로 요약된다. 계약이 실제로 작동하는가, 어디서 이득이 줄어드는가, 그리고 비용은 얼마인가.

| 연구 질문 | 평가 대상 |
|---|---|
| RQ1–RQ2 | 병렬 턴이 선행 차단을 없애는지, 직렬·거부 계약의 비용은 무엇인지 |
| RQ3 | 효과 직렬화가 물리적 오염을 막는지 |
| RQ4 | 병렬성이 어디서 무너지고, 세밀한 락이 무엇을 회복하며, 실제 워크로드가 곡선의 어디에 놓이는지 |
| RQ5–RQ6 | 클라이언트가 정확히 재접속하고, 턴이 계속되는 동안 컨텍스트를 압축할 수 있는지 |
| RQ7–RQ9 | 동시성 아래에서 귀속, 공정성, 수명주기가 정확하게 유지되는지 |
| RQ10 | 실 LLM에서도 순위가 유지되는지, 병렬성이 토큰을 얼마나 더 쓰는지 |
| RQ11 | 첫 사용자가 무엇을 알아차리고, 사건을 어떻게 해석하며, 어떤 조정 규범을 만들고, 어디에 시스템을 쓰려 하는지 |

**평가 범위.** 이 절은 작동하는 아티팩트에 대한 시스템 평가다. Coagora의 프로덕션 경로 안에서 본 계약을 배포 시스템이 사용하는 두 대안과 비교한다. HCI 시스템과 툴킷을 위한 Ledo 등의 분류 [41]로 보면 기술 벤치마킹과 시연을 결합한 평가다. 팀이 실제로 더 잘 협업하는지는 측정하지 않는다. §7은 그라운딩, 중재, 책임성을 인간 대상 연구 의제로 전개하지만, 이 절은 구현의 보장과 비용만 다룬다.

**설정.** 대표 실험은 §5의 결정적 하네스를 사용한다. 서버, 워크스페이스, 락, 전송은 실제이고 LLM의 시간과 행동만 스크립트로 제어한다. 네트워크나 자격증명 없이 재현할 수 있다. 모든 비교는 같은 바이너리에서 스위치 하나만 바꾼다(`--concurrency-contract`, `--lock-scope`, `--per-user-gate`, `--turn-scoping`). §6.10은 핵심 비교를 실 온프레미스 모델로 반복한다. 모든 그림의 원시 JSONL은 `bench/multiuser/out/`에 커밋돼 있다. ✔

✔ 아래에서 팔 사이 대비를 인용하는 곳에서는 계수에 양측 Fisher 정확검정, 중앙값에 고정 시드 퍼센타일 부트스트랩 95% 신뢰구간(재표집 10,000회)을 커밋된 원시 파일에서 재계산해 함께 보고한다(`stats_recompute.py`). 런별 표본이 아니라 집계만 커밋된 실험(§6.8)은 집계만 보고한다.

**고정 오버헤드에 관한 주의.** 모든 턴은 상수 셋업 비용(에이전트 루프 조립 + 스크립트된 첫 토큰 지연)을 진다. 계약 간에 동일하므로 기울기와 동일 조건 비교에서는 상쇄되지만, 측정 세션 사이에는 약간 이동한다. 아래의 선행 차단 그리드는 두 세션에서 수집됐고(L ∈ {2, 6, 15} s, 그리고 나중에 L = 30 s), 그 사이 상수가 약 56 ms 줄었다. 두 번째 세션에서 L = 15 s 를 대조 재측정하니 두 번째 세션의 상수를 정확히 재현하므로, 이 이동은 *L* 의 효과가 아니라 환경적임이 확인된다(`out/e2-drift-control.json` ✔). 결과는 유계이고 해당 위치에 명시한다:

기울기는 면역이다(상수 오프셋은 회귀에서 상쇄된다). 한 *L* 안의 계약 간 비교도 면역이다(각 세션이 그 레벨의 세 계약을 함께 측정했다). 레벨 간 절대값 비교만이 경계를 넘는다.

### 6.1 RQ1 과 RQ2: 세 계약 하의 선행 차단 ✔

사용자 A가 *L* ∈ {2, 6, 15, 30}초인 작업을 시작하고 0.5초 뒤 사용자 B가 한 줄 질문을 보낸다. B의 첫 시도가 서버에 기록된 시점부터 첫 토큰까지를 측정한다. 거부 조건에서는 첫 409가 시작점이므로 재시도 시간도 포함된다. Coagora의 FIFO 기본 계약, 250 ms 간격의 거부-후-재시도, 병렬 계약을 비교한다. 총 240회(셀당 20회) 중 236회에서 귀속 가능한 첫 토큰이 나왔고, 나머지 4회는 아래에서 설명한다. A의 작업은 도구 경계 없이 토큰만 스트리밍한다. 이 조건의 의미도 뒤에서 따로 다룬다.

| 계약 | L = 2 s | L = 6 s | L = 15 s | L = 30 s | 기울기 dTTFT/dL |
|---|---|---|---|---|---|
| 직렬 (FIFO, 출하 모드) | 2.08 s | 6.16 s | 15.34 s | 30.86 s† | 1.028 |
| 거부 + 재시도 | 2.31 s | 6.34 s | 15.42 s | 31.05 s† | **1.027** |
| **병렬 (우리)** | **0.292 s** | **0.291 s** | **0.291 s** | **0.235 s†** | **-0.002** |

† 고정 오버헤드가 약 56 ms 낮은 두 번째 세션에서 측정(설정 절 참조). 기울기와 같은 *L* 에서의 계약 간 비교는 영향받지 않으며, 이 경계를 넘는 것은 레벨 간 절대값 비교뿐이다. 그것이 병렬 행에서만 눈에 띄는 이유는 그 행의 지연이 *곧 그 상수*이기 때문이고, *L* 이 지배하는 나머지 두 행에서는 보이지 않는다. 수치는 원시 데이터가 지지하는 정밀도로 보고한다: 기울기는 소수 셋째 자리, 지연은 유효숫자 세 자리.

핵심 결과는 비율이 아니라 *기울기*다. 직렬과 거부 계약의 기울기는 약 1.03이다. A의 작업이 1초 길어질 때마다 B도 약 1초 더 기다린다. 지연 비율은 *L* = 2초에서 7.1배, 30초에서 131배로 커지지만 이는 실험이 끝난 지점을 보여줄 뿐이다. 병렬 계약의 기울기는 약 0이다. B의 지연은 A의 작업 길이가 아니라 B 자신의 요청에 의해 결정된다.

**적합, 산포, 그리고 분석되지 않은 4회.** 위 기울기는 셀 중앙값에 대한 최소제곱 적합이다. 236 개 개별 점 전체로 다시 적합해도 실질적으로 달라지지 않고(직렬 1.028 로 동일, 거부 1.027 대 1.026, 병렬 -0.002 로 동일), 직렬과 거부의 관계는 거의 완전한 선형이다(R² = 0.99998, 0.99992). 병렬 행의 R² 는 의도적으로 보고하지 않는다: 응답이 의존하지 않는 변수에 대한 적합도는 의미가 없고, 병렬 행의 분산 전체가 설정 절에서 말한 56 ms 세션 드리프트이므로 그 R² 0.81 은 *L* 에 대한 의존이 아니라 그 계단을 기술할 뿐이다.

산포는 기울기만큼이나 계약을 선명하게 가른다. 병렬의 p95 − p50 은 네 셀에서 1.7~2.7 ms 이고 표준편차는 1.7 ms 를 넘지 않는다. 직렬의 산포는 *L* 과 함께 자란다(p95 − p50 이 9.8, 31.7, 69.8, 106.0 ms, 표준편차 8.0~69.4 ms) — 더 긴 스트림 뒤에서 줄 서면 생기는 일이다. 셋 중 가장 예측하기 어려운 것은 거부인데, 재시도 위상이 아무것과도 동기화돼 있지 않기 때문이다: L = 15 s 에서 p95 가 p50 보다 268 ms 위, 표준편차 99.6 ms 로 같은 레벨의 직렬보다 한 자릿수 크다.

끝으로 240 회 중 4 회(병렬 L = 2 s·6 s 각 1회, 거부 L = 2 s·15 s 각 1회)는 B 에 귀속되는 첫 토큰을 남기지 않아 위의 모든 중앙값과 적합에서 제외했다. 조용히 버리지 않고 보고하며, 원인은 규명하지 않았다. 두 계약과 세 레벨에 흩어진 1.7% 의 실행이 1.03 대 0.00 의 기울기 차이를 설명할 수는 없다.

세 가지 독법에 주의가 필요하다. 첫째, 병렬 행은 한 측정 세션의 세 레벨에서 0.291 s 로, 다른 세션에서 측정된 레벨에서 0.235 s 로 평평하다. 통합 기울기는 -0.002 이고 세션 내 기울기는 -0.00003 이며, 둘은 같은 말을 한다. 눈에 보이는 계단은 설정 절에서 서술한 고정 오버헤드 드리프트이고, 그 자체가 주장의 작은 예증이다: 병렬 계약의 TTFT 는 *그 상수 외에 아무것도 아니므로* 상수의 변화가 거기서는 전부 드러나는 반면, *L* 이 지배하는 직렬·거부 행에서는 보이지 않는다(같은 레벨에서 15.337 s → 15.360 s, 0.15% 이동).

둘째, 거부 계약은 배포된 다중 사용자 프레임워크들이 실제로 출하하는 것이므로 강조할 가치가 있다. 이것은 직렬의 선행 차단 대기를 *전부* 치른 *뒤* 세금을 더 낸다. 250 ms 재시도 간격에 대해 네 레벨에서 각각 +232 ms, +182 ms, +79 ms, +190 ms 로 측정된, 간격 1개분의 위상 의존 분수다. 아래로는 재시도가 마침 실행 중 턴이 끝나는 순간에 떨어질 때 0 이고, 위로는 간격 하나가 상한이다.

따라서 *직렬보다 나은 적이 없으며*, 덤으로 재시도 기계를 모든 클라이언트에 떠넘긴다. 기울기가 직렬과 같은 이유는 그 세금이 *L* 의 함수가 아니라 상수이기 때문이다: 거부는 대기를 더 빨리 자라게 만드는 것이 아니라, 같은 대기를 조금 더 길게 만들고 클라이언트를 더 복잡하게 만든다.

그 세금은 우리가 고른 재시도 간격에 대해 측정된 것이므로, 결론이 그 선택에 의존하는지 확인했다 ✔. L = 15 s 로 고정하고 직렬을 같은 세션에서 기준선으로 함께 재니, 250 ms 간격은 직렬보다 172 ms, 1,000 ms 간격은 794 ms 를 더 치렀다. 각각 간격 하나의 0.69 배와 0.79 배이고, 클라이언트는 들어가기 위해 61 회와 16 회의 요청을 썼다. 벌점은 간격에 비례해 커지되 간격 하나 안에 머무르는데, 위상 의존 분수라면 정확히 그래야 하는 모양이고, 두 설정 모두에서 순위는 바뀌지 않는다.

서버를 배려해 느슨하게 재시도하는 클라이언트는 그저 더 늦게 서비스되고, 세게 재시도하는 클라이언트는 더 많은 요청을 쓰면서 직렬의 지연으로 수렴한다. 거부는 어떤 간격에서도 직렬보다 낫지 않으며, 간격이 정하는 것은 얼마나 더 나쁜가뿐이다.

셋째, 그리고 이것이 이 비교에 대한 반론의 가장 강한 형태인데, *직렬 팔은 정확히 무엇인가?* 여기서 직렬화는 맨 큐가 아니다. 도는 에이전트 루프의 내부 턴 경계마다 직렬 계약은 대기 중인 사용자 메시지 하나를 큐에서 꺼내 진행 중인 턴 안으로 접어 넣는다. §6.10 이 그 동작을 반대편에서 측정하는데, 거기서 직렬은 세 질문을 두 번의 모델 콜로 답한다. 그 주입이 발동할 수 있다면 B 의 답은 A 의 실행 *안에서* 생성될 수 있고, 직렬의 첫 토큰까지의 시간은 *L* 이 아니라 A 의 다음 경계까지 남은 시간으로 유계가 된다.

그러므로 위 그리드는 무엇을 고정하고 있는지와 함께 읽어야 한다. A 의 작업은 도구 스텝이 없는 단일 스트리밍 생성이므로 A 의 루프는 정확히 한 턴이고 경계도 정확히 하나, 즉 끝뿐이다. 주입은 직렬 팔에서 켜져 있고 한 번도 발동하지 않는다 — 측정을 위해 껐기 때문이 아니라 이 워크로드가 발동할 기회를 주지 않기 때문이다.

이는 의도된 선택이었고, 양날이다. 이 선택은 메커니즘을 분리한다: 직렬화 하의 선행 차단 지연은 무엇이 점유하든 워커가 *L* 동안 점유된다는 사실에서 오고, 순수 추론은 실행 중 주입과 효과 락 경합을 교란 변수에서 제거하므로 기울기가 워크로드의 도구 구조가 아니라 계약을 잰다. 그러나 이 선택은 직렬을 가장 취약한 상태로 재는 것이기도 하며, 발견을 정직하게 진술하려면 고정된 축의 이름을 불러야 한다.

직렬의 실제 선행 차단 노출은 **경계 밀도**가 좌우한다: 몇 초마다 도구를 위해 멈추는 루프는 주입에 잦은 기회를 주어 A 가 끝나기 훨씬 전에 B 를 서비스할 수 있는 반면, 하나의 긴 생성을 뱉거나 하나의 긴 빌드에 막혀 있는 루프는 아무 기회도 주지 않는다. 실제 코딩 작업을 지배하는 국면 — 몇 분짜리 테스트 실행, 대규모 단발 편집 — 이 바로 저밀도 쪽이고, 그래서 우리는 경계 수가 아니라 *L* 을 헤드라인 축으로 삼는다. 그러나 경계 밀도 축은 아직 측정하지 않았으므로, 이 표가 뒷받침하는 주장은 비율이 시사하는 것보다 좁다: *직렬화 하에서 둘째 사용자는 첫째 사용자의 작업이 경계에 닿기를 기다리며, 이 그리드는 그 경계가 끝뿐인 경우를 측정한다.* 다음 실험이 이 그리드가 고정한 축을 잰다.

**경계 밀도 축, 측정 ✔.** 총 작업 길이를 L = 15 s 로 고정한 채 A 의 작업에 든 모델 콜 수 k ∈ {1, 2, 4, 8} 을 k − 1 개의 도구 스텝으로 쪼개 바꾸고, B 의 질문이 모델에 닿는 시점을 쟀다. 셀당 10 회 반복, 전 구간 직렬 계약. 지표는 **time-to-inclusion** 이다: B 의 제출부터 B 의 질문이 어느 모델 콜의 프롬프트에 들어간 순간까지. 의도적으로 B 의 첫 토큰까지의 시간이 아니며, 그 이유인 계측 사실은 직렬이 제공한다고 말할 수 있는 것의 경계이기도 하다 — 첫 토큰 이벤트는 run 당 한 번만 래치되므로, 도는 턴 안으로 접혀 들어간 질문에는 귀속시킬 자기 첫 토큰이 없다. 따라서 inclusion 은 직렬에 두 번 유리하다. B 가 답을 받은 순간이 아니라 B 의 질문이 프롬프트에 들어간 순간에서 멈추고, 스크립트된 모델에서는 그 다음 콜이 B 에게 답하는 대신 A 의 작업을 계속하기 때문이다. 그럼에도 보고하는 이유는 이 관대한 하한만으로도 질문이 정리되기 때문이다.

| k (A 작업의 모델 콜 수) | 경계 간격 L/k | 주입 발동 | time-to-inclusion p50 |
|---|---|---|---|
| 1 | 15.0 s | 10회 중 0회 | 15.10 s |
| 2 | 7.5 s | 10회 중 10회 | 7.30 s |
| 4 | 3.75 s | 10회 중 10회 | 3.39 s |
| 8 | 1.875 s | 10회 중 10회 | 1.44 s |

세 가지 독법. 첫째, 정합성 체크가 성립한다. k = 1 에서 주입은 한 번도 발동하지 않았고(10회 중 0회) 이는 위 공개가 예측한 그대로이며, 거기서는 B 가 자기 run 을 받으므로 측정 가능한 B 의 첫 토큰까지의 시간이 15.41 s 로, 헤드라인 그리드가 같은 레벨에 대해 보고하는 15.34 s 와 두 측정 세션에 걸쳐 0.5% 일치한다. 그리드의 직렬 셀이 곧 k = 1 셀이다.

둘째, 법칙이 정확하다. 40 회 전체에서 inclusion 을 경계 간격에 회귀하면 기울기 1.041, R² = 0.99995, 절편 −514 ms 인데, 그 절편은 잡음이 아니다. B 의 500 ms 제출 지연이며, 이는 B 를 자기 제출 시점부터 다음 경계까지 기다리게 하는 메커니즘이 정확히 예측하는 값이다. 기울기의 4% 초과분은 콜당 스트리밍 오버헤드로, 콜이 뱉는 토큰 수와 함께 자란다. 셋째, 크기. 동일한 *L* 에서 경계를 하나에서 여덟으로 늘리면 B 의 대기가 15.10 s 에서 1.44 s 로 10.5 배 줄어든다.

결론은 헤드라인 그리드 혼자서는 닿을 수 없던 것이다. *직렬화의 선행 차단 비용은 작업 길이가 아니라 경계 간격이 정한다.* 그리드가 *L* 을 재는 것은 k = 1 을 고정했기 때문이고, k = 1 은 허수아비 설정이 아니라 긴 작업이 실제로 취하는 모양이다 — 하나의 긴 생성, 또는 하나의 긴 빌드는 큐에 끼워 넣을 틈을 주지 않는다. 경계가 조밀하면 직렬은 경계 간격 하나를 향해 우아하게 저하하고, 성기면 작업 전체에 접근한다. 직렬이 결코 하지 못하는 것은 병렬 계약이 하는 일이다. k = 8 에서도, 그리고 직렬을 답에 못 미치는 하한으로 재도, B 의 1.44 s 는 같은 레벨에서 병렬 계약의 0.29 s 의 4.9 배이고, 여전히 B 자신이 아니라 A 의 작업의 함수다.

**사용자 수 축, 측정 ✔.** 헤드라인 그리드는 두 번째 것도 고정한다 — 사용자가 정확히 둘이다. A 가 같은 L = 15 s 작업을 도는 동안 0.5 s 뒤 N − 1 명의 질문자가 **동시에** 제출하게 하고, 총 사용자 수 N ∈ {2, 4, 8} 로 쟀다. 동시성 상한은 N 으로 둬서 입장 게이트가 아니라 계약이 시험 대상이 되게 했다(게이트는 §6.8 이 따로 잰다). 셀당 10 회 반복, 질문자 턴 총 110 개. 첫 토큰까지의 시간 중앙값은 N = 2 에서 236 ms, N = 4 에서 265 ms, N = 8 에서 328 ms 였고, 모든 셀에서 p95 가 중앙값의 33 ms 안에 있었다. 즉 동시 질문자 7 명은 각자에게 1 명일 때보다 7 배가 아니라 **39%** 더 들게 한다. 그 증가는 실재하고 숨기지 않는다: 더 많은 동시 턴을 스레드·연결·하나의 출력 스트림을 더 많은 구독자에게 부채꼴로 내보내는 데 드는 런타임 비용이며, 다른 사용자의 작업을 기다리는 것이 아니라 동시성 자체의 비용이다.

RQ1 에 중요한 것은 헤드라인 행의 평탄함이 사용자가 정확히 둘이어서 생긴 것이 아니라는 점이다. 사용자 수가 4 배가 돼도 질문자의 지연은 여전히 자기 요청 + 유계 런타임 오버헤드이고, 같은 작업 길이에서 직렬 계약의 두 사용자 수치보다 여전히 47 배 낮다. 이 비교는 직렬에 후한 것이다 — 직렬이라면 질문자들이 서로의 뒤에도 줄을 서야 하기 때문이다.

### 6.2 RQ3: 효과 직렬화가 막는 것 ✔

두 작성자가 같은 파일을 반복해서 쓰도록 겹침을 강제한다. 각 본문에는 서로 다른 마커와 체크섬이 있다. 2 ms 샘플러는 스냅샷을 정상, 혼합(두 마커가 섞인 찢어진 쓰기), 손상(구조 또는 체크섬 오류), 부분(쓰기 진행 중)으로 분류한다. 락을 끈 조건과 두 락 범위를 비교한다.

락이 없을 때는 분류된 스냅샷의 **8.2%**가 위반이었다. 110개 중 9개였고 모두 두 작성자의 내용이 섞인 찢어진 쓰기였다. 어느 락 범위를 사용해도 위반은 **0%**였다. 워크스페이스 범위에서 181개 중 0개, 충돌 범위에서 180개 중 0개였다(양측 Fisher 정확 검정, 9/110 대 잠금 조건 합계 0/361: p = 1.6 × 10⁻⁶). 락이 같은 파일에 대한 동시 쓰기를 막으므로 병합, 충돌 대화상자, 롤백이 필요하지 않다.

**이 팔이 실모델을 쓸 수 없는 이유.** 이 절제는 두 writer 와 락을 직접 구동하는데, 여기서 그것은 편의가 아니라 질문을 던지는 유일한 방법이다. 위반은 두 쓰기가 물리적으로 겹치는 동안에만 일어날 수 있으므로, 위반 *비율*을 재려면 표본을 뽑을 만큼 자주 겹치는 쓰기가 필요하다. §6.4 의 실모델 측정이 그것이 에이전트 루프를 통해서는 도달 불가능한 이유를 보인다: 실제 턴은 4분에 흩뿌려진 밀리초 미만의 쓰기 여덟 번을 만들고(효과 시간 비중 10⁻⁵), 두 턴이 *같은* 파일을 대상으로 해도 실측 락 대기가 0.1 ms 다. 즉 그들의 쓰기는 사실상 겹치지 않는다. 이 실험의 분류된 동시 쓰기 스냅샷 110개를 실모델로 재현하려면 수천 턴 규모가 필요하고, 그러고도 나오는 비율은 겹쳤을 때 무슨 일이 일어나는가가 아니라 얼마나 드물게 겹쳤는가에 지배된다.

겹침을 강제하고 락이 버티는지 묻는 것이 I/O 경쟁을 재는 표준적 방법이며, 이는 두 질문을 깔끔하게 분리한다: §6.4 는 실제 작업에서 동시 효과가 *얼마나 자주* 충돌하는지를 재고(드물게), §6.2 는 *충돌했을 때 무슨 일이 일어나는지*를 잰다(락 없으면 손상, 있으면 없음). 이 실험이 뒷받침하는 주장은 구성상 조건부이고, 그 조건을 정량화하는 것이 다른 실험이다.

메커니즘을 명명할 가치가 있는데, 그것이 주장의 경계를 정하기 때문이다. 여기서 쓰기는 truncate 후 하나의 큰 `write(2)` 이며 좁은 인터리브 창을 남긴다. 위반율은 그 창의 속성이다: 쓰기를 청크로 스트리밍하는 실행기를 가진 플랫폼은 창을 넓히고, 완전 원자적 교체를 하는 플랫폼은 창을 닫는다. 불변인 것은 방향과 0 이다. 그래서 우리는 이 비율을 이 플랫폼에서 위험이 실재한다는 증거로, 0 을 계약의 보장으로 보고하며, 8.2% 를 보편 상수로 제시하지 않는다.

### 6.3 RQ4a: 병렬 이득은 어디서 붕괴하는가 ✔

턴이 파일을 쓴다고 해서 병렬성이 바로 사라지는 것은 아니다. 파일 작업이 없는 두 턴의 유효 병렬도는 1.99다. 일반적인 파일 쓰기를 추가해도 모든 셀의 중앙값 락 대기는 1 ms 미만이며, 락 범위나 경로 충돌 여부에 따른 차이가 없다. 실제 파일 쓰기는 마이크로초에서 밀리초만 지속돼 거의 겹치지 않는다. 경계는 쓰기의 *존재*가 아니라 배타 효과 안에서 보내는 *시간 비중*으로 결정된다.

우리는 그 그리드를 과대 해석하는 대신 한계를 밝힌다. 그리드가 의도한 두 번째 축, 즉 턴당 쓰기 *횟수*(0, 2, 6)는 사실 작업량을 바꾸지 못했다: 쓰기 2회와 6회에서 턴 지속시간이 동일하다(중앙값 2,897 ms 와 2,898 ms). 목 모델이 *공유* 트랜스크립트에서 가장 최신인 `[[bench …]]` 지시자를 해소하므로 동시 턴들이 하나의 스크립트로 붕괴하기 때문이다. 이는 §6.2 와 §6.4 가 모델 계층을 통째로 우회하게 만든 바로 그 함정이며, 따라서 이 그리드에서는 위의 락 대기 결과만 읽어야 한다.

이득을 실제로 붕괴시키는 것은 **배타 효과의 시간 비중**이고, 두 독립 측정이 그에 동의한다. 각 턴이 자기 구간의 약 50% 를 배타 셸 스텝 안에서 보내면 유효 병렬도(유용 작업에서 락 대기를 제외)는 1.59 로 떨어지고, 약 90% 에서는 **1.10** 에 이른다. 락을 직접 구동하고 효과 비중을 호스트에서 캘리브레이션하는 §6.4 의 통제 실험이 같은 법칙을 반대 방향에서 재현한다: 전역 락 하에서 유효 병렬도는 턴 2개에 대한 해석적 상한 2 / max(1, 2s)(효과 비중 *s*)를 측정한 모든 비중에서 1.3% 이내로 따라간다(측정된 *s* 가 0.23, 0.45, 0.60, 0.73 일 때 예측 2.00, 2.00, 1.68, 1.38 대 실측 1.99, 1.97, 1.66, 1.37).

설계 공간의 진술: *붕괴 경계는 효과 횟수나 충돌률이 아니라 배타 효과의 시간 비중을 따른다.* 실제 코딩 에이전트 턴은 추론이 지배하고 파일 효과는 짧으므로 일반적인 경우는 경계에서 멀리 있으며, 효과가 무거운 영역에서 락에 남는 일은 지연이 아니라 무결성(§6.2)이다.

### 6.4 RQ4b: 충돌 단위 락이 되찾는 것, 그리고 실제 작업이 앉아 있는 자리 ✔

§4.4 는 전역 뮤텍스가 서로소 경로를 건드리는 턴들까지 직렬화하므로 너무 뭉툭하다고 주장한다. 이 주장을 세우려면 측정이 둘 필요하다. 어느 하나만으로는 답이 되지 않기 때문이다. **통제 스윕**은 뭉툭한 락의 비용이 효과 시간 비중에 따라 어떻게 변하는지를 세운다. **실모델 실행**은 그 곡선 위 어디에 실제 작업이 앉아 있는지를 세운다. 두 번째가 없는 첫 번째는 작동점을 못 찍은 법칙이고, 첫 번째가 없는 두 번째는 "락 스코프는 중요하지 않다"와 "이 워크로드가 아직 중요해지지 않는 자리에 있을 뿐이다"를 구분하지 못한다.

**통제 스윕.** 두 턴이 락 없는 사고 구간과 락 걸린 쓰기를 번갈아 수행하되, 각 락 스코프 하에서, 쓰기 대상을 *서로소* 경로 또는 *같은* 경로로 향하게 한다. 사고 구간은 이 호스트에서 쓰기 한 번이 실제로 얼마나 걸리는지의 실행 시점 캘리브레이션(이번 실행에서 1 MiB 에 26.39 ms)으로부터 정해지므로, 효과 시간 비중이 바라는 속성이 아니라 통제된 축이 된다. 이 팔은 §5 에 적은 이유로 도구와 락을 직접 구동하며, 그 이유는 가정이 아니라 실측했다. 셀당 5회, 총 120회.

| 효과 시간 비중 | 경로 | `workspace` (전역) | `conflict` (우리) | 회복 | `off` (참조) |
|---|---|---|---|---|---|
| 25% | 서로소 | 1.987 | 1.992 | 1.003× | 1.994 |
| 25% | 동일 | 1.988 | 1.988 | 1.000× | 1.994 |
| 50% | 서로소 | 1.974 | 1.983 | 1.005× | 1.986 |
| 50% | 동일 | 1.978 | 1.976 | 0.999× | 1.988 |
| 75% | 서로소 | 1.662 | 1.977 | **1.19×** | 1.988 |
| 75% | 동일 | 1.656 | 1.653 | 0.998× | 1.987 |
| 90% | 서로소 | 1.368 | 1.983 | **1.45×** | 1.992 |
| 90% | 동일 | 1.369 | 1.368 | 0.999× | 1.991 |

*동일* 경로 행을 먼저 읽으라: 그것이 대조군이고, 경로가 실제로 충돌할 때 두 스코프가 구별되지 않음을 보인다(1.000×, 0.999×, 0.998×, 0.999×). 따라서 서로소 경로에서의 이득은 보장을 약화시켜 산 것이 아니다. 그것은 애초에 정렬이 필요 없던 작업을 직렬화하던 비용을 되돌려받은 것이다. 전역 뮤텍스 하의 중앙값 락 대기가 스윕 전체에서 같은 이야기를 한다: 28.9 ms, 26.6 ms, 553 ms, 1,077 ms. `off` 열은 남은 오버헤드의 경계를 짓는다: 충돌 단위 스코프는 락이 전혀 없는 경우의 1% 이내로 도는 반면, §6.2 는 `off` 가 무결성에서 무엇을 치르는지 보인다.

아래 두 행은 해명해서 넘길 널 결과가 아니라 효과의 *모양*이다. 턴이 둘일 때 효과를 완전히 직렬화했을 때의 병렬도 상한은 효과 비중 *s* 에 대해 2 / max(1, 2s) 이므로, *s* ≤ 0.5 에서는 전역 뮤텍스가 완벽하게 뭉툭해도 비용이 0 이다. 한 턴의 사고 구간이 다른 턴의 효과 뒤에 통째로 숨기 때문이다. `workspace` 열은 측정한 모든 비중에서 그 상한을 1.3% 이내로 따라간다(§6.3). 즉 뭉툭한 락의 비용은 튜닝으로 없앨 상수 오버헤드가 아니라, 그 선 아래에서는 0 이고 위에서는 효과 비중과 함께 자라는 것이다.

**실제 작업이 앉아 있는 자리.** 스윕이 측정한 가장 낮은 비중은 0.23 이다. 실제 작동점을 찾기 위해 같은 비교를 목도 우회도 없이 돌렸다: 실 온프레미스 모델이 진짜 턴을 구동하고, 두 사용자가 각각 네 개의 파일을 쓰도록 지시받으며, 각 락 스코프와 각 경로 조건에서 총 12회. 효과 비중은 하네스가 아니라 **서버 자신의 락 계측**(보유 시간을 스레드로 턴에 귀속)에서 도출한다.

실측된 작동점은 **효과 시간 비중 1 × 10⁻⁵** 이고, 12회 전체에서 중앙값과 최댓값이 같다: 263 초짜리 턴 구간에 대해 락 보유 3.4 ms. 락 대기는 중앙값과 최댓값 모두 0.1 ms 였다.

말할 만한 스코프 차이가 없으며(서로소: workspace 1.864 대 conflict 1.854; 동일: 1.873 대 1.890 — 다만 이 넷 중 첫 값은 3 회가 아니라 **2 회**의 유효 런에 근거한다. 아래 서술한 교차 과제 필터가 서로소/workspace 런 하나를 제외했기 때문이다), 더 눈에 띄는 것은 동일 경로 결과다: *같은* 네 파일에 쓰는 두 턴이 측정 가능한 경합을 전혀 만들지 않는다. 4분에 흩뿌려진 밀리초 미만의 쓰기 여덟 번은 사실상 겹치지 않기 때문이다.

**수리된 seam 위 재측정 ✔.** §5 의 스텝 seam 수리 뒤 이 팔을 같은 크기로 반복했다. 이 절이 딛고 선 두 수치는 그대로 재현된다: 효과 시간 비중 1 × 10⁻⁵ 와 락 대기 중앙값 0.1 ms 가 네 셀 전부에서 이전과 같고, 턴 구간만 엔드포인트가 붐벼 약 20% 길어졌다(같은 경로 셀에서 296 s 대 246 s). 같은 경로 병렬도도 재현된다(1.902 와 1.925 대 1.873 과 1.890). 살아남지 못한 것은 **서로소 경로 비교**이고, 그 이유가 §6.7 의 주제다: 서로소 런 여섯 개 **전부**에서 한 턴이 이웃의 과제를 수행했다(원래는 여섯 중 하나). 그래서 의도한 경로 조건을 구현한 런이 하나도 없고 축에 보고할 유효 셀이 없다.

원래의 서로소 수치는 커밋된 데이터이므로 유지하되, 재실행이 그것을 잴 *조건* 자체를 재현하지 못했음을 기록한다. 이는 §6.7 이 직접 재는 현상이 여기서는 결과가 아니라 장애물로 나타난 것이며, 아래 문단이 비율을 크게 과소평가하는 이유이기도 하다.

**완화책이 축을 되살린다 ✔.** 턴 스코핑이 출하 기본값이 된 뒤(§5, §6.7), 서로소 팔을 스코핑을 켜고 세 번째로 돌렸다 — 락 스코프당 3회, 그리고 이번에는 경로 조건을 워크스페이스의 최종 내용이 아니라 *턴* 단위로 판정했다(각 레코드의 `reply_to` 를 그 파일 경로에 조인, §6.7 의 계기). 이 구분이 중요한 이유는 지배적 실패 양상이 두 과제를 다 하는 것이라, 파일들의 합집합만 봐서는 성공과 구별되지 않기 때문이다. 열두 턴 전부가 정확히 자기 파일 네 개만 썼다: 6 런 중 6 이 의도한 서로소 조건을 구현하며, 같은 코드에서 스코핑 없이는 6 중 0 이었다. 되살아난 축은 작동점을 재현한다 — 효과 비중은 중앙값·최댓값 모두 10⁻⁵, 락 대기 0.1 ms, 유효 병렬도는 두 스코프에서 1.88 대 1.84 이고 병렬도 항등식은 0.0003 까지 성립한다 — 그래서 스코프 비교가 이제 셀당 유효 런 3 개 위에 서고, 위에 공개한 2 런짜리 셀을 대체한다. 턴 구간은 원래의 198~413 s 에 대해 354~703 s 로, 엔드포인트는 더 붐볐지만 작동점은 움직이지 않았다. §6.7 이 오염률로 보고하는 것이 여기서는 잴 수 없는 축과 잴 수 있는 축의 차이다.

이 "차이 없음"은 얼버무림이 아니라 측정이며, 정확하게 만들 수 있다. 락 대기가 0 이면 makespan 은 긴 쪽 구간과 같으므로 지표는 항등적으로 1 + 짧은턴/긴턴 으로 환원된다. 12회 **전부**에서 실측값이 그 항등식과 **0.0004** 이내로 일치한다. 실제 시스템이 잃는 병렬도는 남김없이 턴 길이 비대칭이고(실모델에서는 이 편차가 크다. 구간이 198 초에서 413 초까지 퍼졌다), 락의 기여는 그 분해능 아래에 있다.

**두 번째 작동점: 셸이 지배하는 작업 ✔.** 파일 쓰기 측정에는 명백한 반론이 따라붙고, 그것은 제기되어 마땅한 반론이다. 코딩 에이전트의 지배적 효과는 파일 쓰기가 아니라 셸·빌드·테스트 실행이며, §4.4 는 셸의 파일 발자국을 정적으로 알 수 없다는 이유로 셸을 **배타**로 둔다. 셸이 턴 시간의 큰 몫을 차지하면 작동점은 무릎 쪽으로 움직여야 한다. 같은 계측, 같은 2인 실모델 구성에서 과제만 바꿔 각 턴이 파일을 쓰는 대신 셸 명령 세 개를 돌리게 하고 측정했다. 명령당 1 초에서 효과 비중은 0.025 이고 락 대기는 0 ms, 5 초에서는 0.094 이고 락 대기가 4.1 s 로 나타난다.

두 수치가 모두 의미 있다. 비중은 파일 쓰기 워크로드의 10⁻⁵ 보다 서너 자릿수 위이므로 **반론은 실재하고 셸이야말로 문제되는 효과가 맞다.** 그리고 락 대기가 이제 잡음에 묻히지 않고 측정되는데, 이는 배타성이 §4.4 가 말한 그대로 작동한다는 뜻이다. 그럼에도 0.094 는 여전히 50% 무릎보다 다섯 배 아래이고, 법칙이 예측하는 상한은 2.00, 실측 유효 병렬도는 1.84 와 1.87 이며 그 미달분은 종전과 같이 턴 길이 비대칭이다. 셸이 무거운 코딩 워크로드는 곡선 위를 이동하되, 락 입도가 무언가를 결정하는 구간까지는 가지 않는다. 이 팔도 수리된 seam 위에서 반복했고 재현된다: 효과 비중 0.021 과 0.085(원래 0.025 와 0.094), 락 대기 0 ms 와 4.9 s(원래 0 ms 와 4.1 s), 유효 병렬도 1.94 와 1.82. 작동점이 서로 다른 엔드포인트 부하의 두 실행에서 안정적이며, 그래서 이것을 세션이 아니라 워크로드의 속성으로 다룰 수 있다.

**이 쌍이 세우는 것.** 법칙은 뭉툭한 락의 비용이 효과 비중 50% 아래에서 0 이라고 말하고, 실 시스템은 파일 쓰기에서 그보다 네 자릿수 아래인 10⁻⁵ 에, 셸이 지배하는 턴에서도 한 자릿수 아래인 0.094 에 앉아 있다. 따라서 결론은 "락 스코프는 중요하지 않다"가 아니라 더 날카로운 **"이 워크로드는 무릎보다 한참 아래에 있고, 무릎은 여기다"** 가 된다. 이것은 실모델 실행이 통제 실험을 **대체할 수 없는** 이유도 설명한다: 턴 길이 편차 ±100 초가 0.1 ms 의 락 대기를 압도하므로, 실측은 락의 기여에 상한을 씌울 수는 있어도 그 안의 차이를 분해할 수는 없다. 한 실험은 위치를 찍고, 다른 실험은 분해한다.

부수적 관찰 하나를 기록해 둘 가치가 있는데, §6.7 을 확장하기 때문이다. 실모델 12회 중 1회에서 한 턴이 **다른 사용자의 과제**를 수행해 자기 파일 대신 그 사용자의 파일을 썼다. 이는 §6.7 의 공유 트랜스크립트 의미 혼동이 답변 텍스트가 아니라 **부수효과**에서 나타난 것이고, 의도적으로 적대적인 모델이 아니라 실모델에서 나타난 것이다.

이 비율은 일반 추정치가 아니다: 여기서 두 동시 지시는 태그와 파일명만 다르므로 혼동에 가장 유리한 조건에 가깝다. 이것이 세우는 것은 **존재**이며, 위의 경로 축 비교가 의도한 경로 조건을 실제로 구현한 실행만 세는 이유이기도 하다(효과 비중과 락 대기는 전 실행을 쓴다. 어느 쪽이든 쓰기가 일어났고 같은 락을 통과했다).

### 6.5 RQ5: 재접속하는 클라이언트는 같은 세션에 도달하는가 ✔

사람들은 노트북을 닫고, 네트워크를 바꾸며, 세션에 늦게 합류한다. 따라서 유용한 공유 세션은 연결 끊김을 견뎌야 한다. §4.7의 `seq`와 `Last-Event-ID` 설계를 검증하기 위해 같은 라이브 세션의 두 구독을 비교한다.

세 사용자가 병렬 계약으로 90턴을 흘렸다. 한 구독(*control*)은 내내 붙어 있었다. 두 번째(*cutter*)는 11회 끊었다 다시 붙으며, 매번 마지막으로 받은 id 를 브라우저의 `EventSource` 가 하듯 그대로 제시했다. 절단은 타이머가 아니라 이벤트 수로 촉발돼 모든 절단이 트래픽 뒤가 아니라 그 안에 떨어지게 했다.

두 구독은 **동일한** 스트림을 받았다: 각각 180개의 재생 가능 이벤트가, 시퀀스 번호·이벤트명·**페이로드 원문**까지 같았고, 누락 0, 중복 0, 순서 역전 0, 페이로드 불일치 0 이었다. 제출한 90개 질문 마커가 모두 양쪽에 도달했다. 대조가 페이로드 원문을 포함하므로 턴 귀속은 결과 옆이 아니라 결과 안에 있다: 재생된 이벤트가 뭉개지거나 빠진 `reply_to` 를 실었다면 불일치가 됐을 것이다. 11회의 정상 재접속 중 어느 때도 리셋이 발신되지 않았고, 그것이 증분 재생의 요점이다: 클라이언트의 트랜스크립트는 다시 지어진 것이 아니라 이어졌다.

이어서 서버가 살릴 수 없는 커서로 폴백 경로를 강제했다. 다른 스트림 epoch 의 커서(재개 후 재기동 경우)와 발급한 적 없는 앞선 커서 둘 다 같은 답을 냈다: 연결 정체성 바로 뒤, 재생되는 모든 이벤트보다 앞인 두 번째 프레임에 리셋 신호가 오고, 180개 전체의 스냅샷이 뒤따랐다. 세 번째 살릴 수 없는 경우, 즉 보존 창보다 오래된 커서는 같은 분기로 합류하지만 여기서 유발하기는 비현실적이다. 출하 버퍼는 가장 최근 **5,000개**의 영속 이벤트를 보존하는데, 이 실험의 턴은 재생 가능 이벤트를 턴당 2개씩 냈으므로 창의 끝에 닿으려면 한 클라이언트가 끊긴 채로 약 2,500턴의 트래픽이 흘러야 하고, 이벤트를 더 많이 내는 도구 위주 턴이라면 1,300턴 근처다. 그래서 그 분기는 이 하네스가 아니라 유닛 테스트가 덮는다. 라이브 전달은 결코 창으로 잘리지 않는다 — 접속한 클라이언트는 일어나는 대로 전부 받고, 이 상한은 세션 중간 재접속 재생에만 적용되며, 완전한 트랜스크립트는 어느 쪽이든 디스크에 남는다.

### 6.6 RQ6: 턴이 도는 동안 공유 컨텍스트 압축하기 ✔

활성 사용자가 N명이면 공유 컨텍스트는 대략 N배 빠르게 커지므로 압축이 필요하다. 어려운 점은 요약을 만드는 동안에도 턴이 계속 내용을 추가하게 하는 것이다(§2.4). Coagora는 낙관적 절차를 사용한다. 락 안에서 이력을 나누고 세대 번호를 기록한 뒤, 느린 요약 호출 동안 락을 놓는다. 마지막에 세대를 다시 확인하고 그동안 추가된 턴과 함께 요약을 원자적으로 커밋한다.

강제 압박 하에서 측정했다(3 사용자 × 30 라운드, 90턴, 의도적으로 작게 광고한 컨텍스트 창과 800 ms 요약기). 네 번의 압축 모두 3개의 턴이 비행 중인 상태에서 시작했고, 턴들은 무락 요약 구간 *안에서* 계속 흘렀다. 그 구간들에 걸쳐 42개의 턴 이벤트가, 그중 11개의 첫 토큰이 떨어졌는데, 이는 배리어 설계라면 구성상 0 으로 만들었을 가용성이다. 90개 질의 중 0개가 유실됐고, 90개 최종 레코드 전부가 `reply_to` 를 통해 실재하는 질문으로 해소되어 구조적 귀속이 모든 패스를 견뎠다. 네 번의 압축 모두 stale 재시도 0 으로 커밋됐다.

**실 요약기 앞에서 가용성은 유지되고 비용은 훨씬 크다 ✔.** 위의 팔은 요약 콜을 800 ms 로 스크립트하는데, 800 ms 야말로 이 설계가 그 주위에 지어진 바로 그 양이다. 그래서 실모델과 실 요약기로 반복했고, 같은 압력을 만들기 위해 광고 컨텍스트 창을 12,288 토큰으로 고정했다(사용자 3명, 8 라운드, 24 턴). 실제 요약 구간은 **56 s ~ 123 s** 이지 0.8 s 가 아니다. 두 자릿수 차이이며, 이것이 요약을 락 밖에서 도는 것을 세부가 아니라 설계 결정으로 만든다. 가용성은 그 길이를 견딘다. 다섯 구간을 가로질러 턴 이벤트 45 건이 그 **안에서** 발생했고 그중 11 건이 첫 토큰이므로, 사용자들은 몇 분짜리 압축 내내 답을 계속 받았다. 질의는 24 중 24 가 기록됐고 유실은 없다.

다만 값은 목 팔이 시사한 것과 다르다. 압축 다섯 번 중 **2 번이 커밋되고 3 번이 stale** 이었다(목은 4 중 4 커밋, 재시도 0). 이것은 낙관적 설계가 자기 낙관의 값을 치르는 것이다:

2 분짜리 무락 구간은 동시 턴에게 세대를 무효화할 2 분을 주지만, 0.8 초 구간은 거의 주지 않는다. 그럴 때 잃는 것은 없다 — stale 패스는 틀리게 커밋되는 대신 버려지고 재시도된다 — 그러나 낭비된 작업은 실재하는 비용이고, 그것을 과소평가한 쪽은 목이다. 그래서 가용성 속성은 두 팔에서, 재시도율은 라이브 팔에서 보고한다.

그 결과에 이르기 전에 계측이 실제 설계 결함도 잡았다. 첫 구현에서는 동시 턴의 초과 폴백(창을 넘으면 가장 오래된 메시지를 축출)이 모든 요약 구간마다 세대를 올려 낙관적 커밋을 굶겼다: 6번 중 1번만 안착했고 stale 재시도가 5회였으므로, 요약값은 지불되고 버려지는 한편 원시 이력은 요약되지 않은 채 축출됐다(`out/n1-compaction-adversarial.json` ✔). 수리는 압축이 비행 중인 동안 동시 호출자가 예방 목표와 진짜 한계 사이의 여유를 감내하게 하는 것이다.

이 실패를 보고하는 이유는 그것이 단일 사용자 시스템에서는 발견될 수 없는 종류의 상호작용(압축 × 동시성)이기 때문이고, §5 의 계측 평면이 그것을 찾아냈기 때문이다.

### 6.7 RQ7: 휴리스틱이 아니라 구조적인 귀속 ✔

동시 실행에서는 가장 가까운 앞 질문이 답의 실제 원인이라고 볼 수 없다. Coagora는 귀속을 구조적으로 만든다. 한 턴은 한 스레드에서 실행되고, 그 스레드는 원래 질문 id를 저장한다. 스레드가 만든 모든 레코드는 같은 `reply_to` 값을 가지며(§5), 모델의 답변 내용에 의존하지 않는다.

대규모에서 검증했다(4 사용자 × 25 라운드, 100개 동시 턴). 발급 사슬(큐 진입 → 디스패치된 턴 → 스레드 → 발급된 질문 id)이 100/100 정확했고, 최종 레코드들은 질문들과 완전한 전단사를 이뤘다: 중복 0, 미대응 0, 누락 0.

구조적 귀속이 의미적 집중까지 보장하지는 않는다. 모든 턴이 하나의 트랜스크립트를 보므로 모델은 다른 참여자의 최신 질문에 답할 수 있다. 이를 드러내기 위해 항상 가장 최신 질문에 답하는 결정적 적대 모델을 사용했다. 답변 내용이 다른 사용자를 향해도 `reply_to`는 여전히 정확했다. 즉 시스템은 *어느 요청이 이 턴을 만들었는지* 정확히 기록할 수 있지만, 모델이 *어느 요청을 따를지*까지 통제하지는 못한다. 이 현상은 실모델에서도 나타났고 드물지 않았다.

§6.6 의 라이브 압축 두 실행에서는 동시 사용자들이 각자 되뇌라고 지시받은 마커 하나로만 구별되는 거의 동일한 산문 과제를 받는데, 최종 답변 **42 건 중 21 건**이 *다른* 턴의 마커를 달았다. 이전 초안들은 실모델이 자기 질문자에게 답한다는 근거로 3 회 중 3 회 스팟체크를 인용했다. 그 표본은 무엇을 말하기에도 너무 작았고, 더 큰 표본은 반대를 말한다.

**의미적 비율은 안정된 수가 아니며, 우리는 더 이상 하나의 값을 보고하지 않는다 ✔.** 이 구성의 이전 단발 실행이 38% 를 기록했고 우리는 그 값을 최악 케이스로 인용해 왔다. 동일 구성을 반복하면 이야기가 달라진다: 새로 5 회 반복한 비율은 13%, 17%, 19%, 19%, 21% 였고, 같은 호스트의 추가 단발 실행 둘은 4% 와 10% 였다. 이 흩어짐은 측정의 잡음이 아니라 **양 자체**다. 혼선은 턴이 실제로 시간상 겹치는 곳에서만 생길 수 있고 얼마나 겹치는지는 계약이 아니라 호스트 스케줄링의 성질이므로, 이 분포에서 뽑은 한 번의 값은 상한이 아니다. 우리는 그것이 상한이라던 주장을 철회한다.

**안정적인 것은 구조 쪽 전부다**: 아래 절제의 15 회 실행 전부와 위 실행에서 발급 사슬과 `reply_to` 전단사가 매번 완전했고 중복 0, 미매칭 0 이었다. 귀속은 흔들리지 않는다. 흔들리는 것은 모델이 무엇에 대해 말하기로 하는가뿐이다.

**완화책, 그리고 목으로 그것을 시험할 때의 정직한 한계 ✔.** 이전 초안의 심사자들은 의미적 혼선을 기록만 할 게 아니라 줄일 수 있는지 물었고, 그것은 정당한 요구다. 그래서 하나 구현했다: `--turn-scoping` 은 각 턴의 시스템 프롬프트에 그 턴이 수행 중인 요청을 지목하는 섹션을 넣고, 공유 트랜스크립트에 있는 다른 참여자의 동시 메시지는 지시가 아니라 맥락임을 명시한다. 게이트는 두 겹 — 플래그와 병렬 계약 — 인데, 직렬화 하에서 실행 중 주입된 질문은 오히려 그 턴이 받아야 할 것이기 때문이다(§6.1). 아래의 측정이 이것을 병렬 계약의 출하 기본값으로 만들었고, 이 절의 모든 `off` 팔은 명시적으로 끈 것이다.

완화의 *효과*를 재는 일이야말로 스크립트된 모델이 할 수 없는 것이다. 시험 대상이 지시 순응이고, 목의 순응은 우리가 직접 써 넣는 대상이기 때문이다. 그래서 대신 양 끝을 쟀다. 사용자 4명 × 25 라운드, 팔당 5 회 반복:

| 팔 | 의미적 불일치 (5회의 최소 / 중앙 / 최대) | `reply_to` 전단사 |
|---|---|---|
| `off`: 스코핑 없음 (위 구성 그대로) | 13% / 19% / 21% | 5/5 완전 |
| `ignore`: 스코핑 on, 시스템 프롬프트를 읽지 않는 모델 | 1% / 21% / 26% | 5/5 완전 |
| `honor`: 스코핑 on, 스코프를 따르는 모델 | 0% / 0% / 0% | 5/5 완전 |

`ignore` 팔은 음성 대조군이고 통과한다: 지시를 볼 수 없는 모델은 지시를 받은 적 없는 모델과 통계적으로 구분되지 않으며, 그래서 두 라이브 팔의 차이가 프롬프트가 길어진 부수 효과가 아니라 **순응**에서 온다는 것을 알 수 있다. `honor` 팔은 매 실행 0 이고, 그 값어치는 보이는 것보다 좁다. 실모델이 순응한다는 것을 보이지 않는다. 순응*한다면* 메커니즘이 충분하다는 것, 그리고 덜 자명하게는, 스코프가 500 개의 동시 턴(4명 × 25 라운드 = 100 턴의 5 회 반복) 각각에 **그 턴 자신의** 요청을 싣고 도달했다는 것을 보인다.

두 번째 속성은 공짜가 아니다 — 세션 전역 귀속 필드가 동시성에서 무너져 thread-local 이 되어야 했던 바로 그 표면(§5)이고, 이것은 같은 부류의 버그가 새 섹션에서 재발하지 않았다는 종단 확인이다. 실모델이 두 팔 사이 어디에 앉는지는 목이 닿을 수 없는 질문이므로, 직접 물었다.

**라이브 팔: 실모델은 순응하고, 혼선은 사라진다 ✔.** 목을 어디에도 쓰지 않고 온프레미스 모델을 상대로 `off`/`on` 비교를 팔당 20 회 반복했다. 서버 부하의 표류가 한쪽 팔에 몰리지 않도록 팔을 번갈아 돌렸다. 두 사용자가 병렬 계약에서 동시에 제출하며, 지시는 태그와 대상 파일 이름만 다르다 — 완화책을 혼선이 가장 심한 조건에서 시험하려고 고른 것이다(그 조건이 우리가 여긴 만큼 심하지 않았음은 아래 현실 워크로드 팔이 보인다). 판정은 답변을 읽는 대신 **부수효과**로 한다:

히스토리 레코드의 `reply_to`(그 턴이 어느 요청을 서비스 중이었는가)와 기록된 파일 경로를 조인하므로, "이 턴이 저 사용자의 파일을 썼다"는 워크스페이스 최종 상태로부터의 추론이 아니라 귀속에 관한 사실이다. 이 구분이 중요하고, §6.4 의 분류기를 재사용하지 않은 이유도 그것이다 — 최종 파일 집합에서 추론하면 *남의 일을 했다* 와 *제 일에 실패했다* 를 가를 수 없다.

| 팔 | 남의 파일을 쓴 턴 | 자기 과제를 완수한 턴 | 두 과제가 모두 옳았던 실행 |
|---|---|---|---|
| `off` | 40 중 25 | 40 중 36 | 20 중 16 |
| `on` | **40 중 0** | **40 중 40** | **20 중 20** |

제거는 우연의 사정권에 있지 않다(40 중 25 대 40 중 0 에 대한 양측 Fisher 정확검정: p = 2.2 × 10⁻¹⁰). 이 비교는 §5 가 서술한 스텝 seam 수리를 사이에 두고 두 번 돌렸고, 수리된 코드 위의 나중 실행을 보고한다. 같은 크기의 앞선 실행은 40 중 26 대 40 중 0 이었으므로 헤드라인은 팔당 40 턴짜리 독립 집합 둘에서 재현되며 합산은 80 중 51 대 80 중 0 이다. 두 실행이 갈리는 곳은 보조 계수 둘이고 그 차이가 시사적이다:

앞선 실행은 그것들을 분리했고(자기 과제 완수 40 중 34 대 40, p = 0.026; 두 과제 모두 옳음 20 중 14 대 20, p = 0.020) 나중 실행은 그러지 않는다(40 중 36 대 40, p = 0.12; 20 중 16 대 20, p = 0.11). 그래서 가드에 대해서는 두 실행이 함께 뒷받침하는 것만 주장한다 — 분리가 아니라 방향이다: 스코핑이 자기 과제 완수를 줄인 적은 없고, 두 실행 모두에서 올렸다.

이것이 운 좋은 숫자 이상인 이유가 셋이다. 첫째, 두 팔 모두 실제로 동시적이다. 턴은 배리어로 함께 풀려나고, 여기 보고하는 실행에서 짧은 턴은 스코핑을 끈 모든 런에서 긴 턴의 최소 53% 를, 켠 모든 런에서 최소 61% 를 차지하며 중앙값은 각각 89% 와 78% 다. 따라서 `on` 팔의 0 은 턴이 겹치지 않아 생긴 인공물이 아니다. (앞선 실행의 하한은 65% 와 67%, 중앙값은 80% 와 74% 다. 표가 보고하는 실행 쪽을 인용한다.) 둘째, 가드 방향이 옳게 움직였다.

프롬프트 스코핑은 모델을 위축시켜 확신 없는 일을 거부하게 만들 수도 있었지만, 자기 과제 완수는 여기서 40 중 36 에서 40 중 40 으로, 앞선 실행에서는 40 중 34 에서 40 중 40 으로 올랐고, 턴 길이 중앙값은 여기서 92.5 s 에서 80.9 s 로, 앞선 실행에서는 79.0 s 에서 62.8 s 로 줄었다. 모델은 일을 덜 한 것이 아니라 **틀린 일을 덜 한** 것이다.

셋째, 발견된 실패 양상은 §6.4 의 일화가 시사한 것과 다르다. `off` 의 지배적 패턴은 턴이 자기 과제를 버리고 남의 것을 하는 것이 아니라 **둘 다** 하는 것이다 — 자기 파일 두 개를 쓰고 이웃의 것까지 쓴다. 40 중 36 턴이 자기 일을 완수했는데도 40 중 25 가 남의 영역을 침범한 이유가 그것이다. 공유 워크스페이스 위의 중복 노동은 과제가 뒤바뀌는 것보다 조용한 실패이고, 내용은 last-write-wins 가 정한다.

**혼선 최악 조건이 최악이 아니었고, 그것이 발견이다 ✔.** 우리는 완화책이 가장 심한 혼선을 상대로 시험되도록 두 지시를 태그와 파일 이름만 다르게 설계했고, 이전 초안들에서 그렇게 서술했다. 그 서술은 가정이었으므로 측정했다: 같은 코드·같은 호스트에서 같은 크기의 off 팔을 하나 더 돌리되, 두 사용자의 요청이 실제로 다른 일이 되게 했다 — 하나는 파서의 토큰·규칙 파일을 채우고 다른 하나는 도구의 README 도입부와 사용법을 쓴다. 주제·파일명·줄 내용·완료 태그가 모두 다르고, 스팬과 표본이 비교 가능하도록 작업의 **모양**(파일 2 개 × 8 줄)만 공유한다.

현실 쌍이 더 안전하지 *않다.* 남의 파일을 쓴 턴이 **40 중 31** 로, 혼선 쌍의 40 중 25 보다 많고, 20 런 전부가 최소 한 번의 침범을 담았다. 두 워크로드는 통계적으로 구별되지 않으며(p = 0.22) 점추정은 우리가 세운 가정과 반대 방향이다. 자기 과제 완수는 40 중 36 으로 동일했고 현실 쌍의 턴은 오히려 **짧았다**(중앙값 71.5 s 대 92.5 s). 따라서 높은 비율이 헤맬 시간을 더 준 탓도 아니다.

위의 메커니즘이 그 가정이 틀린 이유를 설명한다: 지배적 오류가 **둘 다** 하는 것이고, 서로 충돌하지 않는 명확히 다른 두 요청은 서로의 중복처럼 보이는 두 요청보다 오히려 하나의 할 일 목록으로 합치기 쉽다.

이것은 낮은 기저율이었을 경우보다 배치에 더 중요하다. 교차 사용자 오염은 요청을 구별되게 쓰면 조심스러운 팀이 피할 수 있는, 억지로 만든 지시의 산물이 아니다. 트랜스크립트를 공유한다는 것이 통상적이고 명확히 분리된 작업에 하는 일이다.

완화는 거기서도 유지된다 ✔. 현실 쌍을 `--turn-scoping` 과 함께 같은 크기로 돌리면 남의 파일을 쓴 턴이 그것 없이 40 중 31 이던 것에서 **40 중 0** 이 된다(p = 3.8 × 10⁻¹⁴). 스코핑 없는 20 런이 전부 오염됐던 자리에서 20 런이 전부 청결하다.

가드도 같은 방향으로, 이전보다 크게 움직인다: 자기 과제 완수 40 중 40 대 36, 두 과제 모두 옳은 실행 20 중 20 대 16, 턴 길이 중앙값은 71.5 s 에서 55.7 s 로 **내려갔다**. 겹침도 여기서 검증되며 오히려 더 강하다: 짧은 턴이 스코핑을 끈 모든 런에서 긴 턴의 최소 76% 를, 켠 모든 런에서 최소 74% 를 차지한다(중앙값 98% 와 77%). 이 모델에서 두 워크로드를 합치면 스코핑 팔은 80 중 0, 미적용 팔은 80 중 56 이다. 두 팔이 함께가 곧 발견이다: 트랜스크립트 공유는 통상 작업을 높은 비율로 오염시키고, 각 턴의 요청을 그 턴 자신의 프롬프트에 지목하는 것이 이 모델이 만들어낸 모든 사례를 없앴다 — 그 전부라는 말은 다음 문단이 유계한다.

경계를 분명히 적는다 — 그리고 이번 개정이 그 일부를 실측으로 바꿨다. 이전 초안은 "하나의 엔드포인트 위 모델 하나"가 주장을 유계한다고 헤지만 할 수 있었는데, 엔드포인트가 두 번째 모델을 서빙하고 있어 현실 쌍을 그대로 그 모델에 다시 돌렸다(Qwen3.6-35B-A3B, 희소 mixture-of-experts, 팔당 20회 ✔). 헤지가 측정이 됐다. **스위치의 양쪽이 모두 모델을 따라 움직인다.** 스코핑 없는 오염이 거기서는 더 낮고(40 턴 중 14 대 밀집 모델의 31, p = 2.6 × 10⁻⁴), 스코핑은 0 이 아니라 40 중 9 로 줄일 뿐이다(밀집 모델의 40 중 0 에 대해 p = 2.4 × 10⁻³). 두 번째 모델 안에서 off/on 대비는 이 크기에서 분리되지 않지만(p = 0.32) 가드의 방향은 그대로다(자기 과제 완수 40 중 33 → 38, 두 과제 모두 옳은 실행 20 중 13 → 18 — 가드는 이번에도 비용이 없었다). 이 팔은 트랜스크립트를 보존한 첫 팔이라 텍스트 수준 오도도 부작용과 나란히 셀 수 있었는데, 둘은 동행한다: 답변 텍스트에 *상대* 과제의 완료 태그를 실은 턴이 스코핑 없이 40 중 12, 켜고 40 중 10 이다. 겹침은 중앙값에서 성립하고(0.86 과 0.76) 바닥은 밀집 팔보다 낮은데(0.18), 이 모델의 턴이 여섯 배쯤 짧기 때문이다.

데이터가 지지하는 강도로 결론 둘. 오염 *현상*은 모델 일반적이다 — 밀집, 희소, 적대적 목까지 돌려 본 모든 모델에서 나타났다. *제거*는 그렇지 않다 — 그것은 모델-완화 쌍의 속성이며, 배포는 어떤 모델을 서빙하든 프롬프트 한 절이 간극을 닫아 준다고 가정할 수 없다. 기저율과 가드의 충분성은 둘 다 배포 시점에 측정 가능한 속성이고, 그것을 재는 하니스가 아티팩트에 있다. 의미적 간극이 트랜스크립트 공유에 내재하지도, 헷갈리는 지시에 한정되지도 않는다는 점은 그대로다. 달라진 것은 "모델에게 어느 요청이 자기 것인지 말해 주기"가 이제 고침(fix)이 아니라 **측정된 경계를 가진 완화책**이라는 점이다.

**스냅샷 staleness, 측정 ✔.** §4.3 은 유계 staleness 를 스냅샷 규칙의 알려진 비용으로 명명했고, 이번 개정 전까지 논문은 수치 없이 공개만 했다. §5 에서 추가한 컨텍스트 시퀀스 계측이 그것을 닫는다: 모든 스냅샷과 모든 컨텍스트 변형이 단조 시퀀스 값을 지니므로, 스텝의 staleness — 그 스텝의 스냅샷이 찍힌 뒤 자기 커밋 전에 공유 컨텍스트에 들어간 변형(다른 턴의 질의 도착, 그 답의 커밋) 수 — 는 조인 없는 산술 차가 된다. 위의 귀속 워크로드(사용자 4명, 25 라운드)에서 병렬 계약 5 회 반복은 **500 스텝 중 498** 을 최소 변형 하나만큼 stale 하게 만들었고(깊이 중앙값 3~4, 최대 5), 겹침은 검증됐다(전 실행에서 최대 동시성 4). 직렬 대조군은 **200 중 0** — 구성이 요구하는 그대로다.

staleness 깊이는 한 턴이 생각하는 동안 몇 건이 커밋되는가로 정해지고, 스크립트된 턴은 1 초쯤 생각하는 데 반해 실 턴은 1 분을 생각하므로, 이것은 목이 왜곡할 만한 양이다. 그래서 실모델을 상대로 반복했다(사용자 3명, 4 라운드, 3 회 반복, 직렬 대조군 포함) ✔. 구조적 사실 둘은 유지된다: 병렬 계약에서 **92 스텝 중 75** 가 stale 이었고 전 실행에서 최대 동시성 3 이었으며, 직렬 대조군은 다시 **13 중 0** 이다.

그러나 분포는 목의 것이 아니다. 라이브의 비중은 더 낮고(사실상 100% 대 82%) 라이브의 꼬리는 **두 배 깊다**(최대 변형 10 대 5, 중앙값 2 대 3~4). 일부는 구성 탓이다 — 목 팔이 사용자도 라운드도 많아 컨텍스트가 훨씬 붐빈다. 그러나 꼬리의 방향은 목이 보일 수 없는 효과다: 실 턴은 자기 스냅샷을 1 분간 쥐고 있고, 1 분은 그 뒤로 커밋 열 건이 쌓이기에 충분한 시간이다. 라이브 수치를 배치 관련 수치로 보고하고 목 팔은 조밀 트래픽 대조군으로 남긴다.

지녀야 할 숫자는 비중이 아니다. 비중은 이 절의 혼선률이 겹침의 속성이듯 세션이 얼마나 포화됐는가의 속성이다. 지녀야 할 것은 모양이다: 진짜 동시성 아래에서 턴의 프롬프트는 으레 컨텍스트에 뒤처지고, 보통은 변형 두어 개만큼, 꼬리에서는 열 개만큼 뒤처지며, 그 stale 스냅샷 하나하나가 여전히 잘 형성된 트랜스크립트다. 신선도는 계약이 추론을 결코 막지 않기 위해 치르는 값이다. 그 값은 이제 공개가 아니라 분포이고, 한계 5 가 그것을 지닌다.

### 6.8 RQ8: 폭주 하의 공정성 ✔

한 사용자가 긴 턴 다섯 개를 연달아 제출하고, 다른 넷이 각각 짧은 질문 하나씩을 던진다(상한 = 3, 5회 반복). 사용자별 게이트를 켜면(사용자당 활성 턴 하나, 대기자는 다른 사용자를 위해 건너뜀) 짧은 질문은 중앙값 **76 ms**(p95 148 ms)에 디스패치됐고 폭주자 자신의 백로그는 자기 뒤에서 기다렸으며(중앙값 3.3 s), 사용자별 단일 활성 불변식은 위반 0 으로 지켜졌다. 게이트를 절제하면(순수 FIFO + 상한) 폭주자가 슬롯을 독점했고 같은 짧은 질문들이 중앙값 **1,807 ms**(p95 3,219 ms)를 기다렸다. 24× 나쁘며, 단일 활성 불변식 위반이 20건이었다.

**실모델 앞에서 격차는 세 자릿수 더 벌어진다 ✔.** 위의 팔은 스크립트된 턴을 쓰고, 스크립트된 긴 턴이 초 단위인 데 반해 실 턴은 분 단위다. 그러니 게이트가 지키는 양이야말로 목이 과소평가할 종류다. 목을 어디에도 쓰지 않고 반복했다: 폭주자 한 명이 다중 파일 과제 네 건을 적재하고, 다른 세 사용자가 도구가 필요 없는 질문을 하나씩 던진다(상한 3, 팔당 5 회 반복 — 앞선 2 회짜리 실행이 같은 모양을 줬고(4.4 ms 대 145.3 s) 이 더 큰 실행이 그것을 대체한다). 게이트를 켜면 짧은 질문이 중앙값 **4.8 ms** 에 디스패치됐고 폭주자 자신의 백로그는 자기 뒤에서 **83.3 s** 를 기다렸으며, 단일 활성 불변식은 다시 위반 0 으로 지켜졌다. 게이트를 절제하면 같은 짧은 질문들이 중앙값 **151.2 s**(p95 198.2 s)를 기다렸다. 목 팔의 24 배가 아니라 약 **31,000 배**인데, 짧은 사용자가 이제 줄 서는 대상이 스크립트된 150 토큰 스트림이 아니라 파일 세 개를 쓰는 실 턴이기 때문이다. 목 팔은 메커니즘이 작동하며 자격증명 없이 재현된다는 것을 세우고, 이 팔은 그것이 **얼마짜리인지**를 세운다. 답은 자기 질문을 다 읽기도 전에 도착하는 답과 2 분 반 뒤에 도착하는 답의 차이다.

이 팔에서 게이트에 유리하지 않은 수치도 하나 보고한다. 짧은 질문의 p95 는 4.8 ms 가 아니라 23.6 s 다. 상한이 3 인데 짧은 사용자 셋이 함께 도착하면 세 번째는 여전히 슬롯을 기다리기 때문이다. 게이트는 **한** 사용자가 쥘 수 있는 슬롯 수를 묶을 뿐 용량을 만들어내지 않는다. 그것이 이 보장의 정직한 모양이고, §4.5 가 상한과 게이트를 두 개의 별도 메커니즘으로 서술하는 이유다.

*모든* 사용자에 대해 계산한 순진한 Jain 지수는 절제한 팔에서 오히려 *더 높다*(0.85 대 0.24): 모두가 똑같이 나쁘게 서비스된다. 게이트는 폭주자의 백로그에 대해 의도적으로 "불공정"하며, 그 비대칭이 결함이 아니라 메커니즘 자체다. 그래서 계층별 절대 대기가 정직한 보고이고 스칼라 공정성 지수가 오도하는 쪽이다.

**입장 게이트가 다스리지 않는 층, 측정 ✔.** 위의 게이트는 디스패치 공정성의 값을 매긴다. §4.4 의 효과 락은 게이트가 볼 수 없는 두 번째 줄이고, 추월 금지 FIFO 와 셸의 배타성이 합쳐지면 한 사용자의 빌드가 다른 사용자의 파일 효과 앞의 벽이 된다. 그 벽의 값을 락을 직접 구동해 매겼다(§6.4 의 방법): 사용자 A 는 1 s 생각과 배타 셸 hold(1 s 또는 5 s)를 세 라운드 번갈고, 사용자 B 는 200 ms 마다 파일을 쓴다. baseline 팔은 같은 벽시계 시간 동안 B 만 돌린다.

B 의 효과 대기는 메커니즘이 예측하는 그대로 쌍봉이다. 중앙값은 baseline 과 구별되지 않는다(0.09~0.15 ms 대 0.13 ms) — A 의 생각 구간에 떨어진 쓰기는 아무것도 기다리지 않는다. p95 는 사실상 셸 hold 하나다(1 s hold 에 996 ms, 5 s hold 에 4,992 ms) — hold 안에 떨어진 쓰기는 그 남은 시간을 기다린다. 그리고 최대는 hold 하나를 결코 넘지 않는다(998 ms, 5,001 ms): 셸을 쥔 이웃이 하나면 그보다 깊은 적체는 없다. 다만 배타 스트림이 더 늘면 FIFO 순서로 줄을 서 합산될 것이다. 이것이 §4.4 가 선언한 거래를 최악까지 끌고 간 결과이고, 최악에서 멈춘다. 하드 공정성 보장의 값은 배타 hold 하나로 유계이고, 부하가 아니라 hold 길이에 비례하며, 이 절의 입장 게이트는 그것을 만들지도 없애지도 못한다.

### 6.9 RQ9: 세션 수명주기(중단, 재개, 유계 유지) ✔

공유 세션은 서버 재기동과 수백 턴을 가로질러 *지속*될 때만 유용하다. 이것은 장기 연구가 아니라 **내구성 스모크 테스트**다: 204 턴은 실제 팀 사용으로 치면 며칠이 아니라 몇 분이고, §7.6 은 장기 용량을 여전히 미측정으로 남겨 둔다. 세 사용자가 하나의 세션에서 네 단계에 걸쳐 204턴을 몰았고, 단계 사이에 서버 프로세스를 종료하고 `--resume` 으로 재기동했다(3회 중단/재개).

모든 검사가 통과했다. 최종 단계 후 durable 이력에 204개 질의 중 204개가 존재했고, 재기동을 가로지른 유실은 0 이었다. 질문 id 는 재개를 가로질러 전역 유일로 남았는데, 재개 경로가 id 카운터를 압축된 캐시가 아니라 *전체* 이력에서 재도출하기 때문이다. 그래서 재기동된 세션이 압축은 작업 창에서 떨어뜨렸으나 기록에는 귀속이 남아 있는 id 를 다시 발급하지 않는다. 재개된 각 단계는 새 51턴을 정상 처리했다. 압축은 공유 컨텍스트를 내내 유계로 유지했다: 실행 전체에서 10회 커밋(stale 2, 실패 0)이었고, 압축 후 캐시는 2,610 토큰을 넘은 적이 없다. 세션의 컨텍스트 발자국은 세션 나이가 아니라 압축기가 다스린다.

내구성은 모델이 아니라 저장소의 성질이므로 대규모에서는 스크립트된 팔이 옳은 계기다. 그럼에도 재개 경로를 실모델을 상대로 한 번, 라이브 실행이 허용하는 크기로 확인했다 ✔. 사용자 3명이 세 페이즈에 걸쳐 27 턴을 몰았고 중단·재개 두 사이클을 거쳤으며, 거기서도 모든 검사가 통과했다: durable 이력에 27 중 27, 유실 0, 두 재개를 관통해 id 유일, 재개된 각 페이즈가 새 턴을 정상 처리. 이 팔은 압축을 건드리지 않는데(그 라이브 거동은 §6.6 이 따로 잰다) 이만큼 짧은 세션은 창 근처에도 가지 않기 때문이다.

### 6.10 RQ10: 실모델 검증과 병렬성의 진짜 값 ✔

위의 모든 수치는 결정적 목 지연을 쓴다. 우리는 대표 결과를 스팟체크하고 비용 문제를 실 온프레미스 모델로 정산했다(Qwen3.6-27B, MLX 8비트; 순위 확인은 계약당 12회, 토큰 회계는 6회).

*순위 보존 ✔.* 사용자 A 가 긴 생성을 시작하고 B 가 2 s 뒤 한 줄을 묻는다. 계약당 12 회 반복에서 B 의 첫 토큰까지의 시간은 직렬 중앙값 **38.2 s**(B 가 A 의 턴 전체를 기다린다) 대 병렬 **10.8 s** 로 3.5 배 갈렸다. 이것을 스팟체크 이상으로 만드는 것은 산포다: 12 회 전체에서 직렬은 37.8~38.4 s, 병렬은 10.6~10.9 s 에 걸쳐, 두 분포 사이에 어느 쪽 관측도 없는 구간이 놓인다(중앙값의 부트스트랩 95% CI: 38.0~38.3 s 대 10.7~10.8 s). 병렬 절대값은 실 서버가 무엇을 더하는지에 대해 정직하다 — B 의 10.8 s 는 하네스의 0.29 s 바닥이 아니라 실제 prefill 에 공유 추론 하드웨어에서의 동시 디코드 감속이 더해진 것이다.

§5 의 스텝 seam 수리 뒤 더 붐비는 엔드포인트에서 비교 전체를 반복하니 두 절대값이 약 14% 올랐고 발견은 그대로였다: 직렬 43.6 s 대 병렬 12.3 s, 범위는 다시 겹치지 않으며(42.9~44.3 s 와 11.9~12.5 s), 분리는 원래의 3.54× 에 대해 3.55× 다. 계약이 다스리는 것은 비이고 엔드포인트의 부하가 다스리는 것은 절대값이며, 두 실행의 쌍이 그 둘을 깨끗이 가른다.

*병렬 절대값을 무엇이 묶는가, 측정 ✔.* 우리는 A 의 *존재*로부터의 독립이 제공자의 동시성에 묶인다고 적으면서 그 동시성이 얼마인지는 말하지 않았고, 그래서 그 주장은 반증 불가능했다. 세션을 통째로 우회해 엔드포인트를 직접 쟀다: 동일한 고정 길이 생성 N 개를 동시에 풀고 3 회씩 반복. 벽시계는 N = 1 에서 8.2 s, N = 2 에서 13.7 s, N = 4 에서 15.5 s, N = 8 에서 21.8 s 였다. 즉 동시 요청 8 개는 1 개의 8 배가 아니라 **2.68 배**를 치르고, 총 처리량은 초당 출력 토큰 14.7 에서 44.1 로 올랐다. 엔드포인트는 배치를 하되 공짜가 아니다 — 동시성이 오르면 개별 요청은 느려진다.

이것이 위의 모든 수치를 읽는 분모다. 세션 계약이 보장하는 것은 B 의 요청이 A 를 기다리지 않고 모델에 **도달**한다는 것이고, 남은 지연 중 얼마를 B 가 되찾는지는 이 곡선이 정하며 어떤 동시성 계약도 그것을 움직일 수 없다.

*토큰 회계, 그리고 정정 ✔.* 명백한 두려움은 N 개의 병렬 턴이 약 N 배의 추론 비용을 치른다는 것이다. 동일한 세 질문 워크로드를 계약당 6 회 반복해 측정: 병렬 계약은 3콜에 **23.2K** 입력 토큰, 직렬 계약은 **2**콜에 **15.6K** 로, 3× 가 아니라 **1.49×** 프리미엄이다.

그 다음, 그동안 추측만 하던 축을 실제로 늘렸다. 이전 초안들은 이 프리미엄이 "이력이 길어지면 커진다"고 자인했는데 **그 자인이 틀렸다.** 선행 5 턴을 이미 태운 세션에서 같은 워크로드를 다시 재니 총합은 직렬 17.4K, 병렬 25.5K 로 프리미엄 **1.47×** — 빈 세션의 1.49× 와 사실상 같다. 그동안 워크로드 첫 콜의 입력은 약 7.7K 에서 8.6K 로 늘어, 이력이 실제로 자란 것은 맞다. 프리미엄이 평평한 이유는 산술적으로 강제되기 때문이다: 콜 *c* 개가 각각 시스템 프롬프트 *S* 와 공유 이력 *H* 를 읽으면 비는 *c_병렬(S+H) / c_직렬(S+H)* = *c_병렬 / c_직렬* 이고 *H* 는 약분된다. 이력을 불리면 두 계약이 정확히 같은 비율로 비싸질 뿐 비는 그대로다. 프리미엄은 콜 수의 비, 그것이 전부이며, 논문의 §6.10 자체는 이미 그렇게 말하고 있었는데 한계 (1) 이 그것과 모순됐다.

측정이 전자의 손을 들어 준다. 수리된 seam 위 재실행은 이것을 토큰 단위로 재현한다: 빈 세션에서 직렬 2 콜 15,612 입력 토큰 대 병렬 3 콜 23,198 로 프리미엄 1.486× 로 원래와 동일하고, 선행 5 턴 뒤에는 1.452× 대 원래의 1.466× 다. 토큰 회계는 여기 라이브 측정 중 사실상 결정적인 유일한 것인데, 시간이 아니라 프롬프트 내용을 세기 때문이다.

두려움과 측정 사이의 간극은 두 메커니즘이 설명한다. 첫째, 콜당 입력은 고정 시스템 프롬프트가 지배하므로(여기서는 각 콜의 약 7.7K), 비용은 스냅샷 재독이 아니라 *콜 수*를 따른다.

N× 두려움을 낳은 공유 컨텍스트 중복은 이력이 길어지기 전까지는 부차항이다. 둘째, 직렬 계약은 조용히 *배치*한다: 실행 중 주입이 큐에 든 질문을 도는 턴 안으로 접는다(질문 3개, 콜 2회). 이는 병렬성이 포기하는 실질적 효율이며, 질문당 턴 하나가 바로 §6.1 의 지연 독립성을 사는 것이기 때문이다. 이것은 §6.1 에서 논한 것과 같은 주입 메커니즘을 지연이 아니라 비용 쪽에서 본 것이고, 두 관측은 그 절이 밝힌 이유로 정합한다: 주입은 턴 경계에서만 발동하며, 경계가 존재하는지는 워크로드의 속성이다. 여기서는 실모델 작업이 다단계라 경계가 잦았고 주입이 발동했다. §6.1 그리드에서는 A 의 작업이 단일 생성이라 끝 이전에 경계가 없었고 발동할 수 없었다. 따라서 직렬의 토큰 효율과 직렬의 선행 차단 지연은 원인이 하나이고 함께 움직인다: 직렬이 가장 잘 배치하는 워크로드가 직렬이 가장 덜 막는 워크로드이고, 직렬이 가장 심하게 막는 워크로드에서는 아무것도 아끼지 못한다.

거래의 정직한 진술: 병렬성의 토큰 프리미엄은 콜 수의 비(최대 N, 부하가 걸려 직렬 배치가 실패할수록 줄어든다)이고 지연 독립성의 대가로 치러진다. 이 배포에는 없는 제공자 측 프롬프트 캐싱이 고정항을 더 줄일 것이다.

### 6.11 RQ11: 첫 공유 세션에서 사람들은 무엇을 알아차리고 무엇을 하는가? [TODO: study 대기 중]

앞선 실험은 계약의 동작을 보여주지만, 사용 중인 사람이 무엇을 이해했는지는 알려주지 못한다. 로그는 한 사용자가 기다렸거나, 두 턴이 겹쳤거나, 한 턴이 다른 사용자의 파일을 건드렸다는 사실을 기록할 수 있다. 그러나 참가자가 그 사건을 알아차렸는지, 무엇 때문이라고 생각했는지, 이후 무엇을 하기로 했는지는 기록할 수 없다. 따라서 first-use study는 사람만 관찰할 수 있는 다섯 항목을 중심으로 설계했다. 상대의 현재 작업에 대한 인지(M1), 로그에 기록된 사건의 알아차림(M2), 사건 원인에 대한 귀인(M3), 조정 규범의 형성(M4), 실제 배치 적합성에 대한 판단(M5)이다.

**참가자와 윤리.** 목표 표본은 동료 개발자 2인으로 이루어진 4~6팀이며, 저자와 직접적인 이해관계가 있는 사람은 제외한다. 각 팀은 약 85분 동안 한 세션을 수행한다. 참가자는 화면·음성 녹화 전에 서면 동의하고 언제든 중단할 수 있다. 논문에 사용할 인용문은 참가자의 승인을 받는다. 분석 뒤 `history.jsonl` 원문을 폐기하고, 코딩 결과와 승인된 익명 인용문만 보관한다.

[TODO 모집 완료 후: 최종 팀·참가자 수, 관련 개발 경험, 모집 경로, 보상, 파일럿 처리, 제외·중도 이탈, 기관 연구윤리/IRB 판단을 기록한다. 본 세션 완료가 4팀 미만이면 이 절을 정식 연구 결과가 아니라 pilot observations로 낮춘다.]

**설계와 과제.** 주 비교는 참가자 내 설계다. 각 팀이 Coagora의 기본 직렬 계약과 병렬 계약을 각각 20분씩 사용하며, 조건 순서와 과제쌍은 팀 사이에서 상쇄한다. 두 조건 모두 턴 스코핑을 켠다. 따라서 주 비교는 계약만 다루며, 의미적 오염을 의도적으로 섞지 않는다. 두 참가자는 별도 노트북으로 같은 LAN 세션과 준비된 TaskBook 저장소에 접속한다. 각자 자기 과제 카드만 받으며, 공유 세션을 통해 상대 과제를 알아가는 과정 자체가 인지 연구의 일부다.

두 주 조건 뒤에는 모든 팀이 8분짜리 진단 조건인 Module C를 수행한다. 병렬 계약에서 턴 스코핑을 끈 조건이다. §6.7이 기계적으로 기록한 사용자 간 작업을 참가자가 알아차리는지 확인하기 위해 의도적으로 제한한 조건이다. 참가자가 인터페이스에 익숙해진 뒤 항상 마지막에 수행하며, 동의서에 제한 조건의 존재를 알리고 디브리핑에서 구체적으로 설명한다. 따라서 Module C는 알아차림을 연구하는 데만 사용하며, 오염 발생률을 추정하거나 조건 사이의 인과 차이를 주장하는 데 사용하지 않는다.

**절차와 측정.** 각 블록 시작 때 두 참가자가 첫 요청을 동시에 제출한다. 주 조건 시작 후 8분과 16분에 진행자는 10초 정지 탐침을 제시한다. 질문은 “지금 상대방이 무엇을 하고 있나요?”다. Module C 중간에도 다섯 번째 탐침을 제시한다. 두 명의 독립 채점자가 각 답을 상대의 실제 로그 활동과 비교해 2점(과제 영역과 현재 행동 모두 정확), 1점(영역은 정확하지만 행동이 모호하거나 부정확), 0점(틀림 또는 “모름”)으로 평가한다. 불일치는 합의로 해결한다.

각 주 조건 뒤에는 응답 속도, 상대 작업 인지, 잘못된 요청 수행에 대한 인식, 통제감, 해당 설정에서의 협업 의향을 묻는 7점 척도 5문항과 자유 응답 1문항을 작성한다. 마지막 사건 기반 인터뷰에서 진행자는 `turns.jsonl`과 `history.jsonl`을 이용해 실제 사건 3~5개를 고른다. 사용자 간 파일 효과, 긴 직렬 대기, 인터럽트나 재시도, 압축, 가장 크게 겹친 구간을 우선한다. 참가자는 각 사건을 기억하는지 먼저 답하고(M2: hit/miss), 무엇이 일어났다고 생각했는지 설명한다(M3: 에이전트, 시스템·도구, 상대, 자기, 기타). 이어서 무엇을 했는지 답한다. 로그에 없는 사건 보고도 false alarm으로 보존한다. 인터뷰 후반에는 상대 작업 인지, 인터럽트 권한, 명시적·암묵적 규칙(M4), 계약별 대기 행동, 실무 사용 조건(M5)을 묻는다.

**분석.** 로그는 M1과 M2의 정답지이자 인터뷰 사건 선택 도구로만 사용한다. 이 연구의 결과 변수가 아니다. 지연, 겹침, 오염률은 이미 §6.1–§6.10에서 더 큰 표본으로 측정했다. 표본이 작고 질적인 연구이므로 가설 검정을 하지 않는다. M1 점수 분포와 “모름”, 사건 유형별 M2 hit·miss·false alarm, 독립 코딩한 M3 귀인, 팀 사례 중심의 M4 규범, 사용·조건부 사용·비사용으로 나눈 M5 판단을 보고한다. 조건 설문은 기술 통계로만 제시한다. 하나의 통합된 이야기보다 반례와 가설에 어긋나는 사례를 우선한다.

### 6.12 정확성과 타당성 위협

동시성 기계는 리포지토리의 테스트 스위트가 덮는다: 3,593개 테스트 중 3,558개가 통과하고 35개는 환경 게이트로 건너뛰며, 여기 보고하는 실행에서 실패는 없었다(이전 초안들이 적은 code-index 속성 기반 플레이크는 이번엔 발동하지 않았다). 커버리지에는 턴 레지스트리와 사용자별 게이팅, 턴 스코핑 섹션과 그 두 겹 게이트, 효과 락 스코프와 호환성 행렬, 컨텍스트 스냅샷과 원자 커밋(동시 append 하의 스텝 seam 쌍 원자성 §5, 컨텍스트 시퀀스 staleness 계측 §6.7 포함), 시퀀스 번호와 증분 재생, 읽기 전용 토큰의 엔드포인트별 권한 표(등록된 모든 라우트에 대해 파라미터화되므로, 어느 쪽인지 선언하지 않은 새 엔드포인트는 기본 개방되는 대신 스위트를 깨뜨린다), 중단/재개가 포함된다.

별도의 opt-in 스위트 53개 테스트가 실제 헤드리스 브라우저로 실제 서버를 구동해 유닛 테스트가 닿을 수 없는 행동을 검사한다. 예컨대 속성으로 숨긴 요소가 저자 스타일시트가 적용된 뒤에도 실제로 숨겨지는가 같은 것이다. 이 스위트는 이번 작업 중 소스 수준 단언은 통과시킨 읽기 전용 클라이언트의 실제 결함을 잡아냈다.

§5 가 공개한 두 동시성 결함은 모두 우연히 발견됐다 — 하나는 라이브에서, 하나는 다른 측정을 계측하다가. 그래서 사례가 아니라 부류를 닫았다: §4 가 진술하는 불변식 각각에 대해 어떤 테스트가 그것을 *동시성 하의 프로덕션 seam* 으로 구동하는지, 구현 프리미티브만 두드리는 것은 아닌지 감사했다. 열둘 중 열하나는 이미 seam 에서 검증되고 있었고, 원자 블록 커밋의 테스트는 §5 수리의 회귀 그 자체다. 감사가 찾은 공백은 하나 — 재생 커서의 발급 순서 불변식(§4.7, seq 는 버퍼에 append 하는 그 락 아래에서 발급된다)으로, 종단 재생 실험(§6.5)이 라이브로는 덮지만 유닛 층의 동시성 테스트는 없었다. 이제 동시 emit 스레드들로 회귀 고정됐다. 감사는 읽기 전용 라우트 표도 미검증으로 처음에 잘못 표시했는데, 위에 서술한 파라미터화 스위트가 그것을 강제하고 있었다 — 감사 자체를 두 독자로 하는 것이 낫다는 작은 논거다.
**타당성 위협.** 목 LLM 타이밍은 제공자 측 분산을 배제하며, §6.10 의 실모델 스팟체크와 둘 다 존재하는 곳에서 결정적/실측 쌍을 함께 보고함으로써 완화한다. 측정은 하나의 호스트, 하나의 파일시스템에서 나왔다. §6.2 는 자기 수치 중 무엇이 플랫폼 속성이고 무엇이 계약 보장인지 명시하고, §6.1 은 세션 경계를 넘는 유일한 지점을 명시한다. §6.10 의 토큰 프리미엄은 콜 수의 비이고 이력에 불변임이 측정됐다(1.49× 대 1.47×, §6.10). 절대 비용은 이력과 함께 여전히 커지고, 비가 N× 에 접근하는 것은 직렬 배치가 실패할 때뿐이다. 우리 워크로드는 합성이다.

### 7.1 비대칭 그라운딩

### 7.5 신뢰 모델: 컨텍스트 공유가 노출하는 것

§2.2에서 메신저 연동에 지적한 노출 위험은 이 시스템에도 적용된다. **이 계약은 상호 신뢰하는 참여자를 가정한다.** 이미 저장소와 작업 공간을 공유하는 팀을 위한 설계이며, 서로 신뢰하지 않는 임의의 사용자를 받기 위한 설계가 아니다.

이 가정은 설계에서 나온다. 모든 참여자의 메시지가 공유 컨텍스트에 들어가므로 다른 모든 턴의 프롬프트에도 나타난다. §6.7은 이 사용자 간 채널이 실제로 작동함을 보여준다. 모델은 때때로 다른 사용자의 요청을 따랐고, §6.4에서는 같은 현상이 파일 쓰기로도 나타났다. 우리는 이를 협력자 사이의 정확성 문제로 측정했다. 보안 관점에서는 별도의 취약점 없이도 가능한 주입 채널이다. 공유 세션에 글을 쓰는 행위만으로 다른 턴에 영향을 줄 수 있다.

파일시스템 격리와 프롬프트 격리는 서로 다른 경계다. 컨테이너는 턴이 워크스페이스 밖 파일에 접근하는 것을 막을 수 있지만, 한 참여자의 글이 워크스페이스 안에서 다른 턴의 방향을 바꾸는 것은 막지 못한다. 신뢰할 수 없는 사용자를 받으려면 두 격리가 모두 필요하며, Coagora는 어느 쪽도 보장하지 않는다.

### 7.6 한계

현재 시스템과 결과의 정직한 경계.

1. *토큰 비용, 측정됨*(§6.10): 같은 세 질문에서 병렬 모드는 직렬 모드보다 입력 토큰을 1.49배 사용한다. 병렬은 3콜, 직렬은 2콜을 만들기 때문이다. 직렬 모드는 대기 중인 질문을 실행 중 턴에 주입해 배치할 수 있지만, 병렬 모드는 지연 독립성을 위해 그 효율을 포기한다. 프리미엄은 콜 수의 비이며 이력 길이에 따라 커지지 않는다. 이력은 두 계약의 모든 콜을 같은 비율로 늘리기 때문이다. N배에 가까워지는 경우는 직렬 배치가 완전히 실패할 때뿐이며, 같은 조건에서 직렬 차단도 가장 심하다(§6.1). 우리 배포가 사용하지 않은 제공자 측 프롬프트 캐싱은 절대 비용을 낮출 수 있지만 비율은 바꾸지 않는다.
2. *컨텍스트 용량, 부분 해결*: 공유 컨텍스트는 대략 N배 빠르게 커진다. 동시 턴과 함께 압축해도 레코드는 유실되지 않지만(§6.6), 실 요약은 커밋 전에 자주 오래된 결과가 된다. 실 요약 5회 중 3회가 stale이었고, 스크립트 요약 4회에서는 없었다. 실 요약은 1초가 아니라 약 2분이 걸리기 때문이다. N명의 사용자가 몇 시간 동안 하나의 컨텍스트를 지속적으로 사용할 때의 장기 한계는 측정하지 않았다.
3. *의미론적 충돌은 남는다*: 직렬화는 물리적 무결성을 보호하지만 의미를 보호하지 않는다. 두 턴이 한 파일에 대해 다른 결론을 내리면 나중 쓰기가 남는다. 같은 스냅샷을 읽고 서로 다른 파일을 고친 두 턴도 함께 불변식을 깨뜨릴 수 있다(§4.3). 두 경우 모두 쓰기는 온전하고 순서와 귀속도 정확하지만 저장소는 틀릴 수 있다.

   공유 트랜스크립트는 한 턴이 다른 사용자의 요청을 따르는 문제도 만든다. 적대적 목 모델의 답변 불일치는 반복 실행에서 4%~21%였고 이전 한 실행에서는 38%였다. 차이는 스케줄링 겹침에 따라 달라진다(§6.7). 실모델은 다른 사용자의 파일에도 썼다. 첫 관찰은 12회 중 1회였지만(§6.4), 전용 실험에서는 40턴 중 25~31턴이었다(§6.7).

   `--turn-scoping`은 각 턴의 요청을 명시해 이 문제를 줄인다. 주 실모델에서는 오염이 40턴 중 25턴에서 0턴으로 줄었고 자기 작업의 완료율도 높아졌다. 그러나 두 번째 모델에서는 40턴 중 14턴에서 9턴으로 줄었을 뿐 사라지지 않았다. 서로 다른 요청도 비슷한 요청보다 안전하지 않았고, 스코핑 없이 40턴 중 31턴이 오염됐다. 주 모델의 두 워크로드를 합치면 스코핑 없이 80턴 중 56턴, 스코핑 적용 시 80턴 중 0턴이었다. 따라서 프롬프트 스코핑은 모델에 따라 효과가 달라지는 완화책이지 의미론적 격리가 아니다.
4. *락 봉투*: 도구가 백그라운드로 분리한 프로세스의 효과는 직렬 실행기를 벗어난다.
5. *스냅샷 최신성 지연, 측정됨*(§4.3, §6.7): 실모델 92스텝 중 75스텝이 공유 컨텍스트보다 뒤처진 프롬프트를 사용했다. 중앙값은 2개 변형, 최댓값은 10개였다. 더 조밀한 목 워크로드에서는 500스텝 중 498스텝이 뒤처졌고 중앙값은 3~4개, 최댓값은 5개였다. 두 직렬 대조군은 0이었다. 최신성 지연은 턴의 지속시간 안으로 제한되지만, 실 추론은 스크립트 하네스보다 더 긴 꼬리를 만든다. 아직 이 상태를 모델이나 사용자에게 표시하지 않는다.
6. *단일 인스턴스*: 이벤트 버스·락·레지스트리가 프로세스 내에 있어 세션이 여러 머신에 걸치지 않는다.
7. *격리 깊이*: 컨테이너 수준이 아니라 디렉토리 수준 경로 감금이다. 신뢰할 수 없는 참여자를 받는 배포에는 이 시스템이 주장하지 않는 격리가 필요하다.
8. *인터럽트를 동반한 조타*는 동시 턴에서 미지원이다(순수 취소만).
9. *재생 창*: 증분 재생은 유계 버퍼 안에서 정확하다(§6.5). 창보다 오래 자리를 비운 클라이언트는 명시적 안내와 함께 정확하되 잘린 트랜스크립트를 받고, 완전한 기록은 디스크에 남는다.

## 8 결론

오늘날의 코딩 에이전트는 여전히 싱글플레이어다. 팀은 @멘션으로 일을 맡길 수 있지만 실행 중에는 개입할 수 없고, 여러 사람이 동시에 행동할 때의 규칙도 없다. 하나의 라이브 세션은 모두를 직렬화하거나 상태를 포크해야 한다고 여겨져 왔다.

Coagora는 세 번째 선택지를 보인다. 추론은 병렬로 유지하고 충돌하는 부수효과만 정렬한다. 평가에서 두 번째 사용자의 TTFT는 첫 번째 사용자의 작업 길이와 독립이 됐다(기울기 0.00 대 1.03). 락이 없을 때 강제 겹침의 8.2%에서 찢어진 쓰기가 발생했지만 락을 켜면 없었다. 100개 동시 턴의 귀속이 모두 정확했고, 재접속한 클라이언트의 180개 이벤트가 계속 연결된 클라이언트와 모두 일치했다. 사용자는 다른 사람의 작업을 멈추지 않고 자기 턴만 취소할 수 있다.

기준선도 결과의 의미를 강화한다. Coagora는 이미 직렬 공유 세션을 제공했고 지금도 직렬 모드를 기본값으로 사용한다. 병렬과 거부 모드는 같은 구현에 스위치로 추가됐다. 따라서 실험은 새 프로토타입과 재구성된 기준선을 비교하지 않고, 하나의 프로덕션 경로 안에서 계약만 비교한다.

비용도 측정 가능하다. 세 질문 워크로드에서 입력 토큰은 1.49배였다. 배타 효과가 턴의 거의 90%를 차지하면 유효 병렬도는 1.10까지 내려갔다. 효과 비중이 50%보다 낮으면 세밀한 락의 이득은 거의 없었다. 같은 계측이 이런 비용과 지연·무결성 이득을 함께 보고한다.

공유 세션에는 중요한 인간 문제가 남아 있다. 늦게 합류한 사람은 기존 참여자보다 공통 기반이 적다. 그룹은 “자기 턴을 소유한다”보다 풍부한 제어 정책이 필요하다. 동료의 가시성은 책임성을 높일 수도, 주의를 과부하시킬 수도 있다. 이 질문들이 멀티플레이어 에이전트 연구의 다음 단계를 이룬다. Coagora와 하네스, 원시 데이터는 그 연구의 기반으로 공개돼 있다.
