## 초록 (Abstract)

AI 코딩 에이전트는 파일을 쓰고, 셸을 실행하고, 풀 리퀘스트를 열지만, 배포된 모든 에이전트는 단일 사용자를 전제한다. 에이전트를 함께 쓰려는 팀은 메신저 통합(Claude Tag, OpenAI Codex, GitHub Copilot, Devin, Slack 의 Cursor)으로 몰리는데, 이들은 공통 아키텍처를 공유한다: @멘션이 에이전트를 트리거하고, 스레드 이력이 컨텍스트로 흡수되며, 작업은 분리된 클라우드 샌드박스에서 실행되고, 풀 리퀘스트 링크가 돌아온다. 이 비동기-위임 설계에는 에이전트가 도는 동안의 개입 지점이 없고, 여러 사용자가 동시에 지시할 때의 조정 프로토콜도 없다. 명백한 대안, 즉 여러 사용자가 하나의 라이브 에이전트 세션을 공유하는 방식은 실무자들이 강요된 선택으로 취급하는 문제에 부딪힌다: 추론을 직렬화하거나(내 질문이 당신의 15초짜리 빌드 뒤에서 기다린다), 사용자별로 세션을 포크하거나(협업을 매력 있게 만든 공유 컨텍스트를 잃는다).

우리는 제3의 선택지가 있음을 보인다. 우리는 (i) 다중 사용자 코딩 에이전트 상호작용의 4축 설계 공간(*상태 소재(state locus)*, *동시성 계약(concurrency contract)*, *귀속 단위(attribution unit)*, *개입 지점(intervention point)*)을 정식화하고 아홉 개 기존 시스템을 그 안에 배치하며; (ii) 이전까지 비어 있던 좌표를 차지하는 동시성 계약 **병렬 추론, 직렬 부수효과(parallel inference, serialized side effects)** 를 제안한다: 동시에 도착한 사용자 입력은 하나의 공유 대화 컨텍스트 위에서 독립적으로 동시 비행하는 턴으로 추론되고, 모든 부수효과(파일 쓰기, 도구 실행, 컨텍스트 커밋)는 충돌 단위 계층 락을 통과한다; 그리고 (iii) 이 계약을 두 개의 독립 런타임으로 지어진 오픈소스 시스템 **Coagora** 에서 검증한다: 모든 게시글이 공유 에이전트 세션을 돌리는 격리 샌드박스와 1:1 로 결합되고 누구든 참여·조타·관전할 수 있는 협업 웹 플랫폼, 그리고 같은 공유 세션을 로컬 모델을 돌리는 팀에게 가져다주는 온프레미스 LAN 런타임이다.

웹 런타임에서의 180회 실측에서, 두 번째 사용자의 첫 토큰까지의 시간(time-to-first-token, TTFT)은 첫 번째 사용자의 작업 길이로부터 완전히 독립이었다: 작업 길이에 대한 TTFT 회귀 기울기는 0.000 이었고, 선입선출(first-in-first-out, FIFO) 직렬화는 1.000, 배포된 다중 사용자 봇 프레임워크들이 실제로 쓰는 거부-후-재시도 게이트는 1.001~1.010 이었다. 거부 게이트는 *직렬보다 나은 적이 없다*; 그 벌점은 재시도 위상에 의존해, 0부터 재시도 간격 1개분까지 직렬의 대기 위에 얹힌다. 직렬 실행기를 제거하자 동시 동일-파일 쓰기에서 무결성 위반이 발생했고(통합 측정 호스트에서 6.8%, 쓰기를 스트리밍하던 원 플랫폼에서는 최대 74%), 계약은 병합도 롤백도 낙관적 동시성 제어도 없이 모든 환경에서 이를 0%로 만든다. 이 계약은 한 아키텍처의 산물이 아니다. Coagora 의 두 런타임은 독립적으로 지어졌고(LAN 런타임은 Python 스레드 기반으로, 공유 코드가 아니라 계약의 불변식으로부터 재구축되었다), 두 번째 런타임은 대표 결과를 재현하며(기울기 직렬 1.02 / 거부 1.008 / 병렬 0.000; 락 해제 시 위반 발생, 락 적용 시 0%), 웹 런타임이 남겨둔 두 문제로 계약을 확장한다: 동시 턴이 도는 *도중의* 공유 컨텍스트 낙관적 압축, 그리고 동시성 하의 결정적(비휴리스틱) 응답 귀속이다. 우리는 세션 공유가 *만들어내는* 두 문제, 즉 비대칭 그라운딩과 다자 제어권 중재를 분석하며 마무리하고, 이것이 멀티플레이어 인간–에이전트 프로그래밍의 연구 의제를 규정한다고 주장한다.

## 1 서론

코딩 에이전트는 문턱을 넘었다. 대형 언어 모델(large language model, LLM) 위에 지어진 시스템은 더 이상 자동완성만 제안하지 않는다; 저장소를 읽고, 파일을 고치고, 셸을 실행하고, 테스트를 돌리고, 제한된 감독 아래 풀 리퀘스트를 연다 [1, 2]. 통제 연구는 에이전트가 사용자 혼자서는 끝내지 못했을 작업을 완수함을 발견했고 [2], 대규모 텔레메트리는 실제 세션의 41%에서 에이전트가 코드 전부를 작성함을 보여준다 [3]. 그러나 이 문헌 전체에서, 그리고 우리가 §2 에서 조사한 모든 배포 제품에서, 한 가지 가정이 너무 일관되어 거의 언급조차 되지 않는다: **한 인간, 한 에이전트.** 현대 코딩 에이전트의 상호작용 모델은 싱글플레이어다.

그러나 소프트웨어는 개인이 만들지 않는다. 이 불일치는 이제 업계에서 가시화되었다. GitHub Next 의 Ace 프로토타입은 "2026년 초 현재 모든 코딩 에이전트는 싱글플레이어 경험으로 설계되어 있다. 그러나 소프트웨어 구축은 싱글플레이어 게임이 아니다"라는 선언으로 시작하며, 낭비된 작업·조정 부채·어긋난 산출물을 정확히 이 간극의 탓으로 돌린다 [4]. Claude Code 사용자들은 Google Docs 식 공유 세션을 요청하는 이슈를 올렸다 [5]. 수요가 연구를 앞선다: 여러 인간이 하나의 자율 코딩 에이전트 세션을 동기적으로 공유하는 것에 대한 발표된 연구를 우리는 알지 못하며(§2.3), 그런 공유가 어떻게 조정되어야 하는지 서술한 시스템 논문도 없다.

**메신저 경로와 그 천장.** 오늘날 *팀*이 코딩 에이전트를 쓰는 유일하게 널리 배포된 방법은 메신저 통합이다. Claude Tag, OpenAI Codex, GitHub Copilot, Devin, Cursor 는 모두 Slack(일부는 Teams) 통합을 싣고 있으며, 서로 독립적인 벤더임에도 하나의 아키텍처로 수렴한다(§2.2): @멘션이 에이전트를 트리거하고; 스레드 이력이 컨텍스트로 캡처되며; 작업은 클론된 저장소를 상대로 분리된 클라우드 샌드박스에서 실행되고; 결과는 스레드에 게시되는 풀 리퀘스트(pull request, PR) 링크로 돌아온다. 이 설계에는 실질적 미덕이 있다: 팀이 대화하는 곳에서 팀을 만나고, 현대 구현들은 테스트 실패를 상대로 자율적으로 반복한다. 그러나 그 구조는 아무리 반복해도 제거되지 않는 세 한계를 부과한다. 첫째, *에이전트가 도는 동안 인간 개입 지점이 없다*: 스레드는 트리거이자 알림 표면이지 작업 공간이 아니므로, 조타는 출발 전이나 PR 후에만 일어난다. 둘째, *동시 지시에 대한 조정 프로토콜이 없다*: Anthropic 이 공유 채널에서 "누구든 조타하거나 남이 멈춘 곳을 이어받을 수 있다"고 광고할 때 [6], 두 사람이 동시에 조타하면 무슨 일이 일어나는지에 대해 문서는 침묵한다. 셋째, *컨텍스트가 스레드 경계에 갇힌다*: 코드베이스의 암묵적 상태, 다른 채널에서 내려진 결정, 에이전트 자신의 이전 작업은 기껏해야 텍스트로 재흡수된다. GitHub 문서는 추가 결과에 대해 이례적으로 솔직하다: 스레드 전체가 결과 풀 리퀘스트에 캡처·저장되며, 벤더 스스로 이를 정보 노출 우려로 표기한다 [7].

**명백한 대안과 그에 반하는 통념.** 멘션-위임이 너무 분리되어 있다면, 팀이 하나의 라이브 에이전트 세션을 그냥 공유하면, 즉 하나의 대화 컨텍스트, 하나의 작업 디렉토리에 모두가 붙으면 왜 안 되는가? 지배적인 엔지니어링 통념이 공유 컨텍스트는 두 악 사이의 선택을 강요한다고 보기 때문이다. 하나는 *추론의 직렬화*다: 스레드당 활성 실행 하나만 들이는 busy 게이트로, LangGraph 의 double-texting 전략(거부, 큐잉, 중단, 롤백; 동시 실행은 목록에 없다) [8]과, 스레드당 분산 락을 잡고 동시 요청에 HTTP 409 로 답하는 배포 프레임워크 CopilotKit OpenTag [9]가 그렇다. 이는 헤드오브라인(head-of-line, HOL) 블로킹을 재도입한다: 늦게 온 사람의 한 줄 질문이 남의 긴 빌드 뒤에서 기다린다. 다른 하나는 *세션의 포크*다: 사용자별 브랜치, 작업별 워크트리, 사후 수리를 동반한 낙관적 동시성 [10, 11, 12]으로, 단일 공유 세션을 포기하고 병합 충돌과 컨텍스트 분단으로 대가를 치른다: 당신의 에이전트는 내 에이전트가 방금 한 일을 본 적이 없다. 다중 에이전트 조정의 선행 연구는 비관적 직렬화가 추론을 막는다는 이유로 락킹을 명시적으로 반대한다 [11].

**본 논문.** 우리는 이 선택이 거짓임을 보인다. 상충하는 듯 보이는 두 가치, 즉 병렬 응답성과 공유 상태 무결성은 서로 다른 층에 살고, 이를 분리해서 다루는 계약은 둘 다 가질 수 있다. **병렬 추론, 직렬 부수효과** 아래서 모든 사용자 메시지는 다른 턴의 비행 여부와 무관하게 즉시 LLM 추론을 시작하는 독립 *턴*이 되고; 여러 응답이 모든 참여자에게 동시에 스트리밍되며, 각각은 자신을 유발한 메시지에 1:1 로 귀속된다. 한편 *모든* 부수효과(파일 쓰기, 셸 실행, 패키지 설치, 공유 대화 컨텍스트로의 커밋)는 샌드박스 범위 직렬 실행기를 통과하며, 이는 충돌 단위 계층 락으로 정밀화되어 서로 다른 파일 쓰기는 병렬로 진행하되 셸 명령과 삭제는 배타로 남는다. 읽기 전용이고 길며(수 초~수 분) 사용자가 기다리는 대상인 추론은 결코 막히지 않고; 순서 짓기 쉽고 인터리브되면 파국적인 효과는 결코 동시에 실행되지 않는다. 이 계약은 표준 가르침을 의도적으로 거스른다: 락을 걸되 추론 경로에는 절대 걸지 않으며, 충돌을 수리하는 대신 예방한다. 병합도, 롤백도, 보상도 없다.

우리는 이 계약을 두 번 지어진 하나의 시스템 **Coagora** 에서 검증한다. **Coagora Web** 은 커뮤니티 은유로 조직된 협업 코딩 플랫폼이다: 모든 게시글은 격리 샌드박스와 1:1 로 프로비저닝되고; 샌드박스는 단일 공유 에이전트 세션을 호스팅하며; 인증된 사용자는 누구나 접속해 지시하고 자기 턴을 중단할 수 있고; 미인증 방문자는 라이브 토큰 스트림을 관전할 수 있다. **Coagora LAN** 은 같은 공유 세션을 온프레미스 팀에게 가져다준다: LAN 웹 표면으로 N 명의 동시 사용자를 서비스하는 Python 런타임(단일 사용자 터미널 CLI 로도 동작)이며, 토큰 예산 컨텍스트 압축과 내구성 있는 일시정지/재개를 더한다. 둘 다 시뮬레이션이 아닌 동작하는 구현이다: 턴 다중화 스트리밍, 사용자별 공정성 게이트, 늦은 합류자를 위한 시퀀스 번호 재생(Web), 구조적 응답 귀속(LAN). 결정적 목(mock) LLM 하네스가 이 논문의 모든 수치를 API 키 없이 재현하며, §6.10 은 대표 순위와 토큰 비용 질문을 실 모델을 상대로 확인한다.

**기여.**

1. 상태 소재, 동시성 계약, 귀속 단위, 개입 지점의 4축을 가진 다중 사용자 코딩 에이전트 상호작용의 **설계 공간**: 아홉 개의 배포·프로토타입 시스템을 조직하고 빈 좌표 하나를 드러낸다 (§3).
2. **동시성 계약**, 병렬 추론과 직렬 부수효과: 단일 공유 컨텍스트 위 스냅샷 읽기/원자 커밋, 턴 범위 중단을 동반한 turnId 다중화, 충돌 단위 계층 부수효과 락, 사용자별 공정성 입장으로 정식화된다 (§4).
3. **하나의 오픈 시스템, 두 개의 독립 런타임**: Coagora Web(TypeScript, 이벤트루프 서버, 워커 프로세스)과 Coagora LAN(Python, 스레드 기반, 단일 프로세스). 후자는 공유 코드가 아니라 계약의 *불변식*으로부터 재구축되었으며, 각각 결정적·무키 재현 하네스와 커밋된 원시 데이터를 갖춘다 (§5).
4. **두 런타임에 걸친 실증 검증**: 첫 토큰까지의 시간(TTFT) 독립성(기울기 0.000 vs 직렬 1.000·거부 1.010, n=180; LAN 런타임에서 1.02/1.008/0.000 으로 재현 ✔), 무결성 절제 실험(같은 호스트에서 Web 6.8%→0%·LAN 8.2%→0%; 플랫폼을 고정하면 락 해제 시 손상 강도가 수렴하며, Web 의 원 스트리밍-쓰기 플랫폼에서는 74%였다; 방향과 영점은 불변 ✔), 워크로드가 추론 중심에서 쓰기 중심으로 이동할 때 이점이 붕괴하는 지점의 특성화(§6), 턴이 도는 동안 가용성을 유지하는 **동시 컨텍스트 압축**(§6.6), 규모에서의 **구조적 결정적 응답 귀속**(전단사 100/100; §6.7), 폭주 하의 사용자별 공정성(단기 턴 대기 24× 단축; §6.8), 수명주기 내구성(204턴 × 재개 3회, 압축으로 유계 컨텍스트; §6.9), 그리고 실측 1.49×(N× 아님) 병렬 토큰 프리미엄을 동반한 실 LLM 확인(§6.10).
5. **연구 의제**: 세션 공유는 위임의 문제를 제거하지만 자신의 문제, 즉 참여자 간 비대칭 그라운딩과 다자 제어권 중재를 만들어낸다. 이를 컴퓨터 지원 협력 작업(Computer-Supported Cooperative Work, CSCW) 이론에서 도출해 열린 문제로 제시한다 (§7).

## 2 관련 연구

### 2.1 한 개발자, 한 에이전트

AI 페어 프로그래밍 연구는 한결같이 2인 1조를 구성한다. Imai 의 초기 비교는 Copilot 이 생산 줄 수는 늘리지만 인간 페어 대비 품질을 떨어뜨림을 발견했고 [13]; 이후 연구는 개발자가 AI 제안을 인간 파트너의 제안보다 덜 검증함을 보였다 [1]. Chen 등은 어시스턴트와 자율 에이전트의 첫 통제 비교를 수행해 *에이전트 행동의 이해*를 핵심 도입 장벽으로 식별했다 [2]. SWE-chat 은 6,000개의 실사용 에이전트 세션을 분석해, 사용자는 기회의 39%에서 에이전트를 중단하거나 방향을 바꾸는 반면 에이전트는 거의 묻지 않음을 발견했다 [3]. 이 발견들은 우리의 동기를 이중으로 뒷받침한다: 중단률은 조타가 실제 에이전트 사용에 필수적임을 보여주고, 이 연구들 전부가 정확히 한 명의 인간이 브레이크를 쥔다고 가정한다. 셋일 때는 누가 브레이크를 밟는가(§7.2)?

### 2.2 메신저를 통한 팀 접근

우리는 Claude Tag [14, 6], OpenAI Codex [15, 16], GitHub Copilot [17, 7], Devin [18], Cursor [19]의 Slack/Teams 통합을 조사했다. 다섯 모두 같은 파이프라인(멘션 → 스레드 흡수 → 클라우드 샌드박스 → PR 링크)을 구현하며, 주로 신원에서 다르다: Claude Tag 는 에이전트에게 *자체* 계정을 준다(자체 GitHub App 이 PR 을 열고, 작업은 조직에 귀속된다). Copilot 은 *요청한 사용자로서* 그 사용자의 저장소 권한 아래 행동하고, Devin 은 Slack 신원을 이메일로 사용자별 계정에 매핑한다. 여기서 두 벤더의 자인이 중요하다. GitHub 은 스레드 전체가 PR 에 캡처됨을 문서화하고 그것이 허용 불가하면 다이렉트 메시지를 권한다 [7]: 컨텍스트로서의 스레드는 노출 표면이며, Slack AI 를 상대로 한 간접 프롬프트 주입(MITRE ATLAS 사례 AML.CS0035)으로 실제 세계에서 실현된 위험이다 [20]. 그리고 Claude Tag 의 채널당 한 인스턴스 "멀티플레이어" 공유는 상충하는 동시 지시에 대한 어떤 공개 프로토콜도 없이 출시되었다 [6]. 우리는 이 계열을 허수아비가 아니라 정확하게 특징짓는다: 현대 백그라운드 에이전트는 자율적으로 반복*하고*(테스트 실패에 재시도), Devin 은 웹 앱과 Slack 을 가로질러 세션을 지속*한다*; 이 계열에 불변적으로 결여된 것은 실행 중의 인간 개입 지점과 다중 사용자 조정 메커니즘이다.

### 2.3 여러 인간과 하나의 AI: 코딩 밖에서, 또는 세션 밖에서

가장 가까운 연구 이웃들은 세 방향에서 접근하지만 어느 것도 우리의 설정에 도달하지 못한다. *협업 글쓰기*에서 Lehmann 등은 다중 사용자 편집기에 에이전트를 심고, 일주일의 팀 사용에서 팀이 에이전트를 기존 협업 규범 속으로 흡수함을 발견했다. 에이전트 프로필은 개인 작업 공간처럼, 산출물은 공유 자산처럼 행동했다 [21]; 그러나 문서에는 코딩 조정을 어렵게 만드는 실행 가능한 상태, 비가역적 부수효과, 객관적 테스트 신호가 없다. *그룹 대화*에서 Koala 는 다자 채팅에서 에이전트가 언제 발언권을 잡아야 하는지 탐구했고 [22], GroupMemBench 는 에이전트가 다자 채널에 배포되는데도 에이전트 메모리 시스템은 단일 사용자로 지어짐을 관찰한다 [23]. *교육*에서 Daryanto 등은 구성상 우리와 가장 가까운 연구를 수행했다: 참가자 20명이 2자(인간 1 + AI)와 3자(인간 2 + AI) 프로그래밍을 비교했고, 3자 구성이 AI 코드에 대한 과의존을 줄임을 발견했다. 동료 가시성이 제안을 적용하기 전에 이해해야 한다는 책임감을 만들었기 때문이다 [24]. 우리는 다섯 축에서 다르다: 그들의 설정은 협력 학습이고, AI 는 파일·셸 효과를 가진 자율 에이전트가 아니라 제안 기반 어시스턴트이며, 과제는 일회성 실험실 연습이고, 종속 변수는 학습 성과이며, 지속되는 공유 세션 상태가 없다. 그럼에도 그들의 책임감 발견은 §7.3 에서 되돌아올 가설을 제공한다. 마지막으로, 성장 중인 실증 문헌이 한 에이전트의 *산출물* 주위의 여러 인간을 연구한다: 에이전트가 작성한 풀 리퀘스트에 대한 리뷰어 관여가 통합을 강하게 예측한다 [25]. 그러나 이는 산출물에 대한 비동기·사후 협업이고, 라이브 세션은 여전히 싱글플레이어다. 최근 포지션 논문은 인간–에이전트 상호작용의 공개 데이터가 전반적으로 희소하다고 주장한다 [26]; 다중 인간 세션 데이터는 아예 존재하지 않는다.

### 2.4 공유 상태 위 에이전트를 위한 동시성 제어

시스템들이 공유 가변 상태 위에서 에이전트를 동시에 돌릴 때, 지배적 패러다임은 낙관적이다. CoAgent 는 쓰기를 착지시킨 뒤 잘못 정렬된 것을 사가(saga) 식 undo 로 수리하며, 비관적 락킹은 추론을 막으므로 부적합하다고 명시적으로 가르친다 [11]; STORM 은 낙관적 동시성 제어(버전 추적과 쓰기 시점 충돌 감지)를 한 코드베이스 위 여러 에이전트에 적용한다 [27]; DeLM 은 단일 입장 게이트를 통해 병렬 추론들을 공유 컨텍스트로 들인다 [12]; 상용 병렬 에이전트 제품들은 브랜치나 워크트리별로 격리하고 나중에 병합한다 [10]. LangGraph 의 double-texting 은 한 스레드 위 동시 요청에 대해 거부·큐잉·중단·롤백을 열거한다; 동시 실행은 없다 [8]. OpenTag 는 분산 락과 409 로 스레드당 활성 실행 하나를 강제한다 [9]. 우리의 계약은 이 시스템들이 공유하는 가르침을 뒤집는다: 추론이 결코 기다리지 않는 *효과 층만* 잠그므로 비관적 직렬화가 병렬 추론과 양립하게 되고; 효과가 적용 전에 정렬되므로 낙관적 계열의 충돌 감지/롤백 기계는 회피되는 것이 아니라 불필요해진다. 다중성의 방향도 주목하라: 격리-후-병합 계열은 한 인간을 위해 *에이전트들*을 병렬화하고; 우리는 한 에이전트 위에 *인간들*을 병렬화한다.

인접한 세 연구 줄기가 이 좌표가 다른 방향에서도 비어 있음을 확인해 준다. *서빙* 쪽에서 Justitia 같은 공정성 스케줄러는 가상 시간 큐잉으로 작업 병렬 에이전트들에 GPU 시간을 배분한다 [28]: *작업 또는 에이전트* 간의 공정성이지, 한 세션을 공유하는 인간들 간의 공정성이 아니다; 우리의 사용자별 입장 게이트(§4.5)는 우리가 아는 한 턴 입도의 첫 사용자 수준 공정성 메커니즘이다. *컨텍스트* 쪽에서 병렬 압축 파이프라인은 긴 단일 에이전트 이력을 블록 단위로 동시에 흩어 요약한다 [29]: 압축 자체는 병렬이지만, *동시 사용자 턴들이 덧붙는 도중에* 대화를 압축하는 선행 연구는 없으며, 이것이 §6.6 이 측정하는 문제다. *다중 사용자* 쪽에서 최근 다중 사용자 LLM 에이전트 연구는 주체 간 권한 계층과 프라이버시를 다루고 [30], ProACT 는 협업 사용자 간 조정 붕괴를 감지한다 [31]. 둘 다 다중 사용자 *정책*을 다루지 동시 실행을 다루지 않는다; 이들은 동시성 계약의 경쟁자가 아니라 보완물이다.

### 2.5 이론적 렌즈

네 가지 CSCW 전통이 세션 공유의 의미를 틀 짓는다. *그라운딩* [32]: 협업자들은 매체가 정하는 비용으로 공통 기반을 점진적으로 축적한다; 에이전트가 루프에 들어오면 그라운딩은 3자 문제가 되고, 지속되는 세션은 축적된 인간–에이전트 공통 기반을 늦은 합류자에게는 없는 일급 자산으로 만든다(§7.1). *작업 공간 인식* [33, 34]: 누가 어디서 무엇을 하는지 아는 것; 공유 편집기의 텔레포인터와 구조적으로 동형이나, 에이전트는 어떤 인간보다 더 많은 상태를 더 빨리 바꾼다. *조율 노동(articulation work)* [35]: 협력 작업을 가능하게 만드는 조정 노동으로, 자동화는 이를 제거하기보다 이전시키는 경향이 있다(§7.4). *혼합 주도권 상호작용* [36]: Horvitz 의 원칙들은 에이전트가 언제 행동하고 언제 물어야 하는지를 다스리지만, 한 명의 인간을 전제한다; 다자 설정은 *누구에게 물을지*라는, 원 원칙들이 다루지 않는 차원을 더한다.

## 3 다중 사용자 코딩 에이전트 상호작용의 설계 공간

§2.2–2.4 의 시스템들은 이질적으로 보이지만 네 개의 이산 축을 따라 변주된다.

**D1. 상태 소재.** 에이전트의 세션 상태는 인간이 대화하는 공간에 상대적으로 어디에 사는가? *밖*(대화가 분리된 실행기를 트리거; 상태는 출발 시점의 사본) 또는 *안*(대화 표면이 라이브 세션의 뷰; 상태가 원본).

**D2. 동시성 계약.** 에이전트가 바쁠 때 두 번째 지시가 도착하면 무슨 일이 일어나는가? *거부*(busy 게이트, 409), *직렬화*(선입선출(FIFO) 단일 활성 턴), *배칭*(입력들을 하나의 프롬프트로 합쳐 하나의 융합 답변), *격리-후-병합*(사용자/작업별 포크, 나중에 조정), 또는 *병렬 + 직렬 부수효과*(본 논문).

**D3. 귀속 단위.** 산출물을 그것을 유발한 인간에게 어떤 입도로 추적할 수 있는가? *풀 리퀘스트*, *작업*, 또는 *턴*(모든 에이전트 메시지가 사용자 메시지에 1:1 연결).

**D4. 개입 지점.** 인간은 언제 작업에 영향을 줄 수 있는가? *출발 전/완료 후*만, 또는 *실행 중*. 실행 중이라면 세션 전체 범위인가 개별 턴 범위인가.

표 1 은 아홉 시스템을 배치한다. [NOTE: 제출용으로 정식 표/그림으로 렌더링.]

| 시스템 | D1 소재 | D2 계약 | D3 귀속 | D4 개입 |
|---|---|---|---|---|
| Claude Tag [6] | 밖 | 미정의 (공유 인스턴스, 프로토콜 없음) | 작업 → 조직 신원 | 전/후 |

## 4 계약: 병렬 추론, 직렬 부수효과

### 4.1 모델

**세션**은 삼중항 *S = (C, W, T)* 다: 단일 공유 대화 컨텍스트 *C*(정렬된 메시지 목록), 단일 작업 디렉토리 *W*(한 경로에 뿌리내린 격리 샌드박스), 그리고 턴 집합 *T*. 세션은 *게시글*(발견과 접근의 단위)과, 게시글의 수명주기를 따르는 샌드박스에 1:1:1 로 결합된다. 상호 독립적인 클라이언트가 몇이든 하나의 세션에 붙을 수 있고; 에이전트의 출력은 한 번 생성되어 정렬된 이벤트 스트림으로 모든 구독자에게 팬아웃된다. 세션당 에이전트 프로세스는 하나다; 접속이 사용자별 프로세스, VM, 컨텍스트 포크를 만드는 일은 없다.

계약은 두 가지 약속이다:

> **(P) 병렬 추론.** 모든 사용자 메시지는 독립 턴 *t_i* 가 된다. *t_i* 의 추론은 다른 비행 중 턴과 무관하게 즉시 시작되고; 응답들은 모든 참여자에게 동시에 스트리밍된다.
>
> **(S) 직렬 부수효과.** 어떤 턴이 만들든 모든 효과(파일 쓰기, 도구 실행, 그리고 *C* 로의 모든 커밋)는 샌드박스별 직렬 입장 메커니즘을 통해, 완료 순서로, 충돌하는 효과와는 결코 동시가 아니게 적용된다.

이 비대칭은 원칙에 기반한다. 추론은 읽기 전용이고, 길고(수 초~수 분), 사용자가 기다리는 대상이다; 이를 막는 것은 한 사용자의 작업 길이를 다른 사용자의 지연으로 변환한다. 효과는 짧고, 순서 짓기 쉬우며, 턴들이 서로를 손상시킬 수 있는 유일한 통로다. 두 번째 층의 직렬화는 비용이 적고 실패 클래스 하나의 부재를 통째로 사며; 첫 번째 층의 직렬화는 사용자들이 온 이유 전부를 지불한다.

### 4.2 턴: 독립성, 다중화, 1:1 귀속

동시 메시지들은 결코 하나의 프롬프트로 배칭되지 않는다. 배칭(D2)은 누구의 것도 아닌 융합 답변을 만들고, 메시지별 추론 파라미터를 파괴하며, 턴별 중단 창을 제거한다; 우리는 귀속을 UI 의 친절함이 아니라 정확성 속성으로 취급한다. 각 턴은 *디스패치* 시점에(큐 진입 시점이 아니라: 식별자가 항상 모델에 실제 발행된 작업에 대응하도록) 단조 증가하는 **turnId** 를 받는다. 스트리밍되는 모든 청크, 도구 호출, 도구 확인, 오류는 자신의 turnId 로 태깅되고; 런타임은 에이전트의 단일 stdout 을 턴별 싱크로 역다중화하며, 도구 결과는 복합 키(callId, turnId)로 되돌아와 동시 턴들의 동명 도구 호출이 선을 넘을 수 없다. 영속 저장소에서 각 에이전트 응답은 자신을 유발한 인간 메시지로의 `replyToId` 외래 키를 지니고; UI 는 동시 스트림들을 별도 배지가 달린 말풍선으로 렌더링한다.

**턴 범위 중단.** 중단은 turnId 를 지명해 그 턴만 취소한다: 플래그가 설정되고, 부분 출력은 마무리되어 보존되며(버려지지 않고 완료로 표시), 슬롯이 회수된다. 그동안 다른 비행 중 턴들의 추론·스트리밍·효과는 건드려지지 않는다. 대칭적으로, UI 는 각 사용자를 *자신의* 활성 턴에 대해서만 게이트한다: 남의 실행 중인 턴이 당신의 입력창을 잠그는 일은 없다. 이는 다자 제어에 대한 최소한의 유용한 답(각 사용자가 자기 작업을 지휘)이며; §7.2 는 왜 이것이 최종 답이 아닌지 논의한다.

### 4.3 공유 컨텍스트: 스냅샷 읽기, 완료 순서 원자 커밋

턴들은 하나의 대화 컨텍스트 *C* 를 공유한다; 이것이 시스템의 존재 이유이며, *C* 를 사용자별로 포크하면 격리-후-병합을 소리 없이 재도입하는 셈이다. 두 규칙이 동시성 아래서 *C* 를 일관되게 유지한다:

- **스냅샷 읽기.** 각 추론 스텝에서 턴은 *C* 의 불변 스냅샷을 프롬프트로 읽는다. 다른 턴의 비행 중 부분 출력은 결코 보이지 않는다.
- **원자적 완료 순서 커밋.** 스텝이 완료되면 턴은 결과(tool_calls 를 포함한 어시스턴트 메시지와 그에 대응하는 *모든* 도구 결과 메시지)를 하나의 원자 블록으로, 직렬 커밋 체인을 통해, 완료 순서로 커밋한다. 블록 경계는 불변식이다: 어시스턴트/도구-결과 쌍을 쪼개면 다른 턴의 커밋이 그 사이에 끼어들 수 있고, 이는 LLM 채팅 API 가 강제하는 메시지 짝짓기 제약을 위반한다(그리고 요청을 즉시 거부당하게 한다).

알려진 비용은 유계 신선도 저하다: 턴의 스냅샷은 스냅샷 이후 다른 턴이 커밋한 효과를 놓칠 수 있다. 우리는 이를 해결하는 대신 공개한다(§7.5); 중요한 속성은 신선도 저하가 *신선도*의 한계이지 결코 *일관성* 위반이 아니라는 것이다. *C* 는 언제나 어떤 직렬 이력이 만들어냈을 수 있는 정형 트랜스크립트다.

### 4.4 효과 층: 전역 뮤텍스에서 충돌 단위 계층 락으로

계약의 첫 실행기(Coagora Web)는 샌드박스당 뮤텍스 하나로 효과를 직렬화했다. 그것은 정확했고, 측정은 그것이 너무 무디다는 것을 보였다: 동시 두 턴이 *모두* 파일을 수정하면 전역 뮤텍스는 병렬 이점을 등가 수준으로 붕괴시킨다(통합 호스트에서 결정적 ≈1.06×·실 LLM 1.23×; 원 플랫폼 최초 측정 시 1.07×/1.35×; §6.3). 같은 경로를 결코 건드리지 않을 턴들까지 서로 뒤에서 줄을 서기 때문이다. 그래서 v2 실행기는 분류된 효과 인텐트 위의 호환성 행렬을 사용해 *충돌* 입도에서 직렬화한다:

| 인텐트 쌍 | 결정 | 근거 |
|---|---|---|
| FILE_WRITE/READ(경로 *p*) vs FILE_WRITE/READ(경로 *q*), *p* ≠ *q* | **병렬** | 서로소 자원 |
| FILE_WRITE/READ(*p*) vs FILE_WRITE/READ(*p*) | 직렬 | 동일 자원 |
| 무엇이든 vs SHELL 또는 PACKAGE | 직렬 (배타) | 셸의 파일 발자국은 정적으로 알 수 없다(파이프, 확장, 서브셸); 건전한 경로 키가 없다 |
| 무엇이든 vs FILE_DELETE | 직렬 (배타) | 삭제는 디렉토리를 지울 수 있다; `rm -r src/` 를 `write src/x.py` 옆에서 돌리는 것은 배타 하에서는 없던 ENOENT 경합 클래스를 *만들어낸다*; 삭제는 드물어 배타의 비용이 거의 없다 |
| 미지 인텐트 | 직렬 (배타) | 안전 우선 기본값 |

경로 키는 정규화된다(구분자 통일; 대소문자 무시 파일시스템에서는 케이스 폴딩: `A.txt` 와 `a.txt` 는 충돌해야 한다). 입장은 **샌드박스별 엄격 FIFO, 추월 없음**이다: 큐 머리가 실행 집합과 비호환이면 펌프는 그것을 건너뛰며 스캔하는 대신 멈춘다. 이는 강한 공정성 보장을 위해 일부 동시성을 의도적으로 희생한다: 파일 연산의 흐름이 대기 중인 셸 명령을 결코 굶길 수 없다. 설정 스위치(`LOCK_SCOPE=sandbox`)는 전역 뮤텍스를 복원하며, 즉각적 롤백 경로이자 §6 절제 실험의 대조군으로 쓰인다.

낙관적 계열(§2.4)과의 대조가 이제 정밀해진다. "락은 추론을 막는다"는 CoAgent 의 가르침은 *추론 경로의* 락에 대해 참이고 여기서는 무관하다: 추론은 이 락을 결코 획득하지 않는다. 그리고 비호환 효과들은 적용 *전에* 정렬되므로 감지, 롤백, 보상, 병합할 것이 없다; 동일 자원 쓰기의 논리적 결과는 충돌 해소가 아니라 *순서의 구성상* 후승(last-wins)이다.

### 4.5 입장: 상한, 공정 큐, 사용자당 한 턴

무한한 병렬성은 사용자의 열의를 무한한 토큰 비용으로 변환한다. 세션은 동시성 상한(기본 4 비행 턴)을 강제한다. 상한을 넘는 입력은 거부되지도 배칭되지도 않는다: 첫 *적격* 항목을 찾아 머리부터 꼬리까지 스캔되는 공정 큐에 들어간다. 적격이란 제출한 사용자에게 활성 턴이 없다는 뜻이다(**사용자당 활성 턴 하나**: 병렬성은 사용자들 *사이에* 존재하지 한 사용자의 백로그 안에 있지 않으므로, 요청 다섯 개를 쌓은 한 사용자가 슬롯을 독점할 수 없다). 시스템 개시 턴은 사용자별 게이트에서 면제된다. 큐에 든 항목이 다른 사용자의 즉시 디스패치를 지연시키는 일은 없다. §6 은 공손하게 들리는 대안, 즉 거부하고-재시도하게-두기가 직렬보다 나은 적이 없고, 운 좋은 재시도 위상 정렬 밖에서는 세 계약 중 최악임을 보인다(§6.1).

### 4.6 세션 상태와 수명주기

세션 상태는 *개수 기반*이다: 턴이 하나라도 비행 중이면 RUNNING, 0이면 IDLE. 완료가 유휴를 정의하는 단일한 "그" 활성 턴은 없으며, IDLE 로의 전이는 세션 중간 깜빡임을 피하기 위해 마지막 턴에 게이트된다. 활동이 0이면 샌드박스는 일시정지(프로세스 종료, 디렉토리·파일 보존)했다가 다음 접속이나 메시지에서 재개할 수 있다. 병렬 경로는 **게시글 생성 시 한 번 고정되는 opt-in 게이트**이며 이후 불변이다: 샌드박스는 직렬 또는 동시로 생성되어 결코 전환되지 않으므로, 직렬 턴과 병렬 턴이 한 세션에 공존하는 일도, 컨텍스트 일관성 규칙이 수명 중간에 재협상되는 일도 없다. 손상되거나 없는 게이트 메타데이터는 직렬로 안전하게 실패한다.

### 4.7 순서, 재생, 멱등성

영속되는 모든 말풍선(인간 메시지, 에이전트 응답, 도구 호출, 도구 결과, 시스템 공지)은 게시글별 단조 증가 시퀀스 번호 `seq` 를 지니며, 이는 행을 영속시키는 같은 데이터베이스 트랜잭션 안에서 할당되고 유일성 제약으로 뒷받침된다. `seq` 는 순서·재접속 재생·멱등성의 단일 진실원천이다: 마지막으로 본 id 로 재접속한 클라이언트는 놓친 전부를 턴 귀속이 온전한 채 결정적으로 재생받고; 클라이언트가 제공하는 멱등성 키는 메시지 제출을 재시도해도 안전하게 만든다. 이벤트는 이 내구적 순서 위의 팬아웃 알림이지 순서 그 자체가 아니다; 서버는 의미 있는 클라이언트 상태를 들고 있지 않다.

## 5 구현

Coagora 는 독립적으로 지어진 두 런타임으로 구성된다: §6.1–6.4 의 측정을 담당하는 **Coagora Web**(Node 20 과 Fastify 위 TypeScript 약 5,600줄과 React 프런트엔드; 리포지토리 `Aidit-Code`), 그리고 §6.5–6.10 에서 측정되고 §5.1 에서 서술되는 **Coagora LAN**(Python 약 23,700줄; 리포지토리 `agent-cli`). 여기 보고된 모든 것은 커밋된 원시 데이터와 함께 공개 리포지토리에 있다. 이 절은 재현자가 필요로 할 Web 의 결정들을 조명하고; §5.1 은 LAN 런타임의 독립성이 왜 그 자체로 증거인지 설명한다.

**전송: WebSocket 이 아니라 SSE.** 하류는 게시글당 하나의 서버-전송 이벤트(Server-Sent Events, SSE) 스트림이고; 상류는 평범한 HTTP POST 다. `Last-Event-ID` 를 동반한 SSE 의 브라우저 내장 자동 재접속은 `seq` 순서(§4.7)에 대한 재접속-재생을 *공짜로* 준다: 서버는 재생을 데이터베이스 범위 읽기로 구현하고, 클라이언트별 커서를 들지 않으며, WebSocket 이 요구했을 양방향 세션 기계가 전혀 필요 없다. 관전자(읽기 전용 참여자)는 평범한 미인증 구독자다.

**프로세스 분리: 워커는 제안하고, 서버가 처분한다.** LLM 루프는 파일시스템·셸 접근이 *전혀* 없는 자식 프로세스에서 돈다. 워커는 stdout 으로 도구 *인텐트*를 내보내고; 부모 서버가 각 인텐트를 분류하고, 충돌 단위 락(§4.4)을 획득하고, 세 겹의 가드 뒤에서 효과를 실행하고, (callId, turnId) 로 라우팅되는 확인 응답을 돌려준다. 가드는: (1) *경로 감금*: 모든 경로는 루트 접두 검사 전에 정규화되고 가장 가까운 실존 조상의 realpath 를 통해 해석되어, 아직 없는 파일의 생성은 허용하면서 `..` 순회·절대 경로 주입·심링크 탈출을 무력화한다; (2) *기본 거부 환경*: 자식 프로세스는 무해한 변수의 허용 목록만 받는다. 이 규칙은 가정이 아니라 학습이었다: 초기 빌드는 서버 환경을 도구 셸에 상속시켰고, `echo $API_KEY` 가 프로바이더 키를 모든 SSE 구독자에게 스트리밍했다. 수리는 회귀 테스트와 이벤트 스키마에 대한 지속 통합(continuous integration, CI) grep 게이트로 강제된다; 이벤트 생성자는 열거된 안전 필드만 받으므로, 키 유출은 금지를 넘어 구조적으로 표현 불가능하다; (3) *자원 한도*: 전체 프로세스 트리 킬을 동반한 벽시계 타임아웃과 샌드박스별 프로세스 상한. 우리는 정확히 이만큼만 주장한다: 디렉토리 격리와 이 가드들. 컨테이너·cgroup·네트워크 격리는 구현되어 있지 않고(Docker 개념 증명이 제품 밖에 존재), 이식 가능하게 강제할 수 없는 한도를 시뮬레이션하지 않는다.

**키는 서버 내부다.** 프로바이더 자격증명은 서버 시크릿에만 살고 워커 환경에 주입된다; 어떤 응답, 로그, 이벤트, 클라이언트에도 나타나지 않는다. 세션 레코드는 모델 이름만 저장한다.

**장애 격리.** 턴은 메시지 라우트에서 fire-and-forget 으로 발사된다(201 이 즉시 반환). 초기 버전은 그 경로의 예외(턴 중간에 삭제된 게시글)가 처리되지 않은 거부로 떠올라 서버 전체를 쓰러뜨리게 두었다; 이 장애는 *벤치마크 하네스가 발견했고*(180회 중 39회 연쇄), 지금은 레코드-소멸을 정상 조기 종료로 취급하는 최상위 래퍼가 흡수한다. 워커 사망은 네 개의 턴 레지스트리(레거시 활성/큐, 동시 활성/큐)를 모두 청소해 어떤 프라미스도 걸리지 않고; 중단은 프로세스 경계 양쪽에서 뒤늦은 완료를 억제한다.

**과학을 위한 결정론.** 키가 없거나 테스트 중이면 스텁 모드가 LLM 을 결정적 에코-지연 모델로 대체한다. §6 의 모든 벤치마크는 스크립트된 지연을 가진 로컬 목 OpenAI 호환 서버를 상대로 돈다: 동일 입력은 동일 타임라인을 만들고, 전체 스위트는 네트워크·키 없이 돌며, 논문의 그림은 커밋된 상수에서 재생성된다. 데모 클립과 플롯이 표와 어긋날 수 없다.

### 5.1 하나의 계약, 두 개의 런타임

탄생 구현만 만족시킬 수 있는 계약은 계약이 아니라 서술이다. Coagora 의 두 번째 런타임 **Coagora LAN** 은 프로젝트의 목표는 공유하되 코드는 전혀 공유하지 않는 형제 코드베이스이며, 그럴듯하게 문제가 될 수 있는 모든 아키텍처 차원에서 다르다: TypeScript 대신 Python; 자식 워커를 둔 Fastify 서버 대신 단일 프로세스 CLI/웹 하이브리드; 프로세스 경계 너머로 메시지를 전달하는 이벤트루프 대신 한 힙을 공유하는 OS 스레드; 네이티브 함수 호출 델타 대신 스트리밍된 *본문*(JSON op 배열)에서 파싱되는 도구 호출; 관계형 저장소 대신 append 전용 JSONL 파일로 영속되는 대화. 혈통에 터미널이 있지만 Coagora LAN 은 단일 사용자 도구가 아니다: 같은 다중 사용자 공유 세션을 LAN 웹 표면으로 서비스하며, 터미널은 N 개 클라이언트 중 하나다. 이식이 옮긴 것은 정확히 셋뿐이다: 불변식(스냅샷 읽기/원자 커밋, 디스패치 시점 turnId, 엄격 FIFO 를 동반한 효과 호환성 행렬, 사용자별 단일 활성 입장), 인수 기준으로서의 Web 계약 테스트, 그리고 주석에 기록된 설계 근거. 코드가 아니다.

두 번째 런타임은 첫 번째가 표현할 수 없는 위험들을 만났고, 바로 그것이 이 재현을 유익하게 만든다. *스레드는 메모리를 공유한다*: 공유 `ContextManager` 는 락 규율(한 방향: 컨텍스트 → 렌더러 → 파일-append)을 필요로 했고, 턴별 귀속은 스레드 로컬 상태로 옮겨갔다. 이벤트루프의 협력적 스케줄링 아래서는 정확했던 세션 전역 필드 하나가, 선점형 스레드가 경합하자 동시 세 답변 전부를 마지막 질문에 소리 없이 귀속시켰기 때문이다(라이브에서 발견, 수리, 회귀 고정). *파일은 중개되지 않고 공유된다*: 쓰기를 직렬화할 부모 프로세스가 없으므로 append 원자성이 파일시스템 의존이 되었다. ext4 에서는 무손상, Windows Subsystem for Linux(WSL)의 Windows 드라이브 마운트에서는 손상(16스레드 append 에서 128줄 중 45줄 생존)으로 실측되어, 이력 파일은 스트라이프된 프로세스 내 append 락을 얻었다. *컨텍스트는 유한하다*: LAN 런타임은 Web 에 전혀 없는 토큰 예산 압축을 가져오며, 턴이 비행 중일 때 압축이 무엇을 의미하는지에 대한 첫 답(§6.6)을 강제한다. 락 표 자체에도 정밀화 하나가 필요했다: Web 의 안전 우선 규칙 "미지 인텐트 → 배타"는 스레드 아래서 자기교착한다. LAN 런타임의 복합 도구(서브에이전트, 스킬)는 중첩 루프를 돌리고 그 잎 호출들이 다른 스레드에서 같은 락을 획득하기 때문이다. 그래서 LAN 런타임은 그런 인텐트를 *정렬 대상 아님*(자기 자신의 워크스페이스 효과가 없음; 잎들이 개별적으로 잠금)으로 재분류하고, 진짜로 미지인 파일 효과에 대해서는 "잠근다면 배타"를 유지한다. 반대로, 이벤트루프 구현의 위험들(서버를 쓰러뜨리는 처리되지 않은 거부; 워커 경계를 넘는 뒤늦은 완료)에는 스레드 쪽 유사물이 없다. 하나의 계약, 서로소인 두 위험 집합, 하나의 행동 결과(§6.5): 속성을 지고 가는 것이 런타임이 아니라 계약이라는 증거다.

LAN 런타임은 또한 Web 이 설계만 한 측정 평면을 실제로 싣는다: 턴 수명주기(큐 진입 → 디스패치 → 첫 토큰 → 완료), 효과 락 대기, 압축 세대, 거부를 하나의 단조 시계 위에 기록하는 opt-in 이벤트 스트림(`turns.jsonl`). §6.5–6.10 의 모든 수치는 이 파일에서 계산되며, 목 LLM 하네스는 Web 의 시나리오 지시자 문법을 재사용해 두 런타임이 같은 실험 스크립트를 돌린다.

## 6 평가

우리는 열 개의 연구 질문을 평가한다: 넷은 Coagora Web 에서, 여섯은 Coagora LAN 에서 또는 LAN 으로 인해 가능해진 것이다. Web 에서: **RQ1** 계약은 HOL 블로킹을 제거해 사용자의 지연이 남의 작업으로부터 독립이 되게 하는가? **RQ2** 배포된 대안 계약들의 비용은? **RQ3** 효과 직렬화는 실제로 손상을 막는가, 락 입도는 무엇을 사는가? **RQ4** 이점은 어디서 붕괴하는가? 이어서: **RQ5** 계약은 독립적으로 지어진 런타임에서 살아남는가? **RQ6** 턴이 도는 동안 공유 컨텍스트를 압축할 수 있는가? **RQ7** 귀속은 휴리스틱이 아니라 구조적일 수 있는가? **RQ8** 사용자별 입장은 폭주 하에서 실제로 다른 사용자를 보호하는가? **RQ9** 세션은 재시작과 수백 턴을 견디는가? **RQ10** 순위는 실 LLM 을 상대로도 성립하는가, 병렬성의 진짜 토큰 비용은?

**설정.** 모든 대표 수치는 결정적 하네스(Web 은 §5, LAN 은 §5.1)를 쓴다: 스크립트된 작업 길이의 목 LLM, 실제 서버, 실제 샌드박스, 실제 락. 모델만 모사되므로 측정 구간은 피시험 시스템이 지배하고, 모든 실행은 자격증명 없이 리포지토리에서 재현된다. 두 런타임 모두 하나의 리눅스 호스트에서 측정되었다; Web 수치는 거기서의 신규 재실측이라 런타임 간 비교가 플랫폼을 고정한 채 성립하며, Web 의 원 개발 플랫폼 측정치는 명시 표기된 곳에만 나온다. 실 LLM 대조는 명시된 곳에 나온다. 모든 그림의 원시 JSONL 이 커밋되어 있다. ✔

### 6.1 RQ1–RQ2: 세 계약 하의 헤드오브라인 블로킹 ✔

프로토콜: 사용자 A 가 길이 *L* ∈ {2 s, 6 s, 15 s} 의 작업을 시작하고; 1초 뒤 사용자 B 가 한 줄 질문을 보낸다; B 의 첫 토큰까지의 시간을 측정한다. 계약: *직렬*(FIFO, v0.1 경로), *거부-후-재시도*(busy 게이트가 409 반환; 클라이언트가 백오프로 재시도, OpenTag/double-texting 계열), *병렬*(v2). 총 n = 180(셀당 20).

| 계약 (Coagora Web) | L = 2 s | L = 6 s | L = 15 s | 기울기 dTTFT/dL |
|---|---|---|---|---|
| 직렬 (FIFO) | 1.86 s | 5.86 s | 14.86 s | 1.000 |
| 거부 + 재시도 | 1.85 s | 5.86 s | 14.86 s | **1.001** |
| **병렬 (본 논문)** | **0.254 s** | **0.254 s** | **0.252 s** | **0.000** |

중요한 숫자는 배수가 아니라 *기울기*다. 기울기 1.000 에서는 당신의 빌드 1초가 곧 나의 대기 1초다; L = 15 s 에서의 59× 우위는 효과가 멈추는 곳이 아니라 우리의 측정이 멈추는 곳일 뿐이다. 병렬 계약의 기울기 0.000 은 B 의 지연이 B 자신의 요청의 속성이라는 뜻이며, 이것이 독립의 정의다. 거부 계약은 배포된 다중 사용자 프레임워크들이 실제로 싣는 것이기에 강조할 가치가 있고, 재실측이 그 문제의 본질을 벼렸다. 이 호스트에서는 벌점이 사라졌다(기울기 1.001, 오프셋 직렬과 동일): 1 s 재시도 간격이 정수 초 작업 완료와 우연히 위상 정렬됐기 때문이다. 원 플랫폼에서는 같은 프로토콜이 기울기 1.010 에 ~0.3 s 상수 세금을 측정했고, LAN 런타임(재시도 간격 0.25 s, §6.5)에서는 워크로드에 따라 변하는 1간격 이내의 세금(L 에 걸쳐 79~232 ms)이었다. 정직한 특징짓기: 거부는 직렬의 HOL 대기 전부에 *더해* 0~재시도 1간격 사이의 위상 의존 세금을 내며, 모든 클라이언트에 재시도 기계를 떠넘긴다. 직렬보다 나은 적이 없고, 워크로드가 위상 정렬을 선물하지 않는 한 순위의 바닥이다. ### 6.2 RQ3: 효과 직렬화가 막는 것 ✔

절제 실험: 동시 두 작성자가 구별 가능한 마커로 같은 파일을 반복해서 쓰고, 직렬 실행기를 우회한 팔과 켠 팔을 비교하며, 2 ms 샘플러가 스냅샷을 분류한다. 통합 호스트 재실측에서 실험은 기본 페이로드(1 MiB)에서 먼저 무효를 반환했다: **락 해제 상태에서도 위반 0%**. ext4 의 단일 대형 `write(2)` 는 인터리브 창을 거의 남기지 않기 때문이다. 하네스 스스로 이 구성을 결론 불가로 표기하며, 이 무효는 유익하다: 락 해제 위험은 실재하되 플랫폼이 게이트한다. 하네스 자체 프로토콜대로 감도를 올리면(작성자당 4 MiB × 80회 쓰기) 위험이 드러난다: 우회 시 분류된 스냅샷의 **6.8%** 가 손상(한 파일에 두 작성자의 마커, 6/88); 락 적용 시 **0%**(0/175). 쓰기를 청크로 스트리밍하던 Web 의 원 플랫폼에서는 같은 우회가 **74%** 를 측정했다. 락 적용은 모든 환경에서 0%다. 병합 단계도, 충돌 다이얼로그도, 롤백 기계도 없이, 동시 동일-파일 쓰기가 물리적으로 결코 발생하지 않기 때문이다. 이것이 락이 의례가 아니라 하중을 받고 있음을 보여주는 절제 실험이며, 락이 *무엇에 대해* 하중을 받는지는 플랫폼의 쓰기 역학이 정한다.

### 6.3 RQ4: 이점은 어디서 붕괴하고, 입도는 무엇을 회복하는가 ✔

정직함은 경계를 요구한다. 동시 두 턴이 *모두* 쓰기 중심이면 전역 뮤텍스 실행기는 거의 전부를 직렬화하고, 직렬 계약 대비 종단 간 이점은 **≈1.06×**(결정적, 통합 호스트 재실측; 원 플랫폼 1.07×)와 실 온프레미스 LLM **1.23×**(Qwen3.6-27B, n = 3; 원 플랫폼 1.35×)로 붕괴한다: 병합 대신 예방을 선택한 비용이며, 정확히 워크로드가 충돌할 때 지불된다. 이 측정이 v2 충돌 단위 락(§4.4)의 동기였다: 셸과 삭제는 배타로 유지하면서, 동시 턴들이 *서로소* 파일을 만지는 흔한 경우의 병렬성을 회복한다.

LAN 런타임의 그리드(§5.1 하네스; 동시 2턴, 셀당 5회)는 붕괴가 *무엇의* 함수인지 벼린다. 턴당 파일 쓰기 효과의 *횟수*를 바꾸는 것(0 → 2 → 6)은 유효 병렬도를 1.99 에서 1.50 까지만 움직였고 그 이상은 아니었다. 모든 셀에서 락 대기 중앙값은 1 ms 미만이었고 conflict/workspace 스코프 간에도 동일/상이 파일 간에도 차이가 없었다. 실제 파일 쓰기는 마이크로초~밀리초급 효과라 경합하기에 너무 짧고, 1.50 정체는 락 시간이 아니라 왕복 오버헤드(도구 스텝마다 추론 구간이 하나 추가됨)다. 이점을 *실제로* 붕괴시키는 것은 **배타 효과의 시간 비중**이다: 각 턴이 시간의 ~50%를 배타적 셸 스텝에 쓰면 유효 병렬도(락 대기는 유효 작업에서 제외)는 1.59 로 떨어지고; 배타 셸 비중 ~90%에서 **1.10** 에 도달한다. 이는 Web 의 ≈1.06× 경계를 반대 방향에서 재현하며, 셸이 지배할 때는 경로 입자 락이 아무것도 사지 못한다는 XC-SCOPE 발견을 확증한다. 설계 공간의 명제: *붕괴 경계는 효과 횟수나 충돌률이 아니라 배타 효과의 시간 비중을 따른다*. 실제 코딩 에이전트 턴은 추론이 지배하고 파일 효과는 짧으므로, 흔한 경우는 경계에서 멀리 있다; 쓰기 중심 영역에서 계층 락의 남은 임무는 지연이 아니라 무결성(§6.2, §6.5)이다.

### 6.4 정확성, UI, 장애 격리 ✔

Web 의 백엔드 스위트는 동시성 기계(턴 다중화, 상한·사용자별 게이트, 락 스코프, 워커 동시성, 재생)를 커버한다; 통합 리눅스 호스트에서 36개 테스트 파일 중 35개 통과(실행 테스트 148/150). 유일한 실패는 그 자체로 §5.1 류의 데이터다: 도구 타임아웃 테스트는 프로세스 *트리* 킬을 단언하는데 그 구현이 win32 `taskkill /T` 형태라, POSIX 에서는 분리된 자식이 자연 종료까지 살아남는다. 이는 리눅스에서 벤치 드라이버의 teardown 을 행에 빠뜨리는 것과 같은 근원이다(결과는 행 이전에 기록된다; 수리는 POSIX 프로세스 그룹 킬이며 Web 리포지토리에 후속 작업으로 기록되어 있다). 단언하는 브라우저 종단 간(end-to-end, E2E) 스위트는 두 실제 클라이언트를 동시 턴으로 몰고 가며 어떤 턴 간 UI 귀속 오류에도 실패한다. §5 의 fire-and-forget 장애는 하네스가 발견했고, 수리되었으며, 회귀 테스트로 고정되어, 평가 장치가 시스템을 행복 경로가 아니라 적대적으로 연습시킨다는 증거를 겸한다.

**타당성 위협.** 목 LLM 타이밍은 프로바이더 측 변동을 배제한다(§6.10 의 실 LLM 대조와, 둘 다 존재하는 곳에서 결정적/실측 쌍을 병기하는 것으로 완화); 두 구현은 서로를 재현하지만(§6.5) 측정 호스트는 하나를 공유한다; N-병렬 추론의 토큰 비용 오버헤드는 짧은 이력 워크로드에서 1.49× 로 측정되었고(§6.10) 이력 길이와 직렬 배칭 실패에 따라 커진다; 우리의 워크로드는 현장 로그 혼합 분포가 나오기 전까지 합성이다 [TODO: S1].

### 6.5 RQ5: 계약은 다른 런타임에서 살아남는가 ✔

두 대표 실험을 Coagora LAN(§5.1)에서 재실행했다. 같은 목 LLM 시나리오 문법을 상대로 실제 서버를 HTTP 로 구동하며(여기서 B 는 A 후 0.5 s 에 제출, Web 은 1 s), 모든 구간은 하나의 단조 시계 위 내부 이벤트 스트림에서 계산했다(셀당 n = 20).

| 계약 (Coagora LAN) | L = 2 s | L = 6 s | L = 15 s | 기울기 dTTFT/dL |
|---|---|---|---|---|
| 직렬 (FIFO) | 2.08 s | 6.16 s | 15.34 s | 1.02 |
| 거부 + 재시도 | 2.31 s | 6.34 s | 15.42 s | 1.008 |
| **병렬** | **0.29 s** | **0.29 s** | **0.29 s** | **0.000** |

순위, 기울기, 평평한 병렬 선이 재현된다(Web, 같은 호스트: 1.000 / 1.001 / 0.000); 병렬 계약의 상수 ≈0.29 s 는 LAN 런타임의 턴당 준비 시간 + 스크립트된 200 ms TTFT 이며, p95(0.293 s)는 p50 보다 2 ms 위에 있다: 이 런타임에서도 B 의 지연은 B 의 요청의 속성이다. 무결성 절제 실험은 방향과 영점에서 재현되며, 플랫폼을 고정하자 *크기가 수렴한다*: 락 우회 시 Web 6.8% vs LAN 8.2%. 이 파일시스템에서는 두 런타임의 쓰기가 모두 truncate + 단일 대형 `write(2)` 로 환원되어 같은 좁은 인터리브 창을 남기기 때문이며, Web 의 원 스트리밍-쓰기 플랫폼은 74% 를 측정했었다. 두 락 스코프 모두 모든 환경의 두 런타임에서 위반을 **0%** 로 만든다. 이것이 재현에서 우리가 원하는 증거의 형태다: *계약 수준* 주장(순위, 기울기, 영점)은 런타임을 가로질러 불변이고; *메커니즘 수준* 상수(절대 TTFT 바닥, 위반 강도)는 마땅히 그래야 하듯 플랫폼을 따르며, 플랫폼을 공유하면 수렴한다.

### 6.6 RQ6: 턴이 도는 동안 공유 컨텍스트 압축하기 ✔

Coagora Web 에는 압축이 없다(한계 (2)); LAN 런타임은 토큰 예산 압축을 공유 세션에 들여오고, 그와 함께 어떤 선행 연구도 답하지 않은 질문의 첫 버전을 들여온다: *동시 턴들이 덧붙는 도중에* 대화가 요약되면 무슨 일이 일어나는가? 설계는 낙관적이다: 락 아래서 분할하고 세대를 기록하고, 락 밖에서 요약하고(수 초짜리 LLM 콜), 세대를 재검증한 뒤 원자적으로 커밋하며, 그 사이 동시 턴들이 덧붙인 꼬리를 흡수한다.

강제 압박(사용자 3 × 30라운드, 90턴, 의도적으로 작게 광고된 창, 800 ms 요약기) 아래서 측정했다: 모든 압축은 3턴 비행 중에 시작됐고, 턴들은 무락 요약 창 *안에서* 계속 흘렀다. 압축의 시작과 커밋 사이에 첫 토큰 11개를 포함한 턴 이벤트 42개가 착지했으며, 이는 배리어 설계라면 0으로 만들었을 가용성이다. 90개 질의 중 0개가 유실됐고, 응답 귀속은 매 회를 견뎠다. 계측은 실제 설계 결함도 잡았다: 첫 빌드에서 동시 턴들의 오버플로 폴백(FIFO 축출)이 매 요약 창마다 세대를 올려 낙관적 커밋을 굶겼다. 이 부하에서 압축 6회 중 1회만 착지했고, 더 온화한 지속 부하에서는 28회 중 0회였다; 요약 비용은 지불되고 버려지는데 원시 이력은 요약 없이 축출됐다. 수리는 압축 비행 중에 동시 호출자들이 예방 목표(실 여유의 0.8×)와 실 한계 사이의 마진을 관용하게 한다; 위의 강제 압박 부하로 재실행하자 압축 4회 중 4회가 뒤늦은 재시도 0으로 커밋됐다. 우리가 이를 보고하는 이유는 이것이 단일 사용자 시스템에서는 발견될 수 없는 종류의 상호작용, 즉 압축 × 동시성이기 때문이고, 그것을 찾아낸 것이 측정 평면(§5.1)이기 때문이다.

### 6.7 RQ7: 휴리스틱이 아닌 구조적 귀속 ✔

Web 의 한계 (9)는 1:1 귀속을 에이전트 응답으로 한정하고, 동시성 하의 도구 이벤트는 직전-근접 휴리스틱으로 후퇴시켰다. LAN 런타임은 귀속을 *구조적*으로 만든다: 한 턴 = 한 스레드이고, 유발 질문의 신원이 스레드 로컬 상태에 살므로, 질문을 처리하는 동안 쓰인 모든 레코드는 모델이 무슨 말을 하든 그 `reply_to` 를 지닌다. 규모에서 검증했다(사용자 4 × 25라운드, 동시 100턴): 발급 사슬(큐 진입 → 디스패치된 턴 → 스레드 → 발급된 질문 id)은 100/100 정확했고, 최종 응답들은 질문들과 완전한 전단사를 이뤘다: 중복 0, 불일치 0, 누락 0.

같은 실험은 구조적 귀속이 의도적으로 풀지 않는 *의미론적* 현상을 처음으로 정량화한다: 공유 트랜스크립트에서 보이는 최신 질문에 항상 답하는 결정적 적대 모델에서, 턴의 38%가 *내용상* 다른 사용자의 나중 질문을 다루는 답을 냈다. 그동안 `reply_to` 는 그 턴이 어느 요청을 서비스 중이었는지 정확히 기록했다. 이는 자주 혼동되는 두 주장을 깨끗이 분리한다: *이것을 만든 것이 누구의 턴인가*(구조적, 이제 정확)와 *모델이 누구의 질문에 답하기로 했는가*(하나의 트랜스크립트를 공유하는 것의 속성으로, 여기서 최악 케이스로 유계화; 실 LLM 실행은 3/3 으로 자기 질문자에게 답했다).

### 6.8 RQ8: 폭주 하의 공정성 ✔

한 사용자가 긴 턴 다섯 개를 연달아 제출하고; 다른 네 명이 각각 짧은 질문 하나를 한다(상한 = 3, 5회 반복). 사용자별 게이트(사용자당 활성 턴 하나, 다른 사용자를 위해 대기자 건너뛰기)를 켜면 짧은 질문들은 중앙값 **76 ms**(p95 148 ms)에 디스패치됐고, 폭주자 자신의 백로그는 자기 뒤에서 기다렸으며(중앙값 3.3 s), 사용자별 단일 활성 불변식은 위반 0으로 유지됐다. 게이트를 절제하면(순수 FIFO + 상한) 폭주자가 슬롯을 독점했고 같은 짧은 질문들이 중앙값 **1,807 ms**(p95 3,219 ms)를 기다렸다: 24× 악화다. *모든* 사용자에 대해 계산한 소박한 Jain 지수는 절제 팔에서 더 높다(0.85 vs 0.24)는 점에 유의하라: 모두가 똑같이 나쁘게 서비스받는 것이다. 게이트는 폭주자의 백로그에 의도적으로 "불공정"하다; 그 비대칭이 곧 메커니즘이며, 정직한 보고는 스칼라 공정성 지수가 아니라 클래스별 절대 대기다.

### 6.9 RQ9: 세션 수명주기 (일시정지, 재개, 유계 유지) ✔

공유 세션은 서버 재시작과 수백 턴을 가로질러 *지속*해야만 유용하다. 세 사용자가 네 단계에 걸쳐 한 세션으로 204턴을 몰았고; 단계 사이에 서버 프로세스를 종료하고 `--resume` 으로 재기동했다(일시정지/재개 3회). 모든 검사가 유지됐다: 최종 단계 후 내구 이력에 질의 204/204 존재(재시작을 가로질러 유실 0); 질문 id 는 재개를 가로질러 전역 유일했다. 재개 경로가 id 카운터를 압축된 캐시가 아니라 *전체* 이력에서 재도출하므로, 재시작된 세션이 이미 귀속된 id 를 다시 발급하는 일이 없기 때문이다; 그리고 재개된 각 단계는 새 51턴을 정상 처리했다. 압축은 실행 내내 공유 컨텍스트를 유계로 유지했다: 커밋 10회(뒤늦음 2, 실패 0), 압축 후 캐시는 ~7K 예산 대비 2,610 토큰을 결코 넘지 않았다. 세션의 컨텍스트 발자국은 세션 나이가 아니라 압축기가 다스린다. 이는 Web 의 커뮤니티 모델(U5: 간헐적 활동의 열린 스레드)이 제기했으나 압축 없이는 시험할 수 없었던 수명주기 질문에 다중 사용자 설정으로 답한다.

### 6.10 RQ10: 실 LLM 검증과 병렬성의 진짜 값 ✔

위의 모든 수치는 결정적 목 지연을 쓴다. 대표 결과의 표본 검증과 비용 질문의 결말을 실 온프레미스 모델(Qwen3.6-27B, MLX 8-bit; 순위 검증 5회, 토큰 회계 3회)을 상대로 얻었다.

*순위 보존.* 사용자 A 가 긴 생성을 시작하고; B 가 2 s 뒤 한 줄 질문을 한다. B 의 TTFT: 직렬 중앙값 **27.8 s**(B 는 A 의 턴 전체를 기다린다), 병렬 중앙값 **7.0 s**. 순위는 재현되고, 병렬의 절대값은 라이브 서버가 무엇을 더하는지에 대해 정직하다: B 의 ~7 s 는 하네스의 0.29 s 바닥이 아니라 공유 추론 하드웨어 위의 실제 프리필과 동시 디코드 감속이다. A 의 작업 *길이*로부터의 독립은 성립하고(§6.1/§6.5); A 의 *존재*로부터의 독립은 프로바이더의 동시성에 의해 유계이며, 이는 세션 계약이 만들어낼 수 없는 서빙 층 속성이다.

*토큰 회계.* 한계 (1)은 "N 병렬 턴은 ~N 추론 비용을 낸다"를 우려했다. 동일한 세-질문 워크로드에서 측정: 병렬 계약은 3콜에 입력 토큰 총 **23.2K**; 직렬 계약은 **2**콜에 총 **15.6K**: **1.49×** 프리미엄이지 3× 가 아니다. 우려와 측정의 간극은 두 메커니즘이 설명한다. 첫째, 콜당 입력은 고정 시스템 프롬프트(여기서 콜당 ~7.7K)가 지배하므로, 비용은 스냅샷 재읽기가 아니라 *콜 수*를 따른다; N× 우려의 동기였던 공유 컨텍스트 중복은 이력이 길어지기 전까지는 부차 항이다. 둘째, 직렬 계약은 조용히 *배칭한다*: mid-run 주입이 큐의 질문을 실행 중 턴에 접어 넣는다(질문 3, 콜 2). 이는 병렬성이 포기하는 실질적 효율인데, 질문당 턴 하나가 바로 4× TTFT 를 사는 것이기 때문이다. 트레이드의 정직한 진술: 병렬성의 토큰 프리미엄은 콜 수의 비(≤ N, 부하에서 직렬 배칭이 실패할수록 축소)이며, 지연 독립성의 값으로 지불된다; 이 배포에 없는 프로바이더 측 프롬프트 캐싱은 콜당 고정 항을 더 줄일 것이다.

## 7 논의: 세션 공유가 만들어내는 것

계약은 위임의 구조적 한계를 제거한다. 거기서 멈추면 부정직할 것이다: 하나의 라이브 세션에의 공존은 분리된 위임에는 없던 문제들을 낳는다. §2.5 의 이론에서 넷을 도출한다. 이는 이 논문의 해결된 주장이 아니라 연구 의제다.

### 7.1 비대칭 그라운딩

Clark 와 Brennan 의 그라운딩 이론 [32]은 당사자들이 공통 기반을 *함께* 축적한다고 가정했다. 지속되는 공유 에이전트 세션은 그 대칭을 깬다: 사용자 A 와 에이전트가 30분의 작업 컨텍스트(내려진 결정, 버려진 접근, 만진 파일)를 쌓고, 사용자 B 는 차갑게 붙는다. B 는 트랜스크립트를 재생할 수 *있지만*(§4.7 이 보장한다), 재생은 접근이지 이해가 아니다; 세션의 공통 기반은 이제 소유자 기울기를 가진 인공물이다. 우리의 seq 정렬·턴 귀속 트랜스크립트는 따라잡기 인터페이스(요약, 결정 다이제스트, 파일별 "여기서 무슨 일이" 뷰)의 원재료지만, 이 중 무엇이 간극을 닫는지, 닫는 것이 항상 바람직하기는 한지는 열린 실증 질문이다(계획된 연구 S2: 세 따라잡기 처치 하의 단계적 중간 합류, 이해도·첫 생산적 개입까지의 시간·확정된 결정의 재론을 측정).

### 7.2 다자 제어권 중재

Horvitz 의 혼합 주도권 원칙 [36]은 에이전트가 언제 행동하고 언제 물을지 알려주되, 한 명의 인간을 전제한다. 여럿이면 모든 제어 동사가 간접 목적어를 얻는다: *누구의* 승인, *누구의* 중단, *누구의* 되돌리기? 우리가 실은 정책은 의도적으로 최소다: 사용자별 턴 소유권(당신 것은 중단해도 된다; 내 것은 건드릴 수 없다; 내 턴이 당신의 입력창을 잠그지 않는다). 이는 역할 기반 오버라이드(사고 지휘자는 무엇이든 멈춘다), 파괴적 효과에 대한 정족수 게이트, 사회적 투명성 접근(누구든 무엇이든 멈출 수 있되, 보이게)도 담는 정책 공간의 한 점이다. 솔로 사용자가 39% 확률로 브레이크를 밟는다는 SWE-chat 의 발견 [3]은 질문을 벼린다: 공유 세션에서 브레이크는 중복인가(누군가 잡겠지), 분산인가(모두가 남이 잡으리라 가정하는 방관자 패턴), 증폭인가(눈이 많으니 브레이크도 많다)? turnId 메커니즘은 이 정책들 중 무엇이든 구현 가능하게 만든다; 무엇이 *작동하는지*는 연구 S3 다.

### 7.3 에이전트 속도의 동료 책임감

Daryanto 등은 동료가 당신의 AI 사용을 볼 수 있으면 제안을 적용하기 전에 더 검증함을 발견했다 [24]. 제안 기반의, 인간 속도 설정에서다. 자율 에이전트는 체제를 바꾼다: 효과가 기계 속도로 여러 파일에 착지하고, 동료가 관찰하는 것은 커서 밑의 diff 가 아니라 스트림이다. 분당 검증할 것이 인간이 읽을 수 있는 양을 넘을 때도 가시성은 여전히 검증을 사는가? 우리의 팬아웃 설계는 기본값으로 모든 참여자를 잠재적 검증자로 만든다; 그것이 Daryanto 의 책임감을 낳을지 단순한 경보 피로를 낳을지는 정확히 이 시스템에서 시험 가능하며 아직 미지다.

### 7.4 조율 노동은 이전되지, 파괴되지 않는다

Schmidt 와 Bannon 은 조정 기술이 조율 노동을 제거하기보다 재배치한다고 예측했다 [35]. 위임의 조율 노동은 현장에서 보인다: 어느 채널이 어느 작업을 발사했는지 추적하기, 병렬 멘션 중복 제거하기, 버그를 각각 반쯤 푼 세 PR 을 조정하기. 공유 세션은 이 중 많은 부분을 메커니즘으로 흡수한다: 큐가 정렬하고, 락이 직렬화하고, `replyToId` 가 귀속한다. 그 자리에 새 노동이 나타난다: 실행 중인 턴에 조타를 언제 주입할지 결정하기, 상한을 협상하기, 동시 스트림들의 유영을 읽기. 우리는 이 교환이 유리하다고 추측하지만(기계화된 정렬은 사회적 정렬보다 싸다), 이론과 함께, 옳은 주장은 *이전*이라고 견지한다. 그리고 옛 노동의 소멸을 자축하기보다 새 노동을 측정하는 것(S1 현장 로그)이 중요하다.

### 7.5 한계

현 시스템과 결과의 정직한 경계. (1) *토큰 비용, 이제 측정됨*(§6.10): 동일한 세-질문 워크로드에서 병렬 계약은 직렬 계약의 1.49× 입력 토큰을 냈다(3콜 vs 2콜; 직렬은 mid-run 주입으로 큐의 질문을 실행 중 턴에 배칭하며, 병렬성은 지연 독립성을 위해 이 효율을 의도적으로 포기한다). 프리미엄은 컨텍스트 재읽기가 아니라 콜 수를 따르고, 콜당 입력은 고정 시스템 프롬프트가 지배한다; 직렬 배칭이 완벽하고 이력이 길 때만 N× 에 접근하며, 이 배포에 없는 프로바이더 측 프롬프트 캐싱은 고정 항을 더 줄일 것이다. (2) *컨텍스트 용량, 부분 해소*: 하나의 공유 컨텍스트는 N배 빨리 찬다. Web 에는 압축이 없다; LAN 런타임은 토큰 예산 압축을 동시 턴과 통합하고 측정한다(§6.6): 가용성이 유지되고 레코드는 유실되지 않으며, 지속 과부하 하에서 간혹 요약 콜이 낭비되는 비용이 있다. 장기 지평의 용량 한계(N 명의 지속 사용자가 몇 시간에 걸쳐 하나의 창에 하는 일)는 미측정으로 남는다. (3) *논리적 후승(last-wins)*: 직렬화는 물리적 손상을 막지 의미론적 충돌을 막지 않는다. 두 턴이 파일이 담아야 할 내용에 대해 이견을 가질 수 있고, 나중 것이 이긴다; 의미론적 충돌을 인간에게 드러내는 것은 열린 문제다. 공유 트랜스크립트는 또한 턴의 *답변*이 다른 사용자의 나중 질문을 다루게 허용하며, 이는 적대적 항상-최신-답변 모델 하의 최악 케이스 38%로 이제 정량화되었다(§6.7). 구조적 귀속은 이를 기록하지 방지하지 않는다. (4) *락 봉투*: 도구가 백그라운드로 분리한 프로세스의 효과는 직렬 실행기를 탈출한다. (5) *스냅샷 신선도 저하*(§4.3). (6) *단일 인스턴스*: pub/sub·락·레지스트리는 프로세스 내다; pub/sub 이음새는 분산 백엔드를 위한 인터페이스는 준비되었으나 미구현이다. (7) *격리 깊이*: 디렉토리 수준이지 컨테이너 수준이 아니다(§5); 개방 참여 모델(인증 사용자는 누구나 어느 게시글의 샌드박스에서든 코드를 실행할 수 있다)은 커뮤니티 설정을 위한 것이며 명시된 위협 모델을 요구한다. (8) *중단-후-재지시*는 동시 턴에서 미지원이다(순수 취소만). (9) *귀속, LAN 런타임에서 해소*: Web 은 동시성 하에서 도구 말풍선을 휴리스틱으로 귀속한다; LAN 런타임의 스레드 범위 귀속은 구조적이며 규모에서 정확함이 검증되었으므로(§6.7), 휴리스틱 단서는 이제 Web 에만 적용된다.

## 8 결론

배포된 모든 코딩 에이전트는 싱글플레이어이고, 업계의 팀용 우회로인 @멘션 위임은 팀이 협업자에게 가장 필요로 하는 두 가지, 즉 작업이 진행되는 동안 개입할 능력과 두 사람이 동시에 말할 때의 규칙을 구조적으로 배제한다. 통념은 이를 공유 세션 안에서 고치려면 직렬화나 포크가 강요된다고 보았다. 우리는 그렇지 않음을 보였다. 응답성과 무결성을 서로 다른 층에 두는 것(추론은 병렬이며 결코 막히지 않고, 부수효과는 직렬이며 결코 동시가 아니다)은 여러 인간이 진짜로 공유하는 세션을 낳는다: 모두의 질문이 각자의 속도로 답변되고(TTFT 기울기 0.000), 어떤 파일도 경합으로 손상되지 않으며(락 해제 시 최대 74% → 0%), 모든 답변이 질문자에게 귀속되고, 모든 참여자가 남의 것은 건드리지 않고 자기 작업을 멈출 수 있다. 그리고 계약은 이식 가능하다: Coagora 는 두 번 지어진 하나의 시스템이고, 서로소인 위험 집합, 이벤트루프 대신 스레드, 메시지 전달 대신 공유 메모리로 불변식에서 재구축된 두 번째 런타임은 모든 대표 수치를 재현하며(기울기 0.000, 락 적용 0%), 턴이 도는 동안 공유 컨텍스트를 압축 가능하게 유지하고, 귀속을 휴리스틱이 아니라 정확하게 만든다. §3 의 설계 공간은 이 좌표가 비어 있었다고 말하고; Coagora 는 살 만하다고 말하고; 두 런타임 모두에서 나온 측정은 살 가치가 있다고 말한다.

풀지 못한 것에는 이름을 붙였다. 공유 세션은 비대칭 그라운딩을 발급하고, "자기 턴을 소유하라"보다 풍부한 제어 중재 정책을 요구하며, 동료 책임감이 기계 속도를 견디는지 시험한다. 이것들은 멀티플레이어 에이전트의 결함이 아니다; 에이전트가 멀티플레이어가 되는 순간 열리는 분야다. 시스템, 하네스, 원시 데이터는 우리 것을 포함해 그 작업을 위해 공개되어 있다.
