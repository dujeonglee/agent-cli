## 초록

코딩 에이전트는 보통 한 사람이 하나의 대화와 작업 폴더를 관리한다고 가정한다. 팀 연동은 별도 작업을 시작할 수 있지만 여러 사람이 실행 중인 같은 에이전트와 일하게 하지는 않는다. 실시간 공유 세션은 요청을 줄 세우거나 함께 실행되는 작업을 조정해야 한다.

본 논문은 여러 개발자가 하나의 대화와 작업 폴더를 공유하는 코딩 에이전트 Coagora를 제시한다. 각 요청에는 요청자가 표시된 별도 응답이 생기며 모델 호출은 함께 실행할 수 있다. 각 호출의 입력은 호출 시작 시점의 공유 대화에서 구성한다. 다른 활성 턴의 부분 출력은 제외하고, 완료된 턴은 이후 호출에서 사용할 수 있다. assistant의 도구 호출과 그에 대응하는 도구 결과는 중간에 다른 턴의 기록이 끼지 않는 하나의 이력 블록으로 저장한다. 충돌하는 파일 변경은 하나씩 실행하고 다른 파일의 변경은 함께 진행할 수 있다.

통제 실험에서 첫 번째 사용자의 작업이 1초 늘 때마다 요청을 줄 세우거나 재시도할 때는 두 번째 사용자의 대기도 약 1초 늘었지만, 함께 실행할 때는 측정 가능한 증가가 없었다. 실모델의 중앙 대기시간은 20개 paired block에서 42.1초에서 11.7초로 줄었다. 변경 게이트는 30회 모두에서 두 Coagora 도구가 같은 파일을 동시에 쓰지 못하게 했다. 세 질문 작업에서 요청을 함께 실행하면 입력 토큰을 1.49배 더 사용했다.

Coagora는 요청자 표시, turn-local 대화 보기, 승인 파일에 대한 검증된 반영을 결합한다. 실모델 요청 쌍 60개에서 모든 과제 파일과 최종 폴더가 올바랐고, 다른 활성 요청을 숨기자 응답의 교차 과제 언급이 사라졌다. 의도적으로 어려운 상황 19개는 모든 변경이 Coagora 도구를 사용하고 경로가 안정적일 때 요청이 승인 목록 안의 검사된 파일만 반영함을 확인했다.

## 1 서론

코딩 에이전트는 이제 저장소를 읽고, 파일을 수정하고, 명령과 테스트를 실행하며, 제한된 감독 아래 풀 리퀘스트를 연다 [1, 2]. 연구와 텔레메트리는 에이전트가 상당한 작업을 완수할 수 있고 사용자가 실행 중인 에이전트를 자주 수정하거나 방향 전환한다는 점을 보여준다 [2, 3]. 그러나 그 상호작용 모델은 거의 전적으로 싱글플레이어다. 한 사람이 프롬프트, 컨텍스트, 제어권을 소유한다.

소프트웨어 개발은 협업 활동이다. 여러 제품이 Slack이나 Teams에서 에이전트를 호출할 수 있게 했고 [6, 14–18], 사용자들은 하나의 코딩 에이전트 세션에 Google Docs처럼 함께 접근하는 기능을 요청했다 [5]. 현재 배포된 메신저 패턴은 유용하지만 공동 작업이라기보다 위임에 가깝다. 멘션이 캡처한 스레드로 클라우드 작업을 시작하고, 에이전트는 다른 곳에서 일한 뒤, 풀 리퀘스트를 반환한다. 참가자는 보통 실행 중에 개입할 수 없으며, 두 사람이 동시에 행동할 때 적용되는 일반 규칙도 공개 문서에서 찾기 어렵다.

실시간 공유 세션은 대화, 파일, 제어 기능을 한곳에 둔다. 동시에 조정 문제가 생긴다. 시스템이 요청을 하나씩 처리하면 짧은 질문이 긴 빌드 뒤에서 기다릴 수 있다. 별도 세션은 상태를 격리하고 나중에 결과를 조정하며, Coagora는 하나의 실시간 대화와 작업 폴더 안에서 요청이 겹칠 때 적용하는 계약을 다룬다.

Coagora는 세 번째 방법인 **모델 요청은 함께 실행하되 공유 변경은 조정하는 방식**을 탐구한다. 모든 메시지는 *턴*이라 부르는 별도 응답 스트림을 만든다. 모든 턴은 같은 저장된 대화와 작업 폴더를 사용한다. 턴 식별자는 각 응답, 도구 호출, 결과, 취소 동작을 요청자와 연결한다. 모델은 여러 턴을 함께 처리할 수 있지만 충돌하는 파일 변경은 하나씩 실행하고 완료된 대화 항목은 온전한 단위로 저장한다.

이 설계는 익숙한 데이터베이스와 운영체제 메커니즘을 모델 호출 아래에 적용한다 [11]. 인터페이스의 응답성을 유지하고, 누가 각 동작을 요청했는지 보존하며, 활성 요청의 문맥을 분리하고, 변경이 공유 폴더에 도달하기 전에 파일 반영을 검증한다.

본 논문은 세 가지 기술 질문과 나중에 수행할 한 가지 인간 질문을 다룬다.

- **RQ1 — 응답성.** 다른 요청이 이미 실행 중일 때 새 요청은 얼마나 기다리는가?
- **RQ2 — 안전한 공유 변경과 비용.** 어떤 변경을 하나씩 실행해야 하며 성능과 토큰 비용은 얼마인가?
- **RQ3 — 요청 소유권과 분리.** 한 활성 요청이 다른 요청에 영향을 줄 수 있으며 어떤 보호 장치가 그 영향을 제한하는가?
- **RQ4 — 첫 사용.** 쌍을 이룬 참가자는 실시간 세션을 공유하면서 무엇을 알아차리고, 추론하고, 행동하는가? §6은 계획된 연구를 위해 이 질문을 예약한다.

세 요청 처리 방식은 같은 서버, 대화 관리자, 도구, 측정 기능을 사용하는 하나의 시스템에서 실행된다. 통제 실험은 시스템 동작을 검증하고 실모델 실험은 모델이나 서빙 시스템에 따라 달라질 수 있는 행동을 측정한다.

본 논문의 기여는 다음과 같다.

1. 공유 상태가 어디에 있는지, 동시 요청을 어떻게 처리하는지, 소유권을 어떻게 보여주는지, 사람이 언제 개입할 수 있는지를 묻는 **설계 공간**.
2. 응답 분리, 안전한 대화 저장, 파일 변경 조정, 공정한 대기열, 재연결 복구, 자기 요청 취소를 결합한 **동작하는 공유 세션 설계**.
3. 대기시간, 토큰 사용, 호출 시점의 대화 보기, 파일 충돌 방지, 요청별 파일 제한을 포함한 **설계의 이점과 운영 tradeoff에 대한 측정**.

계획된 첫 사용 연구는 사람들이 협업에서 이 tradeoff를 어떻게 이해하고 관리하는지에 대한 증거를 더할 것이다.

## 2 관련 연구와 설계 공간

### 2.1 개인용 에이전트에서 팀 접근으로

AI 페어 프로그래밍 연구는 대개 한 개발자와 한 어시스턴트 또는 에이전트를 다룬다. Copilot은 인간 페어 프로그래밍보다 산출량을 늘리면서 품질을 낮출 수 있고 [12], 개발자는 AI 제안을 인간의 제안과 다르게 검토하며 [1], 에이전트 행동을 이해하기 어렵다는 점은 도입 장벽으로 남아 있다 [2]. 실제 에이전트 세션 6,000개에서 사용자는 가능한 기회의 39%에서 에이전트를 중단하거나 방향 전환했다 [3]. 이 결과는 조향이 중요함을 보여주지만 제어자는 한 사람이라고 가정한다.

팀 접근은 메신저 연동을 통해 나타나고 있다. GitHub Next Ace, Claude Tag, Codex, GitHub Copilot, Devin, Cursor, OpenTag, 별도 Git worktree에서 작업을 실행하는 도구의 공개 문서를 검토했다 [4, 6, 9, 10, 13–18]. 검토 시점은 2026년 8월 13일로 고정했다. 공개 문서가 대화 또는 파일 상태의 위치와 동시 요청 처리, 보이는 소유권, 개입 중 하나 이상을 함께 설명할 때 포함했다. 문서화된 팀 진입점이 없는 개인용 도구는 제외했다. 포함한 출처가 답하지 않는 필드는 시스템을 표에서 빼는 대신 문서화되지 않음으로 남겼다.

네 축은 두 단계로 도출했다. 먼저 제품 문서에서 상태 위치와 busy-request 처리를 귀납적으로 코딩했다. 다음으로 CSCW의 awareness와 mixed-initiative control 개념 [36–40]에서 소유권과 개입을 추가하고 모든 시스템을 네 축으로 다시 코딩했다. 문서에 없는 내용은 기능 부재가 아니라 *문서화되지 않음*으로 기록한다. 부록 B는 출처 snapshot과 포함 결정을 남긴다. 이 표는 공개 문서의 범위가 정해진 분석 비교이며 체계적 시장 조사나 novelty 증명이 아니다.

다섯 메신저 연동은 비슷한 경로를 따른다. 멘션, 스레드 캡처, 클라우드 작업, 풀 리퀘스트 링크다. 신원과 지속 방식은 다르지만 실시간 상호작용 경계는 비슷하다. GitHub는 전체 스레드가 결과 풀 리퀘스트에 저장될 수 있다고 경고하며 [7], Slack AI를 통한 간접 프롬프트 주입은 채널을 모델 컨텍스트로 취급할 때 보안 문제가 생김을 보여준다 [19]. Claude Tag는 공유 채널 인스턴스를 멀티플레이어라고 설명하지만 동시 지시에 대한 프로토콜은 공개하지 않는다 [6].

### 2.2 여러 사람과 하나의 AI

가장 가까운 인간 중심 연구는 공동 글쓰기, 그룹 대화, 교육에서 찾을 수 있다. 다중 사용자 글쓰기 환경에 배치된 에이전트는 개인 작업공간인 동시에 팀의 공유 자원이 되었다 [20]. 그룹 대화 연구는 AI 참가자가 언제, 어디서, 어떻게 응답해야 하는지 연구했고 [21], GroupMemBench는 다자 대화에서 메모리가 여전히 어렵다는 점을 보여준다 [22].

프로그래밍 교육에서 Daryanto 등은 한 인간/한 AI 구성과 두 인간/한 AI 구성을 비교했다 [23]. 동료에게 보인다는 사실은 참가자가 AI 제안을 더 주의 깊게 살피게 했다. 그러나 그 시스템은 제안형이었고, 작업은 파일 및 셸 접근이 있는 지속적 자율 에이전트가 아니라 일회성 학습 과제였다. 에이전트가 작성한 풀 리퀘스트 연구 역시 실행 후 에이전트의 산출물 주위에서 일어나는 협업을 다룬다 [24]. 여러 사람이 실시간 실행 자체를 공유하지는 않는다. 더 일반적으로도 인간-에이전트 상호작용 공개 데이터는 부족하다 [25].

이 연구들은 인식, 책임성, 제어에 관한 질문을 제기하지만 공유 코딩 작업공간을 위한 동시성 계약은 제공하지 않는다.

### 2.3 공유 에이전트 상태의 동시성

여러 AI 에이전트를 실행하는 시스템에도 공유 파일을 조정하는 방법이 있다. CoAgent는 충돌 뒤에 일련의 동작을 되돌릴 수 있고 [11], STORM은 파일을 쓸 때 충돌 편집을 찾는다 [26]. Worktree 기반 도구는 에이전트마다 별도 브랜치를 주고 나중에 합친다 [10]. DeLM은 여러 에이전트가 정보를 공유하게 하되 출력의 근거 여부를 검사한다 [27]. 이 시스템들은 하나의 목표를 수행하는 여러 에이전트를 조정한다. Coagora는 하나의 에이전트 세션에 요청을 보내는 여러 사람을 조정한다.

프레임워크는 대화가 바쁠 때의 처리 방식도 다르다. LangGraph는 새 요청을 거절하거나, 줄 세우거나, 중단하거나, 되돌릴 수 있다 [8]. OpenTag는 대화마다 하나의 요청만 실행하고 다른 요청에는 HTTP 409 응답을 보낸다 [9]. Justitia 같은 스케줄러는 여러 작업에 모델 처리 용량을 나누고 [28], 병렬 context compaction은 다중 사용자 상호작용 계약을 정하지 않은 채 서빙 지연을 줄인다 [29]. Coagora는 같은 세션에 함께 있는 사람들이 접근 기회를 어떻게 나눌지를 묻는다.

Coagora는 확립된 메커니즘을 사용한다. 각 모델 호출은 호출 시작 시점의 공유 대화를 읽고, assistant의 도구 호출과 그에 대응하는 도구 결과는 끊기지 않는 이력 블록으로 저장하며, 충돌하는 파일 변경에는 락을 사용한다 [32–35]. 기여는 이 메커니즘을 사용하면서도 한 사람의 모델 응답 전체가 끝날 때까지 다른 사람이 기다리지 않게 하는 데 있다.

### 2.4 네 가지 설계 질문

조사한 시스템을 네 질문으로 비교한다.

1. **공유 상태의 위치:** 대화는 다른 곳의 작업을 시작하기만 하는가, 아니면 실행 중인 세션 자체를 보여주는가?
2. **동시 요청 처리:** 새 요청을 거절하거나, 줄 세우거나, 합치거나, 나중에 합칠 별도 작업으로 실행하거나, 현재 요청과 함께 실행하는가?
3. **보이는 소유권:** 인터페이스가 풀 리퀘스트, 과제, 메시지, 개별 응답 중 어느 단위의 소유자를 표시하는가?
4. **개입 기회:** 사용자는 과제 전후에만, 세션 전체에서, 또는 자신의 요청에만 개입할 수 있는가?

| 시스템 | 작업이 있는 곳 | 바쁠 때 새 요청 | 보이는 소유자 | 사용자가 개입하는 시점 |
|---|---|---|---|---|
| GitHub Next Ace [4] | 실시간 공유 workspace | 동시 agent 요청은 문서화되지 않음 | 문서화되지 않음 | 실행 중, 공유 terminal/editor |
| Claude Tag [6] | 분리 | 동시 입력에 대해 문서화되지 않음 | 작업 / 조직 | 전 또는 후 |

| Coagora 직렬 | 실시간 세션 | 줄 세움, 도구 경계에서 삽입 | 응답 / 요청자 | 세션 조향 |
| **Coagora 병렬** | **실시간 세션** | **함께 실행, 변경 조정** | **응답 / 요청자** | **자기 응답 취소** |

문서화된 메신저 연동은 주로 별도 작업을 시작하고, 과제 단위로 소유자를 표시하며, 실행 전후에만 개입하게 한다. Coagora는 하나의 실시간 대화에서 요청자별 응답을 함께 실행하고 각자 자기 응답을 취소하는 방식을 연구한다. 표는 검토한 문서를 설명하며 문서에 없거나 미래에 나올 시스템까지 판단하지 않는다.

CSCW 연구는 이런 선택이 중요한 이유를 설명한다. 협업자는 작업에 대한 공통 이해 [36], 누가 무엇을 하는지에 대한 인식 [37, 38], 과제를 나누고 조정하는 방법 [39]이 필요하다. 혼합 주도권 시스템은 AI가 언제 행동하거나 질문할지도 정해야 한다 [40]. 여러 사용자가 있으면 누구에게 물을지, 누가 행동을 멈출 수 있을지도 결정해야 한다. §7은 이 개념으로 기술 결과를 해석하고 §6은 사용자 대상 연구를 위해 남겨 둔다.

## 3 하나의 공유 세션이 동작하는 방식

### 3.1 요청 하나에 요청자가 표시된 응답 하나

세션은 하나의 저장된 대화, 하나의 작업 폴더, 현재 실행 중인 모든 요청으로 구성된다. 참가자는 같은 세션에 접속하며, 새 참가자가 들어와도 개인용 복사본은 생기지 않는다.

받아들인 모든 메시지는 하나의 응답과 그 응답에 필요한 도구 사용을 포함하는 *턴*을 만든다. 턴에는 고유 식별자가 있으며 스트리밍 텍스트, 도구 호출, 결과, 오류, 저장된 이력에 함께 기록된다. 따라서 인터페이스는 동시에 나오는 응답을 요청자 이름이 있는 별도 카드로 보여줄 수 있다.

참가자는 자신의 활성 턴만 취소할 수 있다. 이 요청자 범위의 취소는 이미 보인 출력을 남기고 처리 슬롯을 비우며 다른 턴은 계속 실행한다.

[FIGURE TODO: 두 참가자가 동시에 요청하는 모습, 요청자가 표시된 별도 응답 스트림, 하나의 공유 대화, 변경 게이트를 보여준다. 비교를 위해 요청을 줄 세우는 타임라인을 옆에 둔다.]

### 3.2 공유 대화와 호출 시점의 문맥

세션에는 모든 참가자가 공유하는 하나의 영구 대화 이력이 있다. Coagora는 각 모델 호출 직전에 그 시점의 대화 이력으로 호출 입력을 구성한다. 호출이 시작되면 입력은 고정된다. 동시에 실행 중인 다른 턴의 부분 출력은 포함하지 않으며, 호출 시작 뒤 저장된 기록도 해당 호출 입력에 소급해 추가되지 않는다. 현재 턴에서 다음 모델 호출이 발생하면 입력을 다시 구성하므로, 그사이에 완료된 다른 턴의 기록을 볼 수 있다.

동시 실행 중에는 turn-local context가 아직 활성 상태인 다른 턴의 기록을 제외한다. 다른 턴이 완료되면 그 기록은 공유 이력에 남아 이후 모델 호출에서 사용할 수 있다. assistant의 도구 호출과 그에 대응하는 도구 결과는 끊기지 않는 하나의 이력 블록으로 저장하며, 그 블록 안에는 다른 턴의 기록이 삽입되지 않는다.

따라서 동시에 실행되는 두 모델 호출은 같은 이전 상태에서 시작할 수 있다. Coagora는 RQ2의 변경 게이트로 그 효과를 조정한다. 충돌하는 파일 동작은 하나씩 실행하고, 강제 모드는 제공된 과제 검사를 통과한 승인 파일만 반영한다.

### 3.3 작업 폴더 변경 조정

응답 생성은 느리지만 그 자체로 파일을 바꾸지는 않는다. 파일 편집과 명령은 대개 더 짧지만 서로 충돌할 수 있다. Coagora는 모델 생성을 함께 진행하고 작업 폴더를 바꾸는 각 동작을 실행 전에 검사한다. 이 검사를 *변경 게이트*라고 부른다.

| 요청된 두 동작 | 정책 | 이유 |
|---|---|---|
| 서로 다른 파일 읽기 또는 쓰기 | 함께 실행 가능 | 파일이 충돌하지 않음 |
| 같은 파일의 동작 | 하나씩 실행 | 변경이 겹치지 않게 함 |
| 셸 명령, 패키지 작업, 삭제 | 폴더를 단독 사용 | 어떤 파일이 바뀔지 모를 수 있음 |
| 더 작은 도구로 구성된 도구 | 실제 파일 동작마다 검사 | 전체 도구가 게이트를 잡으면 무기한 막을 수 있음 |
| 파일을 바꿀 수 있는 새 동작 또는 분류되지 않은 동작 | 폴더를 단독 사용 | 안전한 기본값을 선택 |

경로를 비교하기 전에 상대 경로와 symbolic link를 실제 위치로 바꾼다. 여러 hard-link 이름을 가진 파일은 경로만으로 안전하게 비교할 수 없으므로 폴더 전체를 단독 사용한다. 대기 동작은 도착 순서대로 처리한다. 이 때문에 안전한 파일 편집이 앞선 셸 명령 뒤에서 기다릴 수 있지만 작은 편집이 계속 들어와 셸 명령을 끝없이 미루지는 못한다.

변경 게이트는 Coagora를 통한 충돌 편집을 직렬화하므로 앞선 동작이 해당 경로를 해제한 뒤 다음 동작이 시작된다. RQ2는 이 writer-ordering invariant를 외부 읽기 가시성과 최종 파일 상태에서 분리해 측정한다.

### 3.4 공정한 접근, 재연결, 재개

기본적으로 턴은 최대 네 개까지 함께 실행된다. 추가 요청은 도착 순서대로 기다리고 참가자마다 한 개의 턴만 활성화할 수 있다. 따라서 한 사람이 많은 요청으로 모든 처리 슬롯을 차지할 수 없다. 작업 폴더를 단독 사용 중인 셸 명령은 도착 순서를 유지하며 이후 파일 동작은 그 뒤에서 기다린다.

서버는 저장 이벤트마다 번호를 붙인다. 연결이 끊긴 브라우저는 마지막으로 받은 번호 이후의 이벤트를 요청할 수 있다. 번호가 너무 오래됐거나 이전 서버 프로세스의 것이면 전체 세션 보기를 새로 받는다. 유휴 세션을 중단했다가 재개해도 이력과 작업 폴더는 남는다.

## 4 구현

Coagora는 터미널 인터페이스와 같은 로컬 네트워크의 여러 사람이 접속하는 웹 인터페이스를 제공하는 Python 코딩 에이전트다. 하나의 운영체제 프로세스가 공유 대화와 작업 폴더를 소유하고 활성 턴마다 별도 스레드를 사용한다.

모델 호출 전에 대화 관리자가 저장된 이력으로 고정된 호출 입력을 구성한다. 각 턴에는 요청자 표시와 자체 시스템 지시가 있다. 선택적인 비공개 보기는 아직 실행 중인 다른 턴이 만든 메시지를 제거한다. 턴이 끝나면 그 메시지는 이후 모델 호출에 다시 보인다. 어느 턴에서 나온 내용인지 알 수 없는 공유 요약은 비공개 보기를 사용할 때 숨긴다.

강제 모드는 요청과 함께 바꿀 수 있는 파일 목록과 예상 결과 검사 두 가지를 요구한다. Coagora는 그 파일을 턴에 예약하고 편집을 비공개 임시 복사본에 저장한다. 턴은 자기 임시 편집을 읽을 수 있지만 다른 턴에서는 보이지 않는다. 모델이 끝나면 과제 검사가 통과하는지와 그동안 원본 파일이 다른 곳에서 바뀌지 않았는지 확인한다. 이후 승인된 파일을 각각 교체한다. 어느 검사든 실패하면 임시 파일을 공유 폴더에 반영하지 않는다.

변경 게이트는 각 도구에서 영향을 받는 경로를 받는다. Symbolic link를 실제 위치로 바꾸고, hard-link 이름이 여러 개인 파일이나 영향 경로를 알 수 없는 동작에는 폴더 단독 사용 권한을 준다. 복합 도구는 내부 파일 동작이 실행될 때만 권한을 요청한다. 평가한 파일시스템에서 직접 동시 append 동작이 달랐기 때문에 저장 이벤트 로그에는 추가 락을 사용한다.

브라우저는 번호가 붙은 이벤트 스트림을 계속 받고 마지막으로 본 이벤트부터 재연결한다. 공유 쓰기 토큰은 요청과 변경을 허용한다. 선택적 읽기 전용 토큰은 공유 세션을 보는 권한과 요청·파일 변경·숨은 지시 및 파일 읽기 권한을 분리한다.

서버는 요청, 도구 사용, 대기, 오류, 토큰 사용, 검사, 파일 반영의 시간과 식별자를 기록한다. 측정 로그에는 프롬프트나 응답 텍스트를 넣지 않는다. 첫 토큰 도착 시간은 서버가 사용자의 요청을 처음 받은 시점부터 계산한다. 거절 후 재시도 조건에서는 재시도 시간도 포함한다.

통제 실험은 실제 서버를 사용하고 모델만 예측 가능한 로컬 시험 모델로 바꾼다. 각 조건은 새 작업 폴더와 사용자 디렉터리를 사용한다. 자연스러운 모델 행동이나 서버 부하에 의존하는 실험은 온프레미스 실모델을 사용한다. 부록 A는 각 결과를 원자료와 재현 스크립트에 연결한다.

## 5 기술 평가

시스템이 어떻게 동작하고 사용자가 얼마나 기다리며 안전 검사가 어디까지 적용되는지 평가한다. HCI 시스템과 툴킷 평가 지침 [41]에 따라 통제 실험은 메커니즘을 검증하고 실모델 실험은 배치 환경에 따라 달라지는 행동을 시험한다. 협업 결과는 계획된 사용자 연구에서 다룬다.

비교는 같은 프로그램에서 시험 정책만 바꾼다. 한 시험 안의 개별 관측이 아니라 완전한 시험 한 번을 분석 단위로 사용한다. 예/아니요 결과에는 exact 95% 신뢰구간을 보고하고 같은 시험에서 두 정책을 비교할 때 exact paired 검정을 사용한다. 한 시험 안의 고빈도 관측은 설명용이다. 예상 결과가 완전히 정해진 검사는 실제 발생률 추정이 아니라 소프트웨어 검증으로 해석한다.

실모델 TTFT 실험은 Apple M3 Ultra, 80 GPU core, 256 GB 통합 메모리에서 실행되는 OpenAI 호환 oMLX 0.5.7 endpoint를 사용했다. 서버는 `unsloth/Qwen3.6-27B-MLX-8bit`(32.92 GB, model context 262,144 token)를 load했고, 최대 동시 요청은 8, cache는 켬, chunked prefill은 끔, burst decoding은 balanced였다. Agent-cli는 `/v1/chat/completions`를 `json_fc` text wire format으로 stream하고 thinking을 껐다. Agent-cli는 65,536 output token을 요청했고 서버는 설정된 최대값을 32,768 token으로 보고했다. Temperature, top-p, seed request field는 생략했다. Model override와 서버 기본값에 따른 유효 temperature는 0.2, top-p는 0.95였고 sampling seed는 없었다.

수집 기간은 UTC 2026-08-13 15:13:02–15:42:15였다. 20개 paired block마다 serial과 parallel을 한 번씩 실행했고 seed 20260813으로 첫 arm을 10:10 균형화했다. 각 run은 새 agent process, session, 사용자 디렉터리, workspace를 사용했다. 보존한 manifest로 model capability를 미리 넣어 startup warm-up model request가 없게 했다. 모든 run에서 endpoint request count 증가는 측정한 model call 두 번과 정확히 같았고, 각 run 경계에서 endpoint의 active/waiting request는 0이었다. 계획한 40개 run은 모두 첫 시도에 유효했고 실패·제외는 없었다. Artifact에는 전체 arm 순서, UTC timestamp, run 전후 서버 상태, 환경 manifest, raw TTFT, `agent_cli/**/*.py`·collector·driver를 포괄하는 digest를 저장했다. P1 isolation 실험은 별도로 20개 block에서 세 arm의 여섯 순서를 균형화했고 60/60 run이 첫 시도에 유효했으며 누락은 없었다.

### 5.1 RQ1: 새 요청은 얼마나 기다리는가?

#### 긴 작업 뒤에서 기다리기

사용자 A가 2, 6, 15, 30초 중 하나의 길이를 가진 작업을 시작한다. 사용자 B는 0.5초 뒤 한 줄 질문을 한다. B를 A 뒤에 줄 세우기, 성공할 때까지 B를 거절하고 재시도하기, 두 요청을 함께 실행하기를 비교한다. 240회 중 236회에서 B의 요청에 연결할 수 있는 첫 응답 토큰을 얻었다.

| 정책 | A: 2 s | A: 6 s | A: 15 s | A: 30 s | A의 1초당 추가 대기 |
|---|---:|---:|---:|---:|---:|
| 직렬 | 2.08 s | 6.16 s | 15.34 s | 30.86 s | 1.028 |
| 거절 + 재시도 | 2.31 s | 6.34 s | 15.42 s | 31.05 s | 1.027 |
| **병렬** | **0.292 s** | **0.291 s** | **0.291 s** | **0.235 s** | **−0.002** |

30초 조건은 설정 시간이 56 ms 더 짧은 두 번째 세션에서 실행했다. 대조 실험에서 이 일정한 차이가 재현됐으며 같은 조건 안의 비교와 A의 작업 길이에 따른 변화에는 영향을 주지 않는다. 첫 토큰을 귀속할 수 없었던 네 번은 reject 2초·15초와 parallel 2초·6초에서 각각 한 번씩 발생했다. Artifact는 missing outcome을 기록하지만 timeout, parsing, streaming 중 원인은 남기지 않았으므로 느린 응답으로 바꾸지 않고 누락으로 보고한다. 각 affected cell에는 20회 중 19회가 남는다. 누락이 없는 level만 사용한 sensitivity slope도 reject 1.030(6초와 30초), parallel −0.004(15초와 30초)로 결론을 유지한다.

요청을 줄 세우거나 반복해서 재시도하면 A의 작업이 1초 늘 때마다 B의 대기도 약 1초 늘어난다. 재시도는 지연도 더한다. 15초 작업에서 250 ms와 1,000 ms 간격으로 재시도하면 줄 세우기보다 각각 172 ms와 794 ms 더 기다렸고 61회와 16회 시도했다. 두 요청을 함께 실행하면 B의 대기는 A의 작업 길이에 따라 늘지 않는다.

줄 세우기 방식은 A가 도구를 호출하는 시점에 B의 질문을 넣을 수 있다. 따라서 B는 항상 전체 작업이 아니라 A가 중단 없이 실행하는 현재 구간을 기다린다. A의 전체 작업을 15초로 고정하고 도구 호출 수를 바꿨다.

| A의 도구 호출 수 | 가장 긴 무중단 구간 | A가 끝나기 전 B 삽입 | B가 모델 요청에 들어갈 때까지 |
|---:|---:|---:|---:|
| 1 | 15.0 s | 0/10 | 15.10 s |
| 2 | 7.5 s | 10/10 | 7.30 s |
| 4 | 3.75 s | 10/10 | 3.39 s |
| 8 | 1.875 s | 10/10 | 1.44 s |

이 측정은 B가 답을 받기 전인 모델 입력 시점에 끝난다. 도구를 여덟 번 호출해도 같은 작업 길이에서 병렬 방식의 첫 토큰 시간보다 4.9배 길다. 줄 세우기는 A가 도구를 자주 호출할수록 나아지고, 긴 생성·빌드·테스트 중에는 전체 작업을 기다리는 것에 가까워진다.

모두 바로 시작하도록 대기열 상한을 올린 뒤 전체 사용자를 2명, 4명, 8명으로 늘리면 질문자의 첫 토큰 시간은 236 ms, 265 ms, 328 ms가 되었다. 일곱 명이 동시에 질문해도 7배가 아니라 39% 늘었다. 이 남은 지연은 요청 정책이 아니라 공유 컴퓨팅 자원 때문에 생긴다.

#### 실모델과 토큰 사용

실모델에서 A가 긴 응답을 시작한 지 2초 뒤 B가 질문했다. 20개 paired block에서 B의 중앙 첫 토큰 시간은 **줄 세우기 42.1초, 함께 실행하기 11.7초**였다. 관측 범위는 29.8–57.5초와 7.6–15.3초였고 fixed-seed percentile-bootstrap 중앙값 95% 구간은 41.61–43.70초와 11.20–12.19초였다. 모든 20개 block에서 parallel이 빨랐으며 block별 speedup 중앙값은 3.619배(범위 3.331–4.247배)였다. 이 구간은 manifest에 기록한 배치 환경의 runtime variation을 나타내며 다른 서버나 모델로의 일반화 구간은 아니다.

공유 모델 서버의 처리 용량이 남은 지연을 결정한다. Coagora 없이 응답 여덟 개를 동시에 생성하면 하나보다 2.68배 오래 걸렸고 초당 전체 출력은 약 세 배였다. Coagora가 B의 요청을 즉시 전달한 뒤 모델 서버가 동시 inference 작업을 스케줄한다.

요청을 함께 실행하면 모델 호출 수도 늘어난다. 같은 세 질문에서 줄 세우기 방식은 작업을 2회 호출로 합쳐 입력 토큰 15.6K를 사용했고, 병렬 방식은 3회 호출과 23.2K 토큰을 사용했다. **1.49배**다. 앞선 턴이 다섯 개 있어도 비율은 1.47배였다. 더 빠른 접근에는 더 많은 입력 토큰이 든다.

### 5.2 RQ2: 충돌하는 파일 변경 막기

#### 변경 게이트가 막는 것

이 실험은 두 Coagora 도구가 같은 파일을 강제로 덮어쓰게 한다. 각 정책은 새 프로세스와 폴더에서 30회 실행하고 정책 순서를 무작위화한다. Coagora 밖의 별도 프로그램이 2 ms마다 파일을 읽는다. 두 도구가 동시에 쓰는지, 외부 프로그램이 두 쓰기 내용이 섞인 파일을 보는지, 최종 파일이 올바른지를 측정한다.

| 30회 시험의 결과 | 게이트 없음 | 폴더 전체에 락 하나 | 충돌 파일만 락 |
|---|---:|---:|---:|
| Coagora 도구가 동시에 씀 | 30/30 | 0/30 | 0/30 |
| 외부 프로그램이 두 쓰기가 섞인 내용을 봄 | 27/30, 95% CI [73.5%, 97.9%] | 0/30, [0%, 11.6%] | 0/30, [0%, 11.6%] |
| 최종 파일에 두 쓰기가 섞임 | 3/30 | 0/30 | 0/30 |
| 외부 프로그램이 빈 파일 또는 일부만 봄 | 29/30 | 30/30 | 29/30 |

두 락 정책 모두 시험에서 섞인 쓰기를 없앴다(게이트 없음 대비 paired exact p = 1.49 × 10⁻⁸). 1, 5, 10 ms마다 읽어도 같은 패턴이었다. 게이트 없음에서는 각각 24/30, 24/30, 13/30회 섞인 내용을 봤고 두 락에서는 없었다. 직접 덮어쓰기를 읽을 때 나타난 빈 파일이나 일부만 기록된 중간 상태는 모든 정책에서 관찰됐으므로 writer-ordering invariant와 분리해 보고한다.

#### 폴더 전체 락이 비싸지는 시점

다음 실험은 각 턴에서 응답 생성 대신 파일 변경에 쓰는 시간의 비율을 바꾼다. 각 run의 useful work는 턴의 wall-clock span에서 lock 대기를 뺀 값이다. Effective parallelism은 `(work_A + work_B) / makespan`이며 1은 유용한 겹침이 없음, 2는 완전한 겹침을 뜻한다. 측정 effect share는 `전체 lock-held time / (work_A + work_B)`다. 아래 목표 비율은 inference 구간과 파일 effect를 번갈아 실행하도록 calibration한 값이며 측정 중앙값은 25% 목표의 0.226부터 서로 다른 경로 90% 목표의 0.824까지였다.

두 개의 같은 길이 턴, 완전한 overlap, 이 교대 단계 구조에서는 effect가 모두 직렬일 때 analytic ceiling이 effect share `s`에 대해 `2 / max(1, 2s)`다. 따라서 50% knee는 이 two-turn model의 성질이며 보편적 경계가 아니다. 표는 cell별 독립 5회의 중앙값과 전체 범위를 보고한다. 마지막 열은 두 중앙값의 비율이다.

| 목표 effect share | 두 턴이 쓰는 파일 | 폴더 락 중앙값 [범위] | 충돌 락 중앙값 [범위] | 비율 |
|---:|---|---:|---:|---:|
| 25% | 서로 다름 | 1.987 [1.983, 1.988] | 1.992 [1.990, 1.992] | 1.00× |
| 50% | 서로 다름 | 1.974 [1.973, 1.976] | 1.983 [1.961, 1.985] | 1.01× |
| 75% | 서로 다름 | 1.662 [1.656, 1.671] | 1.977 [1.974, 1.980] | 1.19× |
| 90% | 서로 다름 | 1.368 [1.366, 1.369] | 1.983 [1.977, 1.985] | 1.45× |
| 90% | 같은 경로 | 1.369 [1.367, 1.371] | 1.368 [1.364, 1.370] | 1.00× |

두 턴이 같은 파일을 쓰면 어느 정책이든 기다려야 하므로 성능이 비슷하다. 다른 파일을 쓰면 충돌 파일만 잠그는 방식은 가능한 최대 겹침에 가깝다. 이 방식의 이득은 파일 변경이 턴 대부분을 차지할 때 크게 나타난다.

실모델 턴은 파일 도구 안에서 거의 시간을 쓰지 않았다. 약 4분 동안 파일 쓰기 여덟 번은 전체 턴 시간의 10⁻⁵를 사용했고 락 대기 중앙값은 0.1 ms였다. 셸 명령은 폴더를 단독 사용하므로 영향이 더 컸다. 1초 명령 세 개는 턴의 2.5%를 사용하고 측정 가능한 대기를 만들지 않았지만, 5초 명령 세 개는 9.4%를 사용하고 약 4.1초의 대기를 만들었다. 이 워크로드에서는 일반 파일 편집보다 셸 명령이 락 대기의 주원인이었다.

### 5.3 보조 불변식 검증

다음 실험은 모든 계약에 필요한 substrate 속성을 검사한다. 별도 연구 질문이 아니라 구현 검증이며 상세 절차와 원자료는 부록 A에 있다.

| 속성 | 검사 | 결과 |
|---|---|---|
| 재연결 | 90턴, 지속 연결 대 11회 연결 해제/재연결 | 이벤트 180개가 모두 같은 순서로 돌아왔고 누락·중복 없음 |
| 짧은 대화 요약 | 사용자 3명 × 30라운드, 각 요약 800 ms | 질문 90개 모두 보존; 새 이벤트 42개가 들어오는 동안 요약 4개 모두 저장 |
| 실모델 대화 요약 | 사용자 3명 × 8라운드, 요약 56–123초 | 질문 24개 모두 보존; 요약 2/5개 저장, 3개는 새 메시지가 들어와 폐기 |
| 요청자 표시 | 사용자 4명 × 25라운드 | 질문 100개가 각각 응답 하나에 연결됐고 누락·중복 없음 |

| 공정한 접근 | 한 사용자는 요청을 많이 보내고 다른 사용자는 짧은 질문 | 사용자별 대기열 사용 시 시작 중앙값 4.8 ms, 미사용 시 151.2 s; 사용자당 활성 턴 하나 유지 |
| 중단과 재개 | 204턴, 세 차례 중단/재개 | 질문 204개 모두 보존, 식별자 고유, 저장 상태 유계; 작은 실모델 검사도 27/27 보존 |

대화 요약은 새 턴을 막지 않고 실행된다. 긴 요약이 끝나기 전에 메시지가 들어오면 Coagora는 오래된 요약을 저장하지 않고 폐기한다. 재연결은 놓친 이벤트가 메모리에 남아 있는 동안 정확하며, 더 오래된 브라우저는 전체 세션 보기를 새로 받는다.

사용자별 대기열은 한 사람의 많은 요청이 모든 처리 슬롯을 차지하지 못하게 하지만 이미 작업 폴더를 사용 중인 셸 명령을 건너뛸 수는 없다. 직접 검사에서 다른 사용자의 파일 편집은 95번째 백분위에서 셸 명령 하나와 비슷하게 기다렸다. 1초 명령에서는 996 ms, 5초 명령에서는 4,992 ms였다. 도착 순서 처리는 끝없는 연기를 막지만 이 대기는 그대로 남긴다.

각 모델 호출은 호출 시작 시점의 유효한 대화를 사용한다. 긴 실모델 응답에서는 통제 시험 모델보다 호출 시작 뒤 더 많은 항목이 추가됐으며, 이 측정은 §7.2에서 제안하는 대화 정보 나이 표시의 근거가 된다.

### 5.4 RQ3: 한 요청이 다른 요청의 파일을 바꾸지 못하게 하기

Coagora는 소유자 표시와 점차 강해지는 세 보호 장치를 결합한다. 첫째, 모델 지시문에 현재 요청을 표시한다. 둘째, 비공개 대화 보기가 다른 활성 요청의 메시지를 숨긴다. 셋째, 강제 모드는 턴을 승인된 파일 목록으로 제한하고 과제별 검사를 통과한 뒤에만 변경을 공유 폴더에 반영한다.

실모델 실험은 위 endpoint와 방법 기록을 사용했다. 한 요청은 parser 파일을 만들고 다른 요청은 명령줄 문서를 작성했다. 각 요청은 허용 파일 두 개와 예상 내용을 지정했다. 세 보호 장치를 20개 block에서 평가했고 매번 새 폴더를 사용하며 여섯 가능한 arm 순서를 균형화했다(순열마다 3회 또는 4회). 60개 run은 한 partial source digest에서 모두 첫 시도에 끝났다. Temperature, top-p, seed는 고정하지 않았으므로 결과는 이 서버와 2026년 8월 13일 수집을 나타낸다.

동시에 실행한 요청 쌍이 분석 단위다. 자동 검사는 다른 과제의 파일을 사용하려 했거나 실제로 바꿨는지, 두 과제와 최종 폴더가 예상 내용과 일치하는지, 응답이 다른 과제의 완료 표시를 언급했는지, 전체 시간과 입력 토큰을 기록한다. 강제 모드의 파일 변경은 시스템 감사 로그에서 읽어 승인 파일 목록과 비교한다.

|---|---:|---:|---:|

| 다른 과제의 파일을 바꿈 | 0/20 (0–16.84%) | 0/20 (0–16.84%) | 0/20 (0–16.84%) |

세 구성의 파일 결과는 같았다. 다른 과제를 언급한 응답 하나만으로 구성을 통계적으로 구분할 수 없었다(paired exact 검정, p = 1.0). 다른 활성 요청을 숨기면 입력 토큰 중앙값이 2.5% 적고 더 느린 요청의 중앙 시간이 12.4% 짧았다. 강제 모드는 지시문만 쓴 경우보다 토큰이 1.0% 적고 중앙 시간은 같았다. 이 작은 차이는 해당 서버를 설명할 뿐 일반적인 속도 우월성을 뜻하지 않는다. 강제 모드는 실패 없이 요청 40개의 파일을 검사하고 반영했다.

실모델이 파일을 잘못 사용하려고 시도하지 않았기 때문에 의도적으로 어려운 상황 19개를 별도로 검사했다. 승인 목록 밖 경로, 바뀌는 파일을 알 수 없는 도구, 과제 검사 실패, 다른 프로세스가 바꾼 파일, 같은 파일의 여러 이름, 같은 파일을 요구하는 두 요청을 포함했다. 모두 예상대로 동작했다. 승인되지 않았거나 검사에 실패한 변경은 공유 폴더에 나타나지 않았고 같은 파일에 대한 두 요청은 동시에 실행되지 않았다.

§3.5의 조건 아래 강제 모드는 승인 파일만 바꾸고 제공된 과제 검사를 통과한 뒤에만 변경을 반영한다. Adversarial 검사 19개는 승인 범위 밖 경로, 검사 실패, 동시 원본 변경, 경로 alias, 한 파일에 대한 경쟁 요청에서 이 반영 계약을 확인했다.

### 5.5 증거 범위

평가는 결정적 메커니즘 검사에 예측 가능한 시험 모델을 사용하고, 응답 시간, 요청 분리, 토큰 사용, 대화 요약, 공정성, 중단·재개에는 실모델을 사용한다. 실모델 결과는 manifest를 보존한 온프레미스 endpoint 하나, 세 보호 장치 실험의 모델 하나, host computer 하나와 주로 2–3명의 모의 사용자를 특성화한다.

과제는 동시성 충돌을 의도적으로 드러내며, 측정 비율은 평가한 메커니즘과 workload를 특성화한다.

저장소에는 통과한 테스트 3,617개와 환경 조건 때문에 건너뛴 테스트 35개가 있으며, 이 중 53개는 브라우저 테스트다. 부록 A는 독립 재분석과 반복 검증을 위한 원자료, manifest, 재현 스크립트를 제공한다.

기술 평가는 시스템 메커니즘과 성능 결과를 확립하고, §6의 first-use study는 인식, 조정, 통제, 배치 적합성으로 평가를 확장한다.

**절차와 측정.** 두 참가자는 첫 요청을 동시에 보낸다. 주 조건의 8분과 16분 시점에 진행자는 10초 동안 멈추게 하고 “지금 상대방은 무엇을 하고 있습니까?”라고 묻는다. Module C 중간에도 같은 질문을 한다. 연구자 두 명이 각 답을 상대의 기록과 독립적으로 비교한다. 과제 영역과 현재 행동이 모두 맞으면 2점, 영역만 맞고 행동이 모호하거나 틀리면 1점, 답이 틀리거나 “모르겠다”이면 0점이다. 의견이 다르면 논의해 합의한다.

각 주 조건 뒤 참가자는 응답 속도, 상대 작업 인식, 에이전트가 잘못된 요청을 따른 것처럼 보였는지, 통제감, 협업 의향을 1–7점으로 평가하고 열린 질문 하나에 답한다. 마지막 인터뷰에서 진행자는 기록된 사건 3–5개를 고른다. 다른 과제의 파일 변경, 긴 대기열, 취소나 재시도, 대화 요약, 두 요청이 함께 실행된 시점 등이 포함된다. 참가자는 각 사건을 기억하는지, 원인이 무엇이라고 생각하는지, 무엇을 했는지 설명한다. 로그에 없는 사건을 말했다면 false alarm으로 남긴다. 인터뷰는 쌍이 만든 작업 규칙, 누가 작업을 취소할 수 있어야 하는지, 기다리는 동안 무엇을 했는지, 업무에서 사용할 조건도 다룬다.

**분석.** 로그는 실제로 무슨 일이 있었는지 확인하고 인터뷰 사건을 고르는 데 사용한다. 대기시간이나 파일 충돌률은 더 많은 시험을 사용한 §5에서 이미 측정했으므로 다시 추정하지 않는다. 표본이 작고 질적이므로 가설 검정을 하지 않는다. 상대 작업 인식 점수, 기억하거나 놓친 사건, 원인 설명, 쌍별 작업 규칙, 사용 가능·조건부 가능·사용 불가 판단을 보고한다. 설문 결과는 기술 통계로만 제시하며 공통 패턴뿐 아니라 반례도 함께 보고한다.

## 7 논의

### 7.1 하나의 공유 세션이 조정 문제를 바꾼다

별도 작업과 isolate-and-merge 시스템은 task 또는 branch 경계에서 조정하고 Coagora는 하나의 live context 안의 busy turn을 조정한다. 평가는 이 live-session 경계를 특성화한다. 대기열이 요청 시작 시점을 정하고, 변경 게이트가 파일 동작을 조정하며, 이름표가 누가 요청했는지 보여준다. 이 메커니즘은 협업자가 과제를 나누고, 동시에 나오는 응답을 살피며, 언제 취소할지 결정하도록 명시적으로 지원한다 [39].

저장된 대화는 모든 참가자에게 순서와 요청자가 표시된 같은 기록을 제공한다 [36]. 이 기록은 늦게 참여한 사람을 지원하는 결정 요약, 파일별 이력, 요청자별 필터의 기반도 제공한다.

요청자 범위의 취소는 각 참가자에게 자기 요청에 대한 예측 가능한 통제를 제공한다. 같은 요청 식별자는 역할 기반 중단 권한, 눈에 보이는 동의, 여러 사람의 승인을 추가하는 배치에서도 명확한 제어 대상을 제공한다.

### 7.2 검증 가능한 설계 가설

기술 결과는 first-use 평가를 위한 네 가지 interface hypothesis를 제안한다.

1. **누가 요청했고 모델이 무엇에 행동했는지 함께 보여라.** 요청자 이름표를 응답이 영향을 준 파일 및 명령과 함께 보여준다.
2. **응답이 오래된 정보를 사용할 때 보여라.** 응답이 시작된 뒤 새 메시지가 들어올 수 있다. 대화 정보의 나이 또는 “새 활동 있음” 표시는 계속할지, 다시 시작할지, 취소할지 판단하게 할 수 있다.
3. **모델 지시와 실제 변경을 함께 검사하라.** 요청이 바꿀 파일을 보여주고 승인받으며, 검사 전까지 편집을 비공개로 두고, 필요한 파일이 늘어나면 요청자에게 묻는다.
4. **왜 기다리는지 설명하라.** 요청은 모델 처리 슬롯, 파일 변경 작업, 모델 서버 때문에 기다릴 수 있다. 원인마다 해결 방법이 다르므로 하나의 “사용 중” 표시만으로는 부족하다.

이 가설은 측정한 시스템 행동에서 도출했다. First-use 및 이후 현장 연구에서 이해, 귀속, 통제, 조정에 미치는 효과를 검증한다.

### 7.3 신뢰와 배치 경계

Coagora의 배치 계약은 이미 저장소와 대화를 공유하는 상호 신뢰 협업자를 대상으로 한다. 읽기 전용 토큰은 공유 세션을 보는 권한과 요청 및 파일 변경 권한을 분리한다.

파일 변경 제한과 모델 입력 제한은 서로 다른 문제를 해결한다. 강제 모드는 지원되는 Coagora 도구와 승인 경로를 통제하고, 운영체제 격리는 외부 프로그램을 통제한다. 신뢰할 수 없는 참가자를 포함하는 배치는 이 메커니즘을 참가자별 권한 규칙과 결합할 수 있다 [30, 31].

### 7.4 한계

- **짧고 합성된 워크로드.** 실험은 실제 작업에서 사건이 얼마나 자주 일어나는지가 아니라 메커니즘과 경계를 드러낸다.
- **좁은 배치 환경.** 실모델 결과는 manifest를 보존한 oMLX endpoint 하나에서 나왔고 파일 제한 실험은 모델 하나를 사용했다. Manifest와 run별 기록은 배치 반복과 재분석을 지원하지만 다른 모델, 서버, 부하 패턴에서는 응답 시간과 행동이 달라질 수 있다.
- **토큰 비용.** 측정한 작업에서 요청을 함께 실행하면 두 번 대신 세 번 모델을 호출해 입력 토큰을 1.49배 사용했다.
- **대화 증가.** 공유 이력은 참가자가 늘수록 빠르게 자란다. 요약 중에도 새 요청을 받을 수 있지만 긴 실모델 요약 5개 중 3개는 저장 전에 오래된 내용이 됐다.
- **검증된 반영 범위.** 강제 검증은 요청 dispatch 때 제공된 과제 검사와 승인 파일 목록을 대상으로 한다. 추가 파일은 별도로 승인된 동작을 통해 반영한다.
- **운영 경계.** 변경 게이트 보장은 A1–A5 아래 Coagora를 통한 동작에 적용된다. 셸 명령은 폴더를 단독 사용하고 외부 프로그램은 배치 sandbox가 통제한다.

## 8 결론

코딩 에이전트를 공유하려면 여러 브라우저를 한 채팅에 연결하는 것 이상이 필요하다. 시스템은 각 요청이 언제 시작되는지 정하고, 누가 행동을 요청했는지 보여주며, 공유 파일 변경을 조정하고, 실행 중인 응답이 어떤 정보를 봤는지 설명해야 한다.

Coagora는 모델 응답을 함께 실행하면서 대화 항목과 충돌하는 파일 변경을 통제된 순서로 저장한다. 이 방식은 다른 사람의 전체 모델 응답이 끝날 때까지 기다리는 문제를 없앴다. 측정은 입력 토큰 사용, 호출 시점의 대화 정보 나이, 셸 명령의 단독 사용 대기도 정량화해 인터페이스가 각 tradeoff를 보여줄 근거를 제공한다.

Coagora는 요청자 표시, 활성 요청을 위한 비공개 보기, 승인 파일만 과제 검사 뒤 반영하는 강제 모드를 결합한다. 실모델 요청 쌍 60개에서 모든 과제 파일과 최종 폴더가 예상 내용과 일치했다. Adversarial 상황 19개는 A1–A5 아래 요청이 승인 목록 안의 검사된 파일만 반영함을 확인했다. 공유 에이전트 인터페이스는 요청자, 대화 정보의 나이, 승인 파일, 실제 변경을 보여줄 수 있으며 계획된 first-use study는 사람들이 이 통제를 사용하는 방식을 살펴본다.
