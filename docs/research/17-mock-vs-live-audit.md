# 목 LLM 사용처 전수 감사 — 어디까지가 방법이고 어디부터가 편의인가

> 2026-08-07. 대상: `bench/multiuser/` 전 스크립트. 계기: "이전 실험 중 실 LLM 을 썼어야 하는데 목을 쓴 것이 있는지 확인하라."
> 판정 기준은 하나다 — **재려는 양이 모델의 행동에 좌우되는가.** 좌우되지 않으면 목이 더 낫고(결정적·재현 가능), 좌우되면 목은 답을 *만들어내는* 것이라 무효다.

## 분류 기준

| 범주 | 정의 | 조치 |
|---|---|---|
| **A. 목이 곧 계기** | 실험의 독립변수가 스크립트된 모델 속성 자체다(작업 길이 L, 스텝 수 k, 적대 정책, 순응 여부). 실모델로 바꾸면 그 변수를 고정할 수 없어 **설계가 무너진다.** | 목 유지. 별도의 라이브 대응 실험이 있는지만 확인 |
| **B. 모델 우회** | LLM 을 아예 지나가지 않고 도구·락을 직접 구동한다. 논문이 이미 그 이유를 명시. | 유지 |
| **C. 목은 편의, 주장은 런타임 전용** | 재는 양이 전송·영속·순서 같은 기계의 성질이라 모델이 바꿀 수 없다. | 유지 (라이브는 비용만 늘고 타당성은 그대로) |
| **D. 목이 실상을 왜곡할 수 있음** | 재는 양이 **실제 추론 지속시간·분산·모델 행동**의 함수다. 목의 짧고 균일한 턴이 답을 낙관적으로 만들 수 있다. | **라이브 재실험 필요** |

## 결론

- **A·B·C (11 건)** — 목/우회가 방법론적으로 옳다. 특히 A 는 실모델로 바꾸면 **실험이 성립하지 않는다**. 라이브 대응이 필요한 두 곳(§6.1 랭킹, §6.7 순응)은 이미 각각 §6.10 과 `n3c` 로 존재한다.
- **D (4 건)** — 목이 답을 낙관적으로 만들 수 있다. 넷 다 라이브 팔을 추가한다.

| 대상 | 왜 목이 부족한가 | 라이브 설계 |
|---|---|---|
| `n5_staleness` §6.7 | 목 턴 ~1 s 대 실 턴 ~60 s — staleness 깊이가 추론 지속시간에 비례하므로 목 수치는 하한 | 3 사용자 × 4 라운드 × 3 회 + 직렬 대조군 |
| `n1_compaction` §6.6 | 800 ms 목 요약이 "수 초 요약을 락 밖에서"라는 조건을 대체 | 3 사용자 × 라운드, `--max-context-tokens` 로 압축 강제, 요약도 실모델 |
| `p4_fairness` §6.8 | 폭주자 턴이 실제로 분 단위일 때의 짧은 질문 대기 | 폭주자 1 + 짧은 질문 3, 실 턴 |
| `p7_lifecycle` §6.9 | 실 세션의 재개 확인 부재 | 축소(3 페이즈 × 소수 라운드) 라이브 재개 확인 |

**보고 원칙**: 라이브 결과가 목과 다르면 **라이브를 본문 수치로 올리고 목은 통제 검증으로 강등**한다(§6.1/§6.10 이 이미 쓰는 구조). 같으면 두 층이 일치했다는 사실 자체를 보고한다 — 어느 쪽이든 §6.11 의 타당성 위협 문단이 줄어든다.

## 실행 결과

### D1 `n5_staleness` — 감사의 예측이 절반만 맞았다

| | 목 (4 사용자 × 25 라운드 × 5) | 라이브 (3 사용자 × 4 라운드 × 3) |
|---|---|---|
| 병렬 stale | 500 중 498 (≈100%) | 92 중 75 (82%) |
| 깊이 중앙값 | 3~4 | 2 |
| **깊이 최대** | 5 | **10** |
| 직렬 대조군 | 200 중 0 | 13 중 0 |

- 구조적 사실 둘은 양쪽에서 동일: 병렬에서 stale 이 지배적이고, 직렬에서는 0 이다.
- 감사가 예측한 "목은 과소평가한다"는 **꼬리에서만 맞았다** — 최대 깊이가 5 → 10 으로 두 배다. 실 턴이 스냅샷을 1 분간 쥐고 있으면 그 뒤로 커밋 10 건이 쌓인다.
- 반면 **비중은 목이 더 높다**(≈100% 대 82%). 목 팔이 사용자·라운드가 더 많아 컨텍스트가 훨씬 붐비기 때문이며, 구성 차이지 목/라이브의 차이로 단정할 수 없다. 논문에는 그렇게 적었다.
- 교훈: "목이 하한"이라는 단순한 서사는 틀렸다. 목은 **밀도**를 과장하고 **지속시간**을 과소평가한다. 두 축이 반대로 움직이므로 라이브 없이는 어느 쪽도 알 수 없었다.

### D3 `p4_fairness` — 목이 게이트의 가치를 24배로 과소평가했다

| | 목 (단기 4, flood 5, 5회) | 라이브 (단기 3, flood 4, 2회) |
|---|---|---|
| gate on 단기 p50 | 75.6 ms | **4.4 ms** |
| gate off 단기 p50 | 1,806.9 ms | **145,293 ms** |
| 배율 | 24× | **약 33,000×** |
| gate on 위반 | 0 | 0 |
| gate on 단기 p95 | 148 ms | 21,862 ms |

- 메커니즘은 양쪽에서 같지만 **값이 완전히 다르다**. 폭주자의 턴이 스크립트된 150 토큰 스트림이 아니라 파일 셋을 쓰는 실 턴이면, 게이트 없이 줄 선 짧은 질문은 2 분 반을 기다린다.
- gate on 의 p95 21.9 s 는 게이트에 불리한 수치라 그대로 보고했다 — 상한 3 에 짧은 사용자 3 명이 동시에 오면 세 번째는 슬롯을 기다린다. 게이트는 한 사용자의 슬롯 점유를 묶을 뿐 용량을 만들지 않는다.
- 이 실험이 범주 D 판정의 가장 분명한 정당화다: 목만 있었다면 "24배 개선"이라는, 실제의 1/1000 인 값을 보고했을 것이다.

### D2 `n1_compaction` — 1차 시도 무효, 원인 규명 후 재실행

- `--max-context-tokens 3000` 으로는 압축이 **0 회** 발동했다. 원인: 압축 목표는 그 값이 아니라 **모델이 광고한 컨텍스트 창**에서 나온다(`loop/llm.py`: `target=(context_window − system − max_output) × ratio`). 실모델의 광고 창이 262K 라 목표가 도달 불가였다.
- 수리: 워크스페이스 로컬 `.agent-cli/models.json` 에 창을 12288 로 고정(레지스트리 > 런타임 탐지 우선순위 이용). 제품 코드도 사용자 설정도 건드리지 않는다.
- 부수 관측(무효 실행에서도 유효): 18 턴 중 **11 턴의 최종 답변이 다른 턴의 마커를 달았다** — §6.7 이 부수효과로 잰 혼선이 *답변 텍스트* 수준에서도 실모델로 나타난 것. 재실행에서 같은 통계를 더 큰 표본으로 다시 얻는다.
