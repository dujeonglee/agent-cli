## 0. 이 스터디가 무엇인지, 딱 세 문단

우리는 **여러 사람이 하나의 AI 코딩 에이전트를 동시에 쓰는 시스템**을 만들었다. 한 팀(2명)이 같은 화면 속 같은 AI에게 각자 자기 일을 시키는 상황이다. 시스템에는 두 가지 동작 방식이 있다: 요청을 **한 줄로 세워 순서대로 처리**하는 방식과, **동시에 나란히 처리**하는 방식.

기계로 잴 수 있는 것(속도, 오류율 등)은 이미 다 쟀다. 이 스터디가 알고 싶은 것은 **사람만 답할 수 있는 것**이다: 함께 쓰는 동안 상대가 뭘 하는지 알았는가, 이상한 일이 생겼을 때 알아차렸는가, 알아차렸다면 무엇 탓이라고 생각했는가, 두 사람 사이에 어떤 암묵적 약속이 생겼는가.

그래서 진행자가 할 일은 단순하다: **두 참가자에게 각자 과제를 주고, 20분씩 두 가지 설정에서 일하게 하고, 중간에 짧은 질문 카드를 내밀고, 끝나면 설문을 받고, 마지막에 인터뷰를 한다.** 이 문서는 그 각각을 순서대로, 읽어 줄 대사까지 포함해 설명한다.

## 1. 용어 정리 (이것만 알면 된다)

| 용어 | 뜻 |
|---|---|
| **직렬 (S)** | 시스템 설정 1. 두 사람이 동시에 요청해도 AI가 **한 번에 하나씩** 처리한다. 내 요청은 상대 작업이 끝나야 시작된다. |
| **병렬 (P)** | 시스템 설정 2. 두 사람의 요청을 AI가 **동시에** 처리한다. 답변 두 개가 나란히 흘러나온다. |
| **조건 A / 조건 B** | 세션에서 **첫 번째로 진행하는 20분 블록**이 조건 A, **두 번째 20분 블록**이 조건 B다. A가 직렬인지 병렬인지는 팀마다 다르다(§3의 배정표가 정한다). 참가자에게는 "설정 1/설정 2"라고만 말하고 무엇인지 알려주지 않는다. |
| **모듈 C** | 마지막에 붙는 **8분짜리 세 번째 블록**. 병렬 설정에서 안전장치 하나(아래 "스코핑")를 **의도적으로 끈** 상태다. 사람이 그 상태를 알아차리는지 보는 것이 목적이다. 참가자에게는 역시 "설정 3"이라고만 한다. |
| **스코핑** | AI에게 "지금 너는 누구의 요청을 처리 중"이라고 알려주는 안전장치. 끄면 AI가 **남의 요청 일까지 대신 해 버리는** 일이 자주 생긴다(우리 측정으로 40번 중 최대 31번). |
| **턴** | 요청 하나에 대한 AI의 작업 한 덩어리. "요청 → AI가 일함 → 완료"가 턴 하나다. |
| **오염** | 한 사람의 턴이 **상대방 과제의 파일**을 건드린 것. 모듈 C에서 특히 잘 생긴다. |
| **정지 탐침** | 진행 중 카드를 내밀고 "지금 상대가 뭘 하고 있나요?"를 10초 안에 적게 하는 것. 상대 상황을 얼마나 파악하고 있는지(인지 정확도) 잰다. |
| **상쇄(카운터밸런싱)** | 어떤 팀은 직렬을 먼저, 어떤 팀은 병렬을 먼저 하게 순서를 섞는 것. "먼저 한 설정이 익숙해서 더 좋게 평가"되는 왜곡을 상쇄한다. 과제쌍도 같은 이유로 섞는다. |
| **hit / miss** | 인터뷰에서, 로그에 실제로 있었던 사건을 참가자가 **기억하면 hit, 모르면 miss**. |
| **false alarm** | 참가자가 "이런 일이 있었다"고 말했는데 로그에는 **없는** 경우. 이것도 버리지 말고 기록한다(그 자체가 발견이다). |
| **귀인** | 이상한 일을 겪었을 때 참가자가 **무엇 탓**이라고 생각했는가: AI 탓 / 시스템(도구) 탓 / 상대방 탓 / 자기 탓. |
| **M1~M5** | 이 스터디의 다섯 측정 항목. M1 인지 정확도(정지 탐침), M2 알아차림(hit/miss), M3 귀인, M4 두 사람 사이에 생긴 규칙, M5 "실무에서 쓰겠는가". |

- [ ] **동의서 인쇄**(§9 양식) — "일부 설정은 의도적으로 제한된 기능을 사용합니다" 문구가 반드시 들어 있어야 한다(모듈 C 때문). 소속 기관에 연구윤리 심의가 있으면 지금 문의한다.

- [ ] **인쇄물 준비** — 과제 카드(§7, 참가자별로 자기 것만!), 정지 탐침 카드(§8-2) 팀당 5장, 설문지(§8-1) 1인당 3장.

### D-1 체크리스트 (전날)

- [ ] **장비** — 참가자용 노트북 2대(또는 지참 안내), 모두 같은 네트워크(LAN), 진행자 노트북, 화면+음성 녹화 수단, 타이머.

## 4. 당일: 서버 띄우기 (세션 시작 15분 전)

설정(블록)마다 서버를 **새로** 띄운다. 블록을 바꿀 때는 서버를 끄고, 그 블록용 리포 사본 폴더로 이동해서 다시 띄운다.

```bash
# 공통 환경 (API 키는 절대 파일에 저장하지 말고 당일 터미널에서만 입력)
export AGENT_CLI_PROVIDER=openai
export AGENT_CLI_BASE_URL=<온프렘 엔드포인트 주소>
export AGENT_CLI_API_KEY=<발급받은 키>
export AGENT_CLI_MODEL=<모델명>

# 병렬(P) 블록용
cd <이 블록용 리포 사본 폴더>
agent-cli web --host 0.0.0.0 --port 8765 --token team1-a --turn-metrics \
  --concurrency-contract parallel

# 직렬(S) 블록용
agent-cli web --host 0.0.0.0 --port 8765 --token team1-a --turn-metrics \
  --concurrency-contract serial

# 모듈 C 블록용 (병렬 + 안전장치 끔)
agent-cli web --host 0.0.0.0 --port 8765 --token team1-c --turn-metrics \
  --concurrency-contract parallel --no-turn-scoping
```

- `--token` 값은 `team팀번호-블록`으로 그때그때 바꾼다 (예: `team3-b`).
- 참가자 접속: 각자 브라우저에서 `http://<진행자 컴퓨터 IP>:8765/?token=team1-a`.
### 로그 저장 (블록이 끝날 때마다 — 빠뜨리면 인터뷰·채점을 못 한다)

로그는 서버가 자동으로 남긴다. 서버를 띄웠던 작업 폴더 안 `.agent-cli/sessions/<세션id>/` 에 `turns.jsonl`(시간 기록)과 `history.jsonl`(대화·파일 기록)이 쌓인다. 진행자가 할 일은 **블록이 끝나 서버를 끈 직후, 그것을 팀 폴더로 복사해 두는 것**뿐이다. 세션 id 폴더를 직접 찾을 필요 없이 아래 한 줄이면 된다(저장소 최상위에서 실행):

```bash
# save_logs.py <그 블록의 작업 폴더> <팀번호> <블록 A|B|C>
.venv/bin/python bench/study/save_logs.py ~/study/team1-pair1 1 A
```

- 성공하면 "저장 완료"와 두 파일의 줄 수가 출력된다. **줄 수가 0이면 뭔가 잘못된 것** — 서버를 `--turn-metrics` 로 띄웠는지 확인.
- 같은 블록을 두 번 저장하려 하면 멈추고 알려 준다(실수 방지).
- 블록마다 작업 폴더가 다르다는 것에 주의: A 블록은 A용 리포 사본 폴더를, B 블록은 B용 폴더를 넘긴다.
- 이렇게 모인 `study-data/team<N>/{A,B,C}/` 를 인터뷰 준비(§6-3)와 사후 채점(§10)이 그대로 쓴다.

### 조건 순서·과제쌍 배정표

읽는 법: 자기 팀 번호의 행을 본다. "조건 A" 열이 그 팀이 **첫 20분에 쓸 설정**이고, "A 과제쌍" 열이 그때 나눠줄 카드다. 예를 들어 **팀 2는 첫 블록을 병렬(P) 설정으로 띄우고 과제쌍 2의 카드 두 장(2-P1은 참가자 1에게, 2-P2는 참가자 2에게)을 준다.** 모듈 C는 모든 팀이 마지막에, 항상 과제쌍 3으로 진행한다.

| 팀 | 조건 A (첫 20분) | 조건 B (다음 20분) | A 과제쌍 | B 과제쌍 |
|---|---|---|---|---|
| 파일럿 | S (직렬) | P (병렬) | 쌍1 | 쌍2 |
| 1 | S | P | 쌍1 | 쌍2 |
| 2 | P | S | 쌍2 | 쌍1 |
| 3 | S | P | 쌍2 | 쌍1 |
| 4 | P | S | 쌍1 | 쌍2 |
| 5 | S | P | 쌍1 | 쌍2 |
| 6 | P | S | 쌍2 | 쌍1 |

왜 이렇게 섞는가: 모두가 같은 순서로 하면 "두 번째 설정이 더 좋았다"는 답이 설정 때문인지 익숙해져서인지 구분할 수 없다. 순서와 과제를 팀마다 엇갈리게 하면 그 왜곡이 상쇄된다.

## 6. 진행자 대본과 인터뷰 절차

### 6-1. 도입 (그대로 읽기)

> "두 분이 하나의 AI 코딩 에이전트를 함께 쓰시게 됩니다. 같은 대화창, 같은 작업 폴더예요. 각자 받으신 카드의 과제를 AI에게 시켜서 완료하시면 됩니다. 상대분과 상의하셔도 되고 안 하셔도 됩니다. 상대분의 과제가 무엇인지는 알려드리지 않고, 카드도 서로 보여주지 말아 주세요. 중간에 두 번, 10초짜리 질문 카드를 드릴 거예요. 저는 관찰만 하고, 진행 중에는 질문에 답해 드리지 못합니다. 시작 신호가 있으면 두 분 **동시에** 첫 요청을 보내 주세요."

### 6-2. 블록 전환 (그대로 읽기)

> "다음은 같은 시스템의 **다른 설정**입니다. 무엇이 다른지는 다 끝나고 말씀드릴게요. 새 과제 카드를 드리겠습니다. 이번에도 시작 신호에 동시에 보내 주세요."

### 6-3. 인터뷰 준비: 사건 고르기 (0:59, 4분)

인터뷰는 "전반적으로 어땠어요?"가 아니라 **실제로 일어난 사건**을 놓고 묻는다. 그래서 인터뷰 직전에 로그에서 사건 3~5개를 골라 둔다. 로그를 직접 읽을 필요는 없다 — 도우미 스크립트가 후보를 뽑아 준다:

```bash
.venv/bin/python bench/study/pick_events.py study-data/team1/A
.venv/bin/python bench/study/pick_events.py study-data/team1/B
.venv/bin/python bench/study/pick_events.py study-data/team1/C
```

출력은 우선순위 순서다. 고르는 규칙:

1. **오염(⚠ 표시)이 있으면 무조건 넣는다.** 특히 **모듈 C의 오염은 전부** 넣는다 — 이 스터디에서 가장 중요한 질문("사람이 알아차리는가")의 재료다. ⚠ 표시가 없어도, 출력된 "요청별 건드린 파일" 목록을 정답지(`bench/study/README.md`의 카드별 대상 파일 표)와 대조해서 **자기 카드 영역 밖의 파일**을 건드린 요청이 있으면 그것도 오염이다.
2. 다음으로 긴 대기(직렬 블록에서 나온다), 중단/거부, 압축, 최대 겹침 구간 순으로 채워 총 3~5개.
3. 각 사건마다 메모해 둘 것: **경과 시각**(출력에 분:초로 나온다), **무슨 일**(한 줄), **관련 참가자**(누구의 요청이었나).
4. 사건이 하나도 없으면 그것도 기록한다("조사할 사건 미발생") — 인터뷰는 공통 질문(6-4의 ⑤~⑨)만으로 진행한다.

### 6-4. 인터뷰 진행 (1:03, 16분)

**형식**: 두 참가자와 함께 앉아 진행한다(같이 인터뷰). 녹음이 돌아가는지 확인. 사건당 약 3분, 남는 시간에 공통 질문.

**철칙 — 이것만은 지킨다**:
- 사건을 소개할 때 **시각과 겉으로 보인 것만** 말하고, **무슨 일이었는지 해석은 절대 먼저 말하지 않는다.** 참가자가 스스로 기억하고 해석하는 것 자체가 측정 대상이기 때문이다.
  - 좋은 예: *"시작하고 12분쯤에, ○○님 화면 쪽 파일에 변화가 있었어요. 기억나세요?"*
  - 나쁜 예: *"12분쯤에 AI가 ○○님 파일을 잘못 건드렸는데 아셨어요?"* ← "잘못"이라는 해석을 줘 버렸다. 이러면 그 답은 못 쓴다.
- 참가자가 틀리게 기억해도 **고쳐주지 않는다.** "아 그러셨군요"로 받고 다음 질문으로.
- 침묵을 견딘다. 질문 후 5초쯤 조용해도 기다린다. 먼저 보기를 제시하지 않는다("AI 탓이었을까요, ○○님 탓이었을까요?" 금지 — 열린 질문만).
- 두 사람의 답이 다르면 그대로 둔다. 둘을 화해시키거나 정답을 정해 주지 않는다.

**사건별 질문 4개** (사건마다 이 순서 그대로):

| 순서 | 질문 (그대로 읽기) | 기록할 것 |
|---|---|---|
| ① | "시작하고 [N분]쯤에 [겉으로 보인 것]이 있었어요. 기억나시나요?" | **기억함 = hit / 기억 못함 = miss** (참가자별로) |
| ② | (기억한다면) "그때 무슨 일이라고 생각하셨어요?" | 답을 그대로 받아 적는다. 나중에 채점자가 AI 탓/시스템 탓/상대 탓/자기 탓으로 분류한다 |
| ③ | "그래서 뭔가 하셨나요? 안 하셨다면, 왜 안 하셨어요?" | 자유 기록 |
| ④ | (기억 못했다면) "실은 이런 일이 있었어요: [이제 사실만 설명]. 지금 들으시니 어떠세요?" | 자유 기록 |

**참가자가 로그에 없는 사건을 먼저 꺼내면**: "그런 일이 있었다고 기억하시는군요"라고 받고 **false alarm**으로 별도 기록한다(시각·내용 포함). 부정하지 않는다.

**공통 질문 5개** (사건 질문이 끝나고 남는 시간에, 순서대로):

| # | 질문 (그대로 읽기) |
|---|---|
| ⑤ | "일하시는 동안, 상대분이 지금 뭘 하고 있는지 알아야 했던 순간이 있었나요? 있었다면 어떻게 알아내셨어요?" |
| ⑥ | "상대분의 작업을 멈추고 싶었던 적이 있었나요? 실제로 멈추셨나요? 안 멈추셨다면 왜요? — 멈춰도 되는 거라고 생각하셨어요?" |
| ⑦ | "두 분이 진행하면서 뭔가 정한 게 있나요? 예를 들면 순서라든가, 영역이라든가요. 말로 정하셨나요, 아니면 그냥 자연스럽게 그렇게 됐나요?" |
| ⑧ | "설정마다 기다리는 느낌이 달랐나요? 기다리는 동안엔 뭘 하셨어요? 상대분 때문에 기다린다고 느낀 적이 있었나요?" |
| ⑨ | "이걸 실제 팀에서 쓰신다면 어떨 것 같아요? 어떤 일에는 쓰고 어떤 일에는 안 쓰실 것 같은지, 쓰려면 뭐가 더 있어야 할지 말씀해 주세요." |

**시간 관리**: 1:15가 되면 진행 중인 사건 질문을 마무리하고 ⑨(실무 사용 의향)는 반드시 묻는다 — M5의 유일한 출처다.

### 6-5. 블록 진행 중 관찰 메모 (진행자)

블록이 도는 20분 동안 진행자는 아래 다섯 글자를 시각과 함께 메모한다. 통계용이 아니라 **인터뷰에서 물어볼 후보를 하나라도 더 잡아 두는 용도**다. 완벽하지 않아도 된다.

- `WAIT` 화면만 보며 기다림 · `ASK` 상대에게 말을 걺 · `SURPRISE` 놀람/혼란("어?", 찌푸림) · `CROSS` 상대의 결과물을 언급하거나 만짐 · `ABANDON` 하던 요청을 취소하거나 다시 씀

### 6-6. 디브리핑 (1:19, 그대로 읽기 + 질의응답)

## 11. 분석·보고에서 하지 않는 것 (18의 규칙, 재확인)

- **통계 검정을 하지 않는다.** 팀 4~6개는 통계를 낼 크기가 아니고, 그걸 아는 상태로 설계했다.
- 속도·오염률·겹침 같은 **기계가 재는 수치를 이 스터디의 결과로 보고하지 않는다.** 그것은 본 실험(§6)이 큰 표본으로 이미 쟀다. 여기서 로그는 결과가 아니라 **채점 정답지 + 인터뷰 질문 선택기**다.
- 보고 산출물은 4가지뿐: ① M1 점수표(+"모름"의 빈도) ② M2 hit/miss 표(+false alarm 별도) ③ M3·M4 분류 결과와 대표 인용문(우리 가설과 어긋나는 사례 우선) ④ M5 요약(쓰겠다/조건부/안 쓰겠다 + 이유).
