# 메신저 태그 호출 방식 vs. CLI/세션 기반 다중 사용자 공동 세션 방식 — 구조적·사용자 경험적 비교

> 작성일: 2026-08-05. 근거 문서: `01-repo-analysis-aidit-code.md`, `02-messenger-based-ai-coding-tools.md`, `03-repo-analysis-agent-cli.md`, `04-related-work-cscw-hci.md`.
> "메신저 방식" = Claude Tag / Codex Slack / Copilot Slack·Teams / Devin Slack / Cursor Slack (02 문서 §1–4).
> "공동 세션 방식" = Coagora(게시글=세션, SSE 공유) + agent-cli(공유 워커 웹 세션) 계열.

## 1. 한 문장 요약

메신저 태그 방식은 **"대화 공간(Slack)과 실행 공간(클라우드 샌드박스)이 분리된 비동기 위임"** 이고, 공동 세션 방식은 **"대화·실행·상태가 하나의 살아있는 세션에 합쳐진 동기적 공동 조종"** 이다. 전자에서 인간들은 *에이전트의 산출물*을 두고 협업하고, 후자에서 인간들은 *에이전트의 실행 그 자체* 안에서 협업한다.

## 2. 구조적 비교

### 2.1 아키텍처 축

| 축 | 메신저 태그 방식 | 공동 세션 방식 (Coagora / agent-cli) |
|---|---|---|
| **인터페이스와 실행의 관계** | 분리. Slack은 트리거·알림 표면, 실제 상태는 외부(Codex cloud, Cursor VM, GitHub PR)에 존재 (02 §4) | 통합. 세션이 곧 실행 컨텍스트. Aidit는 게시글↔샌드박스 1:1(`Sandbox.postId @unique`), agent-cli는 1 프로세스=1 세션=1 워커 스레드 |
| **작업 단위** | 태스크(멘션 1회 → PR 1건). 완결형 배치 | 턴(turn). 연속형 세션 안의 열린 흐름 — 인터럽트·스티어링·이어받기 가능 |
| **컨텍스트의 소재** | 스레드 텍스트를 실행 시점에 흡수(복사). 스레드 밖 맥락·리포의 암묵적 상태는 전달 안 됨 (02 §5.1, 5.4) | 세션 자체가 컨텍스트의 원본. Aidit: 단일 공유 `convo` 배열(스냅샷 읽기+원자 커밋), agent-cli: `history.jsonl` + compaction 상태가 디스크에 영속 |
| **컨텍스트 수명** | 스레드 경계에 종속, 벤더별 편차(Devin만 세션 재개·양방향 동기화) (02 §5.3) | 세션이 1급 영속 객체. suspend→resume(Aidit), `--resume` + run↔web 상호 이어가기(agent-cli) |
| **실시간 개입** | 구조적으로 부재 — 자동 자기교정 루프는 있어도 인간의 실행 중 개입 지점은 없음 (02 §5.5) | 핵심 기능. Aidit: `turnId` 단위 인터럽트(남의 턴 불간섭), agent-cli: 실행 중 입력 큐 주입(턴 경계 디큐) + `ask` 선착순 응답 게이트 |
| **다중 사용자 동시 요청** | 미정의(Claude Tag "누구나 조종" — 조정 프로토콜 없음) 또는 직렬화/거부(CopilotKit OpenTag: Redis 락+409) (02 §6.1, 01 §5) | 명시적 계약. Aidit v2: **병렬 추론 + 직렬 부수효과**(cap 4, per-user 1활성턴, 계층 락), agent-cli: 공유 입력 큐 순서화 + 선착순 게이트(409) |
| **산출물 귀속** | 벤더별 상이 — 에이전트 자체 계정(Claude Tag) vs 요청자 권한 차용(Copilot) vs 이메일 매핑(Devin) (02 §4) | 메시지 단위 귀속. Aidit: `Message.replyToId`로 AGENT_REPLY↔질문자 1:1, agent-cli: `[닉네임]:` 라벨 + `author` 키로 history가 다중 화자 트랜스크립트화 |
| **관전(spectating)** | 불가능에 가까움 — 진행 상태는 리액션/링크 수준 | 1급 기능. Aidit: 비로그인도 SSE 관전(`optionalAuth`), agent-cli: 전 접속자 fan-out + 이벤트 버퍼 replay |
| **승인/안전 모델** | 채널 단위 도구 권한 + 지출 한도(Claude Tag), 승인 요청 수신자 불명확 → 승인 피로 (02 §6.5–6.6) | Aidit: 대화형 승인 없음, 격리 경계(pathGuard·ENV 화이트리스트·리소스 cap)로 대체. agent-cli: 위험 shell 승인을 `awaiting_input`으로 영속 대기(부재 중 질문 대기) |
| **실행 환경** | 벤더 클라우드 VM — 온프렘 불가, 리포는 기본 브랜치 클론 | 자가 호스팅. Aidit: 호스트 디렉토리 샌드박스, agent-cli: 온프렘 LLM 전제(LAN 웹 UI) |

### 2.2 구조적 차이의 뿌리: 상태(state)의 위치

메신저 방식의 모든 한계(02 §5–6)는 하나의 설계 결정에서 파생된다: **에이전트 세션 상태가 대화 공간 밖에 있다.** 스레드는 상태의 사본을 트리거 시점에 한 번 넘겨줄 뿐이므로 — (a) 실행 중 개입 채널이 없고, (b) 두 번째 멘션은 새 컨텍스트가 되며, (c) 여러 사용자의 개입은 "다음 태스크"로만 표현된다.

공동 세션 방식은 반대로 상태를 대화 공간 안에 둔다. 그 대가로 새로운 문제들이 생기며, 이것이 연구 대상이 된다:
- **동시 턴 조정** — Aidit가 4계층(coalescing / 이중 디스패치 / XC-CAP / 계층 락)으로 해결한 문제 (01 §2.3)
- **공유 컨텍스트 정합** — 스냅샷 읽기 + 원자 커밋 + assistant/tool 짝 정합 불변식 (01 §2.3-e)
- **순서와 재생** — seq SoT + `Last-Event-ID` 재생 (01 §2.4)
- **선착순 응답 중재** — agent-cli의 409 게이트 (03 §2.3-c)

### 2.3 두 공동 세션 구현의 대비 (계열 내부 스펙트럼)

같은 "공동 세션" 계열 안에서도 두 리포는 다른 지점을 차지한다. 논문에서 설계 공간(design space)의 두 좌표로 쓸 수 있다.

| 축 | Coagora | agent-cli |
|---|---|---|
| 동시 턴 | **병렬** (v2: 동시 추론 스트림, TTFT 기울기 0 실측) | **직렬** (공유 큐가 턴 경계마다 하나씩 주입) |
| 부수효과 | 계층 락으로 충돌 단위 직렬화 | 단일 워커라 자연 직렬 (락 불필요) |
| 사용자 신원 | 계정/게스트(`#hex4`) + JWT, DB 귀속 | 공유 토큰 + 자율 닉네임 (계정 없음) |
| 참여 모델 | 게시판형 공개 참여 (멤버십 없음) | URL 공유형 사설 참여 |
| 에이전트 구성 | 단일 에이전트 (pi) | 다중 상주 서브에이전트 + 오케스트레이터 (인간·에이전트가 같은 메시지 버스 공유) |
| 지향 | 협업 플랫폼 (커뮤니티/스레드 UI) | 개발 도구 (CLI↔web 왕복, 온프렘) |

주목: agent-cli의 "다중 인간 + 다중 에이전트가 하나의 `InputQueue` 위에서 조정"(03 §7.2)과 Aidit의 "다중 인간 + 단일 에이전트의 병렬 턴"은 상보적이며, 합치면 N humans × M agents 조정 문제의 두 축을 모두 커버한다.

## 3. 사용자 경험(UX) 비교

CSCW 이론 렌즈(04 §3)로 정리하면 차이가 선명해진다.

### 3.1 Awareness (Dourish & Bellotti; Gutwin & Greenberg)

- **메신저**: 에이전트 작업 진행에 대한 workspace awareness가 거의 0이다. 눈 이모지 → 링크 → 완료 포스트라는 3개의 이산 신호뿐. 동료가 무엇을 시켰고 에이전트가 지금 무엇을 바꾸는 중인지 알 수 없다.
- **공동 세션**: 토큰·툴콜·파일 변경이 전 참가자에게 실시간 스트리밍(Aidit 9종 이벤트, agent-cli SSE fan-out + 팀 스윔레인). "N개 작업 진행 중" 배지, activeTurns 카운트 등 awareness 정보가 1급 UI 요소다.
- **연구 함의**: 에이전트는 인간보다 훨씬 빠르게 상태를 바꾸므로, 실시간 가시성이 오히려 정보 과부하가 될 수 있는지가 열린 질문 (04 §7.5).

### 3.2 Grounding (Clark & Brennan)

- **메신저**: 매 태스크가 스레드 텍스트로 grounding을 다시 시작한다. A와 B가 같은 스레드를 보므로 인간끼리의 common ground는 유지되지만, **에이전트와의 common ground는 태스크마다 리셋**된다.
- **공동 세션**: 에이전트와의 common ground가 세션에 누적된다. 대신 **비대칭 grounding 문제**가 생긴다 — A가 30분간 쌓은 세션 맥락에 B가 중간 참여하면, B는 인간-에이전트 common ground를 공유하지 못한 채 개입하게 된다 (04 §7.4). agent-cli의 이벤트 버퍼 replay(5,000건)와 Aidit의 seq 재생은 이 격차를 줄이는 장치지만, "다시 보기"가 "이해 따라잡기"와 같지 않다.

### 3.3 제어권과 turn-taking (Horvitz mixed-initiative의 다자 확장)

- **메신저**: 제어권 개념 자체가 희박 — 발사 후 통제 불가(fire-and-forget). Claude Tag의 "누구나 이어받기"는 프로토콜 없는 전권 공유다 (02 §6.1).
- **공동 세션**: 제어권이 명시적 메커니즘으로 분해된다. Aidit: 내 턴만 인터럽트 가능(남의 턴 불간섭), per-user 1활성턴, self-concurrency UI 게이팅("남의 턴은 절대 나를 잠그지 않는다"). agent-cli: 큐 취소는 소유자만, `ask` 응답은 선착순+409.
- **연구 함의**: SWE-chat이 보인 "사용자 39% 제동"(04 §1)이 다자 환경에서 어떻게 변하는가 — 누가 제동하는가, 동료 가시성이 제동을 촉진하는가(Daryanto의 peer accountability 효과, 04 §6-f)가 직접 시험 가능해진다.

### 3.4 Articulation work (Schmidt & Bannon)

- **메신저**: 조율 노동이 스레드 밖으로 밀려난다 — 어느 채널에서 뭘 시켰는지 추적, PR 리뷰에서의 사후 조정, 중복 태스크 발사 방지가 전부 인간 몫. GitHub Next Ace가 말하는 "조율 부채(coordination debt)" (04 §6-a).
- **공동 세션**: 조율 노동이 세션 안으로 들어와 시스템 메커니즘(큐, 락, 귀속, 배지)으로 일부 흡수된다. 단, 새 형태의 articulation work(내 턴/남의 턴 구분, 큐 순서 협상, 스티어링 타이밍)가 생긴다 — "조율 비용은 소멸하지 않고 이전된다"는 가설의 시험대 (04 §7.8).

### 3.5 요약 표 — UX 계약

| UX 속성 | 메신저 태그 | 공동 세션 |
|---|---|---|
| 개입 시점 | 태스크 발사 전 / 완료 후 | 실행 중 언제든 |
| 대기 경험 | 알림 올 때까지 방치 | 실시간 관전 + (Aidit v2) 남의 작업과 무관한 내 TTFT (기울기 0) |
| 신규 참여자 온보딩 | 스레드 읽기 (얕지만 즉시) | 세션 replay (깊지만 비대칭 grounding) |
| 실수 복구 | PR 리뷰에서 사후 반려 | 턴 인터럽트로 즉시 중단, 부분 본문 보존 |
| 책임 소재 | PR 단위 (귀속 모델 벤더별 상이) | 메시지/턴 단위 1:1 귀속 |
| 참여 장벽 | 플랜·리포 연결·관리자 승인 (비개발자 배제) | URL/게시글 진입 (게스트 허용) |

## 4. 논문용 프레이밍 제안

1. **이분법이 아니라 설계 공간으로.** "메신저 vs CLI"가 아니라 **(i) 상태의 위치(대화 밖/안), (ii) 동시성 계약(거부/직렬/병렬+직렬 부수효과), (iii) 귀속 단위(PR/태스크/턴), (iv) 개입 지점(사전·사후/실행 중)** 의 4축 설계 공간으로 제시하고, 기존 도구들과 두 시스템을 좌표로 배치하면 기여가 분류학(taxonomy)이 된다.
2. **"거절+재시도가 직렬보다 나쁘다"는 실측**(01 §1.2)은 OpenTag류 busy-gate 계약(스레드당 1 run, 409)에 대한 정량 반박으로, 메신저 방식 한계 절과 직접 연결된다.
3. **주의**: 메신저 방식을 허수아비로 만들지 말 것. 02 §7의 경고대로 — Devin의 세션 지속성, 자동 반복 교정의 존재를 인정하고, 정확한 주장은 "**세션 지속성이 표준화되지 않았고, 지속되더라도 인간의 실시간 개입 지점과 다자 조정 프로토콜이 없다**"로 한정한다. 또한 비동기 위임이 우월한 시나리오(긴 배치 작업, 방해 최소화)도 존재함을 인정하는 편이 심사에 유리하다.
