# First-use study 프로토콜 — 공유 에이전트 세션의 2인 사용 관찰

> 2026-08-08. 플랜2(`16-review-response-plan-2.md`) Track G / G1 의 실행 문서.
> **이 문서는 세션을 진행할 사람이 그대로 따라 읽을 수 있게 쓰였다.** 참가자 모집·동의·일정은 사람이 해야 하므로 실행은 대기 중이다.

## 왜 하는가 (한 문단)

2차 리뷰(`15-reviewer-simulation-v0.9.md`)의 결정 축은 R2-W1 이었다: 10 개 RQ 전부가 기계로 답해지고, 동기(§1)와 논의(§7.1–7.4)가 말하는 인간 행동은 한 번도 관측되지 않는다. 이 연구는 그 간극을 닫으려 하지 않는다 — 4~6 팀으로 협업 성과를 주장할 수는 없다. 목표는 **§7 의 가설들이 데이터와 처음 접촉하게 하는 것**이고, 논문에는 §6.12 "first-use observations" 로, 통계적 주장 없이 관찰과 인용문으로 들어간다. 결과가 계약에 불리해도(예: 동시 스트림을 읽기 힘들다) 그대로 싣는다 — §7.4 가 예고한 "새 접합 작업"의 첫 증거가 되기 때문이다.

## 설계 요약

| 항목 | 값 |
|---|---|
| 참가자 | 2 인 1 팀 × **4~6 팀** (동료 개발자, 저자 제외) |
| 세션 길이 | 팀당 약 60 분 (도입 5 · 조건 A 20 · 조건 B 20 · 인터뷰 10 · 여유 5) |
| 설계 | within-subject, 계약 2 조건(`serial` / `parallel`) |
| 상쇄 | 조건 순서와 과제 쌍을 팀 간 교차(팀 1: 직렬-과제쌍1 → 병렬-과제쌍2, 팀 2: 병렬-과제쌍1 → 직렬-과제쌍2, …) |
| 환경 | 두 참가자가 각자 노트북에서 같은 LAN 세션에 접속. 워크스페이스는 준비된 소형 리포 사본 |
| 기록 | `--turn-metrics` 로 `turns.jsonl`, 세션 `history.jsonl`, 화면 녹화(동의 시), 인터뷰 메모 |

**스코핑은 두 조건 모두에서 켠다**(`--turn-scoping`). §6.7 이 그것 없이는 통상 작업에서도 40 턴 중 31 턴이 오염됨을 보였으므로, 끄고 진행하는 것은 참가자에게 알면서 망가진 시스템을 주는 것이다. 스코핑 자체의 효과는 §6.7 이 이미 실험으로 답했다.

## 과제 쌍

각 조건에서 두 참가자가 **동시에** 서로 다른 과제를 에이전트에 지시한다. 과제는 실제로 구분되되(§6.7 의 realistic 워크로드 원칙) 20 분 안에 끝나야 한다.

- **과제쌍 1** — P1: 입력 검증 함수에 경계 조건 버그 수정 + 테스트 추가 / P2: `README` 의 설치·사용법 절 갱신
- **과제쌍 2** — P1: CLI 에 `--json` 출력 옵션 추가 / P2: 로깅 포맷을 구조화 로그로 바꾸는 리팩터

각 참가자에게는 자기 과제만 적힌 카드를 준다. 상대의 과제는 **말해 주지 않는다** — 공유 트랜스크립트에서 알게 되는지, 그것을 어떻게 다루는지가 §7.1(비대칭 그라운딩) 관측 대상이다.

## 진행 대본

**도입 (5 분).** "두 분이 하나의 AI 코딩 에이전트를 함께 씁니다. 같은 대화, 같은 작업 폴더예요. 각자 카드에 적힌 과제를 하시면 되고, 상대와 상의하셔도 되고 안 하셔도 됩니다. 저는 관찰만 하고, 막히시면 그때만 개입합니다. 소리 내어 생각하실 필요는 없습니다." 동의서 확인, 녹화 시작.

**조건 실행 (20 분 × 2).** 시작 신호와 함께 두 참가자가 동시에 첫 지시를 제출하게 한다(그래야 겹침이 보장된다). 이후는 자유. 진행자는 개입하지 않고 아래 사건만 기록한다.

**전환 (1 분).** "이번엔 같은 시스템의 다른 설정입니다. 무엇이 다른지는 끝나고 말씀드릴게요."

**인터뷰 (10 분, 반구조화).** 아래 질문을 하되 참가자가 먼저 꺼낸 주제를 우선한다.

1. (§7.1 그라운딩) 상대가 무엇을 하고 있는지 언제, 어떻게 알았나요? 몰라서 곤란했던 순간이 있었나요?
2. (§7.2 중재) 상대의 작업을 멈추고 싶었던 순간이 있었나요? 있었다면 왜 멈추지 않았나요?
3. (§7.3 책임성) 상대가 보고 있다는 것이 에이전트의 결과를 확인하는 방식에 영향을 줬나요?
4. (응답성) 두 설정 중 어느 쪽이 더 빨랐나요? 무엇을 보고 그렇게 느꼈나요?
5. (§7.4 새 노동) 혼자 쓸 때는 안 했을 일을 한 게 있나요?
6. 다시 쓴다면 어떤 상황에서 이 방식을 쓰겠어요? 어떤 상황에서는 안 쓰겠어요?

**디브리핑 (2 분).** 두 조건의 차이(직렬/병렬)를 설명하고 질문을 받는다.

## 측정

**기계측 (기존 계측 재사용, 추가 개발 불요)**

| 지표 | 출처 |
|---|---|
| 각 참가자의 TTFT 분포 | `turns.jsonl` `enqueue`→`first_token` (§5 규칙) |
| 개입(인터럽트) 횟수·시점 | `turns.jsonl` `interrupt` |
| 대기 중 재제출·중복 질문 | `history.jsonl` 질의 간 간격 + 내용 |
| 교차 사용자 오염 | `reply_to` × `files` 조인 (§6.7 판정기 그대로) |
| 동시 겹침 정도 | dispatch/complete 구간 겹침 |

**관찰 코딩 (진행자가 실시간 기록, 사건 단위)**

- `WAIT` — 참가자가 응답을 기다리며 다른 일을 하지 않고 화면만 봄 (시작·종료 시각)
- `ASK` — 상대에게 말을 걺 (내용 요지)
- `SURPRISE` — 에이전트 출력에 놀람·혼란 표시
- `CROSS` — 상대 과제의 산출물을 언급하거나 건드림
- `ABANDON` — 지시를 취소하거나 다시 씀

**설문 (조건마다 직후, 7 점 척도)**: 체감 응답성 / 상대 작업 인지 / 혼선 인지 / 통제감 / 다시 쓰고 싶은 정도.

## 분석 계획

n 이 작으므로 **가설 검정을 하지 않는다.** 산출은 셋이다.

1. **조건별 기술 통계** — TTFT 중앙값·범위, 개입 수, `WAIT` 총 시간. 팀별로 나란히 놓고 팀 간 편차를 그대로 보인다.
2. **사건 코딩 표** — 위 5 개 코드의 빈도와 대표 사례. 기계 로그와 **교차 확인**된 사건만 센다(예: `WAIT` 는 그 시각에 실제로 대기 중이었는지 `turns.jsonl` 로 검증).
3. **인터뷰 인용문** — §7.1–7.4 각 절에 관찰 1~2 개씩 역참조. 반증 사례를 우선 싣는다.

**수용 기준**: 세션 4 개 이상 완료. 미달이면 §6.12 로 승격하지 않고 부록의 pilot observations 로 강등하며, 그 경우 venue 는 UIST 계열(G-b)로 확정한다.

## 개인정보 취급

계측 평면은 구조 메타데이터만 기록하고 프롬프트·응답 본문은 남기지 않는다(§5). 그러나 이 연구에서는 `history.jsonl` 에 참가자가 입력한 텍스트가 남는다. 분석 후 **원문은 폐기하고 코딩 결과와 인용 승인을 받은 문장만 보관**한다. 인용문은 참가자 확인을 거친다.
