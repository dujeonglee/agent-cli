## 1단계 — seq 기반 늦은 합류자 증분 재생

### 목표
모든 SSE 이벤트에 세션 수명 동안 단조 증가하는 시퀀스 번호 `seq` 를 부여하고, 재접속 클라이언트가 `Last-Event-ID`(또는 쿼리 파라미터)로 마지막 수신 seq 를 제시하면 **그 이후 이벤트만** 결정적으로 재생받게 한다. 현재의 전체 버퍼 재생은 초기 접속(또는 seq 미제시) 시의 동작으로 유지한다.

### 구현 요구사항
1. **seq 발급 지점**: 이벤트가 렌더러의 영속 버퍼에 들어가는 단일 지점에서 발급한다(팬아웃 지점이 아니라 버퍼 적재 지점 — 모든 접속이 같은 seq 를 보도록). 먼저 `agent_cli/web/renderer.py`(또는 렌더러 구현 모듈)를 읽고 버퍼 자료구조·`register_connection` 스냅샷 경로·`json_str` 사전 직렬화 지점을 파악하라. 발급은 락 아래 단조 증가 정수 하나로 충분하다(웹 표면은 단일 프로세스).
2. **와이어 형식**: SSE 표준 `id:` 필드로 내보낸다. sse-starlette 의 이벤트 dict 에 `"id": str(seq)` 를 추가하면 브라우저 `EventSource` 가 재접속 시 `Last-Event-ID` 헤더를 자동 전송한다. 페이로드 JSON 안에도 `seq` 를 넣을지는 클라이언트(웹 UI) 필요에 따라 결정하되, `json_str` 사전 직렬화 캐시와 충돌하지 않는 쪽을 택하라.
3. **증분 재생**: `stream_events` 진입 시 `Last-Event-ID` 헤더(및 폴백으로 `?after=<seq>` 쿼리)를 읽어, 버퍼에서 `seq > last` 인 항목만 스냅샷으로 내보낸다. 제시된 seq 가 버퍼에 없을 만큼 오래됐으면(버퍼 트림 — 아래 4) **전체 스냅샷으로 폴백**하고, 클라이언트가 구분할 수 있도록 재생 시작을 알리는 신호(예: 첫 이벤트 또는 별도 `replay_reset` 이벤트)를 정의하라.
4. **버퍼 유계성 확인**: 현재 버퍼가 무한 성장인지 트림되는지 렌더러 코드에서 확인하고, 트림이 있다면 "버퍼에 남은 최소 seq" 를 추적해 3의 폴백 판정에 사용하라. 트림이 없다면 이 단계에서 새로 만들지 말 것(범위 확장 금지) — 폴백 판정만 "버퍼 첫 항목의 seq" 로 구현.
5. **재개(resume)와의 관계**: `--resume` 로 재기동한 세션에서 seq 가 과거 값과 충돌하면 안 된다. 두 가지 중 하나를 택해 문서화하라: (a) seq 를 프로세스 수명 단위로 정의하고 재기동 시 `replay_reset` 을 강제(단순, 권장) — 클라이언트는 전체 스냅샷을 다시 받는다; (b) seq 를 이력에서 재도출(질문 id 카운터가 전체 이력에서 재도출되는 기존 패턴 참고). (a) 를 권장한다: SSE 재생의 목적은 세션 영속성이 아니라 재접속 연속성이다.
6. **직렬/병렬 모드 공통 적용**: seq 는 전송 계층 속성이므로 두 모드에서 동일하게 동작해야 한다. 직렬 경로의 이벤트 내용 자체는 변경하지 않는다(필드 추가만 허용).

### 테스트 (추가)
- seq 단조성: 다중 이벤트 방출 후 버퍼의 seq 가 공백 없이 증가.
- 증분 재생: 이벤트 N개 후 접속(전체 스냅샷) → 절단 → `Last-Event-ID=k` 재접속 시 정확히 `k+1..N` 수신, 턴 귀속 필드 온전.

## 2단계 — 관전자(읽기 전용) 모드

### 목표
세션 소유자가 발급하는 **별도의 읽기 전용 토큰**으로 접속한 클라이언트는 SSE 구독(관전)만 가능하고, 입력·중단·설정 변경 등 모든 변이 엔드포인트에서 거부된다.

### 구현 요구사항
1. **토큰 모델**: 기존 단일 토큰(`WebServer.token`)을 "전체 권한 토큰"으로 유지하고, `view_token`(읽기 전용)을 추가한다. CLI 옵션(예: `--web-view-token` 또는 자동 생성 후 콘솔 출력)은 opt-in, 기본 off(미설정 시 관전 기능 없음 = 기존 동작 그대로).
2. **인증 계층**: `_require_token`(server.py:314) 옆에 `_require_read_token`(둘 중 아무 토큰이나 허용)을 추가하고, 엔드포인트를 전수 분류하라 — server.py 의 모든 라우트(`/api/stream`, `/api/health`, `/api/debug/*`, `/api/directives`, `/api/compaction`, 입력/중단/큐 관련 등)에 대해 읽기/변이 여부를 표로 만들어 커밋 메시지 또는 테스트에 남긴다. 변이 엔드포인트에 view 토큰이 오면 **403**(401 아님 — 인증은 됐고 권한이 없는 것).
3. **디버그 엔드포인트는 읽기여도 전체 토큰 전용**으로 남긴다(`/api/debug/prompt` 등은 프롬프트 원문을 노출한다 — 관전자에게 트랜스크립트 스트림 이상을 주지 않는다는 원칙).
4. **`--trust-local`** 은 기존 의미(전체 권한) 유지.
5. **UI**: 웹 UI 가 view 토큰으로 로그인하면 입력창을 비활성화하고 관전 배지를 표시한다. UI 코드 위치는 `agent_cli/web/` 정적 자산에서 확인.
6. **viewers 카운트**: `/api/health` 의 `viewers` 가 관전자를 포함하는지 여부를 정의하고 문서화(권장: 포함하되 `spectators` 필드 분리).

### 테스트 (추가)
- view 토큰으로 SSE 구독 성공 + 이벤트 수신.
- view 토큰으로 입력 POST → 403; 잘못된 토큰 → 401; 전체 토큰 → 기존 동작.
- 변이 엔드포인트 전수(파라미터화 테스트)에 대한 view 토큰 403 확인.

### 3.1 재생 정합성 실험 (신규, 1단계 기능 검증)
- 스크립트: `bench/multiuser/n4_replay.py` (driver.py 재사용).
- 시나리오: 사용자 3명이 병렬 계약으로 턴을 흘리는 동안, 클라이언트 하나가 주기적으로 SSE 절단→`Last-Event-ID` 재접속을 반복(예: 30라운드 동안 10회 절단).
- 지표: (1) 재접속마다 수신한 이벤트 열이 "절단 없이 계속 들었을 열"과 seq 기준 동일(누락 0, 중복 0, 순서 역전 0); (2) 재생된 이벤트의 턴 귀속(`reply_to`/turn_id) 온전; (3) 오래된 seq 폴백 경로 1회 이상 강제 유발해 전체 스냅샷 + 리셋 신호 확인.
- 산출: `out/n4-replay.jsonl` + 요약(json). 논문 §6 에 1개 문단으로 들어간다(4단계).

### 3.2 v2 충돌 락 동기 수치 (§4.4 대체 근거)
현행 논문 §4.4 는 외부 유래 수치(전역 뮤텍스 하 쓰기 중심 워크로드의 병렬 이점 붕괴)를 인용한다. 이를 agent-cli 실측으로 대체한다.
- 먼저 `bench/multiuser/p2_grid.py` 와 `out/` 의 기존 그리드 결과를 읽고, "양쪽 턴 모두 쓰기+배타(셸) 중심 워크로드에서 workspace(전역) 스코프 vs conflict 스코프의 유효 병렬도 차이" 를 보여주는 셀이 이미 있는지 확인하라. **서로 다른 파일에 쓰는 두 턴** 이 전역 스코프에서는 직렬화되고 conflict 스코프에서는 병렬인 셀(즉 스코프 간 차이가 벌어지는 지점)이 필요하다. 기존 그리드는 쓰기 지속시간이 너무 짧아 스코프 간 차이가 안 났으므로(락 대기 <1 ms), 차이를 드러내려면 **효과 구간을 길게** 만들어야 한다: `[[bench work=…]]`(effect 내 지연) 또는 대용량 쓰기(`fwrite=`)로 턴당 효과 시간 비중을 §의 50%급으로 올린 "서로 다른 파일" 셀을 workspace/conflict 두 스코프로 측정(셀당 ≥5회).
- 기대 결과(가설): conflict 스코프 병렬도 ≫ workspace 스코프(같은 파일 셀에서는 두 스코프 동일). 이 수치가 §4.4 의 "전역 뮤텍스는 서로소 경로까지 줄 세운다 → 충돌 단위로 정밀화" 서사의 근거가 된다.
- 산출: `out/p2-scope-motivation.jsonl` + 요약.
