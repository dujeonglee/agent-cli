## Available Tools
- read_file: Read a text file. Each line comes back tagged LINE#HASH:content; edits address lines by these tags. With no mode you get the whole file. `line_start` and `line_end` return that range of lines (1-based, inclusive). `search` returns the lines matching a regex, each with `context` lines around it. `stat` returns only the line count, size and first 20 lines — the file is not read yet. A whole-file read too large for one context is not delivered: you get an excerpt and how to read the rest in parts.
  Input JSON: {"path": "string, required — File path to read", "line_start": "integer — First line to return (1-based). Omit to start at line 1.", "line_end": "integer — Last line to return (1-based, inclusive). Omit to read to the end.", "search": "string — Regex; returns only the matching lines, each with `context` lines around it.", "context": "integer — Lines shown before and after each `search` match (default 5).", "stat": "boolean — Return only the line count, size and first 20 lines — the file is not read."}
- edit_file: Change part of an existing file — the default way to modify one. Lines are addressed by their LINE#HASH refs, taken from the latest output that showed them: `read_file`, `code_index` "fetch", `write_file`, or an earlier `edit_file`. `op` says what to do at `pos`: "replace" swaps the lines from `pos` through `end` (inclusive; just `pos` without `end`) for `lines`; "append" inserts `lines` after `pos`; "prepend" inserts `lines` before `pos`; "delete" removes `pos` through `end` and takes no `lines`.
  Input JSON: {"path": "string, required — File to change", "op": "string, required — \"replace\" | \"append\" | \"prepend\" | \"delete\" — what to do at `pos` (see the description)", "pos": "string, required — Ref of the target line, LINE#HASH like \"5#VR\" — not a bare number", "end": "string — Ref of the last line of an inclusive range (\"replace\"/\"delete\"), like \"9#KT\"", "lines": "array<string> — The new lines, as they should appear in the file — without LINE#HASH: tags"}
- code_index: Query a read-only index of the project's code and markdown; one call runs one query, chosen by `mode`. Symbol names are written as the language writes them: "Class.method" in Python, JavaScript and TypeScript, "ns::Type::method" in C, C++ and Rust, a heading's text for markdown ("Setup" or "## Setup"). Indexed files have one of these extensions: .c, .cc, .cjs, .cpp, .cxx, .go, .h, .h++, .hh, .hpp, .hxx, .java, .js, .jsx, .markdown, .md, .mjs, .py, .pyi, .rs, .ts, .tsx; other files are for `read_file`.
  Input JSON: {"mode": "string, required — \"list\": the outline of one file (`path`), one symbol per line as `name (kind) file:start-end`; `search` keeps the names it matches. \"fetch\": the body of one symbol (`path`, `name`) with LINE#HASH refs, ready for `edit_file`; a definition wins over a declaration. \"lookup\": where `name` is defined anywhere in the project; `symbol_kind` narrows. \"kind\": every symbol of one `symbol_kind` in the project; `search` narrows. \"file\": every symbol defined in one file (`path`). \"refs\": every place `name` is used, each tagged with what it resolves to; `ref_kind` narrows. \"callers\" and \"callees\": the functions that call `name`, or that `name` calls, under a heading per definition of `name`; a line starting with \"?\" could not be pinned to one definition and may reach any of the definitions it counts. \"slice\": the body of `name` together with its neighbours — `with_callees`, `with_callers`, `with_types`, `with_macros` — to `depth`. \"list\" and \"fetch\" read any file; the other modes see only files under the project root.", "path": "string — File path, for \"list\", \"fetch\" and \"file\"; with \"callers\", \"callees\", \"refs\" and \"slice\" it picks the definition of `name` in that file.", "name": "string — Symbol name as \"list\" or \"lookup\" shows it, for \"fetch\", \"lookup\", \"refs\", \"callers\", \"callees\" and \"slice\". A qualified name, or one led by its module (\"module.function\"), picks one definition when several share the name.", "symbol_kind": "string — Symbol category: \"function\", \"type\", \"variable\", \"constant\" or \"section\" (a markdown heading). Required for \"kind\", optional for \"lookup\".", "ref_kind": "string — Kind of use, for \"refs\": \"call\" (an invocation), \"name\" (the bare identifier — a callback, a pointer) or \"type\" (in a type position).", "search": "string — A regex; \"list\" and \"kind\" keep only the symbols whose name matches.", "with_callees": "boolean — \"slice\": include the bodies of the functions it calls, to `depth`.", "with_callers": "boolean — \"slice\": include the bodies of the functions that call it, to `depth`.", "with_types": "boolean — \"slice\": include the types it uses.", "with_macros": "boolean — \"slice\": include the function-like macros it invokes.", "depth": "integer — \"slice\": how many calls away callees and callers are followed (default 1, at most 5).", "max_bytes": "integer — \"slice\": cap on the output size in bytes (default none)."}
- shell: Run a shell command in the working directory. The result is its stdout, then its stderr under `[stderr]`, then `[exit code: N]` when the exit code is not 0 — the command needs no `echo $?` or `2>&1` for that. For a command that may run longer than about a minute, set `background` to true: the harness starts it for you, sends its output to a log under .agent-cli/tmp/jobs/ and tells you when it ends (exit code + last lines) — keep working meanwhile.
  Input JSON: {"command": "string, required — Shell command to run", "timeout": "integer — Seconds a foreground command may run (default and maximum 120); at the limit it is stopped, together with everything it started. A larger value starts the command as a background job instead.", "background": "boolean — true = start the command as a background job owned by the harness (returns at once with the job id, pid and log path; you are notified when it ends). Use it for anything that may run longer than about a minute. Give the plain command: no trailing `&`, no redirection, no `echo EXIT` — the harness logs it and reports the exit code."}
- ask: Ask the user one question and wait for their reply. One question per call — to ask several, make several `ask` calls in one turn (each is answered in turn). Use only when you cannot proceed without specific input; otherwise end with `complete`.
  Input JSON: {"question": "string, required — The question to ask the user."}
- agent: Work with sub-agents, one-shot or persistent. `mode` "run" gives one task to a sub-agent and you get back only its summary: whatever it read stays in its window, both handoffs drop detail, and its mistakes return in the same confident tone as its findings. Delegate when answering would mean reading across many files and you want the conclusion, not the file dumps. Do it yourself when it is a handful of calls or a lookup whose target you already know; when in doubt, do it yourself. Several "run" calls in one turn are for independent parts that would each flood your context — not for speed: on a single local model server they share throughput, and you are blocked until all of them finish. Spawn (`mode` "spawn") only when the same area will take several rounds of questions — an agent that has studied one area answers follow-ups from full detail. One agent per area (disjoint files/subsystems). Once you have handed work to an agent, do not also do it yourself; how to wait for its reply is in the `## Live Agents` section at the end of the prompt.
  Input JSON: {"mode": "string, required — \"run\": one task, blocking — the result returns in this turn. \"spawn\": create a persistent agent that keeps its context between requests (returns its key). \"request\": send it a message — returns immediately; the reply is delivered to you as an observation when ready. \"status\": list live agents and their state. \"resume\": bring a dead agent back with its full prior context. \"kill\": terminate one.", "profile": "string — \"run\"/\"spawn\": profile from .agent-cli/agents/{profile}.md (loaded into the sub-agent's system prompt; omit for a generalist). The same profile may be spawned more than once — give each instance a distinct `name`.", "name": "string — \"spawn\": optional instance label to tell same-profile agents apart (e.g. two coders as \"ui\" and \"api\"). Display only — always address agents by their `key`.", "task": "string — \"run\": the task (required); \"request\": the message (required); \"spawn\"/\"resume\": optional first request. Brief it like a peer: the goal, what you already ruled out, and which files to read — point at them, do not retype them. Give it the code, not your conclusion: an agent handed your hypothesis tends to return it confirmed.", "instructions": "string — \"run\"/\"spawn\": inline role text that becomes part of the sub-agent's system prompt (for a spawned agent: its whole life, survives resume). Use alone for an ad-hoc specialist, or with `profile` to append session-specific directions.", "key": "string — agent key returned by \"spawn\" (required for \"request\"/\"resume\"/\"kill\"; optional filter for \"status\")", "tools": "array<string> — \"run\"/\"spawn\": tools the sub-agent may use. Omit for the profile's set; without a profile the sub-agent has every tool. With a profile it can only narrow that set.", "context": "string — \"run\"/\"spawn\": \"none\" (default) — the agent starts fresh and knows only the task text; \"fork\" — it gets a copy of your conversation so far."}
- complete: Call this tool when the task is done — always the last call. `result` is the only text delivered as your answer — to the user, or to the agent that called you; what you wrote outside it is not. The user sees it rendered as Markdown. Put the answer first. When it rests on work you did, end with two lines:
Checked: <what you ran or inspected, and what it showed>
Not checked: <what you inferred from reading rather than running, or did not test — 'nothing' if so>
A reply with nothing to check has neither line. When `## Open Items` lists items closed by `complete`, `answers` is required: list the ids your result covers. Ids you leave out stay open. Not for waiting — to pause until a job, monitor or agent reports back, call `wait`.
  Input JSON: {"result": "string, required — The answer, then the Checked / Not checked lines", "answers": "array<string> — Ids from `## Open Items` (`u-…` user requests, `n-…` mail) that this result covers."}

  Hashline refs:
  `read_file` returns lines tagged as LINE#HASH:content, e.g.:
    1#VR:def hello():
    2#KT:    return "world"
  A ref is the LINE#HASH part ("2#KT"), never a bare line number.
  - one edit per call:
      {"action": "edit_file", "path": "app.py", "op": "replace", "pos": "2#KT", "lines": ["    return \"hello\""]}
  - A ref from before the file last changed no longer matches. A hash
    mismatch is a guardrail, not a failure: the error shows the current
    lines around it with fresh refs — retry from those.
  - Several edits to one file can go in one turn as adjacent `edit_file`
    calls, every ref from the same read: they are applied together, so do
    not shift line numbers for each other. If any is rejected, nothing is
    written and the result names the bad ones — resend all, fixing only
    those. Overlapping ranges are rejected; split them across turns.
  `ask` vs `complete` — pick by intent, not tone:
  - `ask`: you genuinely cannot proceed without information from the
    user. A real question with real alternatives where you don't know
    the right answer. "Which of these two paths should I take?",
    "What's the production database name?", "Should I overwrite this
    file or keep both?".
  - `complete`: every other ending. Task done, user said goodbye, user
    said thanks, user gave a casual reply, you finished your answer
    and have nothing else to do. The conversation does not need a
    question to continue — the user can simply reply at the next
    prompt if they want more.

  Common mistakes that keep the loop alive when it should end:
  - "Was that helpful?" / "Anything else?" / "Let me know if you have
    questions" — these are pleasantries, not questions. Use `complete`.
  - "Goodbye!" / "See you next time!" / "👋" — closing remarks. Use
    `complete`.
  - Restating the user's last message back as a question
    ("So you want X?") when their meaning was already clear. Use
    `complete` and answer.

  Rule of thumb: if your "question" could be a statement and the
  conversation would still flow, it's not a real question — use
  `complete`.
  Constraints:
  - If task B depends on task A's result, emit only A now; use its
    result next turn.
  Examples:
  - One-shot: {"action": "agent", "mode": "run", "task": "Read data.csv and count rows"}
  - With context: {"action": "agent", "mode": "run", "task": "Fix the bug we found", "context": "fork"}
  - With profile: {"action": "agent", "mode": "run", "task": "Analyze the auth module and cite risks", "profile": "code-analyst"}
  - Persistent: {"action": "agent", "mode": "spawn", "profile": "code-writer", "name": "ui", "task": "own the UI module"}
